## 一、起点：原套件报告的 220,006 次运行里有多少在做事

原报告结论是"10/10 PASS，220,006 次运行，零失败，Spec 缺口：无"。
逐项实测（probe 直接计数，不是读代码推断）后，这个数字的构成是：

**成因：add 与 del 抽两个不相交的 id 池。**

```
relation_add   的 id ← fc.uuid()
relation_del   的 id ← REL_POOL = ['r0'..'r7']
```

`fc.uuid()` 产出的 id 永远不在 `REL_POOL` 里，于是：

| op | 实测生效次数 |
|---|---|
| `relation_del` | **0 / 2000** |
| `attachment_del` | **0 / 2000** |
| `create_entity`（uuid 造的实体） | 造出即不可引用，无任何后续 op 能碰到 |

六种 op 里有三种是整段 100,000 次运行中的死代码。删除路径、覆盖路径、
以及"删除后索引是否清干净"这一整类问题，从未被表决过。

**另两项属性的输入空间大小是 1。** 属性 3 与属性 4 用 `fc.constant(null)`
作为生成器，各跑 10,000 次——同一个输入重复一万遍。
计入合计的 20,000 次运行，等价于 2 次。

**检查器是单向的。** `checkInvariants()` 原本只问"该有的在不在"，
从不问"在的都该在吗"。把 `relation_del` 里清索引的两行整段删掉，
原有 10 项断言依然全绿。

这三条叠加，使"220,006 次 PASS"与"实现正确"之间没有推理关系。

## 二、一致性下限四件套

与 L4 / L12 同一套下限，逐项落地：

| 件 | 落地物 | 作用 |
|---|---|---|
| 小 ID 池 | `ENTS/RELS/ATTS/TYPES` 各 2–4 个，**add 与 del 共用** | 让删除、覆盖、级联、自环成为可达事件 |
| 影子模型 | `test/model/relation-model.ts` | 索引**从主表重新推导**，与产品的增量维护形成不同算法 |
| 损坏注入 | `test/l8-invariant-checker.test.ts` + 模糊器 `corruptionProbe` | 证明 `checkInvariants()` 不是恒空，且每条子句都可被单独触发 |
| 变异测试 | `mutation/mutants.ts`（96 个） | 证明断言能失败，而不只是能通过 |

**影子模型的全部价值在于算法不同。** 产品的双向索引是一路增量改出来的
（`relation_add` 里 push、`relation_del` 里 filter）；模型的索引是
`dump()` 被调用时**当场从 `relations`/`attachments` 主表扫出来的**。
两者若都对，答案必然一致；任何一侧的增量维护出错，扫描侧不会跟着错。
若模型也维护增量索引，它只会复制产品的错误。

**桶内数组不排序。** `dump()` 的索引桶保持插入顺序，因为 `get()` 会把
这些数组交出去——顺序是可观测的。排序会让 `push`→`unshift` 这类改动
在对照中消失（M24、M78 正是靠这一点被杀）。键可以排序（键序不可观测），
数组不可以。

## 三、实测确认的 13 处缺陷

前 8 条由 probe 与影子对照发现，后 5 条由**变异测试的存活名单**倒推。
全部钉在 `test/l8-regression.test.ts`（35 例）。

| # | 缺陷 | 后果 | 发现方式 |
|---|---|---|---|
| 1 | `createEntity` 同 id 重建静默覆盖 | 旧 stub 连索引一起丢弃，`relations` 主表里的关系就此孤立——**一次合法 API 调用即破坏不变量** | probe |
| 2 | 检查器单向：索引残留项不可见 | 删掉 `relation_del` 清索引的两行，原 10 项断言全绿 | probe |
| 3 | 检查器单向：attachment 未登记在 target 上不可见 | 删掉 `attachments.add(...)` 那行也能全绿 | probe |
| 4 | 索引桶内重复 id 不可见 | `includes` 判据对重复项恒真，重复索引成为幽灵 | 影子对照 |
| 5 | `attachment_add` 按引用入库 | 调用方事后改 `deps`/`target` 即绕过全部前置校验 | probe |
| 6 | `relation_add` 按引用存 `attrs`、返回内部对象 | 改返回值的 `from` 可让关系与双向索引脱钩 | probe |
| 7 | `get()` 交出内部对象 | `get('entity',id).rel.out.get(t).push(...)` 即伪造索引项，**等于没有 Op 边界** | probe |
| 8 | 删除类 op 全程不可达（**测试自身的缺陷**） | 见第一节 | probe 计数 |
| 9 | `createEntity` 的**返回值**也是内部 stub | 创建者天然持有句柄，比 `get()` 那条更易踩到；全套件无一处使用该返回值，故完全无人看守 | 变异 M03 存活 |
| 10 | `get()` 兜底分支未被覆盖 | 未知 type 若返回空对象，调用方的 `if (result)` 会判成"查到了" | 变异 M77 存活 |
| 11 | `dump()` 交出 `attrs` 引用 | 观测面本身可被篡改——"快照"不是快照，对照过程能改变被对照的状态 | 变异 M83 存活 |
| 12 | `cloneAttachment` 未拷 `effects` 内层 `args` | 逐层拷只拷了一层，调用方仍能改到库里的 effect 参数 | 变异 M88 存活 |
| 13 | `cloneEntityStub` 的 **in** 桶共享数组 | out 桶有测试守着、in 桶没有——"对称代码只测一半" | 变异 M92 存活 |

第 9–13 条值得单独说一句：它们全部位于"人眼审阅会认为已经处理过"的位置。
第 12 条尤其典型——`cloneAttachment` 里确实写了 `.map(...)`，看起来是逐层拷，
但 `args` 那一层没拷。变异测试把"拷一层"和"拷到底"区分开了，代码审阅不会。

## 五、等价性证明：先自检，再判定

"跑了 3,000 条序列没有反例"有两种成因：真等价，或模糊器根本没走到变异点。
二者在输出上一模一样。故 `mutation/equivalence.ts` 分两阶段：

**阶段一：14 个已知不等价的哨兵。** 哨兵必须取自与待证目标**同一段代码**——
抓到了别处不能证明"这里看得见"。

| 待证目标所在块 | 同块哨兵 |
|---|---|
| `destroyEntity` 级联体（M14、M15、M95） | M06 M08 M09 M12 M13 |
| `relation_add`（M93） | M20 M22 M24 |
| `dump`（M94） | M78 M80 M81 |
| `checkInvariants` 判据段（M96） | M51 M52 M69 |

**阶段二：3,000 条序列逐字段比对。** 结果 6/6 证明等价，0 证伪。

### 自检第一次没过，暴露的是观测面的结构性盲区

首版自检 11/14 通过，漏掉 **M51、M52、M69**——全是 `checkInvariants` 的子句。
成因不是断言不够细，而是：

> 模糊器跑的全部是**合法状态**，而合法状态下每条不变量子句都返回空。
> "删掉一条报违规的子句"在这个观测面里根本不可观测。

产品是对的，所以合法 API 造不出违规状态。解法是把损坏注入搬进模糊器
（`corruptionProbe`）：绕过 Op 边界直接改内部表，逐种损坏各造一份状态，
把每条子句变成可观测的。加入后自检 14/14。

这条记下来，因为它是可复用的判据：**检查器本身也是被测对象，
观测面必须包含能触发它每条子句的状态，否则"检查器相关的变异体存活"
只是观测面的盲区，不是等价性。**

### M14 / M15 的等价性有前提

- **M14**（先删实体再级联）等价，依赖"被删实体的索引不再被任何人读"。
  `relation_del` 里 `entities.get(rel.from)` 变 undefined 时，只跳过
  **被删实体自己**那侧的索引清理，而它整个 stub 随即消失；另一端仍被正常清理。
  若将来 `destroyEntity` 之后还要读该 stub（例如返回被删内容），等价即失效。
- **M15**（不快照 attachments 集合）等价，依赖"循环内只删当前元素"。
  JS 的 Set 迭代器允许删当前元素并继续；grantedBy 与 dep 两种级联是各自
  独立的后续循环，且都另有快照。观测面里 `p.multi`（5 个 attachment 挂同一
  target）与 `p.chain`（4 个共享同一 dep）专为这条而设。

前提写进清单注释里，不只写"等价"。等价是**在当前语义下**成立的结论，
不是"改了也行"。

## 六、本轮方法论增量

前几层积累的空转形态之外，本层新增两条：

### 七、观测面缺失可触发状态 → 假等价

见上节。判据：**若某段代码只在异常状态下执行，观测面就必须能造出异常状态。**
对不变量检查器而言，这意味着损坏注入不是"额外的测试"，而是
"让检查器可观测"的前提条件。

### 八、对称代码的覆盖不对称

`cloneEntityStub` 的 out 桶有测试守着、in 桶没有（缺陷 13）；
`checkInvariants` 反向校验的 out 侧与 in 侧同理。
写法对称不代表覆盖对称——双向索引的两侧必须**各自**被断言。
判据：见到 `out`/`in`、`from`/`to`、`left`/`right` 这类成对结构，
逐个数断言，不要因为代码是复制粘贴的就认为测试也覆盖了两份。

### 附带确认的一条老坑

M92 的第二个断言初版写成 `expect(a.rel.in).not.toBe(b.rel.in)`——
这是**恒真**的：Map 每次 clone 都新建，共享发生在桶数组那一层。
手动打上 M92 时它没红，才发现断言写错了位置。
"未验证的区分性断言"这条老坑在本层又踩了一次，
再次确认：**为特定变异体写的断言，必须手动打上那个变异体跑一遍**。

## 尚未完成

- `dump()` 目前是为对照而加的观测接口，尚未纳入 Spec。若上层要依赖它，
  需要先确定"索引桶顺序是否属于契约"——本轮把它当作契约（不排序），
  理由是 `get()` 已经把顺序暴露出去了；这个判断需要 Spec 层确认。
- `E_ENTITY_EXISTS` 是本轮新增的错误码，需要在错误码总表里登记。
- 级联删除的**顺序**未纳入契约。当前实现按 out→in→target→grantedBy→dep
  的顺序级联，模糊器只比末态，不比中间态。若上层要在级联过程中挂 Hook，
  顺序就成为契约，需要补逐步观测。
