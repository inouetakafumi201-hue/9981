# wakeup-ai 决策与风险记录

本文档记录 AI 子系统实现过程中遇到的、requirements.md / design.md 未明确规定或存在歧义的
判断点，以及任何自主做出但无法被 Spec 文本直接验证的实现决策。目的是让审阅者能快速定位
"哪些地方是我自己判断的，而不是照抄文档"，以便复核或推翻。

记录范围：`src/core/kernel/ai/**`（AI 契约与决策路径）与 `src/core/kernel/ai/kernel/**`
（内核侧集成适配器），以及为完成集成而修改的 `src/core/kernel/schedule/policy.ts`。

---

> **修订说明（一步到位复审）**：第 1、6、9、14、19 条原先记录的过渡实现已全部替换为最终形态，
> 相应条目已改写为最终决策并保留原方案作为"已否决"记录。本文档不再包含任何计划中的阶段性做法。

## 1. 行动实体贯穿提交契约（最终形态）

**问题**：`CandidateCommitGateway.submit(agent, action)` 只携带 AI Agent 引用，而内核
`intent.submit` 的 `agent` 参数实际是**行动实体 Id**（用作 cost scope 与 effects 的 `self`）。
两者不是同一个概念，直接把 AI Agent Id 传进去会把成本冻结记到错误的作用域上。

**决策（最终）**：把行动实体加入 `AICandidate.actor`，并贯穿整条提交链：
`CandidateCommitGateway.submit(agent, actor, action)`、
`CanonicalSubmissionAdapter.authorize/validateLifecycle/submitCanonical(agent, actor, action)`。
`facade.act` 传 `candidate.actor`，`revalidate` 传同一字段。内核适配只做**校验**：
`authorize` 确认该 Agent 确实控制该实体，`verifyCurrentlyLegal` 确认该实体在权威
`ActionCatalog` 中仍提供这一精确候选。

**已否决的方案**：在适配器内遍历 `controls` 反推 actor，歧义时拒绝。它能工作，但把"谁在行动"
这一必要信息降级成了推断，并在一个 Agent 控制多个实体且着法相同时无法行动。

**依据**：requirements 2.1（`queryActions` 是唯一权威来源）与 2.3（不得以内部理由豁免约束）。
行动实体是提交的必要参数，应显式传递而非推断。

**风险**：低。`intent.submit` 的 `agent` 参数现在接收明确的行动实体，成本冻结作用域正确。
一个 Agent 控制多实体时不再有歧义拒绝。

## 2. 试探隔离依赖 checkpoint/restore 覆盖 `world.rng`，而非重定向随机流

**问题**：requirements 8.2 要求"AI 试探中的随机行为应使用上游影子随机流，且不得推进真实对局
随机流"。但内核随机的流名是由 Effect 的 Op 参数字面给出的（`state.world.rng[streamName]`），
适配器无法在不改写 Op 参数的前提下把 `default` 重定向到 `shadow:default`。

**决策**：隔离通过对**整个 WorldState** 打 checkpoint 并在分支结束后 restore 实现——`world.rng`
就在 WorldState 内，因此任何流的 counter 推进都会随分支回滚。另外为 AI 自身的随机需要（平局
仲裁）保留一个专用流名 `ai:shadow`，使 AI 抽取永不与玩法流共享 counter。

**依据**：requirements 8.1 明确要求"通过上游 checkpoint/restore、事务和同一套合法 Op 机制执行
AI 试探"。在此机制下"不推进真实流"是可证明的结果，而非额外承诺。

**风险**：低，但**证明责任在测试**。已在 `kernel-adapters.test.ts` 与 `sequential-kernel.test.ts`
断言探索前后 `world.rng` 深度相等。若未来有人把随机计数移出 WorldState（例如挪到宿主内存），
该保证立即失效——这与内核决策3（RelationIndex 不得脱离 WorldState）是同一条教训。

## 3. 平局仲裁用影子流的"纯派生"而非"推进流"

**问题**：多人搜索出现同分候选时需要仲裁。若用 `random.pick` 一类 Op，会在**被回滚的分支内**
推进流；回滚后该次抽取不留痕迹，导致同一输入的两次搜索可能得到不同结果，违反 requirements
11.5（相同公开状态 + 相同命名随机流状态 → 可重放的候选结果）。

**决策**：`KernelSearchSession.selectTie` 读取 `world.rng['ai:shadow']` 的 `seed`/`counter`，
连同"参与者、受控实体、correlationId、同分候选的 action id 列表"一起做 FNV-1a 指纹，取模得到
索引。**只读不写**，不推进任何流。

**依据**：requirements 6.5 把"平局随机仲裁实现"列为候选实现（未冻结），只要求不破坏
requirements 2/3/4/7/8 的约束；requirements 11.5 则强制可重放。纯派生同时满足两者。

**风险**：中低。这不是统计意义上的均匀随机，而是确定性伪随机：给定同一局面与同一候选集，
选择恒定。如果将来玩法明确要求"AI 平局选择在同一局面下也应有可观测的多样性"，需要改为
真正推进 `ai:shadow` 流并把该推进纳入 journal——那属于玩法层需求，届时应重新裁决。

## 4. Knowledge 的 `facts` / `seen` 到 `certainty` 的映射规则

**问题**：`BeliefSlice.knownFacts[].certainty` 有 `observed | historical | uncertain` 三档，但
内核 Knowledge 只有 `facts` 与 `seen` 两个区，且没有时间戳，Spec 未规定映射规则。

**决策**：`seen` → `observed`（这是观测记录）；`facts` → `historical`（这是留存知识，可能已过期），
值为 `null` 时 → `uncertain`；同名键以 `seen` 优先。

**明确拒绝的另一方案**：解析 fact 的 key（例如 `position:e:ghost`）取出主体 id，再判断该主体
当前是否可见来决定 `observed`/`historical`。这会把"key 的命名约定"固化成内核机制，属于把
玩法约定偷渡为规则（requirements 12.2 禁止）。

**风险**：中。当前分类偏保守：一个刚刚写入 `facts` 的事实也会被标为 `historical`，策略若据此
打折可能低估自己的信息。这是**信息保守**方向的偏差，不会造成透视。若玩法层需要更细的时效
判断，正确做法是让上游 Knowledge 带上观测时刻字段，而不是让 AI 猜。

## 5. 观测时钟取 `world.turn.phaseEnteredAt`，不用 `Date.now()`

**问题**：`KnownFact.observedAt: number` 需要一个时间来源。

**决策**：使用 `state.world.turn.phaseEnteredAt`（状态内的确定性相位时钟）。

**依据**：requirements 11.5 要求相同输入产生可重放结果。`Date.now()` 会让认知切片随真实时间
变化，直接破坏回放，也会让版本指纹每次都不同。

**风险**：低。副作用是同一相位内的所有事实共享同一 `observedAt`，无法区分相位内先后。若需要
更细粒度，应由上游 Knowledge 写入时记录，而不是由 AI 读取时补。

## 6. 版本令牌用 SHA-256 结构指纹，并按状态对象做 WeakMap 缓存

**问题**：`AIReadScope.knowledgeVersion` / `actionVersion` 的语义未由上游冻结（这是 design.md
依赖状态表中明确登记的缺口之一），但候选重验必须能判断"读过的信息是否已变"。

**决策**：不伪造上游版本号，而是自行计算**可见信息本身的指纹**：`knowledge` 指纹覆盖该 Agent
的 facts、seen、可见 Ref 集合、可见属性；`actions` 指纹覆盖全部受控实体的 `queryActions` 结果。
`isCurrent` 的实现是重新计算并比较。因为 WorldState 不可变，按 state 对象做 `WeakMap` 缓存，
保证同一状态下版本稳定且只算一次。

**依据**：requirements 3.5（认知变化后必须使候选失效并重新验证）与 10.6（缺稳定字段时不得用
猜测性字段替代）。指纹不是猜测上游语义，它衡量的正是"AI 被允许读到的东西是否变了"。

**哈希选择（最终）**：使用 `node:crypto` 的 SHA-256（与 `definition-registry.ts` 计算快照指纹的
做法一致），而不是短校验和。**已否决**：32 位 FNV-1a——它理论上会碰撞，而一次碰撞的后果是把
"可读信息已变"误判为"未变"，属于安全方向的错误，不能用"还有二次重验兜底"来接受。

**风险**：低。剩余代价是 `versions()` 会触发一次全量 `queryActions`，成本与可见集规模线性相关；
这是正确性优先的自觉取舍。指纹本身不是过渡实现：在上游没有版本契约的前提下，"衡量 AI 被允许
读到的内容是否改变"就是该语义的正确实现，若上游将来提供等价令牌可直接替换而语义不变。

## 7. `queryVisible` 强制与该 Agent 的可见集求交

**问题**：`AIReadScope.query(query)` 接受调用方提供的 Query。若调用方省略 `visibleTo`，
`QueryEngine` 不会做任何可见性过滤。

**决策**：适配器先算出该 Agent 的可见 Ref 集合，再把调用方查询的结果与之求交（全知 Agent 跳过）。

**依据**：requirements 3.4（不得通过推断性旁路取得不可见信息）。把可见性正确性交给调用方的
查询写法是不可证明的；求交使泄露在结构上不可能。

**风险**：低。副作用是调用方无法通过该接口查询 `agents` / `intents` / `decisions` 等**不在**
`sources` 枚举范围内的集合（会被求交清空）。当前 `sources` 默认为
`entities/items/nodes/links`。若某策略确实需要查询可见的 Decision，必须显式扩展 `sources`，
这是有意的白名单方向。

## 8. `policyContext` 的暴露范围，以及一处自我发现的缺陷

**决策**：`policyContext` 只暴露声明式公开数据：`policy.id`、`policy.mode`、`policy.props.*`。
不暴露任何 Agent 私有状态、Knowledge 或隐藏实体。

**自我发现的缺陷（已修）**：初版在"策略定义无法从注册表解析"时直接 `return {}`，把 `policy.id`
一起丢掉，导致解释信息无法说明这次决策由哪个策略驱动（违反 requirements 11.2 的可解释性）。
现改为：`policy.id` 无条件保留，定义可解析时才追加 mode / props。该缺陷由
`kernel-adapters.test.ts` 的 `policyContext['policy.id']` 断言暴露。

**风险**：低。`policy.props` 是否一律可公开取决于玩法层是否往策略 Def 里塞敏感内容。当前判断是
"Def 是声明式定义，不是隐藏状态"，若将来玩法层在策略 props 里放不该公开的数值，需要改为白名单。

## 9. 跨相位前瞻经既有 `schedule.advance` 规范 Op（最终形态）

**问题**：`SchedulePhaseParticipants` 需要决定"当前相位最后一个行动者之后是谁"。

**决策（最终）**：当前相位耗尽时，通过既有规范 Op `schedule.advance` 推进相位，然后取新相位
（按其 `actors` 查询与先手规则排序）的第一个行动者。推进会跳过无行动者的相位，循环次数以
`phases.length` 为上界；非循环表停在末相位时 `advance` 是幂等空操作，此时才返回 `undefined`
真正结束前瞻。

**为什么这是安全的**：`schedule.advance` 是人类推进相位用的同一个 Op，会在同一事务内执行
`onExit`/`roundEnd`/`onEnter` 边界效果与资源池重置，并受不变量检查约束；它发生在**已经打开的
试探分支内**，因此随分支 restore 一并回滚。这不是 AI 的第二条写入通道。

**已否决的方案**：在相位末尾直接结束前瞻。它不会给出错误预测，但把前瞻深度硬性限制在单相位内
（三人相位最多三步），是能力上的缺失而非正确性要求。

**依据**：requirements 4.2-4.3（depth 是连续单步决策点，不是回合数）——跨相位推进不改变这一
计数方式，每个决策点仍然只对应一个参与者的一次单步选择；requirements 8.1（试探必须走同一套
合法 Op 机制）。

**风险**：中低。(1) 该能力要求组合根**必须注册 `schedule.advance`**；未注册时返回
`AI_TRANSACTION_FAILED` 失败关闭（已有测试覆盖），不会静默退化成浅前瞻。(2) 推进相位会执行
边界效果，因此试探成本高于纯读取；这由 `BudgetLedger` 的模拟预算约束。

## 10. 按参与者读取统一用 `refGet`，不用"自身相对路径"

**问题**：仓库里存在两种 `resolvePath` 根约定：`query-engine.test.ts` 的 `ctxForSelf` 把路径根
设为**该实体对象**（于是 `{path:'props.hp'}` 是自身相对），而 `ActionCatalog` 的实际接线把根设为
**整个 WorldState**（于是 `{path:'world.props.x'}` 是绝对）。同一个 Expr 在两种根下含义不同。

**决策**：AI 侧全部采用 WorldState 根，按参与者的读取改用内核既有算子
`{op:'refGet', args:[{var:'self'}, 'props.initiative']}`，并在共享上下文里提供
`resolveRefValue`（此前缺失，导致任何 `refGet` 都返回 null——这是一个真实缺陷，已修）。
同时把 `self` 也暴露为 `var`，使谓词可以命名候选引用。

**依据**：`refGet` 的内核注释即"读取 Ref 指向对象的相对字段"，是为此设计的。它在两种根约定下
含义都稳定，而自身相对路径只在特定 ctx 工厂下成立。

**风险**：低。代价是玩法层写可见性/先手表达式时略啰嗦。收益是这些表达式可以跨上下文复用，
不会因为换了一个 ctx 工厂而静默改变语义。

## 11. 先手同分按 id 升序打破

**决策**：`applyOrder` 先按 initiative 降序，同分按 `actor.$` 的 `localeCompare` 升序。

**依据**：requirements 11.5 的可重放性要求确定性顺序。`Array.sort` 对同分元素的相对顺序在
不同引擎/输入顺序下不保证稳定，必须显式指定次级键。

**风险**：低，但需明确：**这不是玩法规则**。它只是让"顺序未被玩法定义时"的行为可复现。若玩法层
要求同分先手用掷骰决定，应由调度层的 `initiativeExpr` 或专门的先手规则表达，而不是改这里。

## 12. 派生参与者：非 AI 合法终止，AI 缺绑定失败关闭

**决策**：下一行动者若由非 AI Agent（human / observer）控制，或无任何 Agent 控制，则返回
`undefined` 正常结束前瞻。若由 AI Agent 控制但**缺少已验证行为绑定**，则返回
`AI_CONTRACT_UNAVAILABLE` 使整次搜索失败。

**依据**：人类选择无法由策略预测，把它建模成任何具体选择都是编造（requirements 4.1 的老实模型
要求每个参与者按自身评估选择）。而 AI 参与者缺绑定属于 requirements 10.6 的契约缺口，必须拒绝
而非用默认值建模。

**风险**：中。这意味着**任何一个未配置绑定的 AI 参与者会让整条搜索链失败**，而不是退化成较浅的
前瞻。这是刻意选择的严格方向：宁可明确报错，也不给出一个建立在编造参与者之上的"最优解"。
运维上需要保证 `behaviorBindingFor` 覆盖全部参与决策的 AI Agent。

## 13. Policy 的 search 模式以可选 resolver 注入，避免 schedule 反向依赖 ai

**问题**：`PolicyEvaluator.searchPlaceholder` 原本是 `TODO(L12)` 的死路（恒返回 null）。接通它
最直接的写法是在 `schedule/policy.ts` 里 import AI 模块，但这会产生 schedule → ai 的依赖。

**决策**：在 `policy.ts` 追加 `SearchPolicyResolver = (def, ctx) => Id | null` 与
`evalSearch(def, ctx)`；`searchPlaceholder` 保留为 `@deprecated` 委托以免破坏现有调用点。AI 侧提供
`AISearchPolicyBridge`，其 `propose` 正好符合该函数签名，由组合根注入。

**依据**：requirements 7.1（不得复制或重定义 Policy 的数据结构与写入机制）。resolver 是纯函数
签名，不携带任何 AI 类型，schedule 层因此不知道 AI 的存在。

**关键语义选择**：`propose` 走 `facade.recommend`（只读推荐）而**不是** `act`。因为
requirements 7.7 规定"Policy 只能选择或提出候选，不得直接执行效果"。想让 AI 自己提交的调度器
必须显式调用 `bridge.submit`。

**风险**：低。`searchPlaceholder` 的行为从"恒 null"变为"有 resolver 时委托"，对未注入 resolver 的
既有调用点行为不变（仍返回 null），已由 schedule 测试全绿验证。

## 14. 解释投影由玩法层声明可公开范围，AI 只负责执行（最终形态）

**决策（最终）**：`projectAIExplanation(result, slice, policy?)` 接受玩法层声明的
`AIExplanationPolicy`：`publishableBindingKeys`（逐键白名单）、`publishCost`、
`summaries`（按节点类型的玩法自撰文案）。AI 执行三重约束，且顺序不可颠倒：
1. 只有被声明的 binding 键才可能出现；
2. 即使被声明，若其值（含嵌套数组/对象）引用了观看者切片中不可见的 Ref，仍然剔除；
3. `reasons` 只保留 `visibleRefs` 全部可见的节点，与是否有自撰文案无关。

未声明 policy 时只发布 action 标识与通用文案——这是**安全默认**，不是占位实现。
`toPublicDiagnostic` 仍按 `code` 查表输出固定 reason/hint，剥离 agent / controlledEntity /
policy / correlationId / upstreamContract / candidateAction。

**已否决的方案**：一律清空 bindings 与 cost。它安全但把可用性问题推给了每个调用方，且无法表达
"这个目标本来就是公开的"。

**依据**：requirements 10.3（UI 通过只读投影获取合法性原因）与 10.5（不得包含无权读取的内容）。
披露范围是玩法决策，判定与执行必须分离：玩法层声明，AI 层强制。

**风险**：低。剩余风险是玩法层可能声明一个本该保密的键；第 2 条约束能挡住其中引用不可见 Ref 的
情况，但挡不住纯标量的敏感值（例如把内部阈值放进 binding）。诊断文案仍不透传，调试需读内部诊断。

## 15. UGC 声明式引用：四字段白名单 + 自定义 schema 版本串

**决策**：`DeclarativeAIUGCValidator` 只接受恰好 `schemaVersion` / `category` / `policy` /
`behaviorBinding` 四个键，多一个键即拒绝；`policy` 与 `behaviorBinding` 必须是恰好只含 `$` 的
Ref 对象；`schemaVersion` 必须等于常量 `'wakeup.ai.binding/v1'`（该串由我命名）。

**依据**：requirements 10.4（UGC 不得注入任意代码、直接状态写入或绕过可见性过滤）。白名单方向
使 `onEvaluate: '() => 1'`、`omniscient: true` 这类越权字段在结构上无法通过。

**风险**：低-中。版本串是我自主命名的，若 UGC 子系统已有版本命名规范（`wakeup-ugc` spec 尚未
接线），需要对齐后统一。白名单也意味着任何合法扩展字段都必须显式加入，属于有意的摩擦。

## 16. 基类层硬编码检测沿 raw `extends` 链，且拒绝 abstract 绑定

**问题**：requirements 9.4 要求拒绝"在基类层 AI 定义中硬编码巡逻路线、具体感知阈值"。但
`DefRegistry.resolve` 返回的是继承合并后的结果，无法区分某个值是基类写的还是玩法写的。

**决策**：(1) 用于决策的绑定必须是具体定义，`abstract === true` 直接拒绝。(2) 用
`DefRegistry.getRaw` 沿 `extends` 链遍历**未合并**的祖先定义，只在 `abstract === true` 的祖先上
检查 `playOwnedPaths`，命中即 `AI_PLAY_CONFIGURATION_REQUIRED` 并指名该祖先与字段路径。

**依据**：requirements 9.1-9.4 的归属划分：可复用定义只能声明 Schema 与引用类型，具体值属于
玩法层。只有 raw 视图能证明"是谁写的"。

**风险**：中。`playOwnedPaths` 清单由基类层通过 `AIBehaviorFamilySchema` 提供，AI 不发明条目——
这意味着**没有配置该清单时该检查完全不生效**。它是一个可用的机制，不是自动生效的保证。

## 17. 自我发现并修正的缺陷：搜索会话把根上下文当作前驱

**问题**：`SearchSession.nextDecisionContext(after)` 的签名只带 `SimulationOutcome`，不带上下文。
我初版实现直接把 `this.root` 作为"上一个参与者"传给解析器，于是解析器永远从根开始找后继，
**三人及以上的链条无法推进到第三个参与者**——第二个参与者的后继又被算成第二个。

**成因分析**：`SequentialSearchPlanner` 的递归在每层持有自己的 `context`，但会话是跨层共享的
单例，签名没有把"是谁在问"传进来。我误以为会话可以用根上下文代替，没有意识到递归层的上下文
已经改变。这类缺陷的通用形态是：**把"当前"状态存在错误的作用域里**（会话级 vs 递归级）。

**修正**：会话按 `outcome.checkpoint` 建立 `Map<string, {handle, context}>`，`simulate` 时记录进入该
分支的上下文，`nextDecisionContext` 与 `restore` 都按 checkpoint 反查。既修正了前驱身份，也让
分支句柄与上下文的生命周期绑定在同一个键上。

**发现方式**：只有当端到端测试用**三个**参与者时才会暴露；两个参与者的测试全绿。这是"边界数量
选 2 不够，必须选 3"的典型案例，值得在后续测试设计中沿用。

**风险**：已修正。遗留风险是签名仍不带上下文，未来若有人新增另一条调用路径而忘记先 `simulate`
注册，会得到 `AI_SIMULATION_FAILED`（失败关闭，不会静默出错）。

## 18. 为完成全量验证而修复的共享内核缺陷（含一处行为变更，需复核）

这些不属于 AI 范围，但阻断了 `npm test` / `tsc`，按"发现即修"处理。

**18.1 `PlaypackLoader.load` 不记录已装载包（行为变更，重点复核）**
原实现的"已存在玩法包"集合只来自构造参数 `existingPlaypacks`，成功装载后不更新。后果：
顺序装载依赖链时 `requires` 永远不满足；且对先前已装载包的 `E_LOAD_CONFLICT` 检测失效。
修正为内部维护 `loaded` 数组（构造参数作为初始基线），成功装载后并入，并新增
`loadedPlaypacks()` 只读快照。**这改变了装载器的可观测行为**，请复核是否符合 L9 的意图。

**18.2 `DiagnosticSink` 软容量语义**
容量满时原实现合成一条 `E_QUOTA_DIAGNOSTICS` fatal 并中止。这与既有测试要求的
"error/fatal 永不丢弃、仅淘汰最旧 info/warn、`getDroppedCount()` 计数"冲突。恢复为软容量淘汰。
同时删除 `HINT_TEMPLATES` 的两处重复键，并把 `halt()` 里的 `throw`-in-`finally` 改写为
`catch` 后 throw（语义等价：onFatal 抛错不得取代终止信号），消除 `no-unsafe-finally`。

**18.3 `definition-registry.ts` 的 `activate` 泛型不匹配**
`prepare` 返回 `CompilationOutcome<PreparedActivation>`，失败分支直接 `return prepared` 与
`CompilationOutcome<CanonicalRegistrySnapshot>` 不兼容。改为分别处理
`infrastructure-failure` 与 `invalid`（后者用 `invalid()` 重建），不改变诊断内容。

**风险**：18.1 中；18.2 / 18.3 低。三者都有既有测试覆盖并已全绿。
