# Requirements Document

## Introduction

### 核心机制需求定位

本文档定义 WakeUp **玩法层**的标准核心机制规则，覆盖行动点（AP）、投点与行动顺序、体力、回合阶段、动作成本、网关、生命与倒地、令其长眠、状态、格挡、隐蔽及恢复边界。

本 Spec 的层级归属如下：

- **引擎层**拥有 `OpRegistry.invoke`、合法 Op、Expr、Query、Hook、Decision、Intent、事务、命名随机流、持久化和诊断机制；本 Spec 只消费这些机制，不重新定义、复制或旁路它们。
- **基类层**拥有可枚举、可组合且不绑定具体玩法的动作族、网关族、资源、状态、伤害、移动、物品、空间和适配契约；本 Spec 只选择并组合已登记的基类与实例。
- **玩法层**拥有本 Spec 中的具体数值、行动经济、阶段顺序、状态约束和规则选择。

本 Spec 不定义具体枪械伤害、掩体效果、出生规则、胜负条件、地图布局、NPC 个体参数或具体物品实例；这些内容只有在权威决策和相应玩法层配置冻结后才能进入规范。

## Glossary

- **核心机制规则集**：本 Spec 定义的玩法层规则集合。
- **玩法层配置**：组合已登记基类与实例、填写具体玩法值并声明规则选择的配置。
- **活体**：可拥有生命、体力和动作能力的玩法语义实体。
- **投点参与者**：尚未观战或退出，且满足当前玩法层投点资格的玩家；零血倒地玩家默认仍是投点参与者。
- **AP（行动点）**：本规则集唯一的回合内时间货币。
- **付费动作**：独立消耗 1 AP、通过合法动作请求执行的动作。
- **附着动作**：没有独立 AP 成本、必须依附于一个已声明的付费动作、不能独立形成决策分支的动作。
- **中间状态**：多步交互在两个付费动作之间保持的、可被明确事件打断的状态。
- **投点等级**：用于分配 AP 和决定玩家行动顺序的玩家可见整数，值域为 1-5。
- **强力骰承诺**：投点前用体力换取投点等级修正的不可撤销承诺。
- **未分配 AP**：玩家本回合不获得可用 AP 的离散结果；UI 不得把它显示为数值 0。
- **天然场景**：由空间系统定义的地图骨架空间。
- **微型场景**：附属于天然场景、表达局部接触关系的空间；本 Spec 只引用其已验证语义。
- **网关**：对动作或过渡的前置条件、成本类别和成功/失败效果进行声明的基类层语义族。
- **零血倒地**：生命耗尽后进入的离散状态；“零血”是状态名称，不授权 UI 显示数值 0。
- **普通倒地**：由显式玩法效果触发、与生命耗尽不同的可恢复状态。
- **令其长眠**：对满足条件的零血倒地目标执行的付费动作。
- **行动轮**：回合内所有参与玩家的执行顺序排名；无并列，采用排名交换制。NPC 不进入行动轮。
- **窗口期**：上一回合行动开始之后、下一回合投点开始之前的提交时段；逆转、超逆转与强力骰承诺都在此时段提交。
- **逆转**：窗口期付费动作，消耗 1 AP，使自身行动轮排名提升 1 位。
- **超逆转**：窗口期付费动作，消耗 2 体力，使自身行动轮排名提升 2 位。
- **过载**：当某效果尝试使活体体力超过上限 5 时触发的离散状态；体力保持为 5，该活体失去本回合行动权并跳过下一次投点。
- **结构化拒绝**：复用引擎层 `Result` 与 Diagnostic 的失败结果；本 Spec 不另建错误模型。
- **稳定契约**：下游 Spec 可以依赖且变更时必须重新评审的语义保证。
- **未冻结契约**：尚无权威结论，不得由实现、工具或下游 Spec 推断默认值的接口或数值。

## Requirements

### Requirement 1: 层级、来源和废案约束

**User Story:** 作为规范维护者，我希望每项核心机制都有唯一层级和可追踪来源，以避免低优先级旧规则变成隐式默认值。

#### Acceptance Criteria

1. 系统应仅把具体数值、行动经济、阶段顺序和具体状态规则作为玩法层内容。
2. 系统应只通过已登记的基类、实例和参数约束表达动作、网关、状态、伤害、移动、物品与空间语义。
3. 若候选规则重新定义引擎层的 Op、Expr、Query、Hook、Decision、Intent、事务、随机或持久化机制，则规范验证应拒绝该候选规则。
4. 若来源内容被标记为示例、候选、待定、未来、可选限制或需专题讨论，则系统不得将其装载为规范默认值。
5. 若来源内容属于 S8 已否决机制，则系统不得将其作为核心机制要求重新引入。
6. 若同优先级来源发生实质冲突且没有已确认决策，则系统应把冲突记录为未决事项并停用受影响的默认规则。
7. 每项规范要求应保留本章格式的“来源追踪”，并至少指向一个权威来源或一个明确冲突裁决。

**来源追踪：** S0 第一至三、六、九条；S1 需求 1、2、16；S7 D-001、D-003、D-009、D-010、D-019；S8 废案清单。R0 中将历史路线图和旧文档直接作为规范依据的表述被本条取代。

### Requirement 2: 唯一写入通道和事务原子性

**User Story:** 作为系统集成者，我希望所有核心机制行为走同一条可审计事务链路，以保证 UI、AI、UGC 和服务端不会产生不同状态。

#### Acceptance Criteria

1. 任何会改变语义状态的核心机制行为都必须映射为一个或多个已登记合法 Op，并且只能通过 `OpRegistry.invoke` 发起。
2. 玩法层、AI、UI、UGC、网络输入和测试输入均不得直接改写 `WorldState` 或调用绕过 `OpRegistry.invoke` 的可写接口。
3. 一个动作、阶段结算、被动触发、资源结算、状态变化或死亡结算涉及多个写入时，系统应在引擎层事务中原子完成全部写入。
4. 若事务中任一步失败或违反不变量，系统应回滚整个事务，并保持事务前语义状态。
5. 行为失败时，系统应原样返回引擎层 `Result`/Diagnostic 契约，不得抛出玩法层异常、静默失败或自行定义第二套错误格式。
6. 随机行为应调用引擎层已登记的命名随机 Op；玩法层不得直接生成随机值或维护独立随机状态。
7. 被动效果和 Hook 只能在合法 Op 产生的事件链上结算；不得以旁路监听器直接写状态。
8. 在 D-002 所述 Hook 接线缺口完成并通过引擎层验收前，依赖真实 Hook 链路的核心机制集成应标记为阻塞，不得宣称端到端可用。

**来源追踪：** S0 引擎层铁律；S2 需求 16、19-24、35、37、40、44；S3“写入通道唯一性”；S4 `ops/` 边界；S7 D-001、D-002。

### Requirement 3: 玩家可见数值与五并列约束

**User Story:** 作为玩家，我希望所有规则数值和同时面对的选择保持在统一认知范围内。

#### Acceptance Criteria

1. 所有玩家可见玩法数值应为 1-5 范围内的整数。
2. 投点等级、AP 分配量、AP 成本、生命、伤害、治疗、体力、体力消耗、正整数持续回合、槽位和玩家可见阈值均应遵守第 1 条。
3. 系统不得向玩家显示数值 0、6、小数、NaN 或无穷值。
4. 资源耗尽应显示为离散状态、空值或无可用资源，而不是玩家可见数值 0。
5. 生命耗尽应在同一事务内转为零血倒地状态，不得把玩家可见生命保留为数值 0。
6. 附着动作应显示为“无独立 AP 成本”的动作类别，不得显示为“0 AP”。
7. 回合编号、实体数量、内部索引、随机流计数器(如骰点)、结算预算和性能统计可以超出 1-5，但必须由引擎层 Schema 明确标记为内部数值，且不得作为玩法值展示。
8. 任一时点向单个玩家并列提供的独立选项不得超过 5 个；公共机制类型只有满足 S0 的公共、同步条件时才可使用例外。
9. 若玩法层配置含有未分类数值，验证应拒绝该配置，而不是推断其为内部数值。

**来源追踪：** S0 第四、五、十二条；S1 需求 5；S7 D-023。冲突裁决：S5/S6/R0 中的可见 d6 结果、0 AP、0 生命和“0 AP 动作”表述低于 S0，分别收敛为 1-5 投点等级、未分配 AP、零血倒地状态和附着动作类别。

### Requirement 4: AP 与动作成本

**User Story:** 作为玩家，我希望每个独立动作都具有统一且可预测的时间成本。

#### Acceptance Criteria

1. AP 应是本规则集回合内执行动作的唯一时间货币。
2. 每个付费动作应恰好消耗 1 AP。
3. 系统不得接受单次消耗 2 AP 或以上的原子动作。
4. 需要多个时间单位完成的交互应声明为多个付费动作和显式中间状态；每一步都应可单独验证前置条件、成功效果和中断效果。
5. 玩家可独立选择的动作应通过引擎层统一合法动作枚举获得，AI、UI 和规则验证不得维护第二份 AP 价格表。
6. NPC 动作应复用与玩家相同的付费动作/附着动作成本类别，但 NPC 的回合资源来源不得从玩家投点规则中推断。
7. 移动到相邻合法位置、拾取、攻击、整理背包、上车、下车、举盾格挡、睡下、起床、站起和令其长眠在启用时均应登记为付费动作。
8. 丢弃物品、使用已声明的随动作消耗品和取消格挡在启用时均应登记为附着动作，并满足 Requirement 8 的依附约束。
9. 若动作请求的 AP 不足、前置条件失效或成本结算失败，系统应结构化拒绝该动作且不产生部分效果。

**来源追踪：** S1 需求 6；S5“行动点系统”“AP 消耗类型”；S8“AP”“一个动作永远 1 AP”；S2 需求 25、26。冲突裁决：S5/R0 中“移动 +1 AP”的字面总成本不得形成 2 AP 原子动作，按 Requirement 9 拆为多步流程。

### Requirement 5: 投点等级与 AP 分配

**User Story:** 作为玩家，我希望通过可复现的投点等级获得本回合 AP，并能从结果直接判断分配原因。

#### Acceptance Criteria

1. 基础投点等级和最终投点等级都应为 1-5 范围内的整数；系统不得产生或展示范围外的投点等级。
2. 启用随机投点的玩法层配置必须引用已审批的基础等级生成策略，并通过已登记命名随机 Op 执行；在 U-001 冻结前，标准核心机制不得自行把历史 d6 改写成均匀 1-5、映射表或其他默认分布。
3. 启用强力骰的玩法层配置必须引用已审批的修正后边界策略；在 U-001 冻结前，系统不得默认采用截断、回绕、重投、拒绝承诺或其他溢出处理。
4. 当投点参与者多于 2 名且某玩家是唯一最高者，并且其最终投点等级领先第二高等级至少 2 时，系统应为该玩家分配 3 AP。
5. 当投点参与者多于 2 名且玩家并列最高，或唯一最高者未满足第 4 条领先条件时，系统应为每名最高玩家分配 2 AP。
6. 当玩家最终投点等级与最高等级相差 1 时，系统应为该玩家分配 1 AP。
7. 当玩家最终投点等级与最高等级相差至少 2 时，系统应把该玩家标记为未分配 AP。
8. 当恰有 2 名投点参与者时，最终投点等级不低于对方的玩家应获得 2 AP；较低者按相差 1 或至少 2 分别获得 1 AP 或未分配 AP；系统不得在双人投点中分配 3 AP。
9. 系统应在一次结算事务中完成最终等级确认、AP 分配、强力骰退还判定和玩家行动顺序确定；若所需生成策略或边界策略未冻结，事务应在产生随机结果或扣除体力前结构化拒绝。
10. 给定相同合法输入、已审批策略、命名随机流状态和已提交承诺，重放应产生相同投点等级、AP 分配与顺序结果。
11. 当投点阶段只有 1 名投点参与者时，系统应按 D-037 分配 **2 AP**：档位裁剪规则为"3 人及以上启用 0~3 AP 全档位；仅 2 人取消 3 AP 档；仅 1 人同样取消 3 AP 档"，单人情形由第 4-8 条算法在屏蔽 3 AP 档后自然落到 2 AP，**不是特例分支**。系统不得为单人情形改写第 4-8 条算法。
12. AP 差值分配算法应能以外部提供的合法最终投点等级独立验证，不得因 U-001 阻塞而把第 4-8 条算法改写成候选规则。

**来源追踪：** S5“投点机制”“回合结构”；S7 D-007、D-008、D-037；S2 需求 35、37；S0 数值约束。冲突裁决：S5/R0 的 d6 可见结果违反 S0 的 1-5 范围；但 S0 未给出替代随机分布，也未裁决 +1/+2 修正越过 5 的处理，因此两者进入 U-001，不得由本 Spec 自行选择。S5 的三人概率示例不构成验收标准。**单人投点已由 D-037 裁决关闭**（第 11 条）：按人数裁剪档位，单人得 2 AP，属算法自然推导而非特例，U-002 因此关闭。

### Requirement 6: 体力、强力骰与恢复

**User Story:** 作为玩家，我希望用有限体力换取投点优势，并且失败时不会丢失已承诺的体力。

#### Acceptance Criteria

1. 玩家体力上限应为 5。
2. 当清理阶段结算时，系统应为每个活体恢复 1 体力，恢复结果最高为 5。！！！这一设计是不对的。看到的并行者顺便解决这个问题，修改有关的文档和实现。正确的回复体力标准方式应该是上床、处决和在一次回合得到0ap时的补偿。
3. 强力骰只应提供两档承诺：消耗 1 体力获得 +1 投点等级修正，或消耗 2 体力获得 +2 修正。
4. 系统不得提供第 3 档强力骰，也不得接受消耗 3 体力或以上的强力骰承诺。
5. 强力骰承诺应在随机投点前完成；进入随机投点后不得撤销或变更本回合承诺。
6. 体力不足时，系统应拒绝强力骰承诺且不冻结部分体力。
7. 在 U-001 的基础等级生成与修正后边界策略冻结前，标准核心机制不得执行强力骰投点结算或扣除承诺体力。
8. 当玩家的 AP 分配结果为未分配 AP 时，系统应在同一结算事务内全额退还该玩家本回合为强力骰实际冻结或结算的体力。
9. 当玩家获得至少 1 AP 时，系统应结算已承诺体力且不得重复扣除。
10. 令其长眠成功后，执行者体力应恢复至 5。
11. 合法睡眠流程应由“睡下”和“起床”两个各消耗 1 AP 的付费动作组成；完成起床动作时，系统应把该活体体力恢复至 5。
12. 已声明的体力消耗品应作为附着动作依附于合法父付费动作，并恢复 1 或 2 体力；具体物品实例、父动作和使用资格由下游配置提供。
13. 体力增加来源的白名单为：自然恢复、强力骰退还、令其长眠、合法睡眠流程、已声明体力消耗品，以及 **D-053 批准的两项施加于他方的体力增加**——弱点命中使被命中方体力 +1、招架成功使攻击方体力 +1。白名单之外的体力恢复或体力增加来源，必须由已验证的玩法层配置显式声明，不得从历史示例推断增量。
14. 任何恢复或增加效果结算后的体力都不得超过 5；达到上限时保持为 5，系统不得产生或展示体力 6。当任一合法效果尝试使体力超过 5 时，系统应在同一事务内保持体力为 5 并按第 16 条施加过载（D-055）。
15. 第 13 条中 D-053 批准的两项属于**施加于另一活体的体力增加，而非自我恢复**：其目标是被命中方或攻击方而不是效果发起者，且不得因发起者体力已满而被跳过、抑制或转移给发起者。装载验证不得因这两项使目标体力上升而把配置判为非法体力来源。
16. 当任一合法效果尝试使某活体体力超过 5 时，系统应对该活体施加过载；第 15 条所述施加于他方的体力增加是过载的合法触发来源。
17. 若过载施加时该活体本回合尚未行动，则系统应使其失去本回合行动权，本回合不再向其授予行动窗口。
18. 当活体处于过载时，系统应使其跳过下一次投点，并在其后的那一次投点（下下回合）重新加入投点；归队计数应作为内部数值记录，不得作为玩家可见玩法数值展示。
19. 处于过载期间，该活体应继续参与其他玩家的回合：其位置、状态、被交互与被攻击资格不变，且可观察局势。
20. 处于过载期间，系统应结构化拒绝该活体提交的主动动作请求，且拒绝不得改变其体力、归队计数或行动轮排名。
21. 过载的施加、行动权剥夺、归队计数递减与解除都应沿合法 Op 事件链自动结算；系统不得为过载向任何玩家发起回合外或他人行动中的即时选择。
22. 清理阶段的自然恢复在活体体力已为 5 时应为无操作，不得据此触发第 16 条的过载。

**来源追踪：** S7 D-007、D-053、**D-055（裁决权威：项目所有者本次会话裁决）**；S6 第 3.2、3.3、3.4、9.3、11 节；S5“体力系统”“零挫败退还”“体力恢复途径”“令其长眠”；S0 数值约束；S2 需求 20.12、26。冲突裁决：S8 的“睡眠每回合恢复 1”低于 S5 的“睡下 + 起床后回满”，标准规则采用 S5。**过载（原 U-003）已由 D-055 裁决关闭**：S6 §3.4 与 §11 术语对照均写“失去本回合行动权”，S6 §9.3 第 2 项写“本回合行动权保留”而紧接的第 3 项写“跳过本回合”；裁决采纳**失去/跳过本回合行动权**，依据是三处陈述中有两处一致，且 `src/play/action-turn/playpack.json` 的 `rule:overload-on-pool-overflow` 既有实现同样按“未行动者跳过本回合”落地。**S6 §9.3 第 2 项的措辞是唯一的离群陈述，必须在来源文档中更正**（“保留”只能被解释为保留观察与被交互身份，见第 19 条）。本裁决为项目所有者本次会话裁决并记录于此，不是本 Spec 的自行推断。第 22 条是本裁决的必要边界：若清理阶段的自然恢复也计入触发，任何满体力活体每回合必然过载，机制自毁；`playpack.json` 的 `props.resolutionPolicy.overloadThreshold` 与其决策记录 A-09 已按此实现。

### Requirement 7: 回合阶段与行动顺序

**User Story:** 作为玩家，我希望每个回合按固定阶段推进，且行动顺序没有隐藏判据。

#### Acceptance Criteria

1. 每个标准回合应依次包含投点阶段、结算阶段、玩家行动阶段、NPC 行动阶段和清理阶段。
2. 投点阶段应在 U-001 所需策略已冻结时收集强力骰承诺并生成投点等级；策略未冻结时应按 Requirement 5 结构化拒绝随机投点。结算阶段应完成 AP 分配、体力退还和玩家行动顺序确定。
3. 玩家行动阶段应按“分配 AP 较多者优先、最终投点等级较高者次优先、仍相同时完全随机”的顺序执行。！！！已经被新玩法机制：行动轮完全替代！请自行查阅并修改！
4. 第 3 条的完全随机顺序应通过已登记命名随机 Op 产生，不得使用固定玩家编号或容器迭代顺序替代随机。
5. 轮到一个玩家时，系统应允许其持续执行合法动作，直到没有剩余 AP 或明确弃权；随后行动权转移给结算阶段确定的下一名玩家。
6. 玩家行动阶段开始后，顺序应保持固定，除非受到 D-053 已批准的例外机制（逆转、超逆转、令其长眠后提升、弱点命中后降低、招架反制后降低）影响；未被 D-053 批准的其他即时重排不得改变当前回合执行队列。
7. NPC 行动阶段应按稳定 NPC 编号顺序执行；NPC 不参与玩家投点，不应用玩家同分随机规则。
8. NPC 每回合可用动作预算必须来自显式玩法层配置，**默认值为 1 AP**（D-052），且该值必须可由玩法层配置覆写；系统不得从玩家 AP 分配表推断 NPC 的具体 AP 数量。
8a. NPC 应拥有独立体力池（D-052）：**默认上限 3、开局 0**，"是否主动使用体力"为玩法层可配置项。NPC 体力**不得用于逆转或超逆转**——NPC 不参与行动轮，无轮次可抢。该体力池的存在目的是使弱点效果的"对方体力 +1"与过载压制在 PVE 中可结算。
9. 清理阶段应结算自然体力恢复、显式状态到期和已声明持续效果；每项写入均应满足 Requirement 2 的事务要求。
10. 当前阶段尚有必需输入、未完成合法动作解算或未满足推进条件时，系统应拒绝阶段推进。
11. 行动轮应是回合内所有参与玩家的执行顺序排名：系统应为每名参与玩家分配唯一排名，不得产生并列排名。
12. 行动轮排名变化应以**排名交换**实现：变化双方互换排名位；系统不得插入新排名位、复制排名位或改变行动轮列表在回合内的长度。
13. 每次行动轮排名变化后，系统应在同一事务内重新排序行动轮，并从排名最高的尚未行动者继续执行。
14. 已行动玩家应保留在行动轮列表中，仅标记为已行动并按 D-035 做低显著性视觉降饱和；系统应通过扫描列表定位第一个尚未行动者来推进执行，不得以出队方式移除已行动者。
15. 行动轮排名变化幅度应恰为下表所列：逆转 +1 位、超逆转 +2 位、处决（令其长眠）成功使执行者 +1 位、弱点命中使被命中方 -1 位、招架成功使攻击方 -1 位。系统不得引入表外幅度。
16. 逆转成本应恰为 1 AP，超逆转成本应恰为 2 体力；两者都只能在窗口期（上一回合行动开始之后、下一回合投点开始之前）提交。
17. 逆转、超逆转与同一回合的强力骰承诺应互斥：若玩家该回合已提交其中任一项，则系统应结构化拒绝另一项，且拒绝不得扣除 AP 或体力。
18. 窗口期提交的逆转、超逆转与强力骰承诺应在提交时立即结算成本，其排名与投点等级修正在下一次投点阶段兑现；系统不得为窗口期提交向任何玩家发起他人行动过程中的即时交互选择（Requirement 8）。

**来源追踪：** S6 第 2.1、2.3、2.4、2.5、9.1、9.2、9b 章；S5“完整回合流程”“行动顺序规则”；S7 D-008、D-035、D-036、D-052、D-053；S2 需求 31、35。**阶段结构的关系（本次会话所有者裁决澄清）**：本章五阶段分解与 S6 §9.1 的三相流程**不是竞争结构，而是同一流程的不同粒度**——S6 §9.1 把 AP 结算与行动轮排名折叠进“投点阶段”内部，本章把它们显式拆为投点阶段与结算阶段；S6 §9b（D-052）把 NPC 行动置于全部玩家轮次之后，本章把它显式命名为 NPC 行动阶段；S6 的“清理阶段”与本章第 9 条一致。因此本章五阶段是 S6 三相流程的**更细粒度精化**，二者不存在需要裁决的冲突，此前“S6 三阶段流程低于 S5 五阶段契约”的表述已作废。第 11-18 条把 S6 §2 与 D-035/D-036 固定的行动轮语义正式纳入规范；NPC 无轮次并在全部玩家轮次之后按稳定顺序行动，已由第 7、8 条规定，本处不重复。**关于即时重排的裁决已由 D-053 更正**：S6 的逆转、超逆转、处决后提升、弱点命中降低、招架反制降低这五项**不再是"被置换的非规范候选"，而是已批准的标准默认机制**（见第 6 条例外条款）。此前把它们整体判为候选的理由（与固定行动顺序冲突）已被项目所有者否决——冲突通过显式例外条款解决，而非通过禁止机制解决。除这五项之外的即时重排仍不得改变当前回合执行队列。NPC 的 AP/SP 默认值见 D-052。

### Requirement 8: 时序纯洁性与附着动作

**User Story:** 作为玩家和 AI 决策者，我希望非当前行动者不会在我的行动中插入主动选择，且无独立成本的动作不会扩大搜索分支。

#### Acceptance Criteria

1. 当前玩家行动期间，其他玩家不得提交需要即时选择的主动动作。
2. 本规则集不得启用回合外反击决策、Overwatch 或要求在 Hook 中等待玩家回答的机制。
3. 在自己回合预先声明、随后由合法事件自动触发且不再征求输入的被动效果可以结算，但必须沿 Op/Hook 事务链执行。
4. 附着动作不得独立出现在玩家或 AI 的顶层合法动作分支中。
5. 每个附着动作必须声明其父付费动作、触发时点、前置条件、效果和失败行为。
6. 当父付费动作不合法、未执行或已回滚时，其附着动作不得执行。
7. 同一父动作可用的附着动作与其他并列选择合计不得违反五并列原则。
8. 若 UI 或 AI 尝试独立提交附着动作，系统应结构化拒绝且保持状态不变。
9. 隐藏信息不得成为绕过时序纯洁性的理由；未经 D-053 批准的隐藏招架和其他隐藏动作不得进入默认合法动作集（D-053 已批准的招架机制不受本条"未冻结"限定约束）。
10. 窗口期动作（逆转、超逆转、强力骰承诺）应只在窗口期由本人提交，并在提交时立即结算成本；系统不得因某玩家在窗口期的提交而向其他玩家发起他人行动过程中的即时选择。
11. 过载（Requirement 6 第 16-21 条）应完全由合法 Op 事件链自动结算：过载的施加、行动权剥夺、跳过投点与归队都不得要求任何玩家在他人行动过程中作答，也不得表现为回合外反击式的交互。

**来源追踪：** S5“时序纯洁性原则”“零费动作”；S8 废案“回合外反击 / Overwatch”；S1 需求 6；S2 需求 27、28；S7 D-053、D-055；S6 第 2.3、3.4、9.2、9.3 节。冲突裁决：S6 的隐藏招架可以被解释为预先准备的被动触发；U-004 已由 D-053 裁决批准，招架机制现为标准默认规则，其完整前置、持续和可见性对齐 S6 第 7 章原始设计。

### Requirement 9: 精密交互与多步移动

**User Story:** 作为玩家，我希望长耗时交互被拆成可理解、可中断的 1 AP 步骤。

#### Acceptance Criteria

1. 精密交互应由“开始”付费动作、显式中间状态和“完成”付费动作组成，每个付费动作各消耗 1 AP。
2. 中间状态应绑定发起者、目标和交互种类，且不得被另一目标的完成动作复用。
3. 当发起者移动、受到有效攻击、主动取消、目标失效或前置条件不再满足时，系统应通过合法 Op 清除中间状态并中断流程。
4. 中断后不得产生完成效果；已经合法完成的第一步 AP 成本不因普通中断自动退还。
5. 撬锁和破锁可作为精密交互的玩法层动作选择，但具体锁、门、工具、检定门槛和破坏效果必须由 space-items 相关配置提供，本 Spec 不填默认值。
6. 重型负重下的大范围移动以及需要额外时间的楼梯、窗户等过渡不得通过单次 2 AP 动作表达；启用时应拆成两个付费步骤和可观察的过渡中间状态。
7. 若第二步执行前空间、负重或过渡前置条件失效，系统应拒绝第二步并按显式中断规则清理状态。

**来源追踪：** S5“精密交互”“成本修正”；S1 需求 6、9；S8“流程”。冲突裁决：R0 中“基础成本之上额外消耗 1 AP”的实现含义被收敛为多步流程，以服从 1 AP 铁律。

### Requirement 10: 三种网关

**User Story:** 作为玩法设计者，我希望所有条件型交互使用统一语义族，以便空间、物品、AI、UI 和 UGC 对成功与失败有相同理解。

#### Acceptance Criteria

1. 核心机制应支持资源转换网关、检定网关和条件网关三种已登记基类层语义族。
2. 每个具体网关配置应声明触发者和目标要求、成本类别、成功条件、成功效果、失败效果或无效果语义，以及 UI 可用的失败原因。
3. 资源转换网关应在输入资源满足时确定性地产生声明效果；输入不足时应结构化拒绝且不得产生成功效果。
4. 检定网关应引用引擎层合法随机或求值能力以及玩法层显式标准；不得自行实现随机函数。
5. 条件网关应引用纯读 Expr；条件不满足时不得产生成功效果。
6. 网关产生的资源扣除、物品移动、状态变化、通路变化或其他写入都必须通过 `OpRegistry.invoke` 的合法 Op 在一个事务中完成。
7. 网关失败不得留下部分资源扣除、半生成对象或半开放通路。
8. 本 Spec 不为商店、锁门、合成台、检定难度、资源数量或网关 AP 成本提供默认值；具体配置必须遵守 1-5 数值域和 1 AP 动作规则。

**来源追踪：** S7 D-006；S1 需求 6；S5“网关机制系统”；S2 需求 12、16、21、35。冲突裁决：S8 中“三种网关暂不加入标配”的旧表述已被更高优先级 D-006 明确取代。

### Requirement 11: 生命、伤害、治疗与零血倒地

**User Story:** 作为玩家，我希望生命耗尽后的状态和可执行行为明确且可预测。

#### Acceptance Criteria

1. 活体生命上限应为 5；处于正常存活状态时可见生命应在 1-5。
2. 单次玩法层伤害和治疗量应为 1-5；具体枪械基础伤害在 T-001 冻结前不得生成默认值。
3. 当一次合法伤害使剩余生命不再为正时，系统应在同一事务内进入零血倒地状态，不得向玩家暴露生命 0 或负数。
4. 零血倒地的玩家仍应参与后续投点，并可按正常规则获得 AP，除非其已选择观战或其他经审批的退出状态。
5. 零血倒地玩家不得移动、站起、攻击、拾取、使用背包物品、整理、开关门、上车、驾驶、执行精密交互、睡下、起床或主动令自己长眠。
6. 零血倒地玩家可以选择观战或退出游戏；任一操作成功后都应永久退出本局后续投点，且不得自行恢复为参战状态。
7. 零血倒地的默认动作集不得因拥有 AP 而自动扩大；任何新增动作都需要权威规则显式批准。
8. 治疗结算后的生命最高为 5；系统不得产生或展示超出上限的生命值。
9. 具体环境淘汰、毒区死亡、NPC 是否可复活及是否可令其长眠应由相应玩法层配置显式声明；本 Spec 不把僵尸历史示例泛化为所有 NPC 默认规则。

**来源追踪：** S5“生命值与倒地系统”；S0 数值约束；S8“倒地”与待深化项；S9 T-001。冲突裁决：S8 允许零血倒地爬行，而优先级更高且标记定稿的 S5 明确“不能移动”；本 Spec 采用 S5。R0 的“生命值归零后保留 0”收敛为原子状态转换。

### Requirement 12: 普通倒地、令其长眠与死亡背包

**User Story:** 作为玩家，我希望普通倒地、生命耗尽和死亡结算是三种不混淆的语义。

#### Acceptance Criteria

1. 普通倒地应只由显式声明的玩法效果触发，不得由生命耗尽隐式触发。
2. 普通倒地活体可以执行爬行付费动作，但不得离开当前所属天然场景。
3. 普通倒地活体可以消耗 1 AP 执行站起动作；成功后应离开普通倒地状态。
4. 格斗系统已按 D-010 降级为可选内容；普通倒地的默认触发源不得从历史格斗招式中推断。
5. 令其长眠应是消耗 1 AP 的付费动作，且只有当目标处于零血倒地、执行者与目标位于同一微型场景并满足目标资格时才合法。
6. 令其长眠成功时，系统应在一个事务内完成目标死亡、执行者体力恢复至 5 和死亡背包创建；任一步失败应整体回滚。
7. 死亡背包应是独立新建的、只允许取出而不允许存入的容器语义实体，不得复用尸体系统或死者原背包实体。
8. 死亡背包初始内容应恰好引用死者死亡事务中可转移的手持、背包和装备物品；不得复制或遗失物品。
9. 死亡背包容量应由创建时的实际内容数量派生，属于内部结构计数；若该计数超过 5，系统不得把它作为玩家可见玩法值展示。
10. 查看死亡背包清单应为只读查询，不消耗 AP；任一界面同时提供的独立取出选择不得超过 5 个。取出物品应通过合法物品移动 Op，并遵守下游物品契约。
11. 若目标不是合法令其长眠目标，系统应结构化拒绝，且不得恢复执行者体力或创建死亡背包。

**来源追踪：** S7 D-010；S5“普通倒地”“令其长眠”；S8“倒地”“死亡背包”“令其长眠”及废案“尸体系统”；S1 需求 8；S2 需求 16.7、17、21。

### Requirement 13: 状态持续、叠加与清理

**User Story:** 作为玩法设计者，我希望状态的持续和组合规则明确，使新增状态不会获得隐式效果。

#### Acceptance Criteria

1. 每个状态应显式声明条件持续或 1-5 回合的正整数持续时间；不得向玩家显示剩余 0 回合。
2. 对于采用“刷新”策略的同名状态，再次施加时应保留两者中较长的合法剩余时间，不得默认叠加强度。
3. 采用计数、独立实例或其他叠加策略的状态必须由已登记基类和玩法层配置显式声明；未声明时不得推断。
4. 清理阶段应使有回合持续时间的状态推进一个单位；剩余 1 回合的状态在本次推进后应移除，而不是保留可见 0。
5. 状态之间只有在显式交互规则存在时才可产生克制、放大、解除或额外效果。
6. D-016 已移除的“淋湿”状态及其组合效果不得作为默认状态交互重新出现。
7. 状态施加、刷新、移除和交互效果都必须通过合法 Op 和事务完成。
8. 若状态配置缺少持续策略、叠加策略、效果引用或中断规则中的必需项，验证应拒绝该配置而不是补全默认语义。

**来源追踪：** S1 需求 9；S5“状态效果系统”；S7 D-016；S2 需求 30。R0 的“所有同名状态统一取最长”被收窄为显式选择刷新策略的状态，避免覆盖基类层允许的其他叠加模式。

### Requirement 14: 格挡与隐蔽

**User Story:** 作为玩家，我希望格挡和隐蔽的持续与解除条件固定，不受低优先级战斗候选规则改变。

#### Acceptance Criteria

1. 举盾格挡应是消耗 1 AP 的付费动作；成功后活体进入格挡状态。
2. 格挡状态应持续到受到攻击，或通过依附于合法父动作的取消格挡附着动作主动取消；不得因普通回合结束自动移除。
3. 受到攻击时，格挡应通过被动 Hook 按盾牌配置结算并自动取消，且不得向防守者发起回合外选择。
4. 具体伤害减免、盾牌类型、破损规则和可格挡攻击范围应由 space-items 的已验证配置提供；本 Spec 不提供默认数值。
5. 隐蔽状态只应在大场景语义中生效。
6. 隐蔽活体移动后应通过合法 Op 移除隐蔽状态。
7. 隐蔽有效时，其他活体不得对其执行“找到”交互；不受影响的查询范围必须由空间与可见性契约显式声明。
8. S6 中的招架、失衡、弱点破防已由 D-053 裁决批准为标准默认动作/状态集的一部分，与本章格挡/隐蔽规则并存；两者不冲突——格挡受攻击自动取消是本章默认规则，弱点命中触发的 [失衡] 状态会额外破除举盾，这是两条规则的正常叠加。“受击后到回合结束才放下盾牌”这一与 D-009 冲突的具体陈述仍不采用。

**来源追踪：** S7 D-009、D-015、D-053；S5“格挡与隐蔽状态”；S8“防具系统”；S1 需求 8、9；S2 需求 23。冲突裁决：D-009 高于 S6 的盾牌持续陈述，因此举盾状态本身采用“受击或主动取消，回合结束不取消”；D-053 已裁决批准弱点破防机制，其触发的 [失衡] 与举盾的自动取消规则叠加生效，不视为矛盾。

### Requirement 15: 生命与体力恢复边界

**User Story:** 作为玩家，我希望所有恢复都来自公开、已验证的规则，而不是隐藏默认值。

#### Acceptance Criteria

1. 医疗物品恢复生命时，应作为附着动作依附于一个合法父付费动作执行，并且单次恢复量只能是 1 或 2。
2. 医疗效果不得使生命超过 5，且不得对不满足目标资格的对象生效。
3. 自然体力恢复、强力骰退还和令其长眠恢复应分别遵守 Requirement 6，不得被同一事件重复结算。
4. 睡眠恢复应由 Requirement 6 规定的“睡下 → 起床”两个付费动作完成，并在起床成功时把体力恢复至 5；不得同时叠加 S8 中已被置换的“睡眠每回合恢复 1”规则。
5. 已声明体力消耗品应依附于合法父付费动作恢复 1 或 2 体力；具体物品实例、父动作、目标资格和消费行为必须由下游配置显式声明。
6. 新增恢复来源时，玩法层配置必须显式声明来源、目标资格、动作类别、恢复资源、1-5 的恢复量或“恢复至上限”语义、触发时点和失败行为。
7. 未声明的自然恢复、隐式回血或隐式体力恢复不得发生。
8. 恢复相关写入必须通过 `OpRegistry.invoke` 的合法 Op，并与物品消耗、状态清理或动作成本处于同一事务。
9. D-053 批准的两项施加于他方的体力增加（弱点命中使被命中方体力 +1、招架成功使攻击方体力 +1）不属于本章的“恢复来源”，而是 Requirement 6 第 13、15 条定义的、由攻防结算派生的体力增加；系统不得把它们计入第 3 条的重复结算判定，也不得因其使目标体力达到上限而抑制 Requirement 6 第 16 条的过载。

**来源追踪：** S5“治疗机制”“体力恢复途径”；S7 D-007、D-053、D-055；S6 第 3.3、4.4.2、5.1 节；S0 数值约束；S2 需求 16、21、26。冲突裁决：S5 的安全屋恢复明确标记待定，不进入默认规则；S8 的睡眠每回合恢复 1 低于 S5 的合法睡眠流程后回满，采用 S5。R0 的“封闭且禁止其他恢复来源”被改为“无隐式来源、显式扩展”，以免阻断合法玩法层扩展。

### Requirement 16: 结构化拒绝、加载验证与可测试性

**User Story:** 作为创作者和质量工程师，我希望每条核心机制都能从输入和结果机械判断，并在非法输入时保持状态不变。

#### Acceptance Criteria

1. 玩法层配置装载前应验证层级归属、来源状态、数值分类、1-5 范围、五并列上限、引用完整性、动作成本类别、网关完整性和未决项使用情况。
2. 任一语义字段缺失、引用损坏、层级越权、废案复活、未决值默认化或引擎层不变量冲突都应导致原子拒绝。
3. 只有非语义表现字段可以按基类层契约降级；规则值、前置条件、效果、成本和引用不得静默补全。
4. 每个运行时拒绝结果应包含引擎层稳定错误码或 Diagnostic、失败原因和可定位主体，并保持请求前语义状态。
5. 每项验收应能通过合法动作枚举、只读 Query、事件日志、事务结果或持久化重放中的至少一种方式观察；不得以主观体验作为唯一判据。
6. 相同初始快照、相同输入序列和相同命名随机流状态应产生相同结果。
7. UI、AI 和 UGC 对同一动作请求应得到相同合法性判定和相同拒绝原因。
8. 若配置引用 T-001（枪械具体伤害数值）、T-002（掩体减伤/命中修正数值）或 U-001 中未冻结内容，验证应拒绝该配置或要求显式标记为非规范实验；不得在标准核心机制中激活。**已裁决关闭的 U-002（D-037）、U-003（D-055）、U-004（D-053）、U-005（D-052）以及 T-002 的结构部分（D-040）不在此列**——引用它们不构成拒绝理由。
9. 过载相关配置的验证应检查：过载触发条件为“尝试使体力超过 5”、体力封顶为 5、未行动者失去本回合行动权、跳过一次投点后在下下回合归队、归队计数标记为内部数值。任一项缺失或与 Requirement 6 第 14-22 条不一致时，验证应拒绝该配置，而不是补全默认语义。

**来源追踪：** S1 需求 11-16；S2 需求 16、20、21、35、37、39、44；S7 D-019、D-023、D-037、D-040、D-052、D-053、D-055；S9 未决事项表。

### Requirement 17: 未决事项不得默认化

**User Story:** 作为产品和设计负责人，我希望所有尚未裁决的问题保持显式可见，以避免实现者擅自选边。

#### Acceptance Criteria

1. “未冻结玩法事项”表中的每一项在获得新的已确认决策、明确来源记录和对应验收标准前都应保持未冻结。
2. 未冻结项不得产生默认数值、默认动作、默认状态、默认接口字段或默认 UI 文案。
3. 下游 Spec 若依赖未冻结项，应显式声明阻塞关系，而不是复制历史候选方案。
4. 未决项获得裁决后，应更新本表状态、受影响需求和来源追踪；仅删除表项不构成裁决。
5. T-003 与 T-004 应按“已裁决但待同步的文档债务”作为文档债务跟踪，不得把它们当成玩法规则未决或运行时阻塞。
6. 每条裁决记录应载明裁决权威来源；由项目所有者在本 Spec 会话中直接作出的裁决应记为“项目所有者本次会话裁决”，并分配一个仓库内未被占用的决策编号，不得复用或撞车既有编号。
7. 已裁决项应从“未冻结玩法事项”表移入“已裁决但待同步的文档债务”表并保留裁决轨迹；仅从未冻结表删除表项不构成裁决（与第 4 条一致）。
8. 来源文档与决策记录之间的不一致应登记为文档债务并载明具体位置与消解方向；系统不得因存在此类不一致而为受影响规则推断默认值，也不得据此把已裁决项退回未冻结状态。

### Requirement 18: 下游稳定契约与未冻结接口

**User Story:** 作为下游 Spec 维护者，我希望清楚知道哪些核心语义可以依赖，哪些仍需等待裁决。

#### Acceptance Criteria

1. 下游 Spec 应只依赖“稳定下游契约”列出的稳定语义，不得把“未冻结契约”中的内容当成已冻结接口。
2. 下游提交行为时应使用统一合法动作契约，并最终通过 `OpRegistry.invoke`；只读展示和决策应使用引擎层 Query/合法动作枚举，不得直接写状态。
3. 下游若需要新增核心机制扩展，应通过基类层登记和玩法层显式配置完成，不得要求引擎层加入具体玩法语义。
4. 任何稳定语义的破坏性变更都应回到需求阶段重新评审其来源、下游影响和迁移要求。

#### 稳定下游契约

| 下游 | 可依赖的稳定语义 |
|---|---|
| **space-items** | 付费动作固定 1 AP；附着动作无独立分支；精密交互使用多步动作与中间状态；同微型场景是令其长眠前置；格挡/隐蔽生命周期；三种网关类别；死亡背包独立、只出不进且物品守恒；睡下与起床各 1 AP、起床成功后体力恢复至 5；医疗和体力消耗品均依附合法父付费动作；所有写入经合法 Op |
| **AI** | 与玩家共用合法动作枚举、Query、成本和前置条件；附着动作不成为顶层搜索分支；玩家顺序在结算阶段确定后保持固定，仅 D-053 批准的五项排名变化可在玩家行动阶段改写执行队列且一律为排名交换制；同 AP 同最终等级时使用命名随机；NPC 固定编号顺序、无轮次；过载活体在过载期间提交的主动动作一律结构化拒绝；AI 请求失败保持状态不变 |
| **UI** | AP、生命、体力是不同资源语义；可见数值仅 1-5；未分配 AP/资源耗尽使用离散状态而非 0；过载以离散状态呈现且体力恒显示为 5，不显示 6，归队计数是内部数值不作为玩法值展示；行动轮排名在回合内常驻可见，已行动者仅做低显著性降饱和而不从列表移除；展示付费动作与附着动作分组、可用性和拒绝原因；显示本回合行动顺序与恢复结果；只读展示不得改写状态 |
| **UGC** | 只接受纯声明式 JSON 候选；复用基类层 Schema 和同一验证链；不得包含任意代码、直接状态写入、未分类数值、废案或未决默认值；语义错误原子拒绝 |
| **持久化/联机** | 相同快照、输入、已审批投点策略和命名随机流可重放；动作及被动效果位于事务和日志链；任何调用来源使用相同合法性结果 |

### Requirement 19: 需求覆盖与设计阶段准入

**User Story:** 作为设计评审者，我希望在进入设计阶段前能机械确认本 Spec 没有越层、矛盾或隐式默认值。

#### Acceptance Criteria

1. 每个设计组件应至少映射到本 Spec 的一项需求和一条来源追踪；无法映射的组件不得进入设计。
2. 设计不得为 Requirement 17 的未冻结玩法事项补写实现结论；只能记录阻塞或隔离为非规范实验。
3. 设计应为 Requirement 2 涉及的全部状态变化提供合法 Op 映射和事务边界，但不得修改引擎层接口定义。
4. 设计应证明所有玩家可见数值、持续时间和选择数量满足 Requirement 3。
5. 设计应证明 AP 多步流程不存在单次 2 AP 原子动作，附着动作不存在独立搜索分支。
6. 设计应证明 AI、UI、UGC 与普通玩家输入共用同一动作合法性和拒绝结果。
7. 设计评审应逐项执行以下反向检查：越层定义、废案复活、具体数值偷渡、历史示例默认化、术语漂移、与引擎层重复建模、不可测试陈述、需求重复、来源缺失、下游契约不明确。
8. 任一反向检查失败时，本 Spec 对应设计不得通过准入。

**来源追踪：** P01 十项强制审查与反向审查清单；S0；S1 需求 15、16；S2 需求 42-44。
