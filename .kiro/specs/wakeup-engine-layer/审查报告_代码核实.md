## 一、载器（L-01/L-02）——用代码核实确认立项判断

立项文档的核心假设「引擎层有 `Container`/`Slot` 承载物品却没有承载活体的**写通道**」经代码层全面核实**成立**，且比立项预判更进一步：

1. **`Slot.holds: Ref` 类型层不设限**（`src/core/kernel/topology/types.ts`），`invariants.ts` / `cascade-destroy.ts` 已按「Item 或 Entity 皆可为 `Slot.holds`」处理（需求 10.6 注释为证），`checkNoContainmentCycle` 已沿 holds 递归实体/物品。**承载活体的机制底座已在，只缺写通道。**

2. **缺写通道是实锤**：全代码库唯一能进槽的 Op 是 `item.move`，且硬性要求对象在 `draft.items` 中；`entity.place` 只写 `node`、强制 `slot: undefined`；没有任何注册 Op 把活体放进槽。`entity.demote` 是把实体现`createItemShape`转成 Item 才进槽——**现在无法让活体占据槽位**（此即 `container.enter` 要补的缺口）。

3. **不变量层面无需大改**：`checkSingleContainment`（Key 为 Id）、`checkNoContainmentCycle`、`checkLocationExclusive` 均对实体/物品一体适用，容器承载活体槽天然纳入。

4. **`checkContainerBidirectional` 是唯一 owner-kind 假设点**（`state.entities[c.owner] ?? state.items[c.owner]`）——载器承载面若挂在 Entity 上，其 `containers` 索引照走 Entity 分支，无需改；若以非 Entity/Item 形态实现才需扩展分发。

结论：载器立项方向与现有机制完全兼容，是**增量补写通道 + 特化具名**而非推翻性改造。

## 二、超越立项文档自身的连带发现（审查新增）

### 2.1 载具参数承载面（`VEHICLE_PARAMETER_BINDING_GAP`）根因改写

立项把根因从「L2 裁决参数承载面」改为「容器承载活体写通道缺位 / 载器特化未命名」。代码核实：
- **目录 `playLayerOwnedFieldNames` 自相矛盾**（`src/class/vehicles/index.json`）：`speed` 同时出现在 `drive` 能力的 `parameters[]`（必填 field-name 槽）**和** `compositionContract.playLayerOwnedFields`——一个字段身兼「能力必填槽」与「玩法层自有字段」，是结构矛盾直接来源。
- **占用/货舱处置无顶层槽**：`occupantDisposition`/`cargoDisposition`（`destruction_sequence` 必填）只在 JSON 声明为 field-name，玩法层 profile 上**无任何对应顶层键**。
- `audit.ts` 用 `vehicleParameters` 绑定字段（目录声明它）但 `PARAMETER_BINDING_FIELD[vehicles]=''` 短路、完全没读——**豁免工具只留了顶层支撑审计，能力参数绑定契约对载具整个失效**。

### 2.2 单调重定义（L-04/D-073）改造点复核

- `PlaypackLoader.findConflicts` 把已存在 id 当 `E_LOAD_CONFLICT` 除非 `overrides` 声明；`applyOverrides` 是对 def 树整体做字符串值重写（同 key 需靠 remap 改名）——**与「后装覆盖先装」相反**。
- L2 `DefinitionRegistry` 用 `overrideIntent` 显式声明 + `REF_OVERRIDE_NOT_DECLARED` 拒绝未声明覆盖（`src/l2/ugc/ports/package-mapping.ts:160,175`）。两套都是「修改须显式声明」模型。D-073 已裁改为单调重定义，需把装载从声明型冲突解决改为同 key 覆盖/新增 + 跨作用域冲突拒绝。

### 2.3 地图锚点 / 唯一性（L-05）——现状为文档级、代码零落实

- `src/play/map/**` 无任何「map 锚点 / 不可替换 / 地图位按 ID 区分 / 官方图/上传图」代码；`CompileOptions.allowUnpublishedMaps` 被解构但**从不用来 gate 任何逻辑**。
- `src/play/types/*`、`src/ui/profile/profile-loader.ts` 与地图装载无关，无 map-slot 唯一性概念。

### 2.4 高级判定（L-06）——Tier 与高级判定混淆现状

- `complexity.ts` 只有 `calculateComplexityScore`（计数 profile/map/rule）与 `suggestPriceTier`（1~4），无任何「引擎层引用/地图定义」可达性扫描。
- `compile.ts` 的 `collectClassReferences` 只是 `'.class.'` 字符串浅收集，非可达性分析；`CompiledPlaypack` 无 advanced 标签。

### 2.5 地图数据面 / 方向压缩（L-07）——已确认的布尔压缩缺陷

- `MapEdge.directionality` 是 `'bidirectional' | 'unidirectional'` 二 token；`linkSpecOf` 把它压成 `directed?: boolean`（只判 unidirectional）。**编译把方向语义丢在布尔里**。
- `MapData` 无 `visualObstruction`/`physicalObstruction`/`transitionWindow`/`semanticAnchor`，`scene.valueset.transition_directionalities` 也无 one-way-down/up token。
- **重要连带缺口**：`MapNode.parent` 与 `MapEdge.weight` 已有文档标注「未接通」——`PrefabDef.nodes[]`/`links[]` 没有 `parent`/`weight` 字段，`prefab.spawn` 建节点/边时不透传，**运行期所有场景是平的、所有连接 weight=1**，距离模型无依据。L-07 必须一并补齐，否则地图数据面增量即使加字段也到不了运行期。
