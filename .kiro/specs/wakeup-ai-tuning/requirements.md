# 需求文档

## 简介

本功能构建「AI 自主学习迭代系统」，让 agent 能自主调优 AI 决策参数（设计货币费目表），当 AI 在某些场景表现不符合预期时，agent 可以观测决策证据链 → 归因到具体费目 → 在受限范围内调参 → 验证没弄坏其他场景 → 记录并生成人类可读的调参说明。系统以 `ai-tuning` skill 作为收尾入口，让任何 agent 能通过一句话快速进入 AI 调参的专业状态，且不会看漏文档或凭 memory 想当然。

系统核心价值是：把「反复 dump 日志 → 人眼看 → 手工改表 → 再测」这种脏活，变成 agent 能独立闭环的流水线，并用防转圈机制（迭代预算 / 环检测 / 回归闸 / 检查点 / 禁碰清单 / 状态哈希锁定 / 单点归因 / 调参历史）保证 agent 不会把系统调崩或原地打转。

调优的目标读者可能是资深玩家而非资深程序员，因此调参报告必须深入浅出，用「问题 → 原因 → 建议 → 影响范围 → 需确认」的叙述结构，而非术语堆砌。

## 术语表

- **设计货币（Design Currency）**：内部估值原语，AI 决策的估值函数主入口。用费目当量 + 分水岭修正 + 稀缺系数给状态优劣打分。Internal_Metric，不展示给玩家。
- **费目（Fee Item）**：设计货币分数表的一个条目（`DesignCurrencyEntry`），例如 `e:enemy.vitality`（敌方生命）、`pool.ap`（行动点）。每个费目有 `unit`（当量）、可选的 `adjustment`（分水岭修正）、`scarcity`（稀缺系数）。
- **当量（Unit）**：费目的单位分数值，例如「一点敌方生命当量 5 分」。内部值，可任意（不受玩家可见 1-5 铁律限制）。
- **分水岭（Pivot）**：费目的修正触发条件，例如 `lethalWindow`（致死窗口，值 ≤4 时触发死亡锚）。
- **信念切片（BeliefSlice）**：AI 感知到的可见/已知事实集合，键为 `<id>.<字段>`，值为数值。设计货币只对它可观测到的事实计分。
- **决策证据链（DecisionTrace）**：一次 `facade.act` 决策的完整审计记录，包含读了哪些事实、每个候选动作的分数构成（ScoreBreakdown）、选了什么、提交成功/被拒。
- **分数构成（ScoreBreakdown）**：单个候选动作的分数分项明细，逐条列出每条费目贡献了多少分，用于归因。
- **行为断言（BehaviorAssertion）**：一条「期望 AI 在某个世界状态下做出什么选择 / 满足什么分数约束」的声明式规格。
- **黄金场景（Golden Scenario）**：一组已知「AI 应正确」的行为断言，作为回归基准。每次调参改动不得让其变红。
- **归因（Attribution）**：给定一个违反的断言 + 决策 trace，定位根因费目的过程。
- **调参（Tuning）**：在受限范围内修改某个费目的 `unit` / `scarcity` / `pivot` 值。
- **回归闸（Regression Gate）**：每次调参改动后跑全量 golden scenarios，任何原本绿的被弄黄即拦截并回滚。
- **检查点（Checkpoint）**：当前最优费目配置的可序列化快照，出问题可回滚。
- **禁碰清单（Forbidden List）**：不允许 agent 修改的参数集合（玩家可见 1-5 值、核心语义锚等）。
- **EARS**：Easy Approach to Requirements Syntax - 基于模式的需求编写方法。
- **INCOSE**：国际系统工程理事会 - 提供要求的质量规则。
- **Internal_Metric**：内部度量值，不展示给玩家，不受玩家可见 1-5 铁律约束。
- **Skill**：本项目的技能入口，让 agent 通过一句话快速进入特定领域的专业操作状态。

## 要求

### 要求 1：决策可审计

**用户故事：**作为调试者，我希望 AI 每次决策都能被完整追溯，以便我能理解 AI 为什么做出某个选择。

#### 验收标准

1. 系统应改造 `scoreDesignCurrency`，使其返回分数构成（ScoreBreakdown）而非仅返回总分标量
2. ScoreBreakdown 应逐条列出每条费目的 `feeItem`、`contribution`、`currentValue`、`fromPivot`
3. ScoreBreakdown 的分项贡献之和应等于总分
4. ScoreBreakdown 应标记每项是否由分水岭（lethalWindow / exhaustionAnchor）或稀缺系数触发
5. 系统应让 `BoundedAIDecisionFacade.act` 暴露决策证据链（DecisionTrace）
6. DecisionTrace 应包含 observedFacts（读了哪些事实）、candidates（每个候选动作及分数构成）、selected（选中动作及原因）、submission（提交成功/被拒及拒因）
7. DecisionTrace 应包含一次决策唯一的 `correlationId` 与决策时世界状态的 `stateHash`

### 要求 2：状态可复现

**用户故事：**作为调试者，我希望重现一个决策场景时能得到相同结果，以便归因不被状态漂移干扰。

#### 验收标准

1. 系统应能对世界状态（WorldState）做可序列化的快照（含 `stateHash` 与完整 JSON）
2. 系统应能从一个快照恢复世界状态
3. 从同一快照连续恢复并执行决策，决策结果应一致（决策确定性）
4. 同一快照的 `stateHash` 应稳定可重放

### 要求 3：行为断言基座

**用户故事：**作为维护者，我希望把「AI 应该怎么表现」规格化成可自动执行的断言，以便 agent 有明确的对错标尺。

#### 验收标准

1. 系统应提供行为断言注册表（BehaviorAssertionRegistry），能从 JSON 加载 / 保存断言
2. 每个行为断言应包含一个可复现的世界快照（setup）与期望（expect）
3. 断言期望不应只断言最终选择，还应支持断言分数项的结构性约束（scoreConstraints）与分水岭触发约束（pivotConstraints）
4. 系统应提供断言执行引擎（AssertionRunner），按 setup 恢复世界、跑 facade.act、检查期望并产出违规清单
5. 系统应把 AI全对局能力规划（M1~M10）翻译成至少 20 条初始行为断言
6. 初始断言中应至少 10 条标记为黄金场景（golden scenarios）
7. 全部黄金场景在当前未调优的设计货币配置上应全绿
8. 断言注册表应以黄金场景作为回归基准，供后续调参回归闸使用

### 要求 4：归因引擎

**用户故事：**作为调试者，我希望系统能告诉我是哪条费目导致了 AI 的错误选择，以便对症下药而不是瞎调。

#### 验收标准

1. 系统应提供归因引擎（AttributionEngine），输入一个违反的断言 + 决策 trace，输出根因费目列表
2. 归因引擎对每个根因费目给出置信度（0-1）与推理说明
3. 归因引擎只返回在决策 trace 的 ScoreBreakdown 中真实出现的费目
4. 对「该选动作 A 却选了 B」的违反类型，归因引擎应对比 A 与 B 的分数构成，输出贡献差异最大的费目为根因
5. 对「分数约束不满足」的违反类型，归因引擎应直接定位到该约束对应的费目

### 要求 5：受限调参器

**用户故事：**作为维护者，我希望 agent 能调整设计货币参数，但又不能破坏玩家可见数值或核心语义。

#### 验收标准

1. 系统应提供调参器（ParameterTuner），能在受限范围内修改费目的 `unit` / `scarcity` / `pivot` 值
2. 每个可调费目应声明允许范围（allowedRange）与步长（step）
3. 调参器应维护禁碰清单，禁止修改玩家可见 1-5 值（如 vitality 上限）、核心语义锚（如 deathAnchor / exhaustionAnchor）
4. 调参器修改超出 allowedRange 时应拒绝并说明原因
5. 调参器应记录每次改动的参数调优记录（ParameterTuningRecord），含归因、改动前后值、验证结果、最终决定
6. 调参器应支持回滚某条调参记录（revert）

### 要求 6：自主调参闭环

**用户故事：**作为调试者，我希望 agent 能独立把一个表现不对的 AI 行为调对，而不用我逐条喂它该怎么改。

#### 验收标准

1. 系统应提供调参编排器（TuningOrchestrator），对目标断言循环执行「跑断言 → 归因 → 检查环 → 单点调参 → 全量回归」直到通过或达到上限
2. 单轮调参应只修改一个费目（单点归因），不同时调多个
3. 调参闭环应受迭代预算上限约束（默认 12 轮），达到上限未收敛应停止并交回完整调参历史
4. 调参闭环应检测「A↔B 反复改」之类的环并停止，不得无限循环于同一组改动
5. 每次调参后应跑全量黄金场景回归，任何原本绿的断言被弄黄即回滚本次改动
6. 若归因置信度过低（< 0.3）或无法归因，编排器应停止并交回历史，不盲目调参

### 要求 7：演化闸门与表自述

**用户故事：**作为项目所有者，我希望 agent 每次自主调参都被验证且留有记录，同时希望我不必读懂原始表就能评审改动。

#### 验收标准

1. 系统应提供检查点机制（saveCheckpoint / loadCheckpoint），保存/恢复当前最优费目配置
2. 系统应把每次成功调参记录持久化，供日后追溯与评审
3. 系统应提供费目自述文档生成器，为每个费目自动生成人类可读的说明（当前当量、触发场景、分水岭、最近调整历史、调高/调低的影响模拟）
4. 每次自主调参闭环成功完成后，应生成一份面向资深玩家（非程序员）的深入浅出调参报告

### 要求 8：调参成功纳入断言集

**用户故事：**作为维护者，我希望 agent 修补一个错误行为后能把验证用的断言保留下来，让我系统逐步积累出更完善的原则体系。

#### 验收标准

1. 当一次调参闭环成功修复了某个违反的断言时，系统应把该断言标记为已固化（可加入断言集）
2. 固化后的断言应持久化进断言注册表，成为后续回归检查的一员
3. 从交互模式用户描述衍生出的临时断言，若调参成功，系统应支持将其保存为正式断言，供后续回归使用
4. 断言集应随成功调参持续增长，从而逐步形成更完善的行为原则体系

### 要求 9：技能入口

**用户故事：**作为调试者，我希望用一句话就能让 agent 进入 AI 调参专业状态，且不会因看漏文档或凭 memory 想当然而出错。

#### 验收标准

1. 系统应以一个 `ai-tuning` skill 作为调优入口
2. 触发 skill 时，skill 应强制加载完整上下文清单（当前费目配置、完整断言集、禁碰清单、最近调参历史、防转圈规则与边界决策指南），缺任一即提示
3. 加载时应做基础校验（文件存在且非空），确保没有看漏文档
4. 加载完成后才允许 agent 开始调参对话，不给「对着 memory 想当然」留空档
5. skill 应支持一键模式：自动扫描断言集找出红色断言，自动跑调参闭环，输出报告交用户审批
6. skill 应支持交互模式：把用户的自然语言场景描述翻译成临时断言，跑一轮归因并给出可理解的调参建议，经用户确认后执行
7. skill 的输出应深入浅出，面向资深玩家；采用「问题 → 原因 → 建议 → 影响范围 → 需确认」的叙述结构
8. skill 遇到边界情况（无解 / 回归震荡 / 置信度低 / 触碰禁区）应请求人类裁决，而非自行硬调

### 要求 10：防转圈与防破坏

**用户故事：**作为项目所有者，我要求任何 agent 自主调参都不能让系统原地打转或越调越糟，这是底线。

#### 验收标准

1. 系统在复现决策场景时应锁定同一状态快照，防止状态漂移导致归因反复
2. 调参闭环在单轮内只允许单点归因（一次只调一个费目）
3. 调参闭环应受迭代预算上限约束，到上限未收敛即停止
4. 调参闭环应检测改动环（A↔B 反复改）并停止
5. 调参闭环应在每次改动后跑全量黄金场景回归，弄坏则回滚
6. 调参器应受禁碰清单约束，不得修改玩家可见 1-5 值或核心语义锚
7. 每次改动都应留有参数调优记录，可回滚
8. 系统应通过检查点机制回到上一个全绿配置

### 要求 11：边界决策上交人类

**用户故事：**作为调试者，我希望当 agent 遇到它解决不了的模糊情况时，明确交给人类裁决而不是自己硬猜。

#### 验收标准

1. 当调参闭环 12 轮未收敛（可能需改玩法）时，系统应停止并请求人类裁决
2. 当修复某断言必然弄坏另一黄金场景（回归震荡，暗示断言矛盾）时，系统应停止并请求人类裁决
3. 当归因置信度低于 0.3 时，系统应停止并请求人类裁决
4. 当唯一根因落在禁碰清单时，系统应停止并请求人类裁决
5. 当出现需要新增费目或新动作的玩法级需求时，系统应停止并请求人类裁决（agent 只在现有费目上调分数，不发明新机制）

## 验收标准合规性

本需求文档遵循 EARS 模式（全称量化、事件驱动、状态驱动、不希望事件、可选特性、复杂子句）与 INCOSE 质量规则：使用主动语态、避免模糊术语与代词、每项要求仅包含一个想法、避免免责声明与绝对性用语、优先肯定陈述、无解决方案内部细节。

涉及序列化/解析的部分（断言 JSON 加载/保存、状态快照序列化/恢复、配置持久化）遵循：解析器要求、整洁打印器要求、往返要求（保存→加载→保存 一致，快照序列化→反序列化→再序列化 一致）。
