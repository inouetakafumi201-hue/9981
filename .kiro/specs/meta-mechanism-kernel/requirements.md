# Requirements Document

## Introduction

本文档为《起床》（WakeUp）项目的**元机制内核（MetaKernel）**制定工程需求。元机制内核是一台通用的离散策略博弈状态机，大逃杀等具体玩法只是运行在其上的一个玩法包（Playpack）。本文档将《元机制内核Spec_v1.md》设计稿中已定稿的十三层原语体系，转化为符合EARS模式与INCOSE质量规则的工程需求，覆盖状态模型、拓扑与容纳、表达式与查询、操作写入通道、效果脚本、事件与钩子、动作与决策、附着物、回合表与玩法包、随机、认知、持久化、安全与诊断共十三个层次。

设计前提：内核不得内置任何具体玩法概念（如生命值、行动点、护甲），所有玩法语义均由玩法包以数据形式声明。内核的合格判据是"不可绕过、三处复用、不含语义"三条完备性判据（见术语表）。

本文档以两条主线贯穿全部四十四条要求，而非仅停留在逐层罗列结构：

1. **拓扑可达性优先于结构罗列**：内核的价值不在于 Entity、Attachment、Intent 等结构本身，而在于容器嵌套、Def 继承、玩法包 MOD 叠加等拓展手段叠加任意深度之后，创作者触达与操作任意要素所用的原语调用形式保持不变（见要求43）。逐层的结构定义（要求1-40）都必须服务于这条约束，而不是自成目的。
2. **AI 是一等公民而非事后接入项**：AI 决策与人类玩家必须共用同一套 `queryActions`、`Query`、Op、事务与试探机制，新增内容对 AI 的可用性应是自动的、结构性的，而不是逐个机制补丁式接入（见要求44）。这条约束贯穿要求25（Action枚举）、要求34（PolicyDef）、要求37（AI搜索的持久化基础）与要求13（具名表达式的可替换判定），要求44 是对它们的统一收束，不是独立于它们的新增范围。

## Glossary

- **内核（Kernel）**：本文档定义的元机制状态机本身，不含任何具体玩法语义
- **玩法包（Playpack）**：`kind:'playpack'` 的 Def，声明具体玩法（如大逃杀、格斗、卡牌）的规则数据
- **圈层（Layer）**：内核对功能分级的四层模型，第0圈需修改内核代码，第1-3圈为零代码创作，第4圈为自定义算法（暂不开放）
- **不可绕过判据**：一个能力若缺失，创作者只能修改内核代码才能实现对应机制
- **三处复用判据**：一个能力至少被三个互不相关的表层机制使用
- **不含语义判据**：一个能力对其所服务的具体玩法内容一无所知
- **Value**：内核状态的值域，包含 null、boolean、number、string、有序表、映射、Ref 七种形态
- **Ref**：形如 `{$: Id}` 的引用，Id 由封闭前缀集合（`e:` `i:` `n:` `l:` `c:` `s:` `a:` `g:` `d:` `w:`）构成
- **props**：实体等结构上的自由区字段，内核不解释其内容，只有 props 之外的结构区受内核不变量约束
- **Entity**：在拓扑上有位置（node）或槽位（slot）的占位者，如活体、载具、容器宿主
- **Item**：在容器槽位中被容纳的对象
- **Attachment**：挂载于 Entity/Item/Node/Link/World 之上、承载状态与规则的结构，覆盖 buff、光环、环境状态、运行期规则
- **Def**：所有蓝图的统一结构，`kind` 取值包括 entity、item、node、link、attachment、action、rule、playpack、decision、prefab、expr、schedule、policy
- **Agent**：决策者与观察者的统一体，包含 `controls`（操控的 Entity）、`knowledgeScope`（认知范围）、`omniscient`（全知）、`authority`（特权）
- **Relation**：实体之间带类型（kind）、方向（from/to）、可选属性（props）的二元关系
- **Node / Link**：拓扑顶点与拓扑边，拓扑为图而非坐标系
- **微型场景（Micro Scene）**：由某个 Entity/Link/Node 触发按需创建、`parent` 指向宿主场景、`props.creator` 记录创建来源的 Node；占用者数量（由查询派生，不单独维护）归零时自动卸载
- **Container / Slot**：宿主上按名称索引的容纳结构；Slot 恒为有序数组，`insert` 取值 `'fixed'` 或 `'shift'`
- **Prefab**：`kind:'prefab'` 的 Def，声明一次性批量创建的子图蓝图，通过 `prefab.spawn`/`prefab.despawn` 实例化与回收
- **Op（操作）**：状态的唯一写入通道，返回 `Result<T>`，不抛异常
- **Expr（表达式）**：内核的纯读运算单元，必须是全函数（任何输入返回值或诊断，不抛异常）
- **具名表达式（kind:'expr'）**：可被多处调用的表达式定义，调用图必须无环，不能调用 Op
- **Query（查询）**：从指定集合按谓词、空间限定、可见性过滤、排序取值的只读结构
- **Event（事件）**：每个 Op 与自定义 emit 产生的记录，含 `cause` 因果链、`depth` 连锁深度
- **Hook**：由 `RuleDef` 承载的事件响应，分 before/modify/instead/default/after 五阶段
- **RuleDef**：`kind:'rule'` 的 Def，声明监听事件、触发阶段、条件与效果
- **Action / ActionDef**：`kind:'action'` 的 Def，声明可发现的合法着法，通过 `queryActions` 枚举
- **Decision**：向非当前行动者征求输入的一等状态对象，`decision.open` 不阻塞
- **Intent**：已提交但未解算的动作，用于同时提交、依序解算的场景
- **响应相位（Response Phase）**：`PhaseDef.kind:'response'` 的相位，承载反应技/反制而非在 Hook 内提问
- **Schedule / ScheduleDef**：回合表数据，由多个 `PhaseDef` 组成
- **PlaypackDef**：`kind:'playpack'` 的顶层声明，内核唯一需要被"启动"的入口
- **PolicyDef**：`kind:'policy'` 的 Def，声明 NPC 决策策略，`mode` 取值 `'rules'`、`'search'`、`'scripted'`
- **RngStream**：命名随机流，随机结果由流状态决定并可复现
- **Knowledge**：以 `Agent.knowledgeScope` 为键的信息不对称结构，`facts` 值域为任意 Value
- **Snapshot / Journal**：状态快照与操作日志，支撑存档、回放、回溯、AI 搜索
- **Diagnostic**：内核产生的结构化诊断信息，含 `severity`、`code`、`at` 归因、`hint`
- **ErrCode**：封闭的错误码枚举，按前缀分组（如 `E_REF_` `E_INV_` `E_OP_`）
- **不变量（Invariant）**：内核自行维护、玩法包不可破坏的状态一致性约束

## Requirements

### 要求 1：值域与地址空间

**用户故事：** 作为内核实现者，我想要一个封闭且可机械校验的值域与地址空间，以便任何状态读写都通过统一路径完成且不产生非法引用。

#### 验收标准

1. 内核应将所有可写状态限定为 Value 类型，Value 类型应仅包含 null、boolean、number、string、Value 有序表、字符串键映射、Ref 七种形态之一
2. 内核应将 Ref 的 Id 前缀限定为封闭集合 `e:` `i:` `n:` `l:` `c:` `s:` `a:` `g:` `d:` `w:`
3. 内核应提供恒定的 world 单例引用 `w:0`，供 `attach.add` 等操作以 World 作为目标
4. 当写入的数值为 NaN 或 Infinity 时，内核应拒绝该写入并生成一条诊断事件
5. 内核应将每一处状态关联到唯一路径，读写操作应仅通过路径寻址完成
6. 内核应将 Entity、Item、Node、Link 等结构上的 `props` 字段标记为自由区，不对 `props` 内部的键与值施加语义解释
7. 内核应将 `props` 之外的字段标记为结构区，结构区字段应仅能通过第4章定义的 Op 修改
8. 内核应维护六个顶层集合：`world`、`defs`、`nodes`、`links`、`entities`、`items`
9. 内核不得将微型场景实现为独立于 `nodes` 的第七个顶层集合

### 要求 2：Entity、Item、Attachment 运行时结构

**用户故事：** 作为玩法包作者，我想要 Entity 与 Item 之间可以相互转换、Attachment 可挂载于多种宿主，以便同一份数据结构服务活体、载具、装备与环境状态等多种表层机制。

#### 验收标准

1. 内核应将 Entity 定义为在拓扑上占据 `node` 或 `slot` 的对象，二者应互斥
2. 内核应将 Item 定义为存在于某个 `slot` 中的对象，Item 应可携带命名容器
3. 当创作者调用 `item.promote` 时，内核应将该 Item 转换为 Entity 并放置到指定拓扑位置
4. 当创作者调用 `entity.demote` 时，内核应将该 Entity 转换为 Item 并放入指定容器槽位
5. 内核应将 Attachment 的 `target` 字段泛化为可指向 Entity、Item、Node、Link 或 World 之一的 Ref
6. 当一个 Attachment 的 `target` 为 `w:0` 时，内核应将该 Attachment 携带的规则视为运行期临时插入的规则集
7. 内核应为每个 Attachment 维护可选的 `grantedBy` 字段，当来源 Attachment 被移除时，内核应级联移除由其授予的全部子 Attachment

### 要求 3：Def 声明与继承

**用户故事：** 作为玩法包作者，我想要通过继承复用已有的 Def 定义，以便新增一类武器或实体不需要重复声明公共字段。

#### 验收标准

1. 内核应支持 Def 的 `extends` 字段引用一个或多个父 Def 的 Id
2. 当一个 Def 声明多个 `extends` 目标时，内核应按声明顺序应用混入，后声明的目标应覆盖先声明目标的同名字段
3. 内核应在加载期完成继承展开，不得在运行期沿继承链查找字段
4. 当 Def 的继承关系形成环时，内核应在加载期拒绝装载并生成一条诊断
5. 内核应支持 `abstract` 标记的 Def，`abstract` 为真的 Def 不得被直接实例化

### 要求 4：Tag 分类机制

**用户故事：** 作为玩法包作者，我想要用字符串标签而非固定分类枚举来标记对象类别，以便新增一类对象不需要修改内核的分类定义。

#### 验收标准

1. 内核不得在内部维护任何固定的对象分类枚举（如实体类别枚举）
2. 内核应允许 Entity、Item、Node、Link 携带任意数量的字符串 tag
3. 内核应提供 `hasTag` 表达式算子，供查询与规则判断对象是否携带指定 tag
4. 当玩法包声明一个新的 tag 字符串时，内核不得要求修改内核代码

### 要求 5：Agent 决策者与观察者模型

**用户故事：** 作为玩法包作者，我想要用同一个 Agent 结构表达人类玩家、AI、观察者、GM 与掉线托管，以便中途加入、观战转参战、AI 难度分级等机制无需专用代码。

#### 验收标准

1. 内核应将 Agent 定义为包含 `kind`（`'human'`、`'ai'`、`'observer'`）、`controls`（Ref 数组）、`knowledgeScope`、可选 `omniscient`、可选 `authority` 的结构
2. 当创作者调用 `agent.bind` 将一个 Agent 与一个 Entity 关联时，内核应将该 Entity 的 Ref 加入该 Agent 的 `controls` 数组
3. 当一个 Agent 的 `kind` 由 `'human'` 修改为 `'ai'` 时，内核应将该 Agent 已操控的 Entity 的决策来源切换为其 `policy` 字段指定的策略
4. 当多个 Agent 的 `knowledgeScope` 指向同一个认知范围时，内核应使这些 Agent 读取到相同的 `knowledge` 内容
5. 内核应允许一个 Agent 的 `controls` 数组包含多个 Entity 的 Ref
6. 当一个 Agent 的 `omniscient` 为真时，内核应在该 Agent 发起的查询中忽略 `visibleTo` 过滤
7. 内核应将特权动作表达为携带特定 tag 的普通 ActionDef，而不是内置的"GM 模式"概念

### 要求 6：Relation 二元有向关系

**用户故事：** 作为玩法包作者，我想要一个独立于 props 的关系结构，以便反向查询谁在操控我、以及宿主销毁时的级联清理不需要逐机制手写。

#### 验收标准

1. 内核应将 Relation 定义为包含 `kind`（字符串）、`from`（Ref）、`to`（Ref）、可选 `props` 的结构
2. 内核应支持同一对 `(from, to)` 之间存在多个不同 `kind` 的 Relation
3. 内核应支持同一个 `from` 对多个不同 `to` 建立同一 `kind` 的 Relation
4. 当创作者查询指向某个 Ref 的入向 Relation 时，内核应通过 `relIn` 算子返回结果
5. 当创作者查询某个 Ref 发出的出向 Relation 时，内核应通过 `relOut` 算子返回结果
6. 当一个 Relation 的 `from` 或 `to` 所指向的对象被销毁时，内核应级联移除该 Relation
7. 内核对 Relation 的 `kind` 字符串不得施加任何语义解释

### 要求 7：拓扑基本结构

**用户故事：** 作为玩法包作者，我想要用图而非坐标系表达空间关系，以便随机地图生成、炸墙开洞、断桥等操作复用同一套结构。

#### 验收标准

1. 内核应将 Node 定义为包含 `id`、`def`、`tags`、`props`、`weight`（默认值 1）、可选 `parent` 的结构
2. 内核应将 Link 定义为包含 `id`、`a`（NodeId）、`b`（NodeId）、`directed`（布尔）、`weight`、`tags`、`props` 的结构
3. 内核应支持通过 `node.create` 与 `node.destroy` 在运行期增删节点
4. 内核应支持通过 `link.create` 与 `link.destroy` 在运行期增删边
5. 当一个 Node 被销毁时，内核应级联销毁以该 Node 为端点的全部 Link
6. 内核不得假设拓扑图是连通的，拓扑应允许存在多个不连通分量

### 要求 8：多份拓扑与子图实例化

**用户故事：** 作为玩法包作者，我想要批量实例化一份子图蓝图，以便副本、程序化地图、载具内部空间不需要逐条手写节点与边的创建代码。

#### 验收标准

1. 内核应支持通过 `prefab.spawn(defId, params?)` 按 `PrefabDef` 蓝图批量创建节点、边与实体，并返回新生成对象的 Id 集合
2. 内核应在 `prefab.spawn` 执行期间将蓝图内部的 key 引用重映射为新生成对象的实际 Id
3. 当 `PrefabDef` 声明了 `attachTo` 字段时，内核应将实例化子图的 `root` 节点与调用方指定的外部节点相连
4. 内核应支持通过 `prefab.despawn(handle)` 回收一次 `prefab.spawn` 创建的全部对象
5. 当 `prefab.despawn` 回收的子图中存在占位者时，内核应将该占位者疏散至有效位置
6. 内核不得对 `PrefabDef` 中声明的蓝图内容施加玩法语义解释
7. 内核应保证 `dist` 查询在两个节点分处不连通分量时返回 `null`

### 要求 9：微型场景

**用户故事：** 作为玩法包作者，我想要微型场景不是一个新结构而是按需创建、按占用者存续的普通 Node，以便活体周身、车内、门口等空间统一由同一套机制表达，且不会在占用者离开后残留悬空的"主人"引用。

#### 验收标准

1. 内核应将微型场景实现为 `parent` 指向宿主场景（天然场景或另一个微型场景）的 Node，不得为微型场景引入独立于 Node 的新结构
2. 内核应在触发创建微型场景的 Entity、Link 或 Node 首次使某占位者进入该空间时创建该微型场景，并在 `props.creator` 字段记录触发创建的 Ref 仅供溯源
3. 内核不得将 `props.creator` 解释为当前占用者或用其判断微型场景是否应继续存在
4. 内核不得为微型场景单独维护占用者数量字段，占用者数量应始于对该微型场景占位者的查询
5. 当微型场景的占位者数量归零时，内核应自动卸载该微型场景
6. 当微型场景声明了 `props.capacity` 时，内核应仅在 `entity.place` 操作发生时校验该容量
7. 当微型场景的父节点被销毁时，内核应级联销毁该微型场景并疏散其占位者
8. 内核应对结构性共享的微型场景（多个触发来源映射到同一空间，如小场景的公共地面）与其他微型场景应用相同的创建与占用者归零卸载规则，不得设置生命周期例外

### 要求 10：容器与槽位

**用户故事：** 作为玩法包作者，我想要一个宿主拥有多个具名容器、槽位可容纳实体、槽位数量可动态增删，以便车厢与后备箱、装备位与背包格、载具座位等机制不需要新建专用模块。

#### 验收标准

1. 内核应将 Container 定义为包含 `id`、`owner`、`name`、`slots`（有序数组）、`insert`（`'fixed'` 或 `'shift'`）、`props` 的结构
2. 内核应允许同一个宿主拥有多个按 `name` 区分的 Container
3. 内核应将 Container 的 `slots` 字段实现为恒定有序的数组，索引应恒定存在
4. 当 Container 的 `insert` 为 `'fixed'` 时，内核应在插入元素时保持其余元素位置不移位，删除时应留空洞
5. 当 Container 的 `insert` 为 `'shift'` 时，内核应在插入元素时使后续元素后移，删除时使后续元素前移
6. 内核应将 Slot 的 `holds` 字段定义为可容纳 Item 或 Entity 的引用
7. 内核应支持通过 `slot.add` 与 `slot.del` 在运行期增删槽位
8. 内核应支持 Slot 的 `accepts` 字段为谓词表达式，当 `accepts` 为空时应接受任意内容
9. 当创作者调用 `item.move` 且未指定目标槽位索引时，内核应按索引顺序选取第一个满足 `accepts` 谓词且为空的槽位
10. 当不存在满足条件的槽位时，内核应使 `item.move` 返回 `ok:false`，不得将该物品放置于容器之外，也不得销毁该物品

### 要求 11：拓扑度量与扩散查询

**用户故事：** 作为玩法包作者，我想要用统一的加权最短路和预算受限扩散来表达距离与声音传播等机制，以便距离范式和感知范围不需要各自实现一套算法。

#### 验收标准

1. 内核应提供 `dist(a, b, opts?)` 函数，返回以 Link 与 Node 的 `weight` 为代价的最短路径长度
2. 当查询的两个节点之间不存在可达路径时，内核应使 `dist` 返回 `null`
3. 内核应支持 `dist` 的 `opts.via` 参数，仅沿满足给定谓词的边计算路径
4. 内核应支持 `dist` 的 `opts.maxCost` 参数，在路径代价超出该值时提前截断计算
5. 内核应提供 `spread(origin, budget, opts?)` 函数，从起点出发进行预算受限的加权广度优先遍历
6. 内核应使 `spread` 的返回结果包含每个可达节点的剩余强度与其上游来源节点
7. 内核应使 `spread` 返回按强度降序、NodeId 升序排列的有序数组，不得返回无序的映射结构

### 要求 12：表达式求值

**用户故事：** 作为玩法包作者，我想要一个绝不抛出异常的纯读表达式系统，以便谓词、伤害计算与派生属性可以安全地嵌入规则与动作定义。

#### 验收标准

1. 内核应将 Expr 实现为全函数，对任意输入返回一个值或一条诊断，不得抛出异常
2. 内核应支持 Expr 的字面量、路径读取（`path`）、局部变量读取（`var`）、运算调用（`op`）、查询（`q`）、具名表达式调用（`call`）六种形态
3. 当路径读取越界或指向不存在的字段时，内核应返回 `null`
4. 当算术运算发生除以零时，内核应返回 `null`，不得抛出异常
5. 内核应将内置算子集合限定为封闭集合，不得允许玩法包在运行期扩展内置算子
6. 内核不得提供 `eval` 或字符串拼接执行能力
7. 内核应提供 `isA(ref, defId)` 算子，沿 Def 继承链判断归属关系
8. 内核不得将 `roll`、`pick`、`shuffle`、`weightedPick` 纳入 Expr 的内置算子集合，因为其求值会推进随机流状态，不满足 Expr 全函数、无副作用的要求（见要求35.5）

### 要求 13：具名表达式

**用户故事：** 作为玩法包作者，我想要将重复使用的复杂谓词定义为具名表达式，以便修改一次判定逻辑就能让所有引用处同步生效。

#### 验收标准

1. 内核应支持 `kind:'expr'` 的 Def，包含 `params`、`body`、恒为真的 `pure` 字段
2. 内核不得允许具名表达式的 `body` 调用任何 Op
3. 当具名表达式之间的调用关系形成环时，内核应在加载期拒绝装载并生成一条诊断
4. 内核应将具名表达式的求值深度计入 Expr 的总预算
5. 内核应支持玩法包通过 `PlaypackDef.overrides` 字段替换一个具名表达式的实现

### 要求 14：查询

**用户故事：** 作为玩法包作者，我想要一个统一的查询语言替代所有"找目标"的专用函数，以便 AI 选目标、范围技能、任务判定、UI 高亮复用同一套实现。

#### 验收标准

1. 内核应将 Query 定义为包含 `from`、可选 `where`、可选 `in`、可选 `visibleTo`、可选 `orderBy`、可选 `desc`、可选 `limit` 的结构
2. 内核应支持 `from` 字段取值 `'entities'`、`'items'`、`'nodes'`、`'links'`、`'attachments'`、`'defs'`、`'agents'`、`'decisions'`、`'intents'`、`'log'` 之一
3. 当查询指定 `in` 字段时，内核应将结果限定在该空间限定表达式所指定的范围内
4. 当查询指定 `visibleTo` 字段时，内核应过滤掉查询发起者不可见的结果
5. 内核应使同一个 Query 结构同时服务 AI 目标选择、范围技能结算、任务条件判定与界面高亮四类使用场景

### 要求 15：查询历史

**用户故事：** 作为玩法包作者，我想要查询最近发生的事件，以便战斗日志、复仇机制、重复上一动作等功能不需要为每种"过去"手动维护镜像计数器。

#### 验收标准

1. 内核应维护一个有界环形缓冲 `world.log`，记录已发生的 Event
2. 内核应支持 `PlaypackDef.logRetention` 字段声明该缓冲的保留窗口（按相位数或按条数）
3. 当查询的 `from` 字段为 `'log'` 时，内核应仅返回保留窗口内的事件
4. 内核不得为超出保留窗口的历史统计提供查询支持，玩法包若需要整局统计应使用 Hook 累加计数器

### 要求 16：Op 唯一写入通道

**用户故事：** 作为内核实现者，我想要状态只能通过 Op 修改，以便每一次状态变化都可日志、可求逆、可被 Hook 拦截。

#### 验收标准

1. 内核不得提供任何绕过 Op 的直接状态赋值接口
2. 内核应使每个 Op 返回 `Result<T>` 类型，取值为 `{ok:true, value:T}` 或 `{ok:false, code:ErrCode, detail:string}`
3. 内核不得允许任何 Op 抛出异常
4. 内核应使每个 Op 的执行产生一个事件，供 Hook 拦截
5. 内核应为属性类 Op（`prop.set`、`prop.del`、`prop.add`、`list.insert`、`list.remove`、`tag.add`、`tag.del`）提供实现
6. 内核应为结构类 Op（`entity.create`、`entity.destroy`、`entity.place`、`item.create`、`item.destroy`、`item.move` 等）提供实现
7. 内核应将拾取、丢弃、装备、卸下、买卖、交易、抽牌、发牌、死亡背包灌注全部实现为对 `item.move` 的调用，配合不同的 `require` 谓词与前后 Hook，不得为其中任何一种单独新增转移原语

### 要求 17：堆叠拆分的原子性

**用户故事：** 作为内核实现者，我想要堆叠拆分操作在无法放置时整体回滚，以便拆分操作不会成为凭空产出物品或销毁玩家资产的漏洞。

#### 验收标准

1. 内核应将 `stack.split(id, n, into?, atSlot?)` 实现为单一事务，包含原栈数量扣减、新物品创建、放入目标槽位三个步骤
2. 当 `stack.split` 的任一步骤失败时，内核应将全部步骤回滚，原栈数量应保持不变，不得产生新物品，不得将物品放置于容器之外
3. 内核不得将 `stack.split` 找不到合法槽位的情况处理为"放在地上"或"吞掉物品"
4. 内核应保证任意 Op 序列执行后，同一 DefId 的物品总量仅因 `create` 与 `destroy` 改变，`stack.split` 与 `stack.merge` 不得改变该总量
5. 内核应将图形界面的拖拽输入视为不可信输入，并对其执行与其他来源相同的校验路径

### 要求 18：变身与拓扑合并/分裂

**用户故事：** 作为玩法包作者，我想要实体变身与节点合并/分裂保留原有引用，以便多段变身、炸墙合并房间等机制不会丢失关系、记忆或容器引用。

#### 验收标准

1. 内核应提供 `entity.setDef(id, def, carry)` 操作，在切换 Entity 的 Def 时保留其 id
2. 内核应支持 `carry` 参数指定在 `entity.setDef` 执行时需要保留的字段集合，至少包括 `props.hp`、`relations`、`containers`、`attachments` 之一或其组合
3. 内核应提供 `node.merge(keep, absorb, carry)` 操作，将 `absorb` 节点的边、占位者、子节点、Attachment 按 `carry` 策略并入 `keep` 节点，并销毁 `absorb`
4. 内核应提供 `node.split(id, spec)` 操作，将一个节点按 `spec` 分裂为多个节点并重新分配占位者与边
5. 内核不得通过"销毁后重建"的方式实现变身或节点合并，因为该方式会丢失指向旧对象的引用

### 要求 19：结构性操作的否决机制

**用户故事：** 作为玩法包作者，我想要在结构性操作执行前插入否决检查，以便负重上限、禁止进入、门被堵、载具满座等约束不需要内核内建。

#### 验收标准

1. 内核应使每个结构性 Op 依次发出 `before` 事件、执行默认效果、发出 `after` 事件
2. 内核应允许 `before` 阶段的 Hook 返回取消（veto）结果以阻止该 Op 执行
3. 内核不得在内核代码中实现负重上限、禁止进入、容量限制等具体约束，该类约束应通过玩法包挂载 `before` Hook 实现
4. 当一个结构性 Op 被 `before` Hook 否决时，内核应使该 Op 返回 `ok:false` 且不产生任何状态改动

### 要求 20：内核不变量

**用户故事：** 作为内核实现者，我想要内核自行维护一组不可被玩法包破坏的状态一致性约束，以便暴力边界测试不会产生半损坏状态。

#### 验收标准

1. 内核应维护引用完整性不变量，不得存在指向已销毁对象的 Ref
2. 内核应维护单一容纳不变量，一个 Item 同一时刻应至多存在于一个 Slot 中
3. 内核应维护单一位置不变量，一个 Entity 同一时刻应至多存在于一个 Node 中
4. 内核应维护位置互斥不变量，一个 Entity 的 `node` 字段与 `slot` 字段不得同时非空
5. 内核应维护无环容纳不变量，一个容器不得直接或间接地容纳自身的宿主
6. 内核应维护拓扑一致不变量，一个 Link 的两个端点必须存在，且节点销毁时其关联 Link 必须一并销毁
7. 内核应维护父子一致不变量，微型场景 Node 的 `parent` 字段必须指向存在的节点，且父节点销毁时子节点必须一并销毁并疏散占位者
8. 内核应维护关系对称不变量，Relation 的 `out` 记录与对端的 `in` 记录必须互为镜像
9. 内核应维护容器双向一致不变量，Container 的 `owner` 字段与宿主的 `containers` 索引必须互相指向
10. 内核应维护槽位索引连续不变量，`insert:'shift'` 的容器不得出现索引空洞，`insert:'fixed'` 的容器索引不得重新排列
11. 内核应维护堆叠守恒不变量，`stack.split` 与 `stack.merge` 不得改变同一 DefId 物品的总量
12. 内核应维护代价守恒不变量，被冻结的代价必须被结算或全额退回，不得存在冻结后遗忘的情况
13. 内核应维护附属一致不变量，Attachment 的 `target` 必须存在，且当授予它的 aura 失效时必须一并被回收
14. 内核应维护堆叠有界不变量，Item 的 `stack` 字段必须大于或等于 1 且小于或等于 `stackMax`，归零时该 Item 必须自动销毁
15. 内核应维护决策有终不变量，每个处于打开状态的 Decision 必须最终被答满或超时，不得永久处于待答状态
16. 内核应维护数值有界不变量，拒绝写入非有限数
17. 当任意 Op 违反上述不变量时，内核应使该 Op 返回 `ok:false`，且不得留下半改状态

### 要求 21：事务

**用户故事：** 作为内核实现者，我想要每一次动作解算、规则执行、AI 试探都在事务中进行，以便任意一步失败都能整体回滚而不产生半损坏状态。

#### 验收标准

1. 内核应提供 `tx.begin`、`tx.commit`、`tx.rollback` 三个事务控制操作
2. 内核应将每一次动作解算、每一条规则执行、每一次 AI 试探包裹在事务中
3. 当事务内任一步骤返回 `ok:false` 且被标记为致命时，内核应将该事务整体回滚
4. 内核应保证暴力边界测试不产生半损坏状态

### 要求 22：效果脚本 Flow

**用户故事：** 作为玩法包作者，我想要一个有界的、非图灵完备的效果脚本语言，以便复杂效果由多条小规则组合表达，同时保证脚本不会挂死。

#### 验收标准

1. 内核应将 Effect 限定为调 Op、局部变量赋值、条件分支、受限遍历（`forEach`）、受限循环（`while`）、事件发出（`emit`）、延迟执行（`after`）、定时执行（`at`）、异常捕获（`try`/`catch`）、主动失败（`abort`）十种形态之一
3. 内核不得为 Effect 提供函数定义、递归调用或闭包能力
4. 内核应为每次 Flow 执行设定 step 预算，默认值为 10⁴
5. 当 Flow 执行的 step 数超出预算时，内核应中止该次执行并生成一条诊断事件，不得使程序挂死
6. 内核应要求 `while` 效果必须声明 `maxIter` 字段，并在加载期对缺失该字段的情况予以拒绝

### 要求 23：事件与钩子管道

**用户故事：** 作为玩法包作者，我想要通过五阶段事件管道表达护甲减伤、格挡、反伤、暴击等几十种表层机制，以便不需要为每种机制单独编写模块。

#### 验收标准

1. 内核应将 Event 定义为包含 `type`、`payload`、可选 `source`、可选 `cause`、`depth`、`cancelled` 的结构
2. 内核应为每个 Event 维护 `cause` 因果链字段，使间接伤害（陷阱、中毒、推落）能够追溯到最初的施动者
3. 内核应将 Hook 的响应阶段限定为 `before`、`modify`、`instead`、`default`、`after` 五个阶段
4. 内核应允许 `before` 阶段的 Hook 取消该事件的默认效果
5. 内核应允许 `modify` 阶段的 Hook 按优先级顺序改写事件的 `payload`
6. 内核应在 `instead` 阶段的多个候选中，按 `(priority, 宿主容器索引, 槽位索引, defId)` 排序取第一个 `when` 条件通过者执行，其余候选不得被执行、不得报错、不得叠加
7. 内核应允许 `after` 阶段的 Hook 以只读方式响应并发出新事件
8. 内核应将 RuleDef 定义为包含 `on`（事件类型或数组）、`phase`、可选 `when`、`priority`、`effects`、可选 `once` 的结构
9. 内核应支持同一个 RuleDef 结构在 `PlaypackDef`（全局常驻）、`AttachmentDef.rules`（状态存续期间生效）、`attach.add(world, mod)`（运行期开关）三种挂载方式下具有不同生命周期，不得为三种生命周期分别设计不同结构
10. 当单条 Hook 内部执行报错时，内核应仅跳过该条 Hook 并生成一条 `warn` 级诊断，事件管道应继续处理其余 Hook，不得因一条第三方规则出错而中断整个管道

### 要求 24：连锁安全

**用户故事：** 作为内核实现者，我想要对事件连锁和跨相位反应链设置独立的上限，以便一条写坏的规则不会导致无限递归或挂死整个对局。

#### 验收标准

1. 内核应为事件连锁深度 `depth` 设定上限，默认值为 32
2. 当事件连锁深度超出上限时，内核应拒绝最深一层的连锁并生成一条诊断
3. 内核应使 `depth` 在事务提交边界处重置
4. 内核应为跨相位的响应往复设定独立于 `depth` 的上限，通过 `PhaseDef.reactionRounds` 声明，且该值必须为加载期常量
5. 内核应按 `(priority, defId)` 字典序执行同优先级的 Hook，以保证确定性排序
6. 内核不得允许 Hook 在同一 `(type, hookId)` 组合下重入

### 要求 25：Action 与合法着法枚举

**用户故事：** 作为玩法包作者，我想要一个由数据生成、AI 与 UI 共用的合法着法清单，以便新增一种交互不需要同时修改 UI 代码与 AI 代码。

#### 验收标准

1. 内核应将 ActionDef 定义为包含 `id`、`label`、可选 `targets`、可选 `require`、可选 `visible`、可选 `reason`、可选 `cost`、`effects` 的结构
2. 内核应提供 `queryActions(actor)` 函数，返回该行动者当前可执行的着法列表，每项包含 `action`、`bindings`、`cost`、可选 `reason`
3. 内核应使 UI 动作菜单、AI 着法生成、网络协议合法性校验、模糊测试动作采样四类使用场景共用同一个 `queryActions` 实现
4. 当一个着法的 `require` 不满足时，内核应使该着法不出现在 `queryActions` 的结果中
5. 当一个着法满足 `visible` 但不满足 `require` 时，内核应使该着法以灰显状态出现，并携带 `reason` 字段说明原因
6. 内核应支持 `TargetSpec` 的 `range` 字段（数值区间选择）与 `count` 字段（多选数量范围）
7. 当 `TargetSpec` 声明 `range` 时，内核应要求该字段包含 `step`，且在 AI 搜索模式下仅采样区间边界、当前可承担的最大值与 `step` 网格上的有限个点，在 UI 模式下应返回完整区间

### 要求 26：代价泛化

**用户故事：** 作为玩法包作者，我想要代价在提交时冻结、解算时结算、失效时全额退回，以便反制技能不会导致代价被白白扣除，也不会出现同一点数被超额提交。

#### 验收标准

1. 内核应将 CostSpec 限定为扣减数值池（`pool`）、消耗物品（`items`）、附加状态（`attach`）、自定义效果（`custom`）四种形态之一
2. 内核应在动作提交时冻结其代价，使可用额度相应减少
3. 内核应仅在动作解算成功时真正结算已冻结的代价
4. 当动作在解算前的前提重检失败时，内核应将该动作标记为 `void` 并全额退回已冻结的代价
5. 内核应在代价退回时生成一条 `cost.refunded` 诊断事件，包含意图 Id、原因与退回明细
6. 内核不得提供任何形式的静默退回

### 要求 27：Decision 一等状态对象

**用户故事：** 作为玩法包作者，我想要向非当前行动者征求输入而不阻塞事务，以便交易确认、反应技、投降请求等机制不需要专用的协议模块或响应栈模块。

#### 验收标准

1. 内核应将 Decision 定义为包含 `id`、`def`、`askees`、`answers`、`ctx`、`opensAt`、可选 `deadline`、`status` 的结构
2. 内核应使 `decision.open` 调用后立即返回并使发起方的事务提交完毕，不得提供任何等待答复的原语
3. 内核应仅通过 `DecisionDef.onResolve` 在另一个事务中处理决策的后续解算，不得在原事务中挂起等待
4. 内核应在 `onResolve` 执行前重新校验发起时的前提条件，当前提已失效时应转入 `onVoid` 处理
5. 内核应使处于打开状态的 Decision 出现在被征询者的 `queryActions` 结果中
6. 内核应支持 `DecisionDef.quorum` 字段取值 `'all'`、`'any'`、`'majority'` 之一，决定何时视为决策已完成
7. 当 Decision 超过 `deadline` 仍未完成时，内核应按 `DecisionDef.onTimeout` 处理并推进相位

### 要求 28：响应相位替代 Hook 内提问

**用户故事：** 作为内核实现者，我想要反应技通过响应相位而非在 Hook 内发起决策来实现，以便避免与未提交事务中途挂起产生的架构矛盾。

#### 验收标准

1. 内核不得允许在 `before` 或其他 Hook 阶段内调用 `decision.open` 并等待其结果
2. 内核应支持 `PhaseDef.kind` 取值 `'response'`，表示该相位用于收集反应类 Intent
3. 内核应要求响应相位的 `reactionRounds` 字段为加载期常量，供 Linter 强制校验
4. 内核应使反制表达为 `instead` 或 `before` 规则，其触发条件为"存在一个针对我的、已被反应 Intent 指定的待解算 Intent"
5. 当响应相位的往复轮次超过 `reactionRounds` 时，内核应强制进入解算相位

### 要求 29：Intent 提交与解算分离

**用户故事：** 作为玩法包作者，我想要动作的提交与解算分离，以便格斗对拼、猜拳暗押、指令排队等需要"先都提交再按序解算"的机制得以表达。

#### 验收标准

1. 内核应将 Intent 定义为包含 `id`、`agent`、`action`、`bindings`、`submittedAt`、可选 `priority`、`hidden`、`status` 的结构
2. 内核应支持通过 `intent.submit` 提交一个 Intent 且不立即解算
3. 内核应在解算 Intent 前重新执行该 Intent 的 `require` 检查
4. 当 Intent 解算前的 `require` 检查失败时，内核应将该 Intent 的 `status` 置为 `'void'` 并退回其冻结代价
5. 内核应使 `hidden` 为真的 Intent 不出现在其他 Agent 的 `queryActions` 结果与 `knowledge` 中
6. 内核应支持 `ScheduleDef.resolveOrder` 表达式对多个待解算 Intent 求值以决定解算顺序
7. 内核不得提供 `order:'simultaneous'` 或任何表示真正同时结算的机制，所有同时提交的 Intent 必须依序解算
8. 内核应使 Intent 作为状态对象可被存档、可被回放、可被 AI 搜索

### 要求 30：Attachment 状态与光环

**用户故事：** 作为玩法包作者，我想要用同一个 Attachment 结构表达中毒、燃烧、护盾层数、光环加成等机制，以便新增一种状态效果不需要新建专用系统。

#### 验收标准

1. 内核应将 AttachmentDef 定义为包含 `kind:'attachment'`、可选 `duration`、可选 `delay`、`stack`（取值 `'unique'`、`'refresh'`、`'count'`、`'independent'`）、可选 `maxStack`、可选 `aura`、可选 `rules`、可选 `onAdd`/`onExpire`/`onRemove` 的结构
2. 内核应支持 `AttachmentDef.aura` 字段声明一个 Query 与授予的目标 Def，向查询命中者授予子 Attachment
3. 内核应仅在光环的依赖集发生变化时重新计算其授予关系，不得逐回合遍历全部对象
4. 内核应默认仅在拓扑变化（实体进出节点等）时触发光环重算
5. 内核应要求 `aura.deps` 显式列出光环查询所依赖的属性路径，当属性路径未在 `deps` 中声明时，内核不得因该属性变化而重新计算
6. 内核应在加载期通过 Linter 检查 `aura` 的查询谓词中引用的属性路径是否已在 `deps` 中声明
7. 当光环本体失效时，内核应通过 `grantedBy` 反查并回收其授予的全部子 Attachment
8. 内核应支持 `Attachment.delay` 字段表示延时生效，当前相位小于 `activeAt` 时，该 Attachment 的规则不挂载、光环不授予、`hasAttachment` 查询返回假

### 要求 31：回合表与相位推进

**用户故事：** 作为玩法包作者，我想要回合表本身是数据而非内核硬编码逻辑，以便大逃杀、格斗、卡牌等不同时序模型复用同一套推进机制。

#### 验收标准

1. 内核应将 ScheduleDef 定义为包含 `phases`（PhaseDef 数组）、`order`（取值 `'fixed'` 或 `'initiative'`）、可选 `initiativeExpr`、可选 `resolveOrder`、可选 `onConflict`、可选 `roundEnd` 的结构
2. 内核应将 PhaseDef 定义为包含 `name`、可选 `actors`、可选 `onEnter`、可选 `onExit`、`input`（取值 `'none'`、`'actor'`、`'all'`）、可选 `kind`、可选 `reactionRounds`、可选 `timeLimit` 的结构
3. 内核不得对"回合"赋予任何语义，仅按 `phases` 表推进并在每个相位边界发出事件
4. 当一个相位的 `input` 要求的决策尚未收集齐全，或存在未到期的打开状态 Decision 时，内核不得推进该相位

### 要求 32：玩法包顶层声明

**用户故事：** 作为玩法包作者，我想要一个统一的顶层声明结构承载 AP/体力/法力池、胜负条件、局面估值等玩法专属数据，以便切换玩法只需更换这一份数据。

#### 验收标准

1. 内核应将 PlaypackDef 定义为包含 `kind:'playpack'`、`schedule`、`pools`、可选 `factions`、可选 `visibility`、可选 `logRetention`、可选 `outcomes`、可选 `evaluate`、可选 `policies`、可选 `linter`、可选 `quota`、`entry`、`version`、可选 `migrations`、可选 `requires`、可选 `conflicts`、可选 `overrides` 的结构
2. 内核不得内置任何数值池（如生命值、行动点），所有数值池应通过 `PlaypackDef.pools` 由玩法包声明
3. 内核应将 PoolDef 定义为包含 `name`、`per`（取值 `'world'`、`'actor'`、`'faction'`）、可选 `max`、`reset`（取值 `'never'`、`'turn'`、`'phase'` 或表达式）的结构
4. 内核应支持 `PlaypackDef.outcomes` 字段为 OutcomeDef 数组，取代单一布尔胜负条件
5. 内核应将 OutcomeDef 定义为包含 `name`、`when`、`scope`（取值 `'game'`、`'agent'`、`'faction'`）、可选 `rank`、可选 `onReach`、`ends` 的结构
6. 当一个 OutcomeDef 的 `scope` 为 `'agent'` 且 `ends` 为假时，内核应允许该行动者被淘汰后整局继续进行
7. 内核应支持 `PlaypackDef.evaluate` 字段为一个 Expr，供 AI 搜索骨架使用，且内核不得因更换该字段而要求修改任何 AI 代码
8. 内核应支持 `PlaypackDef.linter` 字段声明玩法包自定的静态约束规则，并在加载期强制校验

### 要求 33：玩法包组合与 MOD 叠加

**用户故事：** 作为二创社群创作者，我想要多个玩法包能够声明依赖、互斥与覆盖关系并叠加装载，以便"基础大逃杀+僵尸模式+双倍掉落"这类组合不需要逐一手工整合。

#### 验收标准

1. 内核应在装载期对 `requires` 字段执行拓扑排序，当检测到循环依赖时应拒绝装载
2. 内核应在装载期检测 `conflicts` 字段声明的互斥关系，当检测到冲突交集时应拒绝装载并指出冲突方
3. 内核应按装载顺序合并多个玩法包的 Def 集合，后装载玩法包的 `overrides` 应覆盖同名 Def
4. 内核应将 Hook 的执行顺序键扩展为包含包序，使叠加顺序在多包场景下保持可控且确定
5. 内核应在装载期运行全部已装载玩法包的 `linter` 规则，当任一规则失败时应拒绝装载
6. 内核应使全部装载期冲突在装载期暴露诊断信息，不得在运行期以异常形式出现

### 要求 34：PolicyDef NPC 决策策略

**用户故事：** 作为玩法包作者，我想要 NPC 决策策略是数据而非代码，以便新增一个 Action 后所有相关 NPC 自动能够使用它。

#### 验收标准

1. 内核应将 PolicyDef 定义为包含 `kind:'policy'`、`mode`（取值 `'rules'`、`'search'`、`'scripted'`）、可选 `rules`、可选 `search`、可选 `script`、可选 `fallback` 的结构
2. 当 PolicyDef 的 `mode` 为 `'rules'` 时，内核应对 `queryActions` 的输出按 `when` 与 `weight` 打分并选取最优着法
3. 当 PolicyDef 的 `mode` 为 `'search'` 时，内核应复用 `checkpoint`/`restore` 与 `evaluate` 实现试探式搜索
4. 当 PolicyDef 的 `mode` 为 `'scripted'` 时，内核应按 `script` 字段给出的效果序列执行，忽略着法枚举
5. 内核应要求 `search` 模式的 PolicyDef 声明 `budget` 字段，当搜索超出该预算时应返回当前最优着法
6. 当一个 Policy 无法得出任何合法着法且超出预算时，内核应转向 `fallback` 字段指定的策略
7. 内核不得因 NPC 决策逻辑复杂而导致回合推进卡死

### 要求 35：确定性随机

**用户故事：** 作为内核实现者，我想要所有随机都通过命名流产生，以便存档、回放、回溯与 AI 搜索能够完全复现。

#### 验收标准

1. 内核应将 RngStream 定义为包含 `name`、`seed`、`counter` 的结构
2. 内核应要求所有随机操作（`roll`、`pick`、`shuffle`、`weightedPick`）指定一个命名流
3. 内核应将随机流状态作为整体状态的一部分，使其被快照、回放、回溯完整捕获
4. 内核应为 AI 搜索试探提供影子流，试探期间的随机调用不得推进主流的 `counter`
5. 内核应将 `roll`、`pick`、`shuffle`、`weightedPick` 实现为经由 Op 唯一写入通道（见要求16）注册的 Op，不得实现为独立于 Op 注册表之外的表达式算子或组件方法

### 要求 36：信息不对称

**用户故事：** 作为玩法包作者，我想要认知的值域是任意 Value 而非布尔真假，以便错误信息、过时记忆、记忆衰减、侦探推理等机制得以表达。

#### 验收标准

1. 内核应将 `knowledge[scopeId]` 定义为包含 `facts` 与 `seen` 的结构，`scopeId` 应对应 `Agent.knowledgeScope`
2. 内核应将 `facts` 的值域限定为任意 Value，不得限定为布尔类型
3. 内核不得校验写入 `facts` 的值是否与世界真值相符
4. 内核应提供 `knows(scope, key)` 算子，返回该 fact 对应的 Value，当不存在时返回 `null`
5. 内核应支持玩法包提供的 `visibility` 谓词，在查询时对结果进行可见性过滤
6. 内核应使 AI 与玩家使用同一个 Query 接口进行认知相关查询，二者的区别应仅体现在 `visibleTo` 参数上

### 要求 37：持久化、回放与回溯

**用户故事：** 作为内核实现者，我想要用同一套快照与日志机制服务存档、回放、回溯与 AI 搜索，以便 AI 搜索能力成为持久化的自然副产品。

#### 验收标准

1. 内核应提供 `snapshot()` 函数，返回结构共享的不可变状态快照
2. 内核应维护 `journal`，记录每个已执行的 Op 及其逆操作
3. 内核应提供 `replay(seed, ops)` 函数，从种子与操作序列重建状态
4. 内核应提供 `rewind(n)` 函数，将状态回退 n 个相位边界
5. 内核应提供 `checkpoint(label)` 与 `restore(label)` 函数，供 AI 搜索的试探与撤销使用
6. 内核应在 AI 搜索试探期间保证随机不污染主流、`Query` 强制带上该 AI 的 `visibleTo`、`after` 阶段的表现层订阅被静默三项隔离
7. 内核应保证 `PlaypackDef.evaluate` 是唯一因换玩法而改变的 AI 相关字段，不得要求随之修改任何搜索骨架代码

### 要求 38：版本迁移

**用户故事：** 作为 UGC 玩法包作者，我想要老存档能够通过声明的迁移链适配新版本玩法包，以便迭代玩法包不需要为每个版本手写迁移代码。

#### 验收标准

1. 内核应将 MigrationDef 定义为包含 `from`、`to`、`effects`、`onFail`（取值 `'reject'` 或 `'bestEffort'`）的结构
2. 内核应在快照中写入 `playpackId` 与 `version`，并在装载时与当前玩法包版本比对
3. 当存档版本与玩法包版本相同时，内核应直接恢复该存档
4. 当存档版本较旧且存在适用的迁移链时，内核应在事务中按序执行迁移的 `effects`，失败时整体回滚
5. 当存档版本较旧且不存在适用的迁移链时，内核应按 `onFail` 处理，默认应拒绝并生成明确诊断
6. 当存档版本高于当前玩法包版本时，内核应一律拒绝装载并生成诊断
7. 内核不得支持对局进行中热更换玩法包，迁移应仅在装载时发生

### 要求 39：诊断体系

**用户故事：** 作为 UGC 创作者，我想要内核在装载期与运行期给出可定位、可理解、可行动的错误信息，以便我不需要阅读引擎源码或靠试错猜测就能修复自己的规则。

#### 验收标准

1. 内核应将 Diagnostic 定义为包含 `code`、`severity`、`message`、可选 `at`（含 `def`、`field`、`playpack`）、可选 `subject`、可选 `path`、可选 `expected`、可选 `actual`、可选 `cause`、可选 `hint`、`phase` 的结构
2. 内核应将 `severity` 限定为 `'fatal'`、`'error'`、`'warn'`、`'info'` 四级
3. 当发生 `fatal` 级诊断时，内核应回滚当前事务、停止运行并落盘完整现场
4. 当发生 `error` 级诊断时，内核应回滚当前事务并使对局继续，状态应如同该 Op 未发生
5. 内核应将 `ErrCode` 实现为封闭枚举，按层前缀分组（`E_REF_`、`E_INV_`、`E_OP_`、`E_EXPR_`、`E_FLOW_`、`E_HOOK_`、`E_COST_`、`E_DEC_`、`E_LOAD_`、`E_MIG_`、`E_QUOTA_`）
6. 内核应将全部 `E_INV_` 前缀的错误码固定映射为 `fatal` 级别，且该映射不得被玩法包覆盖
7. 内核应要求每个诊断的 `message` 与 `hint` 使用创作者可理解的词汇，并说明具体出错字段与可行动的修改建议
8. 内核应在同一 `(ruleDefId, code)` 在滑动窗口内连续触发 `error` 超过阈值时，自动停用该规则并生成 `W_RULE_DISABLED` 诊断
9. 内核应对相同 `(code, at.def, at.field)` 的诊断进行去重折叠，仅保留首次完整现场、末次时间与出现次数
10. 内核应保证诊断日志有界，超出容量时应丢弃最旧的 `info` 级记录
11. 内核应在加载期执行引用存在性、类型一致性、`while` 必填 `maxIter`、具名表达式调用图无环、Def 继承无环、`aura.deps` 完整性、玩法包冲突、玩法包自定 linter、配额九类检查
12. 当装载期检查发现多个问题时，内核应给出全部问题的清单，不得仅报告第一个问题
13. 内核应将规则熔断的连续错误计数与停用状态纳入整体状态，使其被快照、回放、回溯完整捕获，不得将该状态保存在独立于整体状态之外的宿主进程内存中

### 要求 40：表现层只读通道

**用户故事：** 作为表现层开发者，我想要三条只读通道支撑演出增量、全量渲染与交互菜单，以便开局第一帧、读档、断线重连时界面能够正确绘制。

2. 内核应向表现层提供查询状态通道，通过纯读的 `Query` 与 `Expr` 支持全量渲染

4. 内核应保证 Entity 与 Item 的 id 在整局内保持稳定，供表现层进行视图 diff 与对象复用
5. 内核不得允许表现层通过任何接口直接修改状态，表现层仅能通过调用经 `queryActions` 校验的 Action 间接产生状态变化

### 要求 41：资源配额

**用户故事：** 作为内核实现者，我想要为每个玩法包的实体数、Attachment 数与规则数设定可声明的上限，以便一个失控的生成循环或恶意 UGC 内容不会耗尽运行时资源。

2. 当运行期尝试创建的实体数超出 `quota.entities` 时，内核应拒绝该创建操作并生成一条 `E_QUOTA_ENTITIES` 诊断

4. 内核应在加载期校验 `quota` 字段声明的数值本身为非负有限数

### 要求 42：明确排除的边界

**用户故事：** 作为工程规范的使用者，我想要文档明确列出内核不承担的职责，以便实现阶段不会因"完备"二字而擅自扩大范围，也不会把部署层关切误判为内核缺口。

#### 验收标准

1. 内核不得实现连续空间或物理模拟，拓扑应始终表达为图与加权最短路，不得表达为坐标系
2. 内核不得提供毫秒级真实时循环，时间推进应始终以相位（phase）为单位
3. 内核不得提供图灵完备的脚本能力，Flow 应保持第22章定义的有界指令集
4. 内核不得提供寻路或搜索算法的自定义实现接口，超出 BFS、加权最短路、αβ 搜索骨架之外的算法能力应归类为第4圈，不在本规范范围内
5. 内核不得提供服务器、客户端预测、回滚网络码、匹配或反外挂系统的实现，网络部署拓扑应被视为内核之上的部署选择
6. 内核不得支持对局进行中替换玩法包的 Def 集合，运行期变更应仅限于通过 `attach.add(world, mod)` 开关已声明规则的生效范围
7. 内核应保证第1项至第6项所列边界之外，`queryActions` 权威校验、命名随机流确定性排序、`journal` 增量同步、`Agent.knowledgeScope` 视野下发、`Intent.hidden` 暗牌隔离、`snapshot` 断线重连六项保证对联机部署可用，不得以"内核不做联机"为由省略这些保证本身

### 要求 43：圈层契约与拓展可达性

**用户故事：** 作为玩法包作者，我想要无论叠加多少层拓展（容器嵌套、Def 继承链、玩法包 MOD 叠加、子图实例化），都能通过同一套原语触达并操作系统中的任意要素，以便拓展深度的增加不会迫使我修改内核代码。

#### 验收标准

1. 内核应保证第1圈至第3圈的全部创作行为（放置实例、自定义属性与关系、定义玩法规则）不要求编写超出 Def 声明、Expr、Effect 的代码
2. 内核在决定一项能力是否作为内核原语时，应仅接受同时满足不可绕过判据、三处复用判据、不含语义判据的能力
3. 当一项能力仅服务单一玩法且不满足三处复用判据时，内核不得将该能力实现为内核原语，该能力应以玩法包数据的形式表达
4. 内核应保证访问嵌套结构中任意元素所使用的 Op 与 Query 调用形式，与访问非嵌套结构中同类元素的调用形式相同，不得因嵌套深度增加而引入专用的访问接口
5. 内核应保证容器可以容纳容器、Attachment 可以挂载于任意合法宿主、Def 继承与玩法包 MOD 叠加均可无限嵌套或叠加，不得对嵌套深度或叠加数量设置架构性上限（配额限制见要求41，属资源约束而非架构约束）

### 要求 44：AI 可计算性跨层贯穿

**用户故事：** 作为 NPC 决策策略或局面搜索器，我想要通过与人类玩家完全相同的一套查询与枚举接口感知与操作世界，以便创作者新增的任何 Action、Attachment 或规则都能被我自动获得，而不需要为我单独编写或修改判定代码。

#### 验收标准

1. 内核应使 AI 决策与人类玩家决策共用同一个 `queryActions` 实现，不得为 AI 提供另一套着法枚举接口
2. 当创作者新增一个 ActionDef 且该着法满足某个 `PolicyDef.rules` 评分规则的 `when` 条件时，内核应使采用该 PolicyDef 的全部 NPC 将新增着法自动纳入决策考虑，不得要求修改 PolicyDef 本身
3. 内核应使 AI 与人类玩家的认知查询共用同一个 Query 接口，两者的差异应仅体现在 `visibleTo` 参数取值上，不得为非 `omniscient` 的 AI 提供绕过可见性过滤的专用读取通道
4. 内核应保证 `PlaypackDef.evaluate` 是唯一因更换局面估值方式而需要改变的字段，更换该字段不得要求修改搜索骨架代码
5. 内核应保证 CostSpec 与 `TargetSpec.range`/`count` 在 AI 搜索模式下可被限定为有限的采样点集合，使单个着法的分支数量在搜索预算内保持有界
6. 内核应使 AI 搜索试探（`checkpoint` → 试探 → `restore`）复用与正常状态推进相同的 Op 与事务机制，不得为 AI 试探引入独立于正常状态写入通道的另一套接口
7. 内核应保证具名表达式的 `overrides` 机制同样适用于被 AI 决策引用的判定表达式，使替换局面估值或 NPC 判定逻辑不需要修改引用该判定的全部 Action 或 Rule
