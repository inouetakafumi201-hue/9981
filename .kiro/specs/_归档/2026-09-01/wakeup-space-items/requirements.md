# 需求文档：空间、物品、装备、容器与载具（基类层）

## 一、引言

本文档定义 WakeUp **基类层**中空间、物品、装备、容器与载具领域的可复用语义契约。它不创建具体地图、具名武器、具名载具、具体 NPC、出生分布、胜负规则或平衡数值；这些产物及其数值由玩法层组合本文件定义的基类、参数 Schema 与合法动作契约后提供。

本 Spec 的职责是：

1. 把引擎层的 `Node`、`Link`、`Entity`、`Item`、`Container`、`Slot`、`Op`、`Query`、`Relation`、事务与不变量约束为本领域可复用的语义族；不重复定义其运行时结构或执行机制。
2. 定义天然场景、微型场景、过渡、容器、物品、武器、防具、载具、伤害、距离、移动、掩体与交互的类型身份、组合规则、参数 Schema 与跨层适配接口。
3. 要求玩法层用已登记的基类组合具体实例，并**仅在玩法层**填写伤害、成本、容量、耐久、距离取值、概率、持续时间、出生、地图与模式规则等具体配置。
4. 为 UGC、UI 和玩法层提供稳定的声明式输入、只读投影、诊断与未决接口；不允许输入损坏时猜测或补写语义。

本文档全文为规范正文，验收标准可机械判定。文中"应"表示强制要求，"不得"表示强制禁止，"可"表示允许但不强制。

## 四、术语

- **天然场景**：玩法层地图中的骨架节点所采用的基类层场景类型。天然场景类别包括大场景、中场景和小场景，但类别本身不生成具体地图节点。
- **过渡场景**：连接天然场景的 `Link` 语义，通常不可长期停留（走廊、门、楼梯、窗）。
- **微型场景**：附属于一个有效天然场景、承载局部接触关系的 `Node` 语义。它是**近战与直接交互的唯一空间前提**，不是独立的运行时结构。
- **空旷地**：活体移动到天然场景后，以自身为中心创建的个人微型场景。小场景**禁止**创建个人空旷地，该交互复用为进入小场景自带的共享微型场景。
- **贴身**：两个活体处于同一微型场景的**成对对称关系**（A 贴身 B ⟺ B 贴身 A）。"找到 X"的本质是进入 X 的微型场景。
- **距离范式**：两个活体之间的场景拓扑连接数量（加权），**编号从 1 起算**：距离 1 = 贴身（同一微型场景），距离 2 = 不同微型场景但同一天然场景，距离 3 及以上按距离公式沿过渡边累加（跨天然场景 +1，大场景 ×2）。
- **容器类**：约束引擎层 `Container` 与 `Slot` 的可复用语义，声明容纳资格、槽位角色和放入/取出规则引用。
- **物品类**：可被容纳、装备、消耗、附着或授予动作的语义族。
- **武器类**：区分近战、非枪械远程和枪械的类型身份，并以**组合**表达武器属性（散射 / 扫射 / 连发等）、谱型、伤害引用、弹药与配件兼容性。
- **武器属性**：可选、可多选、**不构成类型身份**的武器能力（散射、扫射、连发等）。不声明任何武器属性即默认单体攻击，无需显式声明"单体"。
- **谱型**：弹道谱型 / 距离档（手枪、霰弹枪、步枪、狙击枪、冲锋枪、机枪各自的距离—威力曲线）。它与已废止的"攻击形状 / 形状轴"是**两个不同概念**。
- **伸长**：轻型 / 中型近战武器可攻击**同一过渡场景另一侧微型场景**目标的属性。此前写作"延长"的表述已更正（D-043）。
- **防具类**：声明装备位置、减伤规则引用、破损条件引用和状态交互接口的语义族。
- **掩体**：按**作用对象**（对玩家生效 / 对场景生效）与**赋予者**（实体赋予 / 场景固有）构成的**二维正交**语义，四象限均合法。
- **载具类**：作为 `Entity` 存在，声明座位、货舱、门引用、可定向部件、邻接、锁定、移动、碰撞和损毁处置接口的语义族。乘员处于"**在实体内**"的状态，**不是**处于某个微型场景中。
- **玩法数值**：伤害、成本、容量、耐久、距离取值、概率、持续时间、阈值与类似的具体赋值；由玩法层拥有。
- **结构边界**：为类型结构、认知上限或引擎不变量服务的约束，**不是**玩法平衡数值。
- **`Unresolved_Item`**：已明确来源但尚未获得控制决策的事项；不得生成默认实现、默认数值或隐式行为。

## 五、需求

### 要求 1：来源追踪、层级边界与建模纪律

**用户故事：** 作为规范维护者，我想要每项空间与物品定义都有可追踪的来源和唯一的层级归属，以便历史材料不能隐式变成可实现规则。

**可追踪来源：** S-01、S-02（要求 1、2、3、4、5、16）、S-04、S-06。

#### 验收标准

1. 本 Spec 应只登记可枚举、可组合且不依赖特定玩法的空间与物品语义基类、实例组合规则、参数 Schema 和适配接口。
2. 每个登记的定义应声明唯一标识、合法引擎层 `Def kind`、语义族、抽象状态、参数 Schema 与 `Source_Record`。
3. 继承只可表达类型身份或契约细化；武器属性、谱型、伤害引用、槽位、标签、附件与可选能力必须通过组合表达。
4. 若候选定义仅因伤害、成本、容量、耐久、概率、距离、持续时间或其他玩法数值而区别于父定义，`Definition_Validator` 应以 `VALUE_L3_OWNERSHIP` 拒绝该继承关系。
5. 若候选定义包含具体地图布局、出生分布、胜负条件、模式顺序、具名实例或绑定某一玩法配置的规则，`Definition_Validator` 应以 `LAYER_L3_OWNERSHIP` 拒绝该定义。
6. 若候选定义重新声明运行时 `Node`、`Link`、`Entity`、`Item`、`Container`、`Slot`、`Relation`、事务、查询、Op 分发、表达式求值、Hook 调度或持久化机制，`Definition_Validator` 应以 `LAYER_L1_OWNERSHIP` 拒绝该定义。
7. 若候选定义使用废用术语或重新引入 S-06 已否决机制，验证器应返回包含控制来源和规范术语的 `Structured_Rejection`。本领域的废用术语与废案至少包括：**模板**（应为"实例"）、**内容层**（应为"基类层"）、**接敌面**、**攻击形状 / 形状轴**、**延长**（应为"伸长"）、**体积分类**（小 / 中 / 大三档）、**口袋槽位**、**尸体系统**（搜尸 / 拖拽尸体）、**已发现关系系统**、**耐久系统**（武器与载具）、**护甲增加抗伤害值**、**感知衰减表**、**噪音残影**、**死后化床**、**多米诺长眠**、**霸体**。
8. 同一来源优先级出现实质冲突时，装载管线应保留来源定位和冲突内容为 `Unresolved_Item`，不得自行选择一项作为默认语义。
9. 若某项审查以"S 表未列出该文档"或"两处来源描述不一致"为理由否决一项已确认决策，则该审查结论应被拒绝，并按 D-060 改为登记待裁决事项。
10. 若候选定义要在未获得新的已确认决策的情况下改写已确认决策的结论，则验证应拒绝该定义，并在诊断中保留原结论与其决策编号。

### 要求 2：参数、数值和结构边界归属

**用户故事：** 作为玩法层作者，我想要基类层提供完整参数接口而不携带平衡结果，以便同一组合能够被多个玩法复用。

**可追踪来源：** S-01 第四、第五条；S-02 要求 5、8、9、16；S-04 D-057、D-060。

#### 验收标准

1. 每个数值字段应在其参数 Schema 中标记为 `Gameplay_Value`、`Structural_Bound`、`Constitutional_Constant` 或 `Internal_Metric` 之一，并声明单位、值域、归属层和来源。
2. 伤害、成本、容量、耐久、距离取值、概率、持续时间、恢复量、阈值、生命值、槽位数量和任何具体动作代价必须作为玩法层参数值，不得写入基类或可复用实例本体。
3. 对玩法层提供的所有玩家可见数值，验证器应拒绝不在 1–5 范围内的赋值，并在诊断中标明字段、实际值、允许范围和 S-01 来源。
4. 节点连接数是受五并列原则控制的结构边界；任一天然场景的连接数不得超过 5。该限制不授权基类层为具体地图指定节点、布局或出生规则。
5. 回合编号、实体数量、查询结果大小、结算预算和性能统计等内部度量必须有显式 `Internal_Metric` 标记；未标记的数值不得借由"内部"理由绕过验证。
6. 若参数字段没有归属分类、结构理由或控制来源，`Definition_Validator` 应以 `VALUE_CLASSIFICATION_MISSING` 拒绝候选定义。
7. 若基类或可复用实例内嵌具体伤害表、概率表、动作价格表、容量表或阈值表，验证器应以 `VALUE_L3_OWNERSHIP` 拒绝，且不得以历史示例补写默认值。
8. UI 显示参数时应取得字段的数值归属和来源；来自玩法层的值必须标记为玩法层配置而非基类默认值。
9. **玩法层选择的默认平衡值不是结构边界**。若某个取值的理由是空间性格、战术平衡或体验节奏，则它属于玩法数值，即使它同时被表述为"上限"（D-057）。验证器不得因为一个数值被称作"上限"就把它登记为 `Structural_Bound`。
10. 结构边界应携带其**结构理由**（类型结构、认知上限或引擎不变量之一）。缺少结构理由的候选结构边界应被拒绝，且不得以补一条来源引用的方式使其成立。

### 要求 3：引擎层依赖与唯一写入边界

**用户故事：** 作为实现者，我想要空间与物品语义只依赖稳定的引擎层接口，以便领域规则不复制运行时机制或形成旁路写入。

**可追踪来源：** S-03 要求 7、9、10、16、19、20、21；S-02 要求 2、6、7、12、13；S-01 第四条 Op 通道铁律。

#### 验收标准

1. 本 Spec 应将 `Node`、`Link`、`Entity`、`Item`、`Container`、`Slot`、`Relation`、`Query`、`Expr`、`ActionDef`、`Attachment` 和 `Diagnostic` 视为类型化依赖；不得重新定义其字段结构、索引策略、事务模型或生命周期实现。
2. 本 Spec 的动作、伤害、状态、资源和网关语义应引用已登记的动作族、伤害族、状态族、移动族、网关族与引擎层效果接口；不得复制其底层解释规则。
3. 所有运行时写入必须经 `OpRegistry.invoke` 的合法 Op 发起。物品转移必须复用 `item.move`；不得新增拾取、丢弃、装备、卸下、死亡物品转移或交易的独立写入原语。
4. 若语义定义要求直接写入世界状态、直接修改容器数组、直接修改关系索引或绕过事务执行，验证器应以 `OP_BYPASS_FORBIDDEN` 拒绝该定义。
5. 当一个空间、容器、物品或载具动作的前置条件不满足时，该动作必须经同一动作契约返回 `Structured_Rejection`；不得以局部状态修改、隐式转移或静默成功替代拒绝。
6. 若候选操作会违反引用完整性、单一位置、单一容纳、无环容纳、拓扑一致、父子一致或容器双向一致等引擎层不变量，事务应被拒绝并保留操作前的语义状态。
7. 对合法的语义引用，`Reference_Resolver` 应在定义激活前验证目标的 `Def kind`、语义族和必需能力；任何缺失或不兼容引用都应产生含 JSON 路径的 `Structured_Rejection`。
8. 依赖 Hook 否决语义的领域机制（如要求 7 第 6 条的死亡容器"禁止存入"）可以引用 `before:*` / `after:*` 分发能力；该能力已由内核接线交付（H-001 已闭合），不再是上游缺口。若某实现所需的 Op 未被标记为结构性 Op 而导致 Hook 不分发，则应作为引擎层交接项登记，不得在本领域旁路实现。

### 要求 4：天然场景与拓扑类型契约

**用户故事：** 作为地图工具作者，我想要天然场景类型提供稳定的结构边界，而不把具体地图设计固化为基类规则。

**可追踪来源：** S-01 第四、第五条；S-02 要求 7；S-03 要求 7、11；S-04 D-003、D-057、D-056。

#### 验收标准

1. 天然场景族应区分大场景、中场景和小场景三种类型身份，但不得因此创建具体地图节点或声明地图布局。
2. 天然场景的最大连接数应作为**单一** `Structural_Bound` 记录为 **5**，携带 S-01（五并列原则 / 拓扑铁律，理由为玩家同时认知上限）的来源记录（D-057）。**按档的 5 / 4 / 3 不是结构边界**：它们是玩法层选择的默认平衡值，由玩法层的地图 Linter 承担；玩法层可在 1–5 区间内自行取值，但不得超过 5。基类层不得按档登记三条结构边界。
3. 地图编辑输入若使天然场景连接数超过结构上限 5，验证器应拒绝整份候选地图配置并报告节点标识、场景类型、实际连接数和结构边界。**按档上限的越界属玩法层校验**，由玩法包自身的地图规则报告，基类层不代为拒绝。
4. 小场景类型应声明**共享微型场景**能力，并排除个人空旷地能力；不得将小场景错误归类为微型场景。大场景与中场景应声明**个人空旷地微型场景**能力面（活体移动到"空旷地"时创建个人私有微型场景）；**微型场景的合法父级是大 / 中 / 小三档中的任意一档**，不得把父级限制为仅小场景（D-056）。
5. 具体出生点、关键资源位置、地图连通性目标、缩圈范围、缩圈顺序、地形叙事和地图平衡规则属于玩法层；本 Spec 不得指定或推导这些配置。
6. 拓扑计数若作为内部校验数据，应显式标记为内部度量；其结果不得被错误宣传为玩法层可自由突破的参数。
7. 若候选天然场景定义将结构上限 5 改写为其它数值、删除其来源，或将具体地图节点登记为基类，验证器应拒绝该定义并生成诊断。**注意**：玩法层为某一档声明 4 或 3 **不属于**"把边界改写为平衡数值"——那正是 D-057 划给玩法层的职责。
8. 大 / 中 / 小三档之间的父子容纳关系（若声明）仅作为**可选叙事分组**，**不参与距离计算、不参与微型场景生命周期、不参与"找到"判定**（D-056）。空间拓扑与距离由"三档 + 过渡"的图模型承担，距离沿过渡边累加；任何把三档解释为严格容纳树、并据此推导距离或限制微型场景父级的候选定义必须被拒绝。
9. 缩圈机制的中心选取、周边拟合算法与每回合缩去一个天然场景的节奏属于玩法层规则；本 Spec 只提供"天然场景可被标记为已缩去"的状态能力，不提供具体算法。
10. 缩圈对附属微型场景的处置（随父场景一起处理）与载具不受缩圈父场景切换规则约束（载具是实体，位置随其自身状态变化）应作为组合规则登记，具体伤害数值（如每回合毒伤）由玩法层配置。

### 要求 5：微型场景的附属、创建与生命周期契约

**用户故事：** 作为空间规则作者，我想要微型场景的归属和存续只取决于父场景与当前占用，以便不会产生悬空归属或专用生命周期分支。

**可追踪来源：** S-02 要求 7；S-03 要求 9、20；S-04 D-011、D-056；S-06 天然场景与微型场景条目。

#### 验收标准

1. 微型场景应映射为引擎层 `Node` 的语义类型，并且必须恰有一个解析为有效天然场景的 `parent` 引用。**该父级可以是大场景、中场景或小场景中的任意一档**（D-056）：大 / 中场景承载**个人私有**微型场景（活体移动到"空旷地"时创建）、过渡承载**共享**微型场景（平行双侧、垂直单侧），小场景**自带一个共享**微型场景且禁止个人空旷地。任何把父级限制为单一档位的候选定义必须被拒绝。
2. 微型场景的创建触发者可来自实体、过渡或结构性共享场景能力；触发来源只能写入不可变的 `props.creator` 溯源字段。
3. `props.creator` 不得表示所有者、当前占用者或生命周期依据。若定义用该字段决定销毁、保留或访问权限，验证器应以 `MICRO_SCENE_CREATOR_MISUSE` 拒绝。
4. 微型场景的生命周期资格必须由有效 `parent` 和当前占用关系共同判定；占用人数必须由查询派生，不得维护独立人数状态。
5. 当微型场景占用归零时，生命周期处理必须调用引擎层支持的节点回收路径；当父天然场景被候选事务移除时，该事务必须同时解决全部子微型场景和占用者的合法去向。
6. 若微型场景缺少父引用、父引用不是有效天然场景、父场景移除后留下子引用，或候选操作使占用关系悬空，系统应拒绝该候选操作并保持事务前状态。
7. 结构性共享微型场景与按需微型场景必须使用同一父场景、占用查询和回收语义；不得为共享场景创建基于创建者或固定所有者的例外。
8. 载具不是微型场景；任何将载具定义为微型场景、以微型场景父级规则决定载具存续或把载具内部误作载具本体的候选定义都必须被拒绝（D-038）。
9. 过渡场景创造的微型场景，双侧（平行过渡）或单侧（垂直过渡）各自的 `props.creator` 指向同一过渡 `Link`，但各自的 `parent` 分别指向所在那一侧的天然场景。
10. **贴身**必须建模为两个活体各自私有微型场景之间的成对对称关系（大 / 中场景）；小场景内所有活体共处共享微型场景，贴身成本天然为 0。脱离贴身的成本、大 / 中场景"找到"的成本属于玩法层参数，本 Spec 只提供关系与状态转换的接口。

### 要求 6：过渡、接触、距离与网关的可组合接口

**用户故事：** 作为玩法层作者，我想要通过可组合的过渡、距离和接触接口配置通行与交互，而不需要把具体动作流程或数值写进空间基类。

**可追踪来源：** S-02 要求 6、7、9；S-03 要求 11、16、19、25、26；S-04 D-006、D-013、D-014、D-045、D-051。

#### 验收标准

1. 过渡族应声明允许的天然场景端点类型、方向性、通行条件引用、阻挡能力引用、视线/影响传播接口和可选距离策略引用。
2. 过渡端点、阻挡来源、条件表达式、伤害结算引用和移动效果引用必须解析为兼容的类型；缺失、悬空或不兼容的引用必须导致 `Structured_Rejection`。
3. 过渡的动作应通过动作族声明行动者条件、目标条件、成本类别、效果引用、中断条件和完成状态；不得在本 Spec 定义新的运行时动作引擎。
4. 需要资源、检定或条件的通行互动必须分别引用资源转换、检定或条件网关契约。具体门槛、成本、成功效果和失败效果由玩法层提供。
5. 多阶段互动应由有序的付费动作和中间状态表达；依附动作应绑定付费动作且不能单独形成 AI 或玩家决策分支。
6. 跳窗、楼梯、攀爬、接触、阻挡、视线桥接、距离权重和动作流程差异均可由玩法层在本接口上配置；本 Spec 不得指定具体成本、距离取值、伤害、反应窗口或地图中的具体通道。
7. **距离范式**应登记为基类层的组合规则：距离编号**从 1 起算**（距离 1 = 贴身，即同一微型场景；距离 2 = 不同微型场景但同一天然场景；距离 3 及以上按公式沿过渡边累加，跨天然场景 +1、大场景 ×2）（D-051）。本 Spec 只登记距离**计算规则的结构**，不登记任何具体的距离—数值映射表（如枪械命中 DC 表）；后者由玩法层配置并引用本规则。
8. **跳窗到下层的距离**应作为距离范式的一条组合规则登记：按当前基准（距离从 1 起算）等价表述为**距离 2**，不与常规楼层过渡的"离开 +1、进入 +1"叠加计算（D-013，经 D-051 平移）。该数值本身（"2"）属于距离范式的结构性等价关系，不是可由玩法层重新配置的自由数值——它是"贴身之外第一级、且不叠加"这一规则的直接表达。
9. **过渡点封堵规则**应保留：过渡场景创造的微型场景中，任意一侧有活体或具有阻挡能力的实体时，整个过渡不可通行。回合制下不存在"同时"，因此该判定实现为简单的占用检查，不得引入优先权竞争或掷骰仲裁（D-045）。
10. D-014 的远程动作流程默认策略（两步：瞄准/蓄力 → 反应 → 发射，枪械简化为一步是特例）只可作为玩法层选择的策略输入，通过过渡与武器参数 Schema 引用；不得被提升为不含上下文的引擎层规则。
11. 若候选过渡将具体场景、具体数值或模式绑定规则写入基类定义，验证器应以 `LAYER_L3_OWNERSHIP` 或 `VALUE_L3_OWNERSHIP` 拒绝。

### 要求 7：容器、槽位、物品与装备能力契约

**用户故事：** 作为内容作者，我想要容器、物品和装备共享可验证的容纳与装备接口，以便不同玩法可以复用存取、携带、装备和转换能力。

**可追踪来源：** S-02 要求 5、8、11、12、13；S-03 要求 10、16、17、20；S-04 D-041、D-059；S-06 废案与死亡背包条目。

#### 验收标准

1. 容器族应声明宿主类型、容器角色、槽位接受谓词、存取能力、可否存入、可否取出和转移动作引用；具体槽位数量与容量必须由玩法层配置。
2. 物品族应声明容器资格、装备位置要求、可携带标签、授予动作、附件点、使用位置、消耗行为和可选实体转换能力。
3. 容器和槽位的实际结构、顺序、插入策略、默认槽位选择、容纳检查与移动失败语义由引擎层拥有；本 Spec 只能引用这些能力，不得重写其实现。
4. 若 `item.move` 找不到满足接受谓词的合法槽位，动作应失败且不得创建地面替代物、吞没物品或绕过容纳约束。
5. 物品与实体转换必须通过合法的引擎层转换 Op 和事务表达。候选转换若导致引用、容器、位置或附件关系不完整，必须原子拒绝。
6. **死亡背包**（死亡容器）只能表达为玩法层选用的死亡容器能力：该能力应引用新建、禁止存入的容器和由死亡事务导出的内容引用；具体容量、清单可见性、动作成本和物品范围由玩法层拥有。**"禁止存入"的表达形态按 D-059 分两层**：
   - **声明层**用能力组合表达（组合"禁止存入"能力，与"存入"能力互斥；并组合"内容派生自死亡事务"能力），基类层只登记这一层。
   - **运行期机制**必须表达为**可替换的机制引用**，不得硬编码为某个具体实现字面量。当前唯一已知可行实现是"宿主携带标记时由 `before:item.move` 否决"。
   - **灌注时序是契约的必需组成部分**：禁止存入的标记必须在**灌注事务提交之后**才生效。理由：`Slot.accepts` 是结构区字段，已登记 Op 集合中没有任何 Op 能在容器创建后修改它，若创建时即写 `accepts: false`，灌注自身的 `item.move` 也会被拒。任何机制实现都必须满足该时序义务；不满足者拒绝装载。
7. 不得引入物品体积分类、口袋槽位或其他 S-06 已否决的携带机制。若候选输入包含该类语义字段，验证器应以 `DEPRECATED_MECHANIC` 拒绝并给出控制来源。
8. 重型、可装备、可消耗、可转换等标签可作为可组合能力存在；这些能力产生的具体成本、状态效果、触发时机和数值必须引用玩法层规则。
9. 若物品组合产生悬空的槽位、容器、装备位置、消耗效果、附件点或转换目标，`Reference_Resolver` 应拒绝该组合并保留最后一个有效定义集。
10. **出生初始装备**（空手进场，D-041）应表达为玩法层的开局配置，而非基类层默认值：基类层只提供"槽位可全空"这一状态能力，不得为槽位预置任何默认物品引用。
11. **重型标签的负重聚合**应表达为组合规则：沿携带关系树向上聚合重型标签，且该聚合结果不因"放入容器/背包"而免除；具体的移动 AP 惩罚数值由玩法层配置。

### 要求 8：武器、武器属性、谱型、伤害与配件组合契约

**用户故事：** 作为玩法层作者，我想要用稳定的武器、谱型和伤害接口组合具体实例，以便差异不被错误建模为按数值分叉的继承树。

**可追踪来源：** S-01 第一、第三、第四条；S-02 要求 3、5、8、9、16；S-04 D-014、D-018、D-043、D-050；S-05 T-001。

#### 验收标准

1. 武器族应区分近战、非枪械远程和枪械三种类型身份；它们的**武器属性**（散射 / 扫射 / 连发等）、目标规则、谱型、距离策略、伤害引用、弹药行为、配件兼容性和动作序列必须通过组合声明，不构成类型身份。不声明任何武器属性的武器默认单体攻击，不需要显式声明"单体"分类。散射 / 扫射属性不设固定命中目标数上限（命中数由拓扑与场景占用情况决定，受五并列原则连接数 ≤5 的天然约束）；连发属性的目标上限由玩法层给出。
2. 伤害族应声明伤害类别、来源条件、目标条件和结算管道引用，不得声明具体伤害量、命中门槛、暴击增量或伤害表。
3. 谱型族应声明弹道谱型身份（距离档，非攻击形状）和可组合参数接口，不得将具名枪械、具体距离表、弹药数量或具体伤害写成基类默认值。
4. 具体武器必须由武器类、武器属性（可选）、谱型、伤害类、动作序列、弹药行为和配件能力等组合形成；若候选定义仅以数值区分而创建子类，验证器应拒绝并建议使用组合。
5. 配件应通过兼容性引用、附件点和效果引用与武器组合；具体兼容名单、数值加成、装卸成本、弹药类型和显示规则属于玩法层。**武器配件系统 MVP 阶段不实装**（D-044）：本 Spec 保留配件能力接口供未来使用，不要求玩法层现在就填充其效果数值。
6. 非枪械远程与枪械可分别引用不同的动作序列策略，但动作阶段、反应条件、命中逻辑、成本和结算结果必须由玩法层配置；本 Spec 不得为任一具体武器写入默认流程数值。远程武器的**默认策略**是两步流程（瞄准/蓄力 → 反应窗口 → 发射），枪械简化为一步流程是被登记为特例的策略选择，不是通用规则（D-014）。
7. **非枪械远程武器的命中与射程组合规则**（D-050）：该类武器可组合"必中"能力（不引用任何 DC 判定）与"射程上限"能力（默认射程档为距离 1–2）；若某候选非枪械远程武器声明的射程超出该上限，验证器应要求其改归枪械类型身份，不得保留在非枪械远程武器族内。
8. **近战武器的伸长属性**（D-043）应登记为可组合能力：声明武器可攻击同一过渡场景另一侧微型场景的目标。轻型 / 中型近战武器通常组合该能力，重型近战武器与拳头不组合该能力；远程武器（含枪械）无视过渡场景限制，不需要声明该能力。
9. 枪械基础伤害表不得出现在任何基类或实例定义中。包含具体表项、推断默认伤害或将未决表项视为零值的候选输入必须被拒绝（`U-SPACE-001`，见要求 13）。
10. 伤害、命中、弹药、反应和附件引用损坏时，系统必须以 `Structured_Rejection` 拒绝整个候选组合；不得用同类武器、同类谱型或历史数值进行语义替换。
11. 谱型的距离—DC 映射表（如枪械命中判定表）是**玩法层数值配置**，不是基类层默认值；基类层只提供"谱型可引用一张按距离取值的判定表"这一参数接口形状。

### 要求 9：防具、盾牌、掩体、状态与移动能力契约

**用户故事：** 作为系统设计者，我想要防具、掩体和移动能力通过可复用规则引用表达，以便防护、破损、负重和状态效果不会固化为单一玩法的数值表。

**可追踪来源：** S-02 要求 5、8、9、16；S-04 D-009、D-015、D-016、D-017、D-038、D-039、D-040；S-05 T-002；S-06 废案与可选机制条目。

#### 验收标准

1. 防具族应声明装备位置、减伤规则引用、破损条件引用、伤害类别兼容性和状态交互接口；不得嵌入具体减伤、生命、耐久或破损阈值。防具减伤的**三档分档结构**（轻型 / 中型 / 重型，各自的减伤与破损规则形状）已由 D-039 确认为最终版本，属可复用的规则引用形状；具体数值仍由玩法层配置。
2. 盾牌族应声明持有要求、格挡动作引用、损耗规则引用、破损条件引用和可选交互能力；具体盾牌数值、特殊互动范围和模式可用性属于玩法层。
3. **掩体机制**（D-040）应实现为**二维正交模型**：按作用对象分「对玩家生效 / 对场景生效」，按赋予者分「实体赋予 / 场景固有」，四象限均合法。
   - **场景固有掩体**在空间领域的场景族侧登记（对场景生效 + 场景赋予、或对玩家生效场景不适用此象限的组合，具体由场景族能力声明）。
   - **载具半掩体**（D-038）属「实体赋予 + 对玩家生效」象限：半掩体授予对象是**玩家**（可注册给单个或多个玩家），**不是**实体注册给微型场景，因此**站在车旁边的人不受益**；**载具被摧毁 → 掩体消失**。
   - 掩体的**减伤量与命中修正的具体数值**未冻结（`U-SPACE-002`，见要求 13），本 Spec 不得提供任何减伤字面量或默认值；旧"远程伤害 -1"的单一规则已被本二维模型取代，不得复活为默认值。
   - 掩体的**遮挡与位置关系**判定（如"两人处于同一微型场景时能否打到车内的人"）按 D-038 明确保留为**独立子课题**，本 Spec 不推断。
4. 移动族应区分地面、载具与其他移动类型的遍历语义，并暴露成本、速度、距离、地形修正、载荷修正和碰撞效果的玩法层参数接口。
5. 物品携带关系可通过引擎层查询和关系接口聚合标签，但任何由标签导出的移动成本、状态、清除时机和效果均应由玩法层规则提供。
6. 状态效果必须引用状态族和附件族的持续、叠加、触发、打断与清理接口；不得把引擎层运行时迁移伪装成新的基类语义。
7. D-015 所列盾牌特殊互动（扔盾 / 盾击 / 电锯破防暴盾）和 D-010 的格斗范围属于可选玩法层内容；基类层只保留可组合的动作与状态接口，不将其作为标配行为。
8. D-016 已移除的 `[淋湿]` 状态不得成为基类、实例、默认标签或隐式状态交互的一部分；发现该语义时必须拒绝。
9. 若防具、盾牌、掩体、状态或移动定义含有未分类玩法数值、缺少效果引用或引用不兼容的伤害/状态/动作类型，验证器应拒绝并报告字段与来源。

### 要求 10：载具实体与交互能力契约

**用户故事：** 作为玩法层作者，我想要载具作为可组合实体族提供完整交互面，以便不同载具实例复用座位、货舱、门、移动、碰撞和损毁能力而不误入微型场景语义。

**可追踪来源：** S-02 要求 7、8、9；S-03 要求 2、10、16、19、20；S-04 D-011、D-012、D-030、D-038、D-047、D-048。

#### 验收标准

1. 载具族必须映射为引擎层 `Entity`，不得映射为 `Item` 或微型场景。乘员是"**处于实体内**"的状态，**不是**处于某个微型场景中（D-038）；载具**不受**缩圈的父场景切换规则约束——其位置随自身 `Entity` 状态变化。
2. 载具族应提供参数化的座位角色、货舱容器、稳定门引用、可定向部件（如轮胎）能力、邻接判定、锁定能力、移动能力、碰撞能力和损毁处置接口。
3. 座位、货舱和门必须使用引擎层容器、槽位、引用与动作契约；本 Spec 不得定义独立的车内存储、乘员位置或门访问运行时结构。
4. 每个已声明门标识必须在解析后的定义中保持稳定且可单独引用；门索引与乘员互动范围必须是可独立组合的输入。
5. **位置优先于门索引**（D-030）是本领域的默认交互策略：载具整体只占极小空间，门索引是叙事 / 引用意义上的区分（用于分别针对性破坏），不是物理阻隔意义上的区分；行动方站在车辆旁边即可对车内**任意一名乘员**发起交互，不需要区分具体哪扇门。选择该策略的玩法层配置必须将车辆邻接与乘员交互策略一起声明；基类层不得把具体门数量、乘员数量或互动结果写为默认值。
6. D-011 所确认的撞击、部件损毁、锁定、推行、车上互动和损毁处置范围，必须通过本接口可表达；其具体车辆种类、数值、步骤、目标限制、反应条件和掉落结果均由玩法层配置。
7. **撞击伤害的结构**（D-048）应登记为组合规则：撞击对目标造成**固定**伤害（不随载具当前生命值浮动），且**同时对载具自身造成固定的自损伤害**；"伤害 = 载具当前生命值"这一浮动计算方式已被否决，验证器应拒绝把撞击伤害声明为载具生命值的函数。具体的固定伤害数值与自损数值由玩法层配置。
8. **爆胎与部件损毁的结构**（D-047）应登记为组合规则：可定向部件（轮胎）不建模为拥有血量的子实体，而是组合"伤害阈值免疫"能力（对低于某阈值的单次伤害不响应）；近战攻击该部件需要前置的姿态网关（蹲下），远程攻击可将其作为独立子目标直接选择。具体阈值数值、蹲下的中断规则细节（打断即取消并起立，不保留进度）之外的数值、以及部件损毁对载具生命值上限的影响幅度由玩法层配置。
9. 载具若涉及容器、座位、门、动作、移动、碰撞、损毁、可定向部件、附件或状态引用，`Reference_Resolver` 必须在激活前验证所有引用；任何悬空或不兼容引用必须原子拒绝。
10. 若候选定义把载具生命周期绑定为微型场景父子关系、将载具内部错误视为载具本体，或直接修改乘员/货舱状态，验证器应拒绝该定义。
11. **载具损毁**必须组合以下处置：撤销所有乘员的半掩体状态（D-038）、乘员自动转移到载具所在天然场景节点、货舱物品转移到该节点、载具残骸实体保留。具体的掉落细节和残骸交互由玩法层配置。
12. **推行能力**（如电瓶车可推、汽车不可推）应登记为载具族的可选组合能力，具体推行的 AP 成本、移动节奏由玩法层配置。

### 要求 11：UGC、UI 与玩法层的稳定适配接口

**用户故事：** 作为创作者、UI 开发者和玩法层作者，我想要得到同一份已验证的空间与物品语义投影，以便工具、界面和具体玩法不会复制规则或修改底层状态。

**可追踪来源：** S-02 要求 11、12、13、14、15、16；S-03 要求 25、39、40；S-04 D-019。

#### 验收标准

1. UGC 输入必须使用带版本的纯声明式 JSON，表达类型、组合、参数、条件、引用和已知效果；不得包含可执行代码、命令式循环、动态求值或直接状态赋值。
2. UGC 适配器应将候选定义提交给与手写定义相同的 `Definition_Validator`、`Reference_Resolver` 和原子激活路径；不得存在绕过领域验证的导入入口。
3. 若语义字段缺失、损坏或不兼容，系统应拒绝候选定义且不得发明默认武器、防具、载具、容器、场景、数值、引用或行为。
4. 若仅表现字段缺失，UI 适配器可提供类型兼容的表现降级，并输出不改变语义的 `Warning_Diagnostic`。
5. UI 应通过只读语义投影获取场景类型、可用动作、不可用原因、装备角色、容器角色、载具交互意图、状态标签和资源语义；UI 不得直接修改语义状态。UI 消费的距离取值应是**已计算好的投影结果**，不得由 UI 端重新计算。
6. 玩法层实例配置应只消费已登记基类、参数 Schema、已验证引用和可组合能力；若配置绕过基类、写入基类禁止的数值或违反引擎层不变量，验证器应拒绝且保持此前有效状态。
7. UI 与 AI 的动作可用性判断必须复用引擎层 `queryActions` 和相同的动作前置条件；不得因表现需求或自动决策创建第二套领域判定。
8. 适配接口应暴露每个语义字段的来源、归属层、待决状态和诊断结果，使调用方能够区分已冻结契约、玩法层配置和 `Unresolved_Item`。
9. 本 Spec 向 `wakeup-ui-animation` 提供的投影字段名与枚举值应与该 Spec 已声明的待汇合契约保持类型兼容；若字段命名变更，应作为交接项登记，不得直接静默改名后要求对方跟进。

### 要求 12：拒绝、诊断、原子性与可验证性

**用户故事：** 作为质量工程师，我想要所有非法组合都可定位地拒绝且不留下部分状态，以便空间与物品扩展能在广泛输入下安全演进。

**可追踪来源：** S-02 要求 12、13、15、16；S-03 要求 16、17、19、20、21、39；S-05；S-09 进度真相原则。

#### 验收标准

1. 本 Spec 的每个规范要求必须关联至少一个 `Source_Record`、至少一种可观察验证结果，以及非法输入的拒绝或诊断行为。
2. 诊断至少应包含稳定代码、严重级别、定义标识、JSON 路径、来源、原因与修正建议；多项可独立发现的问题应在同一次验证结果中全部报告。
3. 因层级越界、未分类数值、废案复活、错误类型身份、继承环、引用损坏、非法组合、未决项被擅自赋值或引擎层不变量冲突而拒绝时，系统必须返回含 `Error_Diagnostic` 的 `Structured_Rejection`。
4. 候选 `Definition_Package` 发生任一错误时，定义注册表不得激活其中任何一项；此前有效定义集必须保持不变。
5. 运行时动作发生前置条件失败、结构性 Op 被否决或事务提交触发不变量冲突时，系统必须保留操作前语义状态，不得产生部分容纳、部分位置、部分移动、部分状态或部分载具关系。
6. 测试接口应能分别生成合法与非法的天然场景、微型场景、过渡、容器、物品、武器、防具和载具组合，并观察解析、验证、激活、拒绝和状态不变结果。
7. 测试接口应覆盖：连接数边界、微型场景父/占用生命周期、容器无合法槽位、物品/实体转换回滚、悬空引用、数值越界、废案字段、载具非实体化、玩法层数值写入基类和未决接口误用。
8. 对任意被拒绝的候选定义或运行时操作，测试应验证其后的注册表或语义状态与操作前等价；不得仅以"未抛异常"作为通过条件。
9. 测试接口应覆盖要求 4 第 2、7、8 条描述的天然场景连接数结构边界（单一 5）与玩法层按档取值（4/3）不被基类层拒绝的对照场景，防止把二者混淆为同一断言。
10. 本 Spec 的可验证性结论应以**测试套件与类型检查的实跑结果**为准，不得以 `tasks.md` 复选框作为完成证据（S-09）。若测试现实与 `tasks.md` 状态不一致，应先更新 `tasks.md`，不得反向要求测试迎合复选框。

### 要求 13：未决接口与禁止默认化

**用户故事：** 作为后续专题的维护者，我想要未决事项有明确接口边界而不被当前 Spec 替我作出设计决定。

**可追踪来源：** S-01 第七条待访谈事项；S-02 要求 16；S-04 D-017、D-018、D-038、D-042；S-05 T-001、T-002。

#### 验收标准

1. `U-SPACE-001`（T-001，枪械基础伤害表及其与 AP 经济学的平衡验证）必须保持 `Unresolved_Item`。本 Spec 仅提供武器、谱型和伤害引用接口；不得提供具体基础伤害、默认伤害、替代伤害、平衡结论或推断规则。
2. `U-SPACE-002`（T-002，掩体机制）**结构部分已由 D-040 冻结，收窄为仅"数值"未冻结**。
   - **已冻结，本 Spec 应当实现**：见要求 9 第 3 条的二维正交模型与载具半掩体象限。
   - **仍未冻结**：掩体的**减伤量与命中修正的具体数值**（随 T-001 处理）。本 Spec 不得提供任何减伤字面量或默认值；旧"远程伤害 -1"不得复活。
   - 掩体的**遮挡与位置关系**判定按 D-038 明确保留为**独立子课题**，本 Spec 不推断。
3. `U-SPACE-003`（Q-01，武器谱型"特殊"档机制框架）必须保持 `Unresolved_Item`；谱型接口不得用任意既有类别替代该机制。
4. `U-SPACE-004`（Q-02，远程武器多阶段流程与枪械流程的跨文档精确对齐）必须保持 `Unresolved_Item`；本 Spec 只暴露动作序列策略接口，不裁决未冻结的细节。**注意**：D-033 已裁决瞄准状态的**可见性**（低显著性公开，见 `wakeup-ui-animation` 要求 3），流程本身仍待对齐，两者不得混淆。
5. `U-SPACE-005`（Q-04，载具内部微型场景与外部交互点边界）**部分已由 D-038 / D-030 冻结**。
   - **已冻结**：载具是**实体（Entity）**，乘员处于"**在实体内**"的状态，**不是**处于某个微型场景中——因此载具内部**不建模为微型场景**，这条歧义已关闭。交互范围按 D-030：**站在车辆旁边即可对车内任意乘员发起交互**，不区分具体哪扇门；两个门索引仅在"针对性破坏车门"等场景下有区分意义。
   - **仍未冻结**：车内外**互相攻击**的判定细则（D-038 第 6 条明确保留为独立实现逻辑）。本 Spec 不得推断该判定。
6. `U-SPACE-006`（Q-05，盾牌 MVP 标配范围）必须保持 `Unresolved_Item`；基类层只保留盾牌能力接口，不设定可选互动的默认可用性。
7. `U-SPACE-007`（丢弃物品依附时机）**已由 D-042 裁决关闭**：丢弃物品等零费动作归入**零费菜单**。菜单呈现规则为——正常情况下显示**有费用的菜单**并提供**切换按钮**切到零费菜单；**所有行动结束后**只保留零费菜单 + 结束回合按键（该按键**直接进入 3 秒倒计时**）。铁律"0 AP 动作不得与 1 AP 动作同处一个菜单"仍然成立，但零费动作**不限于回合末执行**。此前"部分附赠限次"的设想不再采用。
8. 任何候选定义、导入工具或 UI 若试图为上述未决项填入默认数值、默认流程、默认动作或默认可用性，验证器必须拒绝并在诊断中引用对应未决项编号。
9. 将未决项提升为规范契约前，必须提供新的控制决策、来源记录、拥有层和替代关系；在此之前，历史示例不得作为提升依据。
10. 本领域派生的次级待确认项（非阻塞，登记不裁决）：
    - 「蹲下」姿态是否正式进入姿态物理拓扑表（D-047 派生）；
    - 电瓶车撞击是否也自损（D-048 派生，汽车已确认自损，电瓶车未明确）；
    - 防具对毒素伤害是否减伤（D-049 派生，暂按防具规则通用适用处理）；
    - NPC 的 `speed`（1 / 1.5 / 2 小数）到整数 AP 的映射规则（D-052 派生）。
    这些事项不阻塞本 Spec 的其余要求生效，但不得由本 Spec 自行拍板默认映射或默认结论。

### 要求 14：跨 Spec 稳定依赖与待汇合边界

**用户故事：** 作为跨领域架构审查者，我想要知道本 Spec 已冻结的依赖和仍待汇合的接口，以便后续一致性审查不会把领域差异误解为实现缺口。

**可追踪来源：** S-01、S-02、S-03、S-04、S-05；架构决策原则（解耦优先、基层长远；不跨 Spec 改交付物）。

#### 验收标准

1. 本 Spec 对引擎层的稳定依赖为：图拓扑、容器与槽位、`item.move`、合法结构性 Op、事务、查询、引用完整性、微型场景父/占用语义、不变量、诊断与只读表现通道。
2. 本 Spec 对基类层内部的稳定依赖为：继承决定类型、组合决定配置、参数 Schema、动作/网关/伤害/状态/移动/附件语义族、原子装载和来源追踪。
3. 本 Spec 向玩法层稳定提供：天然场景类型、微型场景能力、过渡能力、距离范式的结构规则、容器与物品能力、武器 / 武器属性 / 谱型 / 伤害接口、防具 / 掩体接口、载具接口、动作与网关引用、UGC/UI 语义投影和诊断接口。
