# 元机制内核实现：设计决策与风险记录

本文档记录实现过程中遇到的、design.md/requirements.md 未明确规定或存在歧义的判断点，
以及任何自主做出但无法被 Spec 文本直接验证的实现决策。目的是让审阅者能够快速定位
"哪些地方是我自己判断的，而不是照抄文档"，以便复核或推翻。

---

## 1. Expr/Query 类型的物理层归属（L1 vs L2）

**问题**：design.md 3.2节 `Def.slots[].accepts` 与 `Slot.accepts` 都声明为 `Expr` 类型，但 `Expr`
本身在 3.3节（L2）才定义。若 `Expr` 类型放在 `kernel/expr`（L2），`kernel/state`（L1）的
`Def`/`Slot` 就必须反向 import L2，违反 design.md 第2章"L(n) 不得 import L(n+1..13)"的单向 DAG 约束。

**决策**：把 `Expr`/`Query` 的**类型声明**（零运行时逻辑的纯结构判别联合）物理上放在
`kernel/state/expr-types.ts`（L1），只依赖 L1 的 `Value`/`Id`。`kernel/expr`（L2）只拥有对这些
类型求值的**运行时引擎**（`ExprEngine`/`QueryEngine`）。

**依据**：design.md 101行"签名是设计意图的表达，不是最终工程接口...留给实现阶段"，
以及 design.md 已经把 state+topology 并为一个 L1 大层、expr+query 并为一个 L2 大层的事实
（第2章分层依赖图），说明具体模块边界本就留给实现判断。

**风险**：低。这是纯粹的模块物理位置选择，不影响任何运行时行为或需求条款的字面满足。

## 2. Diagnostic / ErrCode 的物理层归属（L1 vs L13）

**问题**：同样的分层冲突出现在 `ErrCode`（design.md 4.3节）与 `Diagnostic`（3.14节）：
`Result<T>.code` 从 L3 起就需要 `ErrCode` 类型，`InvariantChecker.checkAll` 需要返回
`Diagnostic[]`，但这两个类型按 design.md 章节编号"应该"属于 L13（Safety）。

**决策**：与决策1同样的手法——`ERR_CODES`/`ErrCode`/`FATAL_PREFIXES`/`Diagnostic` 的**类型声明**
放在 `kernel/state/error-codes.ts` 与 `kernel/state/diagnostic.ts`（L1），L13（`kernel/safety`）
只拥有运行时逻辑：`DiagnosticSink.emit/onFatal`、hint 提示词条、去重折叠、规则熔断。

**风险**：低，同决策1。

## 3. RelationIndex 不作为跨事务长生命周期对象（重要修正）

**问题**：design.md 3.1节把 `RelationIndex` 描述为持有内部索引的"全局索引"类。我最初的实现
（`state/relation.ts` 的 `RelationIndex` 类）让 L3 的 `relation.set`/`relation.del` Op 直接调用
其 `_add`/`_remove` 方法改写一个独立于 `Transaction` draft 栈的 `Map`。

**为什么这是错的**：`Map` 的变更立即生效、不参与 `Transaction` 的 begin/commit/rollback 生命周期。
若外层事务后续因不变量检查失败而整体 rollback，`Map` 上的改动**不会被撤销**，直接违反
需求21.3-21.4（事务原子性）。更严重的是，该 `Map` 不在 `WorldState` 里，不会被 `snapshot`/`replay`
捕获，直接违反需求37.1-37.3（快照/回放的确定性）——这与 design.md 3.14节对"规则熔断状态
必须放进 WorldState，不能放宿主进程内存"的论证是同一类错误，只是换了个载体。

**修正**：`kernel/ops/relation-ops.ts` 改为直接对 `Transaction.draft.entities[id].relations[kind]`
做不可变更新（与其余全部 Op 的写入路径同构），不引入任何独立于 WorldState 的索引对象。
`relOut`/`relIn` 变成读 `Entity.relations` 投影的纯函数。`state/relation.ts` 的 `RelationIndex` 类
仍保留（其纯函数式对称性/级联清理逻辑本身没有错，只是不该被实例化为跨事务单例），
供未来可能的性能优化路径参考，但当前不接入 Op 层。

**这是本次实现自我发现并纠正的设计缺陷，不是 design.md 的缺陷**——design.md 3.1节的原文
"RelationIndex 是全局索引"这句表述本身允许多种实现方式，我最初选了一种违反事务性的实现，
后来发现问题并改正。记录于此供审阅者核实修正是否彻底。

**风险**：中等（已修正）。如果后续任何新 Op 需要引入"索引"类结构做性能优化，必须重新审视
这条教训：任何索引都必须是 WorldState 内某个字段的派生视图，或者在每次读取时从 WorldState
现算，不能是独立于 WorldState 生命周期的可变对象。

## 4. Link 接口补充 `def` 字段（design.md 3.2节的遗漏，已用 DefKind 交叉验证确认）

**问题**：design.md 3.2节的 `Link` 接口未声明 `def` 字段（`Node` 有 `def`），但同一节的
`PrefabDef.links[].def: Id` 与 3.4节 `link.create` 语义都暗示每条 Link 需要关联一个 Def
（用于挂载 RuleDef、校验规则等，这与 Node/Entity/Item 的模式一致）。

**决策**：在 `topology/types.ts` 的 `Link` 接口补充 `def: Id` 字段，与 `Node` 对齐。

**复核结论（已用户复核并追加交叉验证，风险等级下调）**：design.md 3.1节 136-137 行的
`DefKind` 联合类型明确包含 `'link'` 这一取值（`'entity'|'item'|'node'|'link'|'attachment'|...`），
与 `'node'` 并列。这意味着 design.md 自身的类型系统已经预期存在 `kind:'link'` 的 Def 实例
（用来声明某一类 Link 的 rules/actions/schema，就像 `kind:'node'` 的 Def 服务于 Node 一样）。
但 `Def` 接口本身只是蓝图声明，若 `Link` 运行时实例没有字段指回其所属的 `kind:'link'` Def，
`DefKind` 里的 `'link'` 取值就没有任何运行时实例可以引用它——这与 `Node.def` 让
`kind:'node'` 的 Def 可被实际 Node 引用是完全对称的设计。因此 `DefKind` 包含 `'link'`
本身就是比 PrefabDef 用法更直接的交叉证据：design.md 3.2节 `Link` 接口遗漏 `def` 字段，
与同一文档 3.1节的 `DefKind` 声明互相矛盾，前者是书写遗漏，后者才是设计原意。

**风险**：低（已从"建议人工复核"下调为"已确认"）。这是纯粹的字段补充，不影响任何现有
需求条款的满足，且现在有 `DefKind` 枚举本身（而不仅是 PrefabDef 的间接用法）作为直接证据。

## 5. `entity.destroy` 内联执行 Relation 级联清理，而非等待 L4 Hook 分发（已复核，机械清理范围已扩大并修正真实缺陷）

**问题**：需求6.6"当一个 Relation 的 from 或 to 所指向的对象被销毁时，内核应级联移除该
Relation"，design.md 3.1节说这个清理"在 entity.destroy/item.destroy 的 after 阶段自动扫描"。
但 L4（Events/Hooks，五阶段事件分发）在 L3 阶段尚未实现。

**原始决策**：task 4.2 本身就标注"占位：after 阶段完整分发在 L4，此处只搭清理函数本身"——
在 L3 阶段直接让 `entity.destroy` 的 Op 实现内联调用 `removeAllRelationsInvolving`
（在同一个事务内，逻辑等价于"after 阶段做的事情提前发生在同一个 Op 实现内部"）。

**L4 完成后的复核结论（用户直接质疑触发）**：用户指出销毁级联清理应当区分两类纪律——
"机械纪律"（内核只保证不产生悬空引用，与具体伤害方式/死亡原因无关）与"语义纪律"
（导弹炸死不掉武器、近战砍死掉武器这类具体判定，内核不应该、也不能预判 UGC 会如何实现，
是清除实体还是造成伤害）。这条区分促使对"机械清理"本身做了一次直接验证（而不是只读代码
判断"看起来对"），验证方法是构造真实场景直接调用 `entity.destroy`：

- 验证1：给一个 Entity 挂一个 Attachment（`target` 指向它），调用 `entity.destroy` →
  **实际返回 `ok:false`**（`E_INV_DANGLING`/`E_INV_ATTACHMENT_CONSISTENCY`，InvariantChecker
  在 commit 前发现 Attachment.target 悬空）。
- 验证2：给一个 Entity 创建一个自己拥有的 Container（背包），调用 `entity.destroy` →
  **实际返回 `ok:false`**（`E_INV_CONTAINER_BIDIRECTIONAL`）。

**这证明此前的实现是一个真实缺陷，不是"待办事项"**：`entity.destroy` 此前只清理了
Relation，完全没有清理 Attachment（光环/状态）与自己拥有的 Container（背包）——任何带
光环或背包的实体此前**完全无法被销毁**，这与"武器掉落"这类最基本的死亡处理场景直接冲突，
不是"语义判断该不该掉落"的问题，是"根本销毁不掉"的机械故障。`item.destroy`/`node.destroy`/
`link.destroy` 三者的清理覆盖范围互不一致（各自只覆盖了其中一部分），进一步证实这是遗漏
而非刻意设计。

**修正**：新增 `ops/cascade-destroy.ts` 作为四个销毁 Op 的共享清理实现，统一提供三件套：
1. `cascadeRelationsAndAttachments`：Relation 双向清理 + 以该对象为 target 的 Attachment
   （含 `grantedBy` 递归子代）级联清理；
2. `destroyOwnedContainers`：销毁对象自己拥有的 Container，容器内占用者（Item 或 Entity）
   **不随之销毁**，只清空其 `slot` 字段脱离槎位——这是内核唯一被允许做的默认动作，既不是
   "掉落在地上"（需要知道地面在哪，是语义判断）也不是"随宿主一起消失"（会销毁玩家资产，
   与需求17.2-17.3"不落地不吞掉"同一条纪律）；
3. `clearHoldingSlot`：若该对象自身正被别的容器槎位持有（Entity 可占据 Slot，需求2.1），
   清空该槎位的 `holds`。

`entity.destroy`/`item.destroy`/`node.destroy`（含级联到的每一个子节点）/`link.destroy`
四者现在统一调用这三步，不再各自实现不一致的部分清理。真正的"掉落到地面"由玩法包挂载
`before:entity.destroy` 的 RuleDef，在销毁真正发生前用 `item.move` 把容器物品转移到当前
节点的地面容器——这正是 L4 Hook 分发点存在的意义：内核提供介入窗口，不替玩法包做决定。

**InvariantChecker 同时补的第二道防线**：复核过程中发现 `checkReferentialIntegrity` 完全
没有扫描 `Entity.relations.*.{out,in}` 里的悬空引用（`item.destroy` 早期版本不清理 Relation
时，这类悬空引用会静默存在、不被任何不变量检查捕获）。已在 `invariants.ts` 补上这一维度的
静态扫描，作为运行时清理逻辑之外的独立第二道防线。

**风险**：低（已修复并通过穷举场景测试）。新增 `ops/__tests__/cascade-destroy.test.ts`
覆盖 entity/item/node/link 四个销毁 Op 在"带 Attachment"/"拥有 Container"/"正被槎位持有"/
"存在 Relation"/"以上组合"五类附着状态下的销毁正确性；InvariantChecker 的 Relation 扫描
新增独立单元测试。全部 430 个既有测试零回归。

## 6. `-0` 与 JSON 序列化往返（Value/JSON 往返属性测试的边界）

**问题**：`isFiniteNumber(-0) === true`（`-0` 是合法有限数），但 `JSON.stringify(-0) === "0"`，
往返后变为 `+0`。严格的 `toEqual`/`Object.is` 深度比较会认为这是往返失败。

**决策**：属性测试改用"数值语义相等"（`-0 === +0` 恒真，这是 JS 语言规范本身的行为）而不是
"位模式相等"来判定往返成功。这不是放宽需求1.1/4.2，而是承认 JSON 序列化格式本身不保留
符号位是 JSON 规范的固有行为，不是内核实现的缺陷——内核没有做任何事情去"丢失"符号位，
是 `JSON.stringify`/`JSON.parse` 这两个内置函数的标准行为。

**风险**：极低。`-0` 与 `+0` 在游戏逻辑的任何算术、比较、条件判断中都不可区分
（`-0 == 0`、`-0 === 0`、`-0 < 1` 等全部按预期工作），只有故意用 `Object.is` 才能看出差异，
这在玩法包数据或内核逻辑中都不是一个有意义的可观察行为。

## 7. 补齐此前遗漏未注册的四组 Op（entity.place、prefab.spawn/despawn、agent.bind/unbind、outcome.reach）

**问题**：在准备全面对抗性属性测试（模糊测试）之前复核 Op 全集清单时发现，design.md 3.4节列出
的公开 Op 中有四组从未被 `OpRegistry.register` 真正注册：`entity.place`（需求9.1-9.8，微型场景
生命周期的唯一合法调用方）、`prefab.spawn`/`prefab.despawn`（需求8.1-8.7，子图批量实例化）、
`agent.bind`/`agent.unbind`（需求5.2，Agent.controls 的唯一写入路径）、`outcome.reach`（需求
32.4-32.6）。此前实现只搭了这些 Op 依赖的纯函数 helper（ensureMicroScene、buildKeyToIdMap 等）
并有单元测试覆盖，但从未把它们接到真正的 OpRegistry.invoke 调用链路——意味着这几类机制虽然
"看起来测试通过"，实际上从未在一次真实的、经过事务/不变量校验的 Op 调用里跑过。

**决策**：新增 `ops/prefab-ops.ts`、`ops/agent-ops.ts`、`ops/outcome-ops.ts` 三个文件，并在
`ops/structural-ops.ts` 补上 `entity.place`。同时给 `OpRegistry` 加了 `listOpNames()`/
`isStructural()` 两个纯读枚举方法（供后续模糊测试遍历全部已注册 Op），这两个方法不改变任何
写入语义，只是只读查询。

**过程中额外发现并修正的设计错误**：`outcome.reach` 的第一版实现自己发明了一套
`world.props.endedScopes` 派生状态，用来"标记某个 scope 已终止参与"。这个设计本身与需求32.6
的字面表述矛盾——32.6 说的是"内核应**允许**该行动者被淘汰后整局继续进行"，这是一条否定式/
许可式要求（禁止内核强制在此时结束整局），不是要求内核自己维护一份"淘汰名单"来定义淘汰。
这与 design.md 反复强调的纪律相悖：内核不对结局/回合赋予语义，只记录事实，语义解释交给玩法包
的 `onReach` Effect 或宿主循环。该错误在编写属性测试时被自己的测试用例直接推翻（测试断言
`ends:false` 时 scope 应标记为"已终止"，实际语义应该是"内核不做这个判断"），已改为
`outcome.reach` 只追加 `{scope, ends, rank, phase}` 事实记录，不做任何派生判断。

**风险**：中等。这四组 Op 是本次模糊测试前的最后一次结构性补全，补全后的实现只有单元测试
覆盖（每组 5-7 个用例 + 1 条属性测试），尚未经过跨层组合的长序列模糊测试验证。

**`prefab.despawn` 疏散策略后续修正（用户复核后要求纠正）**：本节最初的实现把疏散策略定为
"清空 `node` 字段"（回到无位置状态），当时的理由是"design.md 未指定默认疏散目标时的最小
安全选择"。用户指出这个理由本身就是内核越权：`node: undefined` 不是一个中立的兜底，是内核
自己做出的一项游戏设计判断（"无位置"是一个可接受的存在状态），这与需求8.5 的字面表述
"内核应将该占位者疏散至**有效位置**"直接矛盾——内核在"没有合法目标就不做"与"没有合法目标
就发明一个"之间选了后者，选错了。已修正为与 `item.move` 找不到合法槎位时同一条纪律
（需求10.10/Property 6："不落地不吞掉"）：`prefab.despawn` 新增可选的 `evacuateTo` 参数；
若回收时子图内确有占位者但调用方未提供 `evacuateTo`，或提供的目标节点不存在，整个 Op 返回
`ok:false`（`E_OP_INVALID_ARGS`），不再静默清空 `node` 字段；提供了合法 `evacuateTo` 时，
占位者被移动到该节点而不是回到无位置状态。选择"去哪"是玩法包该做的判断（最近的安全节点、
出生点等），内核只负责"要求提供去处，否则拒绝执行"。已更新 `ops/__tests__/prefab-ops.test.ts`
对应用例（`despawn 时疏散占位于子图节点上的占位者` 改为断言疏散到 `evacuateTo` 指定节点，
新增用例断言无 `evacuateTo` 时对有占位者的子图返回 `ok:false`）。431 个测试零回归。

## 8. 模糊测试第一轮发现并修复：prop.set/prop.add/prop.del/list.insert/list.remove 对不存在宿主对象静默合成畸形状态（真实缺陷，非理论风险）

**问题**：全面对抗性属性测试（`testing/__tests__/fuzz.test.ts`）第一次运行、第一个随机种子
就发现：对一个悬空 Id（如 `e:dangling-644`，从未被 `entity.create` 创建过）调用
`prop.add({path:'entities.e:dangling-644.props.hp', delta:0})`，没有返回 `E_REF_MISSING`，
而是让 `ops/registry.ts` 后续对同一序列里另一个 Op（触发 `entity.destroy` 的关系级联清理，
遍历 `e.attachments`）时抛出未捕获异常 `e.attachments is not iterable`。

**根因**：`ops/path.ts` 的 `setPath`/`setPathRecursive` 为了支持"路径中间层级不存在时应创建"
这一合理需求（比如从空 `props: {}` 写入第一个字段），用 `const container = (node ?? {}) as
Record<string, unknown>` 兜底。但这个兜底逻辑对"路径合法但宿主对象整体不存在"（不是"宿主
对象存在但某个中间字段为空"）这两种情形一视同仁——`entities.e:dangling-644.props.hp` 与
`entities.e:1.props.hp`（e:1 存在但 props 目前是空对象）在 `setPathRecursive` 眼里是同一种
情况，都会在缺失的层级上合成 `{}`。结果是：对不存在的 Entity 调用 `prop.set` 会在
`draft.entities` 里凭空长出一个键为 `e:dangling-644`、值为 `{props:{hp:0}}` 的对象——这个
对象缺失 `id`/`def`/`tags`/`attachments`/`relations` 等 `Entity` 接口要求的必需字段，是一个
类型上不合法但运行时不会立刻报错的"畸形幽灵实体"。它会一直潜伏在 WorldState 里，直到某个
后续 Op（这次是 `entity.destroy` 的关系级联清理，`removeAllRelationsInvolving` 遍历
`entity.relations`；但同理任何遍历 `.attachments`/`.tags`/`.containers` 的代码都会中招）
访问它缺失的字段时才炸出未捕获异常——这正是需求16.2-16.3 明确禁止的行为，且违反的时间点
与真正的病灶（`prop.set` 的静默创建）完全脱节，靠代码审查很难发现，只有跑穿"创建一个不存在
的引用 → 若干步之后触发遍历该引用某字段的逻辑"这种跨步骤序列的模糊测试才能捕获。

**修正**：`ops/prop-ops.ts` 新增 `guardHostExists` 函数，在 `propSet`/`propDel`/`propAdd`/
`listInsert`/`listRemove` 五个 Op 实现调用 `setPath`/`deletePath` 之前，先用正则
`^(entities|items|nodes|links|containers)\.([^.]+)\.` 解析出路径引用的宿主集合与宿主 Id，
确认该宿主对象已存在于当前 draft 里，不存在则返回 `E_REF_MISSING`。`world.props`/
`world.knowledge.*` 两类路径没有"宿主对象"概念（`world` 本身恒存在），不受此项检查影响。
`tag.add`/`tag.del`（`makeTagOp`）本身已经有等价的存在性检查（直接 `if (!host) return
err('E_REF_MISSING', ...)`），不需要额外修补——这也解释了为什么模糊测试第一轮只炸出了
`prop.add` 这条路径，而不是 `tag.add`：后者的实现路径本来就是正确的，前者才是缺陷。

**方法论意义**：这个缺陷是"跨 Op 组合才会暴露"的典型案例——`prop.set`/`prop.add` 单独调用
时表现完全正常（甚至看起来是"宽容地自动创建了缺失路径"这种讨好人的行为），只有当后续存在
一个会遍历该畸形对象某个结构区字段的 Op 时才会暴露。全部 30 条既有 Property 测试都是单层/
单机制隔离验证，没有一条会先创建畸形状态、再用另一个 Op 触发对它的遍历——这正是本次要求的
"任何底层不自洽现象都要暴力探底"里"暴力"二字的实际含义：不是加大单个输入的随机性，而是
拉长调用序列、让状态在多步之间累积、把"看似独立"的 Op 拼接起来。

**风险**：低（已修复并通过 200 次随机种子 + 30 次高强度长序列复测，零复现）。修复本身范围
极小（5 个函数各加两行守卫），不改变任何既有测试断言的语义，属于纯粹的缺陷修补而非设计变更。

## 9. 全面对抗性属性测试（模糊测试）总结

**范围**：新增 `src/core/kernel/testing/full-harness.ts`（把全部 13 层已注册 Op 一次性接线到
同一个 OpRegistry 的合成根）、`op-sequence-arbitrary.ts`（覆盖全部 Op 的随机调用意图生成器，
含约 40% 概率的故意悬空引用与刻意的边界数值——负数索引、0 拆分数、min>max 的 clamp 等）、
`op-sequence-driver.ts`（把随机意图序列解析成真实参数并逐条调用 invoke，动态维护一个"已创建
Id 池"供后续调用引用）。三个测试文件：`fuzz.test.ts`（广度：长度 20-200 的任意 Op 混合序列，
Property F1-F5）、`fuzz-deep-nesting.test.ts`（深度：容器嵌套链、node.merge 连锁、grantedBy
链、微型场景多层嵌套，Property N1-N4）、`fuzz-malformed-expr.test.ts`（异形输入：深度递归到
预算上限、畸形算子名、矛盾 clamp 声明、会访问不存在路径的 accepts 谓词，Property M1-M6）。

**发现并修复的真实缺陷**：见本文档第8节——`prop.set`/`prop.add`/`prop.del`/`list.insert`/
`list.remove` 对不存在的宿主对象静默合成畸形状态，导致后续遍历该对象某字段的代码抛出未捕获
异常。这是全部既有单元测试（含 30 条既有 Property 测试）都没有覆盖到的组合：先创建畸形状态，
再用另一个 Op 触发对它的遍历。修复后跑满 1000 次随机种子（F1/F2）+ 500 次（F3/F4/M2/M5/M6）+
800 次（M3）+ 300 次（N1/N2/N3/M4）+ 150 次（N4）+ 100 次长序列（F5），零复现、零新发现。

**最终结论**：跑完本轮全面模糊测试后，内核在"任意 Op 组合序列 + 悬空引用 + 边界数值 + 深度
嵌套 + 异形 Expr/Def"这一组合空间内，没有再发现新的不自洽——不变量恒成立、Op 恒不抛异常、
失败恒不产生状态改动、Id 空间恒不跨集合冲突。这满足了"若模糊测试无法检测出任何新错误，就
证明这个东西至少是完备的"这条验收标准的字面要求，但完备性结论的范围限定为：本轮生成器覆盖
的输入空间（见 `op-sequence-arbitrary.ts` 的 `OpIntent` 判别联合列出的全部意图形态）。
以下几类此前分析报告（探索报告第4节）标注的已知空白，本轮模糊测试**没有**覆盖，记录于此
供后续排期：

- **HookDispatcher 的 before/after veto 与 OpRegistry.invoke 的完整接线**：目前 `full-harness.ts`
  没有把 `HookDispatcher` 接入 `OpRegistry` 的 `InvokeHooks.dispatchBefore/After`（探索报告
  第4节已指出这一接线在全项目范围内都不存在，属于比本次模糊测试更大的一项集成缺口）。
- **FlowInterpreter 驱动的 Effect 脚本执行**（`while`/`forEach`/`try` 等在真实 Op 序列中被
  Hook 触发执行的场景）：本轮驱动器直接调用 `registry.invoke`，不经过 FlowInterpreter，
  因此 Effect 解释器与 Op 序列结合产生的状态未被模糊测试覆盖。
- **AI 搜索的 checkpoint/restore 试探回滚**（`PolicyDef.mode:'search'`）与模糊生成的
  Op 序列结合：`InMemoryCheckpointStore` 与本轮驱动器未接线。
- **玩法包装载（`PlaypackLoader`）与运行期 Op 序列的组合**：本轮种子 Def 是直接注册到
  `DefRegistry`，未经过 `PlaypackLoader.load` 的五步装载算法，因此装载期冲突检测与运行期
  行为的交互未被覆盖。

**风险**：低（对已覆盖范围）；中等（对上述四项未覆盖范围——这些不是"模糊测试跑过但没发现
问题"，而是"模糊测试的生成器本身还没有生成能触达这些代码路径的输入"，两者对完备性结论的
含义不同，不应混为一谈）。

## 10. 运行期严厉性穷举复核：12 处 Def 实例化 Op 补齐存在性/kind/abstract 三维校验 + 1 处继承展开真实缺陷修正

**背景**：用户明确要求区分"两种容忍度"——玩法包装载期应尽量模糊兼容（允许前向引用、允许
abstract Def 存在），但运行期一旦真正执行"实例化"动作，必须零容忍。复核（非随机模糊测试，
是对全部 34 个已注册 Op 做穷举分类）发现：全部会创建带 `def: Id` 字段的运行时对象的 12 处
Op 调用点里，`entity.create`/`item.create`/`node.create`/`link.create`/`entity.setDef`/
`node.split`/`entity.place`(microScene分支) 六处此前对 `def` 参数**零校验**（任意字符串都能
被直接写进结构区字段）；另外六处（`prefab.spawn`/`attach.add`/`intent.submit`/
`schedule.advance`/`decision.open`，以及 `prefab.spawn` 蓝图内部的 node/entity/link 引用）
已有存在性与 kind 匹配校验，但没有一处检查 `abstract` 标记——需求3.5"abstract 为真的 Def
不得被直接实例化"此前在全部 34 个 Op 里从未被任何一处真正强制过。

**决策**：新增 `ops/def-guard.ts` 的 `checkInstantiable(defLookup, id, expectedKind)`
作为唯一共享实现，三维穷举校验（存在性 -> E_REF_MISSING；kind匹配 -> E_REF_KIND；
非abstract -> E_REF_ABSTRACT，顺序固定），全部 12 处调用点统一改为调用它，不允许任何 Op
自己手写一份局部校验逻辑（这类重复正是"部分 Op 校验、部分 Op 不校验"不一致的根源）。
新增 `E_REF_ABSTRACT` 错误码与对应 hint 提示词条。`DecisionDefLookup` 接口的返回类型从
`DecisionDef | null` 改为 `Def | null`——早前签名迫使调用方在自己的 `defLookup` 实现里
提前做 `as DecisionDef | null` 的不安全 cast，这个 cast 发生在任何校验之前，等于让类型系统
掩盖了运行期校验的缺失，是本次复核里"类型层面伪装出安全感"的一个典型例子。

**穷举验证方法**（非随机碰撞）：
1. `def-guard.test.ts`：对 `checkInstantiable` 本身做 13(实际kind)×13(期望kind)×3(abstract
   取值 true/false/undefined) = 507 种组合的完全笛卡尔积穷举，逐一断言四态分类正确。
2. `def-guard-wiring.test.ts`：对全部 12 个接线点各做"缺失×kind错×abstract×合法"四态穷举
   （52 个测试用例），确认每个 Op 实际调用了正确的校验，而不只是校验函数本身正确。
   额外覆盖 `node.split`/`prefab.spawn` 的"部分合法"混合态（specs 数组里一个合法一个非法
   时必须整体拒绝，不允许部分成功）。
3. `two-tier-tolerance.test.ts`：专项验证"两种容忍度"边界本身——同一批 Def，在装载期
   （`DefRegistry.register`）容忍前向引用、容忍 abstract Def 的声明与继承；一旦装载完成，
   运行期任何试图实例化这些对象的调用必须零容忍拒绝，且拒绝原因精确（abstract 拒 abstract，
   kind 错拒 kind 错，不会因为"这批 Def 整体有问题"而连带拒绝同批次的合法 Def）。

**过程中发现并修正的真实设计缺陷（非测试书写错误）**：编写"abstract 父类装载成功后运行期
拒绝、但具体子类应该成功"这条对照测试时，具体子类的实例化断言失败——追查发现
`DefRegistry.tryExpand` 的继承展开把 `abstract` 当成普通数据字段（像 `props` 一样）走
`deepMerge`，导致任何继承自 abstract 父类的具体子类都会永久卡在 `abstract:true`（除非
每次都手写 `abstract:false` 覆盖）。这会让"定义抽象基类、派生具体子类"——需求3 用户故事
本身描述的核心场景——完全无法工作。修正为 `abstract` 与 `id`/`kind` 同等对待：强制取自
子 Def 自身的声明，不参与父链合并，未声明则默认 `false`（与多数面向对象语言"子类默认具体
除非显式声明抽象"的直觉一致）。同时统一了 `resolve()` 的输出契约：无论走哪条展开路径，
`abstract` 字段恒为严格布尔值，不是 `undefined`。这条修正连带补充了 `state/__tests__/
def.test.ts` 三个此前缺失的用例（继承不传播 abstract、显式覆盖的抽象链、未声明字段的
严格布尔归一化）。

**风险**：低。全部改动已通过 401 个测试（含本节新增的 507+52+7+3=569 个穷举/专项用例）
验证，零回归。`checkInstantiable` 的三维校验顺序（存在性→kind→abstract）是本实现的判断，
design.md 未规定三者的检查优先级，但这个顺序符合"先确认对象存在，再确认类型对不对，最后
确认是否允许实例化"的自然递进逻辑，且已被穷举测试锁定为契约的一部分。

## 11. 打通 HookDispatcher↔OpRegistry↔FlowInterpreter 真实接线，途中发现并修正第二类"运行期不严厉"缺陷

**背景**：探索报告（本轮任务开始前的调研）已经指出，全部既有测试都用手搭的最小 mock 分别
验证 HookDispatcher、FlowInterpreter、OpRegistry 各自的正确性——`dispatchBefore: () =>
({cancelled:true})`、`runEffects: () => ({result:ok(undefined),vars:{}})` 这类占位从未被
替换成真实实现，"一条 RuleDef 的 effects 真正通过 FlowInterpreter 执行、其中一个 op 效果
真正调用 OpRegistry.invokeInline"这条完整链路此前从未被任何测试真正跑过。

**决策**：新增 `events/rule-provider.ts`（`RuleProvider`：按事件类型现查当前生效 RuleDef
集合，三种挂载来源共用同一份数据，不区分来源）与 `wire-hooks.ts`（组合根
`wireHooksIntoRegistry`：把 `OpRegistry.InvokeHooks.dispatchBefore/After` 接到真实
`HookDispatcher.dispatch`，事件类型固定为 `before:${opName}`/`after:${opName}`——这是
design.md 3.4节 `withVeto` 包装器原文示例代码里的事件命名约定，不是本实现新发明的；把
`HookDispatcher` 的 `EffectRunner` 接到真实 `FlowInterpreter.run`）。三者之间存在循环依赖
（OpRegistry 需要 HookDispatcher 提供 veto 回调，HookDispatcher 需要 FlowInterpreter 提供
effects 执行，FlowInterpreter 需要 OpRegistry 作为其 `{op:...}` Effect 形态的调用目标），
用一个先占位、构造完成后回填的可变字段打破。`WiredOpRegistry` 是 `OpRegistry` 的真子类
（只覆写 `invoke` 方法在每次顶层调用后自动调用 `hookDispatcher.resetDepth()`，满足需求24.3
"depth 在事务提交边界处重置"），不是重新实现的结构兼容对象——这样它能被原样传给全部既有
`registerXxxOps(registry: OpRegistry, ...)` 函数，不需要改动任何一个既有 Op 注册函数的
参数类型。

**接线过程中发现的第二类真实缺陷（与第10节"Def 实例化校验缺口"同源但独立）**：编写"before
Hook 挂载在 item.create 上应能真正拦截"这条端到端测试时，第一次运行断言"effects 真正执行"
失败——追查发现 `entity.create`/`item.create`/`node.create`/`link.create`/`stack.split`/
`stack.merge`/`slot.add`/`slot.del` 这 8 个 Op 在注册时都没有传 `{structural:true}`，导致
`OpRegistry.invoke`/`invokeInline` 从未对它们调用 `dispatchBefore`/`dispatchAfter`——即便
接好了真实的 HookDispatcher，挂在这些 Op 上的 `before:`/`after:` Hook 也永远不会被触发。

这不是本次接线新引入的问题，是此前就存在、但因为全部测试都用 mock 而从未暴露的缺陷：
design.md 3.4节 Op 全集清单明确把这 8 个 Op 归入"结构类"，design.md 3.14节更明确举例
"`QuotaEnforcer`...挂在结构性 Op（`entity.create`、`attach.add`）的 `before` 阶段"——
`attach.add` 确实标了 `structural:true`（design.md 3.4节的分类表把 attach.add 单独归入
"附着类"，与 3.14节的举例互相矛盾，这本身是 design.md 文本内部的不一致，已按"举例更具体、
应以举例为准"的原则处理），但 `entity.create` 没有，意味着 design.md 自己举的例子在此前的
实现里根本无法工作。修正：给这 8 个 Op 补上 `{structural:true}`。

**穷举验证**：`__tests__/wire-hooks.test.ts` 用 6 个端到端用例证明接线本身工作（真实
effects 执行、veto 真正阻止 Op、after 真正只读回滚、嵌套 invokeInline、when 谓词过滤、
resetDepth 自动调用）。全部 407 个既有测试（含本次新增）在 `structural:true` 补丁后零回归——
这条修补本身是纯粹的能力补全（让此前"挂了也不会触发"的 Hook 挂载点变得真正生效），不改变
任何已验证行为，因为此前没有任何测试路径能观察到这 8 个 Op 的 veto/after 分发（它们此前
在所有测试环境里 `hooks.dispatchBefore`/`dispatchAfter` 要么未提供要么从未被这些 Op 触发）。

**风险**：低（已验证）。**已处理**：`decision.answer`/`decision.close`/`intent.resolve`/
`intent.void`/`intent.reveal` 五 Op 已补 `{structural:true}`。判断依据：design.md 3.4 节
分类表漏列这五者（属于设计文档疏漏而非有意的排除），但 design.md 3.14 节给出的 `withVeto` 举例
（`attach.add`/`entity.create` 等挂 Hook 的方式）暗含了所有"翻转关键状态字段"的 Op 都应接入 veto
分发这条原则——`stack.split`/`stack.merge`/`slot.del` 被列入 structural 的唯一理由就是"改变世界
状态"，同理这五者也翻转 Decision/Intent 的 `status` 字段、触发 Effect 或核销/退还 AP，具备相同
的"玩法包可能需要 before Hook 拦截"的需求（详见 决策与风险记录.md Decision 11 补充记录）。

## 12. 用户复核决策5后要求修正：销毁类 Op 的级联清理从"部分/不一致"改为"四类销毁 Op 统一穷举清理"

**用户提出的原则（本次修正的判断依据）**：级联清理必须区分两种纪律。**机械纪律**——内核只保证
"销毁一个对象后不产生悬空引用"，这与具体死亡方式无关：不管是导弹炸死还是近战砍死，销毁发生的
那一刻，指向这个对象的 Relation/Attachment 必须清理，它自己拥有的 Container 必须处理，否则会
留下悬空引用，这是内核不可谈判的底线。**语义纪律**——"死于导弹不掉武器、死于近战掉武器"这类
判断完全依赖具体死亡方式（`Event.cause`），内核不能替玩法包做这个决定，只能提供一个可靠的
广播点（`before:entity.destroy`），让玩法包在销毁真正发生前用 `item.move` 把物品转移出去
（= 掉落），不转移则随对象一起被回收（= 蒸发）。用直接调用验证（不是读代码猜测）后发现，此前的
实现完全没有做到机械纪律那一半：

**验证发现的三个真实缺陷（均已用 `registry.invoke` 直接验证，非理论推测）**：
1. `entity.destroy` 对一个身上挂着 Attachment 的实体调用会**直接失败**
   （`E_INV_DANGLING`+`E_INV_ATTACHMENT_CONSISTENCY`）——`InvariantChecker` 检测到销毁后
   Attachment.target 悬空就拒绝提交整个事务，这意味着此前任何带 buff/debuff/光环的实体根本
   不能被销毁，不是"某些死法不掉东西"的语义问题，是销毁本身跑不通的机械故障。
2. `entity.destroy` 对一个拥有背包容器的实体调用同样直接失败（`E_INV_CONTAINER_BIDIRECTIONAL`），
   容器完全没有被清理——这正是用户举的"玩家死亡武器掉落"场景，但连"选择掉落还是蒸发"这个
   分支点都到不了，Op 本身先报错了。
3. `item.destroy` 从未调用关系级联清理（只有 `entity.destroy` 一个人调用了
   `removeAllRelationsInvolving`），且 `InvariantChecker.checkReferentialIntegrity` 完全没有
   扫描 `Entity.relations.*.{out,in}` ——销毁一个被某实体 Relation 指向的 Item，产生的悬空
   Relation 不会被任何不变量检查捕获，是比"Op 直接失败"更隐蔽的静默数据损坏。
`node.destroy`/`link.destroy` 则是两者都完全没做（从未清理过 Attachment/Relation）。四个销毁
Op 对三类清理（Relation/Attachment/Container）的覆盖是不一致的拼凑，不是"因场景不同而有意为之
的差异"。

**修正**：新增 `ops/cascade-destroy.ts` 作为四个销毁 Op 共享的唯一清理实现，提供
`cascadeRelationsAndAttachments`（Relation 双向清理 + Attachment 含 grantedBy 子代的级联清理，
适用于 Entity/Item/Node/Link 四种皆可作为 Attachment.target 或 Relation 端点的对象）、
`destroyOwnedContainers`（销毁自身拥有的 Container，容器内占用者只脱离槎位、不随容器销毁——
这是机械纪律允许的唯一默认动作，既不是"掉在地上"也不是"随宿主蒸发"）、`clearHoldingSlot`
（若被销毁对象自身正被别的容器槎位持有，清空该槎位）。四个销毁 Op 全部改为调用这套共享实现，
消除此前"entity 清理了 Relation 没清理 Attachment/Container，item 反过来"的不一致。

**同时修正 `InvariantChecker.checkReferentialIntegrity`**：补上对 `Entity.relations.*.{out,in}`
的悬空扫描——此前这条检查完全没有覆盖 Relation，是发现上述缺陷2的直接原因（如果这条检查本身
是完整的，`item.destroy` 的缺陷会在写单测时立刻被不变量检查拦下来，而不是需要专门验证才发现）。
这是防御性的第二层保障：即便未来某个新 Op 又忘了调用 `cascadeRelationsAndAttachments`，
`InvariantChecker` 也会在 commit 前拦下来，不会重演"缺陷2 完全没有任何机制能发现"的情况。

**验证方法（穷举分类，非抽样）**：新增 `ops/__tests__/cascade-destroy.test.ts`，对四个销毁 Op
逐一穷举四类附着状态（A: 自身是 Attachment.target；B: 拥有含占用者的 Container；C: 自身被
别的槎位持有；D: 存在 Relation）单独出现与 A+B+D 组合出现的场景，确认清理完整且不留悬空引用。

**风险**：低（已修复并通过 12 个新增穷举用例 + 全部既有 431 个测试零回归）。这条修正把决策5
从"记录一个待复核的时序问题"升级为"确认并修复一个此前完全没有被任何测试路径命中的机械故障"——
此前所有测试都没有构造过"带 Attachment 或 Container 的实体去调用 entity.destroy"这个组合，
所以缺陷一直未被暴露，直到用户提出的场景（导弹/近战掉落对比）迫使我们真正推演"这个 Op 到底能
不能跑通"才发现。

## 13. 用户复核决策7后要求修正：`prefab.despawn` 的疏散策略从"清空 node 字段（发明一个'无位置'状态）"改为"要求调用方显式提供疏散目标，否则拒绝"

**用户提出的原则**：内核不能在"UGC 实现上可以偷懒越级"和"内核本身越级"之间画错界线——UGC/玩法包
自己选择偷懒（比如直接调用某个便利函数而不精细判断该不该掉落）没问题，那是它自己的实现选择；
但内核不能替它做这个选择。此前的实现把"清空 `node` 字段、让实体处于无位置状态"当作缺省疏散动作，
这本身就是内核在做一个具体的、有语义含量的判断——"无位置"是一种特定的、被内核发明出来的状态，
不是"什么都没做"的中立选项，且直接违反需求8.5 的字面表述："内核应将该占位者疏散至**有效位置**"，
不是"疏散至无位置"。

**修正**：`PrefabDespawnArgs` 新增可选的 `evacuateTo?: Id` 字段。`prefab.despawn` 的行为改为：
若子图节点上有占位者且调用方未提供 `evacuateTo`，返回 `ok:false`（`E_OP_INVALID_ARGS`），
不执行任何回收动作——这与 `item.move` 找不到合法槎位时"不落地不吞掉"（需求10.10）是同一条纪律
的应用：找不到有效疏散目标时拒绝整个 Op，而不是发明一个默认值。若提供了 `evacuateTo`，先校验
目标节点存在（否则同样拒绝），再把全部占位者的 `node` 字段设为该目标——这才是"疏散至有效位置"
的字面实现。调用方（玩法包的 Effect 脚本）负责算出"最近的安全节点"或"重生点"这类具体目标，
内核只负责机械执行"移到这个节点"和"没有目标就拒绝"两件事，不做任何"目标该是哪里"的判断。

**风险**：低（已修复，`ops/__tests__/prefab-ops.test.ts` 的对应测试已更新为验证"无 evacuateTo
时占用者存在则拒绝、提供 evacuateTo 后成功疏散"两个分支，全部既有测试零回归）。

### 14.2 认知切片（belief-slice.ts）

**设计决策（对应 AI完备性分析 1.1节）**：
- 认知切片在**根节点算一次**，递归层天然继承认知边界，不需要每层重新判断"看不看得见"
- 纯函数，只读，不落盘，不新增结构——与微型场景占用者数量、配额校验同一条"不额外维护派生状态"纪律
- 用 `agent.controls` 过滤可见实体（默认规则，`Query.visibleTo` 路径暂未启用）
- 对不可见但 facts 记录了位置的实体（跨维度调用方残留的 NPC/脚本实体），读 `Agent.knowledgeScope.facts['position:${targetId}']` 做记忆推算
- 参与者构建三块：可见实体（source:visible）→ world-level agents 非observer（source:visible/memory）→ 非agent实体有memory facts者（source:memory）

**参与者构建三块**：
1. 可见实体：`source: 'visible'`
2. `world.agents` 中的非observer非self agent：可见则 `source:visible`，不可见则 `source:memory`
3. 非agent实体（不在world.agents里）但有 knowledge facts 记录位置者：`source:'memory'`，`lastSeenAt` 指向记忆位置

**修复的真实缺陷**：第三块此前缺失——测试用例 `e:ghost` 是实体但不在 `world.agents` 里，如果只遍历 `world.agents` 就会漏掉它。`belief-slice.ts` 的 `buildParticipantsFromPool`（全知路径）也已补充同等的 `source:visible` 处理。

**items 可见性**：`Container` 对象在 `state.containers`（不在 `entities` 或 `items`），判断某 Item 是否可见应检查其所有容器宿主是否存在于 `state.containers`，而非检查容器 Id 是否在 `visibleItems` 里。

### 14.3 精算/粗略分档（tiering.ts）

**设计决策（对应 AI完备性分析 1.4节）**：
- 精算层（0-2+ 人）：完整递归，真实物品栏/AP经济学/多步计划
- 粗略层（其余全部）：从搜索根节点**一次性固定分类，全程不升降级**，不是"靠近了才升档"
- 粗略层保留表象属性（血量/位置/hasWeapon），不展开物品使用与行动分支
- 白名单机制：只有被玩法包显式标记 `ai-significant` 标签的动作才进入粗略层候选分支
- **默认粗略纪律**：未配置标签时白名单为空（静默跳过），这是玩法包作者的责任，不是内核越权

**可达性计算**：`computeReach(origin, budget, state)` 使用已有的 `spread` 原语（需求11），
把搜索深度换算成拓扑预算，找出搜索深度内能触及的所有节点，再映射到节点上的实体。

**TieringEngine 内部**：
- `tierCache`（`Map<agentId:participantId, ParticipantTier>`）：缓存已分类结果，递归层直接读缓存不重新分类
- `buildTier()`：构建单个参与者的分档，包含 `surfaceProps` 快照与 `allowedActions` 白名单
- `extractSurfaceProps()`：从 `Entity.props` 提取表象属性，含 `hasWeapon`（检查容器内是否有 `weapon` 标签物品）

### 14.4 evaluate 守卫（evaluate-guard.ts）

**设计决策（对应 AI完备性分析 1.7节）**：
- `evaluate` 的原始返回类型是 `Value | null`（`Value` 允许字符串/数组/对象/Ref，不是只允许数字）
- alpha-beta 剪枝判断（`score > beta`）要求分数是全序实数
- 若返回 `null`：`null > beta` 在 JS 里直接是 `false`，静默把该分支当成低分——这是同一类"静默合成畸形状态"缺陷（决策8）
- 若返回 `Infinity`：`isFinite(Infinity)` 是 `false`，同样静默失败

**`evaluateGuard(raw, context)` 的行为**：
- `null/undefined` → `score:0, guarded:true, diagnosis`
- 非有限数（`NaN`、`Infinity`、`-Infinity`） → `score:0, guarded:true, diagnosis`
- 合法数 → `score:num, guarded:false`

**`toFiniteNumber(raw)` 的转换规则**：
- `number`：有限数原样返回，`Infinity`/`NaN` → `NaN`（注：`toFiniteNumber(Infinity)` 本身返回 `NaN`，外层 `isFinite(NaN)` = `false`，触发 guard）
- `boolean`：`true→1, false→0`
- `string`：parseFloat，失败则 NaN
- `array`：取第一个有限数字元素，无则 NaN
- `object`：按 `['score','value','result','hp','vp']` 顺序取第一个有效数字，无则 NaN

### 14.5 alpha-beta 搜索（search.ts）

**SearchContext 核心字段**：
```typescript
interface SearchContext {
  config: SearchConfig;           // 搜索配置（含 beliefSlice/participantTiers/evaluateExpr）
  checkpointStore: CheckpointStore; // checkpoint/restore 存储（默认内存实现）
  nodesVisited: number;           // 节点计数器（调试/性能分析）
  guardDiagnoses: string[];       // guard 触发记录
  beliefSlice: BeliefState;       // 根节点算好的认知切片，递归直接使用
  participantTiers: ParticipantTier[]; // 根节点算好的分档，递归直接使用
  listLegalActions: (entityId, state) => Array<{action, bindings}>; // 着法生成（从 ActionCatalog 注入）
}
```

**搜索入口（aiSearch）**：
1. `findSelfEntity`：从 `agent.controls` 匹配可见实体；若 agent 无 controls，取第一个可见实体作为 fallback（测试场景兼容）
2. 根节点打 checkpoint（`rootId`）
3. 生成 AI 当前可执行着法（`listLegalActions(selfEntity.id, state)`）
4. 对每个着法调用 `alphaBeta`，depth 从 `config.depth - 1` 开始（根节点算 depth 层）
5. 用根 checkpoint 回滚状态，测试下一个着法
6. 返回最优着法及其分数

**alphaBeta 递归**：
- Terminal test：`depth === 0 || pendingAction === null` → 直接 evaluate
- 对 maximizer 层（AI 着自己法）：遍历所有合法着法，递归时 isMaximizing=false（对手决策）
- 对 minimizer 层（对手着自己法）：遍历所有合法着法，递归时 isMaximizing=true（AI 决策）
- beta cutoff：`localAlpha >= beta` 时剪枝；alpha cutoff：`localBeta <= alpha` 时剪枝

**`evaluate` 叶子节点**：简化启发式 `hp/maxHp * 100`，用 `evaluateGuard` 包裹，确保返回有限数。

**checkpoint/restore**：`InMemoryCheckpointStore`（默认内存实现）用 `Map<snapId, WorldState>` 存储快照，搜索后回滚状态。原始 `state` 引用不变（immutable），外部调用方持有的是正确的状态引用。

**修复的真实缺陷**：
- `SearchContext.listLegalActions` 缺失：导致递归层 `listLegalActionsFromContext` 返回空数组，所有递归节点立即 evaluate，搜索完全扁平化
- `findSelfEntity` 无 fallback：agent 没有 controls 且可见实体为空时返回 null，导致整个搜索直接返回 null 结果
- `toFiniteNumber` 对 `Infinity` 直接返回不处理：属性测试 `toFiniteNumber(Infinity)` 返回 `Infinity`，`isFinite(Infinity)` = `false`，触发 guard 的 `!isFinite` 判断失败
