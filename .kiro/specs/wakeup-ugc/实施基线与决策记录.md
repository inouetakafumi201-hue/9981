### 1.1.1 工程配置核对（已逐字读取）

| 项目 | 事实 | 证据文件 |
|---|---|---|
| 包管理与模块制 | `"type": "module"`，纯 ESM。相对 import 必须带 `.js` 扩展名 | `package.json` |
| 测试命令（非 watch） | `npm test` → `vitest run` | `package.json` scripts |
| 类型检查命令 | `npm run typecheck` → `tsc --noEmit` | `package.json` scripts |
| Lint 命令 | `npm run lint` → `eslint src --ext .ts` | `package.json` scripts |
| 测试发现范围 | `include: ['src/**/*.test.ts']`，`testTimeout: 20000`，**`globals: false`** | `vitest.config.ts` |
| TS 严格性 | `strict: true`、`noUncheckedIndexedAccess: true`、`noImplicitOverride: true`、`isolatedModules: true` | `tsconfig.json` |
| TS 可选属性语义 | **`exactOptionalPropertyTypes: false`** | `tsconfig.json` |
| 编译目标 | `target: ES2022`、`module: ESNext`、`moduleResolution: Bundler`、`lib: ["ES2022"]`（**无 DOM**） | `tsconfig.json` |
| 类型全局 | `types: ["vitest/globals", "node"]` | `tsconfig.json` |
| 属性测试库 | `fast-check@^3.19.0`（devDependency，已安装） | `package.json` |

**对 UGC 实施的强制约束（由上表直接推出）：**

1. **测试文件必须显式 `import { describe, it, expect } from 'vitest';`**。`vitest.config.ts` 设置 `globals: false`，同时 `.eslintrc.cjs` 只 `extends: ['eslint:recommended']` 且未声明测试全局变量，未显式 import 会同时造成 `npm test` 运行期 `ReferenceError` 和 `npm run lint` 的 `no-undef` 错误。这正是当前唯一既有失败的成因（见 1.1.3）。
2. 生产与测试文件都放在 `src/core/ugc/**`，测试文件名必须以 `.test.ts` 结尾才会被发现。property 测试按 tasks.md 命名为 `*.property.test.ts`，仍匹配 `src/**/*.test.ts`。
3. 所有跨文件 import 必须写 `.js` 后缀（`moduleResolution: Bundler` + ESM 输出约定，与仓库现有代码一致）。
4. `noUncheckedIndexedAccess: true` 意味着所有数组/索引访问结果是 `T | undefined`，UGC 的解码器、图遍历、排序比较必须显式处理 undefined，不得用非空断言 `!` 掩盖。
5. `lib` 不含 DOM，禁止使用 `TextEncoder`/`TextDecoder` 之外的浏览器 API；`types` 含 `node`，`TextDecoder`/`TextEncoder`/`Buffer` 可用（来自 Node 类型）。

### 1.1.2 ESLint 分层规则对 UGC 的适用性

`.eslintrc.cjs` 的 `LAYER_ORDER` 只覆盖 `src/core/kernel/<dir>/**`，`src/core/ugc/**` 不在任何 `no-restricted-imports` override 内。

**结论：ESLint 当前不会阻止 UGC 违规 import `kernel/state`、`kernel/ops`、`kernel/safety`。**
因此 design.md 的 Security invariant 1–4 和 tasks.md 任务 2.4 的架构边界**必须由 UGC 自己的静态架构测试保证**（读取源码文本、断言 import 白名单），不能依赖 ESLint。这是任务 2.4 的实质工作，不是可省略的形式检查。

## 1.2 上游端口契约证据（frozen / unavailable 逐项判定）

判定标准（取自 tasks.md 1.2）：一个端口只有在**同时**满足「被某个 `.kiro/specs` 任务认领为交付物」「有测试证据」「路径与文档一致」时才算 frozen。仅"看起来可用"或"本地能跑"不构成冻结。

### 1.2.1 `JSON_Codec`（基类层统一 JSON 解码 + 规范化）

- **状态：unavailable（未冻结）**
- 候选实现 `src/core/kernel/spec-compiler/json-codec.ts` 的 `StrictJsonCodec`：不被任何 `.kiro/specs` 任务认领为交付物，且不被 `src/core/ugc` 之外的生产代码引用。
- 影响阶段：无。UGC 的 `decode` 与 `canonicalize` 阶段**由 UGC 自身拥有**（design.md 明确把 `StructuralJsonDecoder` 与 `CanonicalizationGateway` 落在 `src/core/ugc/`），因此不存在"缺端口就无法解码"的问题。基类层的 `JSON_Codec` 只在任务 11.1 需要证明"UGC 与基类层用同一 codec"时才成为阻塞项。
- 失败关闭：不适用（UGC 自持）。

### 1.2.2 `Definition_Validator`（统一定义验证器）

- **状态：unavailable（未冻结）**
- 所有者：基类层（`l2-base-layer-spec`）。`src/l2/model/**` 正在写入，`src/l2` 下尚无 validator 实现文件落盘（实测目录只有 `model/`）。
- 必需能力（design.md「Upstream definition ports」逐条）：closed/open Schema、required/type/cross-field、legal Def kind、唯一 ID/override、abstract 实例化、基类层/玩法层归属、全部数值分类、继承环、组合冲突、语义字段严格性、完整错误聚合。
- 影响阶段：`definition-validation` 及其之后全部阶段。
- 失败关闭：`E_LOAD_UNRESOLVED_CONTRACT`，change-set scope，禁止调用 `ReferenceResolutionGateway` 和激活。
- 证据位置：`src/core/ugc/ports/unavailable.ts` 的 `unavailableDefinitionValidationGateway`。

### 1.2.3 `Reference_Resolver`（类型化引用与依赖图）

- **状态：unavailable（未冻结）**
- 所有者：基类层。必需能力：expected kind / semantic family / provider domain 解析、missing/ambiguous/wrong-type、稳定 inbound+outbound 图、变更定义的传递入边闭包、引用环与包环、确定性排序。
- 影响阶段：`reference-resolution` 及之后。
- 失败关闭：`E_LOAD_UNRESOLVED_CONTRACT`。

### 1.2.4 `Definition_Registry`（批量原子注册表）

- **状态：unavailable（未冻结）**，且**现有内核实现明确不满足契约**。
- 必需契约：工作副本（working copy）→ 完整入边重验 → compare-and-swap 发布 → 确定性快照指纹；单次 `activateAtomically` 调用完成 add/replace/remove 全集。
- 现有 `src/core/kernel/state/def.ts` 的 `DefRegistry`（已逐字读取）**不满足**，具体缺口：
  - `register(def)` 是**逐项可变写入**：`this.raw.set(def.id, deepClone(def))` 直接写活动 Map，重复 ID **静默覆盖**，无 override 授权检查。
  - 只做 `extends` 环与 expr `call` 环检测；**无 Schema 校验、无字段类型校验、无引用解析、无入边重验、无层级/数值归属检查**。
  - 注释明说「缺失父定义仍允许作为装载批次内前向引用」——即它接受未解析状态，与 UGC 的"激活前必须完整"相反。
  - 有 `fork()` / `replaceFrom(candidate)`，形状上接近工作副本+发布，但 **`replaceFrom` 无版本令牌、无 expected-baseline 比较、无 CAS、无快照指纹、无依赖图**，因此不是 compare-and-swap，无法承担 `activateAtomically(change, expected)`。
  - **明确禁止**：不得通过 `for (const def of defs) registry.register(def)` 循环伪造原子性。批次中途失败会留下已写入的前缀，直接违反 R13.8。
- `src/class/specification-compiler/` **在当前仓库不存在**（design.md 对其 `AtomicDefinitionRegistry` 的 CAS 描述无法验证）。
- `src/core/kernel/spec-compiler/registries.ts` 的 `InMemorySpecificationRegistry` 未被任何 `.kiro/specs` 任务认领，只能作设计参考。
- 影响阶段：`activation`。失败关闭：`E_LOAD_UNRESOLVED_CONTRACT`（端口缺失）/ `E_LOAD_ACTIVATION_FAILED`（端口存在但提交失败）。

### 1.2.5 关于在途 `src/l2/model/**` 的禁止导入决定（本会话的自主判断，需记录）

`src/l2/model/**` 正在被 `l2-base-layer-spec` 会话写入，其中已出现 `diagnostic.ts`、`diagnostic-codes.ts`、`result.ts`、`json.ts`、`schema.ts`、`def-kind.ts`、`reference.ts`、`family-contracts.ts`、`definition.ts`、`snapshot.ts`、`ordering.ts`、`diagnostic-factory.ts` 等与 UGC 端口高度同名的模块。

**决定：本实施阶段（任务 2–10）一律不 import `src/l2/**`。** 理由：

1. tasks.md 1.2 的冻结判定要求"Spec 认领 + 测试证据 + 路径/文档一致"三者同时成立。该目录正在秒级持续变动，形状随时改变，不满足任何一条。
2. 若现在耦合，UGC 的每个模块都会随对方中间态反复破裂，且会把对方的未完成语义当作已冻结契约固化下来——这正是 design.md「Unresolved Integration Boundaries」第 1 条禁止的"看起来可用就当冻结"。
3. UGC 侧的正确做法是 design.md 规定的方案：定义**最小端口接口 + opaque handle**，用 unavailable adapter 失败关闭，测试用替身（double）。真实接入是**任务 11.1** 的工作，且必须等 l2 端口冻结。
4. 该决定不降低交付标准：它把"是否已接入真实上游"变成一个显式、可审计的门禁状态，而不是隐藏在 import 里的假设。

**后果（必须在验收中如实报告）**：任务 11.1、11.3 的"真实上游集成证据"在 l2 冻结前**无法取得**，任务 11 只能以端口替身完成本地行为验证，不得据此宣称集成完成。

### 1.2.6 `RuntimeCompatibilityGateway`（运行时兼容/生命周期转交）

- **状态：上游能力存在，但 UGC 侧端口需自定义（按 unavailable 处理直到宿主注入）**
- 已核实的上游事实（`src/core/kernel/persistence/persistence.ts`）：存在 `Snapshot`/`takeSnapshot`、`Journal`、`replay`、`CheckpointStore`/`InMemoryCheckpointStore`、`rewind`、`MigrationDef`、`applyMigration`、`compareVersions`、`LogStore`。
- `MigrationDef` 的形状为 `readonly transform: (state: WorldState) => WorldState`，即**可信宿主代码**。`applyMigration` 在 transform 抛出时返回原状态（Property 28）。
- **铁律**：候选 JSON **绝不可**转成 `MigrationDef.transform`。文档 Schema 迁移（UGC 拥有编排、宿主拥有转换函数）与运行时状态迁移（引擎层拥有）是两条不可互通的路径。
- UGC 只调用 `RuntimeCompatibilityGateway.validatePlaypackOrSaveDeclaration` / `rejectActiveMatchReplacement`，保留上游拒绝结果原样，不读写持久化。
- 失败关闭：gateway 缺失时兼容声明返回 `E_LOAD_UNRESOLVED_CONTRACT`；**无兼容声明的候选不触发任何 persistence/lifecycle 调用**。

### 1.2.7 `SchemaVersionCatalog` / `SchemaMigrationGateway`

- **状态：UGC 接入边界拥有编排，可信宿主拥有迁移边**。UGC 侧实现 `schema-migration-graph.ts` + `schema-migration-coordinator.ts`（任务 4.1/4.2）。
- 迁移边由宿主以 `TrustedSchemaMigration`（纯 AST → AST 转换）注册；候选不能声明迁移函数或新边。
- 与引擎层 `MigrationDef` 完全分离，见 1.2.6。

### 1.2.8 `StableFingerprintGateway`

- **状态：需注入，UGC 提供默认实现。** 仓库现有 `hashText`/`hashBytes`/`hashUtf8` 位于禁止导入的 `spec-compiler`，因此 UGC 定义自己的 `StableFingerprintGateway` 端口。
- **默认实现使用 `node:crypto` 的 `createHash('sha256')`。** 这是本会话修正后的判断：初稿曾打算手写纯 TS 哈希以求"零宿主依赖"，但实测 `node:crypto` 已是本仓库既定选择——`src/core/kernel/ai/kernel/state-read.ts:8`（内核生产代码）、`src/l2/model/source-record.ts:1`、`spec-compiler` 的 `registries.ts`/`output-lease.ts`/`filesystem-artifact-store.ts` 以及 `safety/fatal-boundary.ts` 均直接 import 它，且 `tsconfig.json` 的 `types` 已含 `node`。自行实现密码学哈希只会引入一处未经检验的自研实现，与"不走捷径、不特殊化"相悖。端口保持可注入，测试可替换为确定性替身。
- 指纹只表示规范化内容，**不是来源真实性签名**。

## Bug 记录：同一文件的并行 fs_append/fs_write 造成 700 行源文件结构性损坏

**现象**：`src/core/ugc/codec/strict-json-decoder.ts` 一度膨胀到 890 行，其中 712–890 行是
`parseLiteral`/`parseNumber`/`readHex4`/`parseString` 四个方法的**重复副本**，且位于 class 之外，
同时文件末尾多出一个孤立的 `SIMPLE_ESCAPES` 常量。`tsc` 只报一个 `TS1005: '}' expected`，
掩盖了真正的问题（结构错位而非缺一个括号）。

**根因**：在**同一个工具调用块里**对**同一个文件**同时发出多个 `fs_append`（以及一次 `fs_write`）。
这些调用之间没有顺序保证，实际落盘顺序与我书写的逻辑顺序不一致，导致：
1. 后写的方法体落到了 class 闭合括号之后；
2. 一次 `fs_write` 与并发的 `fs_append` 交错，产生了内容重复。

**二次伤害（更值得记住的那一半）**：我据 `Select-String` 的行号定位"重复区从 712 行开始"，
直接 `Set-Content` 截断到 710 行。但那份行号来自**已被并发写入改变过的**文件版本；截断执行时
文件内容已经位移，710 行处并不是重复区的边界，而是 `decode()` 方法的中间。于是我把
`decode()` 的后半段（UTF-8 拒绝分支、扫描器调用、`readSchemaVersion`、`ugcOk` 返回）
连同重复区一起删掉了，把"重复"变成了"缺失"。

**修复**：以**追加**方式补回 `decode()` 缺失的尾部，而不是重写整个文件——因为该模块已存在一份
41KB 的测试（130 个用例），重写会同时失去这份独立校验。补回后 `tsc` 对 `src/core/ugc` 零错误，
`npx vitest run src/core/ugc` 130/130 通过。

**教训（后续必须遵守）**：
1. **绝不在同一个工具调用块内对同一个文件发出多次写操作。** 同一文件的写入必须严格串行：
   一次调用、等结果、再下一次。跨**不同**文件的并行写入是安全的，本次损坏只发生在同名文件上。
2. **基于行号做破坏性截断前，必须在同一次操作中重新读取并校验边界内容**，不能复用上一次
   搜索得到的行号。工作区存在并发写入时，行号的有效期实际上只有几秒。
3. 单个 `tsc` 语法错误不足以判断损伤范围。遇到"只差一个括号"却定位不到时，应先核对文件的
   整体结构骨架（class/function 的起止清单），再动手。
4. 需要写长文件时，优先"一次 `fs_write` 写完整文件"或"串行追加"，不要用并行追加拼装。

### 自主设计判断汇总（design.md 未规定，由本会话决定，需复核）

1. **`UgcResult<T>` 而非复用内核 `Result<T>`**（`model/result.ts`）。内核 `Result` 失败分支只能带一个
   `code` + `detail`，无法表达"一次返回全部可独立发现的错误"（需求 14.6）和"拒绝必含 error 级诊断"（需求 14.5）。
   `ugcReject` 在诊断集合不含阻断级诊断时追加 `E_LOAD_DIAGNOSTIC_FAILURE`，把该不变量变成结构性保证。
2. **类型与行为分离，model 作为依赖 DAG 唯一根**。design.md 的模块 DAG 把 `quota`、`codec`、`canonical`
   等既当类型持有者又当行为持有者，直接实现会产生 `model ↔ quota`、`ports ↔ canonical` 双向依赖。
   本实现把纯类型（`QuotaBudget` 接口、`JsonAst`、`CanonicalCandidate`、`IntegrationContractSnapshot` 等）
   收进 `model/`，行为留在各功能模块，行为模块之间的依赖方向与 design.md 一致。
3. **`diagnosticCatalogVersion` 由内容派生**（§1.3.5），不用手写常量。
4. **默认指纹实现使用 `node:crypto` SHA-256**（§1.2.8 已修正）。
5. **深度配额按峰值而非累计计量**（`DepthTracker`）。按累计计量会让"宽而浅"的合法文档
   （如 1000 个兄弟对象各深 2 层）累计出与真实结构深度无关的巨大深度用量而被误拒。
6. **`Diagnostic.messageKey` 编码为 `ugc/<stage>/<category>/<condition>`**。它同时充当稳定 reason class
   （跨来源等价比较用）和 `DiagnosticSink.diagnosticDedupKey` 的去重维度，比自由文本 message 精确。
7. **任务 3.3 由关键字黑名单改为端口委托**。详见 `prohibited-construct-gate.ts` 顶部注释：
   纯 JSON 本身不含可执行构造，"禁止构造"只在相对某个赋予成员名语义的 Schema/效果契约时才成立；
   硬编码 `set`/`for`/`while` 之类名字会误报本引擎**已登记**的声明式效果（`while`+`maxIter`、`prop.set`）。
   契约不可用时失败关闭，不退化为猜测。

### Bug 记录（补充）：并发写入工作区时，单次测试失败不可直接采信

**现象**：任务 4 完成后运行全量 UGC 套件，`strict-json-decoder.test.ts` 报 4 个失败，其中两个是

## 关键发现：wakeup-ugc 与 l2-base-layer-spec 存在架构级冲突（需人工裁决）

复查 `src/l2`（此刻仍在被写入，`registry/definition-registry.ts` 距今约 2.5 分钟前修改）后发现，基类层
并未按 wakeup-ugc `design.md` 约定的"四个离散冻结端口"形状实现，而是走了**另一套架构**。这不是
"端口还没冻结"，而是"两个 Spec 对同一职责给出了不兼容的设计"。

### 两套设计的实际形状对比

| 维度 | wakeup-ugc（本 Spec） | l2-base-layer-spec（实际落地） |
|---|---|---|
| UGC 职责 | UGC 是**薄接入边界**，消费基类层的四端口 | 基类层**自带**完整 UGC 接入（`src/l2/ugc/ugc-adapter.ts` 的 `fromUgc → parsePackage`） |
| 验证入口 | `DefinitionValidationGateway.validate(request, context, budget) → ValidationStageResult`（离散、可注入、按能力自证） | `validateFullPackage({package, activeNodes, ...})` 内嵌在 `activate` 里，无独立可注入网关 |
| 引用解析 | `ReferenceResolutionGateway.resolve(...) → ReferenceStageResult`（独立阶段） | 并入 `validateFullPackage`，无独立入口 |
| 激活 | `activateAtomically(change: ValidatedChangeSet, expected: ValidationBaseline)`，提交时对基线做 CAS | `activate(active: ActiveRegistry, candidate: DefinitionPackage) → Result<ActivationSuccess>`，纯函数返回新注册表，无 baseline 参数、无 CAS 语义 |
| 工作单元 | 每文档 `CandidateChangeRequest` → branded `ValidatedChangeSet` | 整包 `DefinitionPackage`（definitions/overrideIntent/removals/dependencies） |
| 不可伪造产物 | branded + WeakSet 铸造守卫 | 无此概念，`activate` 直接吃 `DefinitionPackage` |

### 为什么这不能由我单方面适配

把 l2 的 `activate(registry, package)` 桥接进 wakeup-ugc 的 `DefinitionRegistryGateway` 需要：
1. 从 `ValidatedChangeSet` 反造一个 `DefinitionPackage`（形状转换，我在 §1.2.5 已明确推迟）；
2. 决定"我的完整验证/解析流水线"与"l2 的 `validateFullPackage`"的关系——是**双重验证**（我先验一遍、
   l2 再验一遍，语义可能不一致），还是**旁路我自己的流水线**直接委托 l2（那样 wakeup-ugc 的整个端口
   架构就形同虚设）；
3. 把我的 baseline-CAS 提交模型硬套到 l2 的无基线纯函数 `activate` 上。

这三点每一条都是**改变某一个 Spec 语义**的决定，属于 `docs/L0_规范宪法.md` 与两个 Spec 的
"Cross-Spec Contracts Pending Merge / Unresolved Integration Boundaries" 明确要求**人工裁决**的范畴，
不是薄适配器能消化的工程细节。加之 l2 仍在活跃写入，此刻耦合必然反复破裂。

### 结论

- 任务 **11.1 / 11.3 维持阻塞**，阻塞原因从"端口未冻结"**升级**为"两个 Spec 架构冲突 + 依赖仍在活跃变更"。
- 我**不会**通过强行 force-fit 适配或旁路自身流水线来"凑"出这两项——那会以牺牲某个 Spec 的完整性为代价，
  违反"不特殊化、不走捷径"与跨 Spec 冲突需裁决的原则。
- 需要人工裁决的问题（择一）：
  1. **wakeup-ugc 消费 l2 端口**：则 l2 需**额外导出**符合 wakeup-ugc `design.md` 的四端口冻结形状
     （离散 validate/resolve 网关 + baseline-CAS 的 `activateAtomically`），wakeup-ugc 再写 11.1 适配器。
  2. **l2 已吸收 UGC 接入**：则 wakeup-ugc 的 11.1/11.3 应被重新定义或归档，因为职责已由 l2 承担；
     此时应更新 wakeup-ugc 的 requirements/design 以反映"UGC 接入归 l2"，而不是保留一套平行实现。
  3. **两者并存、明确分工**：需要一份跨 Spec 裁决文档界定边界（例如 wakeup-ugc 只做"来源无关的候选
     规范化 + 配额 + 禁止构造前置"，把验证/解析/激活整体委托 l2）。

在裁决给出前，wakeup-ugc 的本地实现（任务 1–10、11.2/11.4/11.5/11.6、12）保持完整、自洽、全绿，
并通过失败关闭端口与替身证明了自身编排逻辑正确；它没有对 l2 做任何假设性耦合。

### 冲突分类结论：结构性问题（详见独立审查报告）

已判定 wakeup-ugc ↔ l2 冲突为**结构性问题**（职责所有权重复），非接口问题。完整分析与裁决选项见
`docs/L_审查报告/跨Spec冲突_UGC接入职责重叠.md`。要点：
- `src/core/ugc/**` 与 `src/l2/ugc/**` 各自独立实现了 UGC 接入这同一职责，两个 Spec 都声称"唯一统一入口"。
- 接口差异（`activate` vs `activateAtomically`、`DefinitionPackage` vs `ValidatedChangeSet`）可桥接，
  但重复的**职责所有权**桥接不了，且 R13 的 baseline-CAS 安全属性在 l2 侧不存在。
- **立即停止**：在两处并行发展 UGC 接入；扩张 `src/l2/ugc` 独立接入角色；写 11.1 桥接适配器；
  把任一方宣称为"唯一入口/已完成"。
