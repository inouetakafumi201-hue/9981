# 架构决策原则

## 一、解耦优先、基层长远（2026-08-08 确立）

面对跨层 / 跨 Spec 的取舍，**优先选择解耦更彻底、对基层更长远稳定的方案，即使短期工程量更大**。

判定顺序：

1. **解耦程度**：哪个方案让双方能独立演进、改动一侧不波及另一侧？
2. **基层长远稳定**：引擎层 / 基类层的决策以"上层可长期复用、可独立演进"为准绳。
   不为上层的短期便利牺牲基层边界清晰度。
3. 只有在 1、2 打平时，才比较短期工程量。

### 由此推出的具体做法

- **依赖端口，不依赖内部形状。** 当依赖方仍在活跃变更时，不要写"适配它当前内部实现"的适配器——
  那个适配器本身就是新的硬耦合。正确做法是**发布稳定端口契约**，由被依赖方实现。
- **契约要机器可校验。** 跨 Spec 边界除文档外，应有编译期/运行期可断言的契约件
  （参考 `src/core/ugc/integration/l2-port-contract.ts` + 其测试）。
- **零耦合要有守卫。** 用测试断言"尚未耦合"，防止有人提前绑定到未冻结依赖
  （参考"has zero coupling to src/l2 while the base layer is unfrozen"用例）。
- **不跨 Spec 改别人的交付物。** 需要对方改动时，写成**交接项**，不直接动对方目录。

### 反面模式（禁止）

- 为了"让任务能勾选完成"而 force-fit 适配、或旁路自己的验证流水线去迁就对方架构。
- 在两处并行实现同一职责，然后用适配器把重复"连起来"——那会固化重复。
- 把"替身/默认值通过"当作集成完成。

## 二、职责重复优先按结构问题处理

发现两个模块/Spec 实现了同一职责时，先判定是**结构问题**（职责所有权重复）还是**接口问题**
（同架构、异签名）。结构问题必须先做所有权裁决，**不能**用适配器绕过；接口问题才适合适配。

判据：若两处都自称"唯一入口 / 唯一权威"，则一定是结构问题。
