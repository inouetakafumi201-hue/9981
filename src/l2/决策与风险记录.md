# L2 基类层实现 — 决策与风险记录

> 本文件记录实现 `l2-base-layer-spec` 时相对 design.md 做出的自主设计判断、
> 理解性补充，以及未完成/需后续关注的事项。宪法与 spec 是权威；本文件只记录"实现如何落地"。

## 一、相对设计的自主判断（Design 补充）

### D-L2-001：标识符用 `string` + 校验，而非 branded type
候选定义来自手写 JSON / UGC 解析结果，进入模型前全是 `string`。用名义类型会在每个解析
边界产生大量无语义强制转换，反而削弱"校验是唯一真相源"。与 L1 `state/ids.ts` 同风格。
形状由 `isWellFormedId` 保证；不设长度上限（无权威来源，Requirements 5.12 禁止臆造常量）。

### D-L2-002：编译入口签名调整为 `compile(statements)`
design.md 的 `Source_Record` 只含追踪元数据，不含"被主张的内容"，无法被裁决。
实现把可裁决单元建模为 `SourceStatement`（内嵌其 `SourceRecord`）。裁决语义不变。

### D-L2-003：`semanticFamily` 用 `SemanticFamilyReference` 而非内嵌完整登记体
每个定义都内嵌完整登记体会导致同族 N 个定义出现 N 份可能矛盾的登记理由。
改为：始终携带 `familyId`，仅"首次提议新族"时内嵌 `registration`（三判据证据 + Source_Record）。
保留设计意图（新族须随定义提交分类理由与来源），消除矛盾风险。

### D-L2-004：`Definition_Package` 新增 `removals`
design.md 只有 `overrideIntent`，但 Requirements 12.10–12.11 与任务 5.1 要求处理删除。
`removals` 与 `overrideIntent` 对称：都先进候选工作副本再重验入边依赖。

### D-L2-005：违规检测面字段
family-contracts 与 definition 上保留 `concrete*`/`named*`/`embedded*`/`ownerField`/
`representsL1RuntimeTransition`/`differsOnlyByNameOrValue` 等字段。它们不是给合法 L2 定义用的，
而是让越层/伪装声明能被**确定性发现并定位**，避免对任意 JSON 做启发式猜测。合法定义中它们必须缺省。

### D-L2-006：规范化与往返在 `JsonValue` 层
`canonicalize`/`parseCanonical` 作用于纯 `JsonValue`（键排序、-0 归一、拒绝非有限数）。
Property 6 的"等价定义"通过对解析结果再规范化字节比较实现，避免把 typed 解码卷入往返。

### D-L2-007：KernelContract 端口 + cause 回调
L1 `OpRegistry.invoke(name, args)` 目前无 `cause` 形参（H-001 Hook/cause 链缺口）。
`op-registry-adapter.ts` 通过 `recordCause` 回调把 L2 构造的因果链交给宿主记录，
L1 增加形参后只需改适配器，L2 调用点不变。唯一写入通道仍是 `OpRegistry.invoke`。

### D-L2-008：已知族在验证上下文中的登记占位
`buildValidationContext` 对 `KNOWN_SEMANTIC_FAMILY_IDS` 塞入 `undefined` 值占位（靠 `.has` 判定"已登记"）。
这些已知族不需要三判据登记体；只有未知新族才要求 `registration` 并再验三判据。

## 二、Schema 版本与约定
- 声明式 JSON schemaVersion 固定接受 `l2-declarative/1`。
- Paid_Action 恒 1 AP、Attached_Action 恒 0 AP（来源：术语表 Glossary 定义，作为结构约束执行）。

## 三、未完成 / 需后续关注（实事求是）

1. **familyContract 引用的运行时前置条件**：`submit` 只校验动作可解析、目标可见、Op 映射存在、
   Hook 门禁；**未**实现网关运行时判定的逐条前置条件求值（Requirements 6.10 的运行时分支），
   因为 Expr 求值属 L1，L2 只透传 KernelContract 结果。检定/条件网关的"运行时条件失败不调用效果"
   目前依赖 L1 Op 实现返回失败来体现，L2 未额外拦截。属设计边界内的合理留白，接入真实 L1 后需补集成验证。

2. **依赖重验证的覆盖兼容性**：`revalidateDependents` 对"覆盖导致依赖类型失效"依赖引用图的
   kind/family 匹配来发现；未对"覆盖改变了被依赖定义的 Type_Identity 契约细节"做深层语义 diff。
   Requirements 12.6–12.7 的"重验证每个依赖者"已覆盖引用层面，语义契约层面的破坏性覆盖检测是后续可拓展点。

3. **继承字段合并策略**：`union`/`intersect`/`replace` 三种策略目前对参数字段统一取后者
   （`prefer-declared-order` 完整实现）。字段级 union/intersect 的深层合并语义留待有真实用例再细化。

4. **全项目 tsc 与全测试套件的预存失败**：`src/core/kernel/spec-compiler`、`src/class`、
   `src/play`、`src/core/ugc`、`test/properties` 存在**先于本次工作**的失败（运行 `vitest run src`
   即可复现，与 L2 无关，部分为随机种子导致的 flaky）。本次未修复，因不在 L2 范围。
   L2 隔离验证：`tsc -p tsconfig.l2.json`（0 错）、`eslint src/l2`（0 问题）、
   `vitest run test/l2`（80 测试全过）。

5. **Q-01~Q-05 保持未决**：验证器对 `specialTierMechanism`（Q-01）、`interiorMicroSceneBoundary`（Q-04）
   等主动拒绝，不推导默认机制。Q-02（远程两步/枪械一步）不强制序列长度。Q-03/Q-05 只留接口。

## 四、花时间较长的问题（避免重蹈覆辙）

- **"有效"测试定义的悬空引用**：最初 `validActionContract` 等把 effect/pipeline 引用设为
  `required: true`，导致自包含单定义包在**激活**（跑引用图）时报 `REF_MISSING_TARGET` 失败，
  而结构验证（不跑引用图）却通过。教训：区分"结构验证"与"全量激活"两条路径的测试夹具需求 ——
  自包含夹具的对外引用应设 `required: false`，缺失必需引用的场景用 Property 8 的专用夹具单独覆盖。

- **`hook-unavailable` 故障对非 Hook 动作不触发拒绝**：故障注入测试最初用不要求 Hook 的动作，
  导致 `hook-unavailable` 分支下动作照常成功、断言失败。教训：要测某前置条件的失败路径，
  被测对象必须真正依赖该前置条件（改用 `requiresHookIntegration: true` 的动作）。
