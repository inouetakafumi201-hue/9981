# L2 基类层实现 — 决策与风险记录

> 本文件记录实现 `l2-base-layer-spec` 时相对 design.md 做出的自主设计判断、
> 理解性补充，以及未完成/需后续关注的事项。宪法与 spec 是权威；本文件只记录"实现如何落地"。

## 一、相对设计的自主判断（Design 补充）

### D-L2-001：标识符用 `string` + 校验，而非 branded type
候选定义来自手写 JSON / UGC 解析结果，进入模型前全是 `string`。用名义类型会在每个解析
边界产生大量无语义强制转换，反而削弱"校验是唯一真相源"。与 L1 `state/ids.ts` 同风格。
形状由 `isWellFormedId` 保证；不设长度上限（无权威来源，Requirements 5.12 禁止臆造常量）。

### D-L2-002：编译入口签名调整为 `compile(statements)`
design.md 的 `Source_Record` 只含追踪元数据，不含"被主张的内容"，无法被裁决。
实现把可裁决单元建模为 `SourceStatement`（内嵌其 `SourceRecord`）。裁决语义不变。

### D-L2-003：`semanticFamily` 用 `SemanticFamilyReference` 而非内嵌完整登记体
每个定义都内嵌完整登记体会导致同族 N 个定义出现 N 份可能矛盾的登记理由。
改为：始终携带 `familyId`，仅"首次提议新族"时内嵌 `registration`（三判据证据 + Source_Record）。
保留设计意图（新族须随定义提交分类理由与来源），消除矛盾风险。

### D-L2-004：`Definition_Package` 新增 `removals`
design.md 只有 `overrideIntent`，但 Requirements 12.10–12.11 与任务 5.1 要求处理删除。
`removals` 与 `overrideIntent` 对称：都先进候选工作副本再重验入边依赖。

### D-L2-005：违规检测面字段
family-contracts 与 definition 上保留 `concrete*`/`named*`/`embedded*`/`ownerField`/
`representsL1RuntimeTransition`/`differsOnlyByNameOrValue` 等字段。它们不是给合法 L2 定义用的，
而是让越层/伪装声明能被**确定性发现并定位**，避免对任意 JSON 做启发式猜测。合法定义中它们必须缺省。

### D-L2-006：规范化与往返在 `JsonValue` 层
`canonicalize`/`parseCanonical` 作用于纯 `JsonValue`（键排序、-0 归一、拒绝非有限数）。
Property 6 的"等价定义"通过对解析结果再规范化字节比较实现，避免把 typed 解码卷入往返。

### D-L2-007：KernelContract 端口 + cause 回调
L1 `OpRegistry.invoke(name, args)` 目前无 `cause` 形参（H-001 Hook/cause 链缺口）。
`op-registry-adapter.ts` 通过 `recordCause` 回调把 L2 构造的因果链交给宿主记录，
L1 增加形参后只需改适配器，L2 调用点不变。唯一写入通道仍是 `OpRegistry.invoke`。

### D-L2-008：已知族在验证上下文中的登记占位
`buildValidationContext` 对 `KNOWN_SEMANTIC_FAMILY_IDS` 塞入 `undefined` 值占位（靠 `.has` 判定"已登记"）。
这些已知族不需要三判据登记体；只有未知新族才要求 `registration` 并再验三判据。

### D-ECS-001：ECS 收敛 —— 定义侧校验边界、compositionKind 四形、未注册-op 差异

> 本节记录 ECS 收敛（`.kiro/specs/wakeup-base-layer-ecs`）相对 design.md 的落地边界。
> `diagnostic-codes.ts`、`composition-registry.ts`、`diagnostic-projection.ts`、
> `composition-alignment-rules.ts` 头部均引用本决策号。

**1. ECS 字段不经 decoder 变入 `CandidateDefinition`，规则经 cast 读取。**
`BaseDefinition` 接口用 `parameterSchema`（非 `parameters`）；ECS 新增字段
`parameters`/`compositionKind`/`kernelOps`/`familyId` 不在接口中，`codec/definition-decoder.ts`
构造候选定义时也不解析它们。`composition-alignment-rules.ts` 通过 cast to `Record<string, unknown>`
读取，是该新收敛结构的定义侧 shape 校验入口 —— 目前真实 catalogs 中 `component.*` id 零出现，
是待目录重写的结构约定，而非既有数据会在当前触发的规则。

**2. 定义侧校验四类，op 存在性与许可集合不在其中（H-ECS-03）。**
`Definition_Validator` 在 `/definitions/<n>/` 上做四类形状校验：
`SYSTEM_BINDING_MALFORMED`（parameter 缺非空 name）、`SYSTEM_BINDING_MISSING_KERNELOPS`
（kernelOps 非法形状 / 空 / 缺失 / op 名不合 `namespace.operation`）、
`SYSTEM_BINDING_MISSING_FAMILY`（component.* 缺 familyId）、`COMPOSITION_KIND_*`
（未声明 → `COMPOSITION_KIND_NOT_DECLARED`，非法值 → `COMPOSITION_KIND_INVALID`）。
op **存在性 / 许可集合**（Requirement 3.3）不在 context：`ValidationContext` 无 kernel 引用。
该连接留给族级集成测试对比 `listOpNames()`，既有先例 `space-items-write-channel-rules.ts`
同样只做 op 名格式检查。若收紧许可集合需引擎层补充 op 注册证据面，属 H-ECS-03 交接项，
本线不直接改引擎层目录。

**3. compositionKind 四形单一权威源。**
`compositionKind` 仅取 `static | transient | modified-explicit | modified-capability` 四形。
规则的 `COMPOSITION_KINDS` 从 `composition-registry.js` 导入（单一权威），不在规则内重复定义。

**4. `MISSING_CAPABILITY_FOR_COMPOSE` 小写值刻意匹配既有 code 字符串。**
`DIAGNOSTIC_CODES.MISSING_CAPABILITY_FOR_COMPOSE` 取小写 `'missing-capability-for-compose'`
（其它 ECS 码为大写）。这是 Requirement 2.6 的既有 code 字符串常量，`ALL_DIAGNOSTIC_CODES`
按字典序稳定排序可容纳大小写混合。该码当前无发射路径，登记以备组合模板校验之需。

**5. diagnostic-projection 边界。**
`diagnostic-projection.ts` 用 `satisfies Readonly<Record<DiagnosticCode, DiagnosticSelector>>`
全枚举 —— 每个 `DiagnosticCode` 都要求 selector，属于机械守卫：新增 ECS 码若漏接 selector
会编译失败。7 个 ECS 码全部落位：`SYSTEM_BINDING_*` → `LAYER_L1_OWNERSHIP/engine-primitive-request`；
`COMPOSITION_KIND_*`、`MISSING_CAPABILITY_FOR_COMPOSE` → `COMPOSITION_CONFLICT/composition-conflict`；
`COMPONENT_ID_CONFLICT` → `IDENTITY_CONFLICT/duplicate-id`。

## 三、未完成 / 需后续关注（实事求是）

1. **familyContract 引用的运行时前置条件**：`submit` 只校验动作可解析、目标可见、Op 映射存在、
   Hook 门禁；**未**实现网关运行时判定的逐条前置条件求值（Requirements 6.10 的运行时分支），

   目前依赖 L1 Op 实现返回失败来体现，L2 未额外拦截。属设计边界内的合理留白，接入真实 L1 后需补集成验证。

   Requirements 12.6–12.7 的"重验证每个依赖者"已覆盖引用层面，语义契约层面的破坏性覆盖检测是后续可拓展点。

3. **继承字段合并策略**：`union`/`intersect`/`replace` 三种策略目前对参数字段统一取后者
   （`prefer-declared-order` 完整实现）。字段级 union/intersect 的深层合并语义留待有真实用例再细化。

4. **全项目 tsc 与全测试套件的预存失败**：`src/core/kernel/spec-compiler`、`src/class`、
   `src/play`、`src/core/ugc`、`test/properties` 存在**先于本次工作**的失败（运行 `vitest run src`
   即可复现，与 L2 无关，部分为随机种子导致的 flaky）。本次未修复，因不在 L2 范围。
   L2 隔离验证：`tsc -p tsconfig.l2.json`（0 错）、`eslint src/l2`（0 问题）、
   `vitest run test/l2`（80 测试全过）。

5. **Q-01~Q-05 保持未决**：验证器对 `specialTierMechanism`（Q-01）、`interiorMicroSceneBoundary`（Q-04）
   等主动拒绝，不推导默认机制。Q-02（远程两步/枪械一步）不强制序列长度。Q-03/Q-05 只留接口。

## 四、花时间较长的问题（避免重蹈覆辙）

- **"有效"测试定义的悬空引用**：最初 `validActionContract` 等把 effect/pipeline 引用设为
  `required: true`，导致自包含单定义包在**激活**（跑引用图）时报 `REF_MISSING_TARGET` 失败，
  而结构验证（不跑引用图）却通过。教训：区分"结构验证"与"全量激活"两条路径的测试夹具需求 ——
  自包含夹具的对外引用应设 `required: false`，缺失必需引用的场景用 Property 8 的专用夹具单独覆盖。

- **`hook-unavailable` 故障对非 Hook 动作不触发拒绝**：故障注入测试最初用不要求 Hook 的动作，
  导致 `hook-unavailable` 分支下动作照常成功、断言失败。教训：要测某前置条件的失败路径，
  被测对象必须真正依赖该前置条件（改用 `requiresHookIntegration: true` 的动作）。

#### 5.2.5 `queryActions` 悬空结论

- 权威实现 owner：引擎层 `src/core/kernel/actions/catalog.ts::ActionCatalog.queryActions(actor: Ref, mode: 'ui'|'ai'): LegalAction[]`。UI 与 AI 共用同一实现；mode 只改变 target 展开粒度。
- `src/l2/adapters/ai-adapter.ts::legalActionsOf` 只遍历 `policy.requiredActionRefs` 并从活动定义构造 `AiLegalAction`，没有调用 `ActionCatalog.queryActions`，也没有执行动作 `require/visible`。
- `src/l2/registry/read-only-projection.ts::createProjection` 只投影 definitions、entities、beliefSlices、visibility 与 fingerprint；没有动作列表或不可用原因。
- `KernelContract` 没有只读动作查询方法；全 `src/l2/**` 无 `queryActions` 消费点。

因此要求 11.7 当前为 **unavailable**。owner 分工：引擎层发布稳定的只读动作查询 provider；L2 `KernelContract` 或独立只读端口承接稳定签名；`read-only-projection.ts` 与 `ai-adapter.ts` 只消费该端口。禁止让 L2 直接依赖 `ActionCatalog` 内部依赖形状，也禁止在 AI 适配器内补第二套判定。

#### 5.2.6 `typecheck:l2` 边界结论修正

`tsconfig.l2.json` 的 root include 是 `src/l2`、`test/l2`、`registry.ts`、`result.ts`，但 TypeScript 会把被 import 的其它文件传递纳入 Program。当前 `space-items-diagnostic-categories.ts` 已 type-import `src/core/kernel/state/error-codes.ts` 且门禁通过，直接证明“import 其它 kernel 路径必然失败”不成立。该配置是窄编译入口，**不是 import 防火墙**。零耦合的机器守卫来自 P12 的静态扫描（只允许 `kernel/op-registry-adapter.ts` 绑定 `OpRegistry`）及模块 DAG 测试；后续新增领域边界要继续用架构扫描或 ESLint import-boundary 断言，不能单独引用 `typecheck:l2` 作为零耦合证据。

### 5.3 错误码与领域诊断等价映射

源码常量真实名称是 `DOMAIN_CODE_MAP`，不是任务文字中的 `CODE_MAP`。它以
`as const satisfies Record<DomainDiagnosticCategory, Readonly<Record<string, ErrCode>>>`
封闭 21 个类别、71 个条件；本轮 `typecheck` 与 `typecheck:l2` 均通过，故每个目标字面量都属于 `ErrCode`。本轮运行时快照：`Object.values(ERR_CODES).flat().length === 127`，拼接前缀后的唯一成员数也是 127。没有缺失映射目标；没有使用 `E_LOAD_UNRESOLVED_CONTRACT` 替代已登记码的路径。

| requirements 措辞 | 既有真实发射码 / 状态 | 领域类别 → 条件 → 已登记码 | 等价关系与 unavailable 结论 |
|---|---|---|---|
| `VALUE_L3_OWNERSHIP`（仅数值差继承） | `INHERIT_GAMEPLAY_VALUE_ONLY_DIFFERENCE`，由 `validateInheritanceTypeIdentity` 发射。通用越层数值仍有 `VALUE_L3_OWNERSHIP`。 | `COMPOSITION_CONTRACT` → `value-only-subtype` → `E_LOAD_NUMERIC_OWNERSHIP`。 | 三者表示同一拒绝原因的不同观察面：L2 规则码、领域类别、共享 ErrCode。 |
