## 一、实现形态与边界

本玩法包是**纯数据**：从磁盘读入文本 → `StrictJsonCodec` 解析 → `decodePlaypack` 严格解码
→ `PlaypackActivator` 激活 → 在通用管道上执行。全过程不含任何玩法专用内核代码。

| 机制 | 表达方式（全部为通用原语组合） |
|------|-------------------------------|
| 行动轮排名 | `world.props.actionTurn.queue` 有序表 + `list.move` |
| AP / SP | `PlaypackDef.pools` 声明 + `pool.*` 通用资源池 Op |
| 投点/行动/清理三相 | `ScheduleDef.phases` + `onEnter`/`onExit`/`roundEnd` |
| 强力骰、逆转、超逆转、招架、完成行动 | `ActionDef` + `CostSpec` + `Intent` |
| 失衡、过载、招架准备、强力骰选择、逆转选择 | `AttachmentDef` |
| 弱点连锁、招架拦截、过载、处决提升 | `RuleDef` + Event + Flow |
| 招架不可见 | `Intent.hidden` |
| 随机 | `random.roll` 命名流（可重放） |

**引擎层 0 追加玩法语义**：内核中不存在 `stamina.*`、`actionTurn.*`、`parry.*`、
`weakness.*`、`dice.*` 之类操作。测试
`declares no mechanic-specific kernel operation` 机械地钉死这一点，并反向校验玩法包
引用的每个带命名空间的 Op 都真实注册。

## 二、文档冲突的采用决议

设计稿内部存在互相矛盾的表述。以下为本包的采用结论与理由；**未采用项不是被忽略，
而是记录在此并给出取舍依据**。冲突决议同时写入
`playpack.json` 的 `props.resolutionPolicy`，与实现同源，避免文档与代码漂移。

| 冲突 | 文档分歧 | 采用 | 理由 |
|------|----------|------|------|
| 常规逆转成本 | 2.3 / 9.2 / 术语表为 `1 AP`；3.5 示例称 `2 AP` | **1 AP** | 三处规则正文一致，3.5 是叙事示例，示例让位于规则 |
| 过载触发点 | 3.4 为"严格大于 5"；术语表为"达到 5 即触发" | **尝试使 SP 严格超过 5** | 若"达到 5"即触发，清理阶段的自然恢复会让任何满体力玩家每回合必然过载，机制自毁 |
| 过载后行动权 | 9.3 同时写"行动权保留"与"未行动则跳过" | **未行动者跳过本回合**；"保留"解释为仍保留观察与被交互的身份 | 两句只有这一种非矛盾读法；3.4 亦写明"失去本回合行动权" |
| 弱点是否必然失衡 | 4.4.2 效果表无失衡；5.4 / 6.4 将失衡列为弱点必然结果 | **必然施加失衡** | 5.4/6.4 是"盾牌唯一破解路径"的机制支点，去掉失衡该路径不成立 |
| 弱点判定形态 | 曾被实现为 10×10 倍率矩阵 | **`DMG_0N` → `WKN_0N` 一对一触发** | 4.2/4.3 是一对一清单，非倍率表；倍率矩阵已删除 |
| 招架成功率 | 未定义 | **条件满足即确定性拦截** | 文档无概率，禁止臆造 `50%` 之类硬编码 |
| 2.4 示例队列 | 示例结果与"提升 1 位"文字相反 | **按规则文字实现** | 示例自相矛盾，规则文字优先 |

### 2.1 排名变化的生效时机（两类，勿混同）

文档 2.4 说"立即生效"，2.3 又把逆转限定在"窗口期"。这两者不冲突，但必须区分实现：

- **行动阶段内的排名变化**（弱点命中、招架成功、处决成功）：规则命中即
  `list.move` 改写队列，立即生效。
- **窗口期选择**（逆转、超逆转、强力骰）：动作在窗口期提交并**立即结算成本**，
  效果以 `AttachmentDef` 挂起，在**下一个投点阶段**兑现为排名与骰值修正。
  这是 2.3 定义的时机（上一回合行动开始后、下一回合投点开始前）的直接落地。

## 三、自主设计与理解性补充

以下内容**文档未规定，由我判断后设计**，需要你确认是否符合意图。

| 编号 | 自主设计 | 说明与理由 |
|------|----------|------------|
| A-01 | ~~**骰子采用 d5，而非文档的 d6**~~ **【已裁决，D-054，原提案被推翻】** | 原提案前提：d6 产出 6 违反宪法四·4.2（玩家可见数值 1-5）。**裁决推翻了该前提**：原始骰点被认定为 Internal_Metric（内部瞬时比较值），仅作为 allocateAp 的输入，不作为玩家可见玩法数值持久展示；玩家可见产出为 AP 与行动顺序，均落在 1-5 内，故不触及铁律。**实现已改回 1d6，与文档 §9.1 一致。** 详见 `resolutionPolicy.initiativeDie`（playpack.json）。 |
| A-02 | ~~**骰点直接作为 AP**：`AP = clamp(骰点 + 强力骰加成, 1, 5)`~~ **【已裁决，见 resolutionPolicy.apAllocation，原提案被取代】** | 原提案采用最简的骰点直取映射。**裁决取代为差值分配算法（allocateAp）**：2 人局最高者 2AP、差 1 得 1AP、差≥2 未分配；3+ 人局唯一最高且领先第二高≥2 得 3AP、并列最高或领先不足 2 得 2AP、差 1 得 1AP、差≥2 未分配。原始骰点不再直接充当 AP。详见 `resolutionPolicy.apAllocation`（playpack.json，基于 wakeup-core-mechanics Requirement 5）。 |
| A-03 | **AP/SP 存于 `world.props.pools`**，由 `PlaypackDef.pools` 声明 | 玩法资源不属于引擎结构区。明确拒绝在 `WorldState` 顶层加 `stamina` 字段 |
| A-04 | **行动轮状态存于 `world.props.actionTurn`**（`queue`/`acted`/`skipped`） | 走通用属性 Op，可 snapshot / journal / rollback / replay；拒绝事务外的调度器对象 |
| A-05 | **战斗事件契约由玩法包自定**：`combat.nearDamage`、`combat.weaknessHit`、`execution.success` 及其载荷字段 | 引擎不定义战斗语义，因此触发这些机制的事件必须由玩法层声明。契约字段记录在 `playpack.json` 的 `props.eventContracts`，供其他玩法包对接 |
| A-06 | **窗口互斥用单选位** `agent.props.windowChoice` | 文档要求逆转/超逆转与强力骰互斥，但未给实现。单选位使互斥成为 `require` 前置条件，而非事后校验 |
| A-07 | **过载恢复计数** `remainingRolls = 2`，每次投点阶段递减，归零即解除 | 落地"下下回合重新加入投点" |
| A-08 | **平局破法**：AP 相同再比 `initiativeTie`（独立命名随机流） | 文档 2.2 说"完全随机"，用独立流保证可重放 |
| A-09 | **清理阶段恢复前先读取上限** | 若直接 `pool.add`，满体力者会因"尝试超过上限"而被自然恢复误判为过载。先 `pool.get` 判断再恢复，避免恢复机制反过来触发惩罚 |

## 四、Bug 记录（含成因，避免重蹈覆辙）

| 编号 | 问题 | 成因 | 修复 |
|------|------|------|------|
| B-01 | **Agent 与 Attachment 的 Id 会碰撞** | `agent.create` 用 `a:${agents数量+1}` 生成 Id，而 Attachment 用共享计数器 `nextId('a')`。两者同用 `a:` 前缀但计数来源不同，先建 1 个 Agent（`a:1`）再建 1 个 Attachment（也是 `a:1`）即碰撞，导致 Ref 解析在两类对象间产生歧义 | `agent.create` 改用同一个 `nextId('a')`，前缀内唯一性由单一计数器保证 |
| B-02 | **JSON 里拿不到 Op 返回值** | `Flow` 的 `op` 效果直接丢弃 `invokeInline` 的返回值，`random.roll` 的骰点无法进入变量，纯数据玩法无法表达"投点→用点数" | `Effect.op` 增加可选 `result` 字段，把返回值绑定为 Flow 变量 |
| B-03 | **Op 发出的事件不触发规则** | 规则分发原先只挂在 `FlowInterpreter.onEmit` 上，走 `ctx.emit` 的 Op 内部事件（如资源池溢出）永远不进规则管道，过载机制无法用声明式规则实现 | 分发下移到 `OpRegistry` 的 `ctx.emit`，Flow 与 Op 的事件汇入同一管道；同时移除 Flow 侧的重复分发，避免同一事件分发两次 |
| B-04 | **钩子载荷与附件目标形态不一致** | `intent.submit` 的 `agent` 是字符串 Id，而 `Attachment.target` 是 `{$:id}` 形式的 Ref。`eq` 直接比较两者永不相等，过载/失衡拦截规则静默失效——**声明了门禁却不生效，是最危险的形态** | 规则内用 `coalesce(get(x,'$'), x)` 归一化，两种形态都能匹配 |
| B-05 | **定义双源** | `FullHarness` 同时维护 `DefRegistry` 与旁路 `defs` Map，玩法包装载只更新前者，各层 Op 的 `defLookup` 读后者，装载后立即不一致 | 统一为单一 `DefRegistry`；`defs` 仅保留只读兼容视图 |

## 五、未完成与待确认（**需要你裁决**）

### 5.1 架构级冲突：同一机制存在两套实现

| 项 | 声明式（本包） | 命令式（并行产出） |
|----|----------------|--------------------|
| 位置 | `src/play/action-turn/playpack.json` | `src/play/action-round/action-round.ts` + `action-round-runtime.ts` |
| 形态 | 纯 JSON 数据，装载即执行 | TypeScript 代码，规则写在编译产物里 |
| 状态位置 | `world.props.pools` + `world.props.actionTurn` | `world.props.play.actionRound` |
| 规则可见性 | 进入 Event/Rule/Hook 管道，可被其他玩法包挂钩、覆盖 | 不进管道，外部无法挂钩 |
| 迭代方式 | 改数据 | 改代码并重新编译 |

两者实现的是**同一份设计稿**的同一批机制（排名、体力+过载、逆转/超逆转、弱点、招架），
但状态存放位置不同，**同时激活会产生两份互不同步的行动轮状态**。

我**没有删除**任何一方：这是架构路线选择，应由你决定。我的建议是保留声明式版本并把
`action-round` 降级为参考实现或删除，理由是宪法五·5.2 要求玩法层可高频迭代且不回溯修改
下层——数据形态才能满足，且规则进入 Hook 管道才可被其他玩法包组合。**在你裁决前，不要
同时激活两者。**
