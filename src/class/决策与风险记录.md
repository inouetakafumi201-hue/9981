## 一、本文档的边界

本文档只记录**基类层**的决策与风险。依宪法二·基类层铁律，基类层实例
**不含玩法数值约束、不含具体玩法规则**，因此本文档同样**不复制任何具体玩法数值表**
（伤害值、血量、状态时长、AP 成本等）。这些值全部属于玩法层，位于
`src/play/profiles/**`，其取舍记录随该处 profile 一同维护。

| 内容 | 归属 |
|------|------|
| 语义类、能力、参数槽的划分依据 | 本文档 |
| 具体实例的数值配置与其冲突记录 | `src/play/profiles/**` |
| 行动轮与体力玩法的机制决议 | `src/play/action-turn/决策与风险记录.md` |

```
src/class/
├── weapons/              # 武器语义类（无数值）
├── items/                # 物品语义类与能力
├── statuses/             # 状态语义（无时长、无数值）
├── npcs/                 # NPC 语义类与能力
├── vehicles/             # 载具语义类与能力
├── damage-types/         # DMG_01..DMG_10 伤害语义
├── vulnerability-types/  # WKN_01..WKN_10 弱点语义
├── schemas/              # JSON Schema
└── 决策与风险记录.md
```

## 二、核心设计决策

| 决策 | 内容 | 理由 |
|------|------|------|
| D-001 | 实例不含玩法数值约束 | 霰弹枪不写"伤害=3"，只声明谱型与伤害语义 |
| D-002 | 实例不含具体玩法规则 | 霰弹枪不知道自己出现在哪种玩法模式 |
| D-003 | 实例可组合、可继承、可扩展 | 支撑 UGC 与玩法层高频迭代 |
| D-004 | 具体实例与数值下沉玩法层 | 同一基类可被多个玩法包以不同数值复用 |
| D-005 | 伤害与弱点采用独立编号语义目录 | `DMG_01..10` / `WKN_01..10` 各自独立，映射关系属玩法层 |

### 2.1 三层迁移（2026-08-07 完成）

此前基类层 JSON 内直接写入了具体玩法数值，违反宪法二·基类层铁律。已完成迁移：

| 原位置（含数值） | 迁移后 | 基类层保留 |
|------------------|--------|------------|
| `weapons/index.json` 具体武器 | `src/play/profiles/weapons/*.json` | 武器语义类、谱型类、伤害类引用 |
| `items/index.json` 具体物品 | `src/play/profiles/items/*.json` | 物品语义类与能力声明 |
| `npcs/*.json` 具体 NPC | `src/play/profiles/npcs/*.json` | NPC 语义类与能力（FSM 范式属能力，不含阈值数值） |
| `vehicles/*.json` 具体载具 | `src/play/profiles/vehicles/*.json` | 载具语义类与能力 |
| `statuses/*.json` 具体状态配置 | `src/play/profiles/statuses/*.json` | 无值状态语义（无 duration/priority/effects 数值） |

**验证**：`src/class` 下非 schema 的 JSON 已无任何 number 叶值（机械校验）。

## 八、空间族裁决（2026-08-08，接手并行产物）

> 背景：`src/class/scenes/index.json` 与 `.kiro/specs/wakeup-space-items/` 由两个会话并行产出，
> 二者在空间模型上不一致。本节记录三项裁决与其依据。完整论证见
> `.kiro/specs/wakeup-space-items/design.md` 待人工复核项 R-14 / R-15 / R-16。

### 8.1 连接数：基类层只登记天花板，按尺度收紧归玩法层（R-14，改设计不改代码）

| 层 | 登记内容 | 来源 | 强制点 |
|---|---|---|---|
| 基类层 | `structural-bound.scene.connection_limit` = **5** | L0 第五条 五并列原则 | 目录结构边界契约 |
| 玩法层 | `CONNECTION_LIMIT = {large:5, medium:4, small:3}` | `docs/L2_基类层/03_空间系统.md` | `validateMapStructure` → `MAP_CONNECTION_LIMIT_EXCEEDED` |

裁决依据：4 与 3 在 03 号文档中的理由是**空间性格与选择密度**（「毁掉一夫当关的空间性格」），
属地图编排规则，不是拓扑或认知结构的必然。把它们登记为基类层 `Structural_Bound` 会让只有 L2
文档支撑的数值伪装成带 L0 来源的结构边界，并与玩法层形成两份可漂移的表。

因此**原并行产物是对的**，与之冲突的 `wakeup-space-items` 设计初稿已被改正。两层关系新增测试
`src/play/map/__tests__/connection-limit-layering.test.ts`（5 条）钉死：每一档 ≤ 天花板，且至少
一档严格更紧——后者防止分工退化成重复登记同一个数。

### 8.2 微型场景父级：三档尺度均可（R-15，改代码）

原登记令大/中场景 `admitsMicroScene: false`、微型场景 `admittedParentSceneScales: ["small"]`。
该登记与两处已确认内容冲突：

1. `03_空间系统.md`「微型场景的三种创建者」：活体在**大/中场景**移动到空旷地时创建个人微型场景；
   过渡连接在其两侧天然场景各创建一个（两侧可为任意档）。
2. **D-046**：大/中场景「找到 1 AP + 处决 1 AP = 2 AP」，且该 2 AP 是 3 AP 奖励档的价值锚点。
   而「找到 X」的定义就是「来到 X 的微型场景」——父级若限定小场景，大/中场景的「找到」无承载物。

修复：三档 `admitsMicroScene: true` 且均具备 `micro_scene_parenthood`；微型场景父级三档全含。

为保持三档在 `findPseudoSubtypes` 判别键上仍互不相同（原先靠 `parentSceneRef`/`childSceneRefs`
的参数差异区分，见 8.3），新增两项**有来源**的必需能力：

| 能力 | 归属 | 来源 |
|---|---|---|
| `scene.capability.personal_vacant_ground` | 大场景、中场景必需 | 03 号文档「空旷地」表：大/中创建个人微型场景，小场景禁止 |
| `scene.capability.traversal_weight` | 仅大场景必需 | 03 号文档「距离范式」：跨天然场景 +1，**大场景 ×2** |

并新增 `scene.valueset.micro_scene_kinds`（`personal-vacant-ground` / `shared-contact`）：共享模式是
**配置**而非类型身份，两种模式共用同一套父级契约、占用查询与回收语义（对应 L2 要求 5.7）。

### 8.3 天然场景层级：编排期输入，永不进入运行期附属字段（R-16，加固）

发现一个真实的**潜伏严重缺陷**：引擎层以 `Node.parent !== undefined` 判定「是否微型场景」
（`makeEntityPlace` 与 `onMicroSceneOccupantsChanged`）。若天然场景之间的层级被编译进同一字段，
则最后一名占用者离开该天然场景时，它会被按微型场景回收，并**级联销毁其子节点与关联连接**。

当前 `src/play/map/compile.ts` 的 `nodeSpecOf` 只输出 `key/def/props`、不输出 `parent`，因此缺陷
尚未引爆；但 `src/play/map/types.ts` 已把「接通层级」列为待办，接通即会引爆。

加固措施：
- `parentSceneRef` / `childSceneRefs` 全部改为 `required: false`，描述中写明不得编译进运行期附属字段；
- 新增禁令 `prohibition.scene.natural_scene_nesting_in_runtime_parent`（`LAYER_L1_OWNERSHIP`）；
- 新增测试断言这两个参数恒为可选、且该禁令在册。

距离模型**不需要**该层级：「同一天然场景」= 两个微型场景共享同一 parent；「跨天然场景 +1」= 过渡图
距离；「大场景 ×2」= 节点权重。因此保留层级仅为地图编排校验（`MAP_ILLEGAL_SCENE_NESTING` 等）。

> **仍需人工决定**：若将来要让层级进入运行期（`PrefabDef.nodes[]` 增补 parent），必须先把
> 「是否微型场景」的判据从 `parent !== undefined` 改为显式判据，否则上述缺陷立即成立。这条不属于
> 基类层，已登记在 `wakeup-space-items/design.md` R-16。
