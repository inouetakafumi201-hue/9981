## 一、起点：招牌用例是重言式

重建前 L4 的核心用例 `HOOK-2` 跑满 10 万次，断言形如：

```ts
const first = system.collectAndSortInstead(type);
const second = system.collectAndSortInstead(type);
expect(first).toEqual(second);
```

**这个断言对任何确定性、无副作用的比较器都恒真。** 它不检验排序是否正确，
只检验排序是否可重复——而"完全不排序"同样可重复。把实现改成 `return candidates`
（直接返回收集顺序、不排序），这条 10 万次用例依然全绿。

同一文件另有 `fc.uuid()` 生成 ID 的问题（与 L7 相同）：UUID 永不碰撞，
排序的末两级 tiebreak（defId、hookId 相等时才生效）永远得不到表决机会。

这不是"测试写得不够多"，是**断言的形状不对**。断言必须对照独立重写的预期值，
不能对照自己的另一次调用。

## 二、重建的四件套

沿用 L7 已验证的方法，全部**增量添加**，不改动既有文件：

| 文件 | 作用 |
|------|------|
| `test/l4-order-model.test.ts` | 排序影子模型。独立重写 6 级 tiebreak，逐位对照 |
| `test/l4-dispatch-model.test.ts` | 调度影子模型。对照**完整执行轨迹**，非最终结果 |
| `test/l4-invariant-checker.test.ts` | 向私有状态注入损坏，反向验证检查器每条分支真会报错 |
| `mutation/run.ts` + `mutants.ts` | 70 个单点故障变异体 |
| `mutation/equivalence.ts` | 等价变异体差分模糊器（含自检） |

为支撑对照，`src/hook-system.ts` 增加了三处**纯观测面**（不改变任何调度行为）：
`startRecording()/takeTrace()` 执行轨迹、`snapshot()` 结构快照、
`checkInvariants()` 14 项内部一致性校验。

两处关键设计决定：

**轨迹对照强于结果对照。** 调度模型比对 `kind:type:phase:hookId:depth` 的完整序列，
于是阶段顺序、prevent 的中断位置、嵌套深度、被跳过的 Hook 全部变成可观测量。
只比对最终结果的话，这些都藏在同一个"结果相同"背后。

**身份标签强于 id 数组。** 排序末级 `order` 生效时，前几级键必然全部并列——
这意味着参与比较的 id、defId、priority 都相等。此时比对 id 数组，顺序翻转逐字节不可见。
故给每个候选一个**不参与任何排序键**的唯一标签（`Map<HookDef, string>`），比对标签序列。

## 三、发现的产品缺陷：BUG L4#1

**根级 `emit` 的反应态清理不是异常安全的。**

由 `l4-dispatch-model.test.ts` 的"任何场景执行后系统回到干净空闲态"用例发现，
反例极小：同一事件 `A` 上两个 `before` 阶段 Hook，**id 相同**（均为 `h1`），
第一个调用 `ctx.react('A')`，第二个调用 `ctx.emit('A')`。

第二个 Hook 的嵌套 `emit` 触发重入检测抛错，该错误穿透根级 `emit`，
**绕过了 `drainReactions()`**。于是第一个 Hook 排入的反应数据留在队列里，
污染下一次根级 `emit`——`checkInvariants()` 报 `E_INV_QUEUE_LEAKED: queue=1`。

修复：把根级清理放进 `finally`。

```ts
try {
  this.dispatch(type, data);
  if (isRoot) this.drainReactions();
} finally {
  // 根级 emit 无论正常返回还是抛错，都必须把反应态归零。
  if (isRoot) {
    this.reactionQueue = [];
    this.reactionRounds = 0;
  }
}
```

值得记下的是**为什么 48 项既有测试全都漏掉它**：它们各自单独验证"重入会抛错"
和"反应队列会被消费"，但没有一项在**抛错之后**继续检查系统状态。
缺陷只存在于两条正确行为的交界处。这类缺陷靠加用例很难碰到，
靠"每步之后校验全部不变量"的模型对照几乎必然碰到。

## 四、变异测试：全绿之后才是真正的开始

三个新套件写完后全部通过。此时变异测试仍找出 **12 个存活变异体**——
即已经全绿的套件里有 12 处盲区。这与 L7 的结论一致：**通过 ≠ 有效**。

12 个存活者分三类，根因各不相同：

**（1）输入维度缺失（M02/M23/M24/M25）** — 生成器里所有规则的 `on`、`phase`、`when`
都取"会被收集"的值，于是三重过滤的每一条都没被独立考验；`priority` 从不取 `undefined`，
于是 `?? 0` 缺省契约无人验证。修法：让少数规则刻意取"不该被收集"的值，
并按规则逐条断言"该在/不该在候选集里"。

**（2）身份不可观测（M12/M13/M20/M27）** — 即上文的 id 数组问题。改为标签对照。

**（3）并列情形构造不出来（M09）** — 全局 Hook 的 meta 是 `(0,0)`，与 `hand` 容器
slot 0 完全相同。这是**唯一**能让 `defId` 与 `hookId` 彼此独立取值的构造，
也就是唯一能纯粹考验第 4 级 tiebreak 的构造。补上确定性用例。

第二轮 94.12%，第三轮 100.00%。

一条附带发现：**变异体本身也要审查是否语法合法。** M51 原写法只删 `} finally {`,
留下无 catch 的 `try`——那是语法错误，"击杀"来自编译器而非任何测试，属**假击杀**，
反而掩盖了真实盲区。改成语法合法的整块替换后，它被 BUG L4#1 的回归用例真实杀死。

## 五、等价变异体：存活也要给出证据

5 个变异体存活是**正确结果**——它们语义等价，删掉的是当前不可观测的纵深防御。
但"我推理它等价"不是证据。`mutation/equivalence.ts` 用同一确定性 PRNG 生成的
操作序列同时跑原实现与变异体，逐步比对错误、轨迹、结构快照、`ctx.result`、不变量输出。

| 变异体 | 内容 | 结论 |
|--------|------|------|
| M15 | 排序前不复制数组 | 等价（90,000 步无反例） |
| M44 | instead 阶段恒不阻止 default | 等价（同上） |
| M50 | depth 归零时不清理调用栈 | 等价（同上） |
| M61 | drain 结束后不清空队列 | 等价（同上） |
| M64 | 根 emit 不清空上次残留队列 | 等价（同上） |

M50/M61/M64 三处清理是**因为修了 BUG L4#1 才变得冗余**——新增的 `finally`
已保证离开根级 `emit` 时反应态归零。按非破坏性原则，这三处清理**不删**，
它们仍是合法的纵深防御；这里只证明"当前删掉它不可观测"。

### 差分模糊器自己必须先过自检

"跑了 9 万步没发现分歧"有两种可能：真等价，或者模糊器根本没走到变异点。
所以该工具第一步拿 **12 个已知不等价的变异体当哨兵**，必须全部被发现
才允许输出等价结论。哨兵刻意选在待证变异体的**同一代码块**内
（要证 dispatch 的 `finally` 清理等价，就拿同一 `finally` 里的 M49/M51 当哨兵）。

首次自检就抓出两个漏检，两者性质不同：

- **M13（order 级 tiebreak）** — 可修。根因是两个池不相交：全局 Hook 的
  `meta.defId` 取 `hook.id`，物品规则取 `item.def`，池分别是 `h1/h2` 与 `d1/d2`。
  两者在 `defId` 级永远分出胜负，末级 `order` 永远得不到表决机会。
  **池必须故意重叠**——改成 `DEFS = [...IDS]` 后立刻被发现。

- **M46（depth 上限边界）** — 不可修，是随机差分的**固有覆盖上限**。
  需要构造 32 层嵌套 dispatch，而重入锁在 `TYPES×IDS = 6` 个不同帧处即拦截。
  这不能靠换哨兵蒙过去：已在工具里写明该边界由确定性用例覆盖
  （M46/M47/M48 均由 `l4-dispatch-model`/`l4-regression` 的确定性深度用例杀死，
  不依赖本工具），并改用同一代码块内可达的 M49/M51 作哨兵——
  对 M50 的判定力反而更强。

自检通过后，12 个哨兵全部被发现，最快 1 步、最慢 4,250 步。
