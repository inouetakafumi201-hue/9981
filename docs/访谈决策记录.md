### D-001 内核对12_v2十一项"根基缺失"的覆盖定性

- **结论**：内核（`src/core/kernel/`）提供的是通用数据型计算原语（查询引擎、事件分发器、光环/聚合引擎等），理论上足以表达12_根基完备性审查_v2列出的11项缺失（物品堆叠/条件网关/资源池/动态属性/事件系统/查询服务/被动触发/阵营关系/节点状态/视野迷雾/脚本触发器）绝大部分场景，且均有测试用例覆盖。但**内核不实现任何具体玩法语义**——不定义"物品拆分"这样的具体动作，不定义"阵营"这样的具体数值维度。这11项因此不是"内核缺口"，而是**必须在玩法层用内核原语单独设计和实现的上层内容**。
- **涉及文档**：`docs/12_根基完备性审查_v2.md:65-843`（11项清单）；对应内核代码 `src/core/kernel/state/`、`src/core/kernel/topology/`
- **理由**：内核定位是"底层数据型计算内核"，不含语义，这与元机制内核Spec第17章"关键重定位"的说法一致。
- **对下游影响**：后续访谈涉及物品堆叠、阵营系统、事件驱动的任务/成就等具体玩法内容时，讨论范围是"玩法包如何用现有内核原语实现"，不再是"内核要不要补功能"。12_根基完备性审查系列文档需要在收敛阶段做定位澄清（从"审查内核缺口"改写为"梳理玩法层必须覆盖的设计维度清单"）。
- **状态**：已确认

### D-003 顶层设计原则的正确表述与优先级关系

- **结论**：01_核心设计理念_v2.md中的顶层原则列表（当前写作"1.低心智负担优先于可玩性 2.如无必要勿增实体/状态/属性 3.五并列原则 4.结构复用优于功能堆砌"）是**残缺/错误的转录**。正确表述应为四条独立原则，且构成**有先后否决权的层级**（不是简单加权）：
  1. **低心智性**（玩家需要同时维护的独立信息越少越好）
  2. **可玩性**
  3. **复用性**
  4. **常识性**
  
  层级含义：即使一个机制非常符合常识、复用程度很高，只要它持续增加玩家必须维护的状态或污染行为菜单，就应优先删除。可概括为："先保证玩家想得动，再保证玩家愿意想；然后保证学会一次能反复使用，最后才让结果尽量符合常识。"
- **涉及文档**：`docs/01_核心设计理念_v2.md:42-63`（需重写）；原始定义来源 `起床游戏改策略..md:4217-4234`
- **理由**：这是项目最初期就定下的机制审查总纲，01_v2的现有措辞把"低心智负担优先于可玩性"和"五并列原则""结构复用"混在一个列表里，丢失了"可玩性"和"常识性"这两条独立准则，并且弄丢了"否决权层级"这个关键结构。
- **对下游影响**：后续所有机制取舍讨论（02-04等文档涉及的具体设计争议）应统一使用"低心智性>可玩性>复用性>常识性"这个四级否决序，替代01_v2当前的1-4号表述。01_v2需重写"设计原则金字塔"一节。
- **状态**：已确认
- **日期**：2026-08-03

### D-007 体力上限确认5点，强力骰维持2档（+3档暂缓）

### D-038 载具是实体，提供可注册给玩家的半掩体；载具摧毁则掩体消失

### D-052 NPC 默认 1 AP（可配置）；NPC 有 SP 且默认上限 3、开局 0，但不可用于抢轮次

- **结论**：NPC 的资源配置为：
  1. **AP**：**默认 1 AP**，**可配置**
  2. **SP**：**NPC 有体力系统**。其存在目的**纯粹是为了让玩家能在 PVE 中打出弱点甚至过载**
  3. **可配置项**：NPC **是否会主动使用体力**、**体力上限**、**体力数值**均可配置
  4. **默认值**：体力**上限为 3**，**开局体力 0**
  5. **硬性限制**：NPC 的体力**不可能用来抢轮次**（不可用于逆转/超逆转）
- **涉及文档**：`docs/L3_玩法层/05_NPC行为配置.md`（待编写，本条为该文档的核心配置依据）；`docs/L3_玩法层/01_行动轮与体力博弈系统.md`（NPC 无轮次、AP 在玩家轮次结束后顺序行动的既有结论需与此合并）
- **理由**：给 NPC 配 SP 的动机是**让体力博弈系统在 PVE 中可用**——如果 NPC 没有体力，弱点攻击的"对方体力+1"和过载压制就在 PVE 中完全失效，玩家学不到这套机制也无法在打僵尸时练习。上限 3（低于玩家的 5）意味着 NPC 更容易被压到过载，这正是"去杀僵尸"的收益之一。禁止 NPC 用体力抢轮次则守住了既有结论（NPC 没有轮次，统一在玩家轮次结束后顺序行动）。

### D-054 裁决 U-001：投点固定使用 1d6，`wakeup-core-mechanics` Spec 为完全权威

- **结论**：
  1. **投点骰固定为 1d6**：任何时候都投 1d6，不再使用 1d5。这正式裁决 `wakeup-core-mechanics` Requirement 17 未冻结事项 U-001 中"基础投点分布策略"部分——分布来源为一枚六面骰。
  2. **`.kiro/specs/wakeup-core-mechanics/` Spec（requirements.md + design.md）为完全权威**：其 `allocateAp` 差值分配算法、五回合阶段、成本三态、U-002 单人阻塞、结构化拒绝与投影契约等全部条款按原文执行；仅 U-001 的"骰面数"由本决策裁决为 d6，其余未冻结项（U-002、U-003、U-005、T-001、T-002）保持原状态。
  3. **强力骰修正溢出处理**：由于采用"最高点差距结算法"（`allocateAp`），投点原始结果只作为**比较输入**参与差值计算，AP 产出恒为 1-5 合规值（0=未分配，以离散状态呈现），因此基础骰点 + 强力骰修正（+1/+2）即使超过 5 也无需截断/回绕——差值算法只关心相对高低，不关心绝对上界。这一并裁决了 U-001 中"修正结果越过 5 如何处理"的子问题。
- **与 L0 的关系（重要）**：L0 规范宪法第四条限定"玩家可见数值严格限制在 1-5"，同时明确"内部数值例外"。本决策把 **1d6 的原始骰点判定为内部瞬时数值（Internal_Metric）**：它只作为差值结算的输入，不作为持久化的玩家可见玩法数值展示。玩家可见的产出仍严格为 AP（1-3，未分配以离散状态呈现）与行动顺序，全部落在 1-5 内。因此本决策**不构成对 L0 的修改**，无需 L0 手动审批。若未来需要把 d6 原始点数本身作为持久可见玩法数值展示（如 UI 常驻显示骰点 6），则需另行提交 L0 修订审批——本决策不覆盖该情形。
- **涉及文档**：`.kiro/specs/wakeup-core-mechanics/requirements.md`（Requirement 5.2、17 未冻结事项 U-001）；`.kiro/specs/wakeup-core-mechanics/design.md`（3.3 节投点结算、`RollPolicyBinding`）；`src/play/action-turn/playpack.json`（投点相位骰面数与 AP 分配算法）；`docs/L2_基类层/02_游戏机制.md`（最高点差距结算法为 d6 来源）

### D-053 裁决 U-004：批准逆转/超逆转/招架/失衡/弱点破防作为玩法层正式机制

- **结论**：`.kiro/specs/wakeup-core-mechanics/requirements.md` Requirement 17 未冻结事项 U-004（弱点、招架、失衡与隐藏动作组合）正式裁决为**已批准**。以下六项机制被采纳为玩法层标准规则，作为玩法层的最新增加：
  1. **逆转**：消耗 1 AP，行动轮排名 +1，窗口期动作，与强力骰互斥
  2. **超逆转**：消耗 2 SP（体力），行动轮排名 +2，窗口期动作，与强力骰互斥
  3. **处决后行动轮提升**：令其长眠成功后，执行者行动轮排名 +1
  4. **弱点命中**：伤害类型克制暴露弱点时，对方 SP +1、对方行动轮排名 -1、暴露的弱点装备脱落、对方获得 [失衡] 状态；不影响伤害数值本身
  5. **招架**：消耗 1 AP，对他人完全隐藏（真隐藏信息）；被近战攻击命中时生效——免伤 + 攻击者 SP +1 + 攻击者行动轮排名 -1 + 攻击者获得 [失衡] 状态；被远程或过期时静默失效，无动画无提示
  6. **[失衡] 状态**：破除举盾/防御/招架等一切"准备动作"状态，持续到当前回合结束
  实现位置为 `src/play/action-turn/playpack.json` 的 `action:reverse`/`action:super-reverse`/`rule:execution-rank-up`/`rule:weakness-hit`/`rule:parry-intercept`/`rule:parry-must-be-hidden`/`attachment:staggered`/`attachment:parry-ready`/`rule:overload-*` 等 Def。
- **涉及文档**：`.kiro/specs/wakeup-core-mechanics/requirements.md`（Requirement 17 未冻结事项表 U-004、Requirement 7 验收标准第 6 条、Requirement 8 验收标准第 9 条、Requirement 14 验收标准第 8 条，均需同步修订为"已裁决"）；`.kiro/specs/wakeup-core-mechanics/design.md`（3.5 节关于 turnOrder 固定性排除逆转/超逆转/处决提升/弱点/招架排名变化的表述需同步修订）；`docs/L3_玩法层/01_行动轮与体力博弈系统.md`（S6，原始设计来源，第 2.3/2.5/4/5/6 章）
- **理由**：项目所有者明确决策：这套战斗博弈深度机制（逆转/超逆转/处决提升/弱点/招架/失衡）是玩法层的最新增加，应当被纳入标准规则，不受 `wakeup-core-mechanics` 规范此前基于"S6 文档内部自相矛盾、且与 Requirement 7 固定行动顺序冲突"而做出的排除裁决约束。这是对 U-004 的正式重新裁决，裁决权归属项目所有者（S7 访谈决策记录的权威来源地位与 `.kiro/specs/wakeup-core-mechanics/requirements.md` 裁决链中 S7 高于 S6 一致）。

### D-060 并行审计的判定原则：不得以"文档没写"否决已批准机制

- **结论**：所有并行审计、Spec 修订与目录校验一律适用以下三条判定原则。
  1. **授权方向**：玩法层数值与规则**不需要宪法逐项授权**。只要不越层、且玩家可见数值落在
     1-5 内，就是合法的。宪法列出「连接节点数：1-5」是给出**区间**，不是要求每个取值另找来源。
  2. **文档矛盾 ≠ 机制无效**：来源文档自相矛盾时，正确处置是**提请裁决并登记**，
     **不是默认否决**。默认否决等于让"写得乱"变成"禁止实现"，会把已批准的设计反向删掉。
  3. **来源清单不完备 ≠ 无权威**：Spec 的 `S-0x` 来源表是**引用便利**，不是权威白名单。
     `docs/L0_规范宪法.md`、本文件中已确认的决策、各层定稿文档，无论是否被某个 Spec 列入 S 表，
     **都具备其固有位阶**。
- **涉及文档**：`docs/L_审查报告/00_并行产出裁决与整理.md`（本原则的完整证据链与逐条裁决）；
  各 Spec 的"权威来源与适用顺序"章节应引用本条。
- **理由**：本轮核实发现多个并行会话独立犯了同一个错误：把"S 表没列这份文档""两处文档描述不一致"
  当作"该机制违反原则"的充分理由，据此把行动轮争夺、`[失衡]`、体力过载等**已由项目所有者批准的
  最新玩法**判为不得进入默认规则。这三条原则与各 Spec 自己声明的适用顺序
  （规范宪法 → **已确认访谈决策** → 引擎层不变量 → 基类层契约 → 玩法层定稿 → 历史示例）一致：
  已确认访谈决策的位阶**高于**任何 Spec 自身的契约条款，因此 Spec 文本落后于决策时，
  应修 Spec，不是否决机制。
- **对下游影响**：审计报告的职责边界明确为"发现 + 登记 + 提请裁决"，**不含裁决权**；
  裁决只在本文件与 `docs/L_审查报告/00_并行产出裁决与整理.md` 产生。

### D-066 全局颜色语义重新冻结，金银不构成严格评级

- **结论**：全游戏共用一套颜色语义：红=生命减损/伤害/致命危险；蓝=科技/清醒/SP/处决机会；黄=感官/注意/警戒；橙=AP/行动消耗及进度；绿=安全/正面/免费与让利；紫=关系约束/局部菜单替换/远程；珊瑚=近战/格斗/攻击性/暴力；青=社交/交流/经济；灰=冷却/延迟；灰白=中性与高级材质基底。金银仅作少量品级高光，不构成严格评级阶梯。
- **双重分类裁决**：主色取玩家只看颜色时最可能猜中的下一项主要功能；次要语义使用徽章、边缘或文字。商店以青为主、紫表达约束、绿表达折扣；远程瞄准线用紫，命中伤害用红；近战目标用珊瑚，伤害结算用红。
- **灰阶裁决**：灰白与灰色不同；灰色对象仍可点击时用高光、凸起与高级材质感，不可点击态扁平无高光；橙→灰表示冷却。

### D-067 三层仅表示对局规则运行依赖链；表现等系统是正交架构域

- **结论**：随机选择器是引擎层提供的无玩法语义接口，只负责在给定候选与显式随机流下完成选择。AI 性格差异、多维难度 Profile、Temperature/Softmax 权重与行为偏好，是玩法层对该接口的声明式包装；二者是基础接口与上层策略的关系，不互相取代。
- **涉及文档**：`docs/L2_基类层/07_AI系统.md`、玩法包 AI Profile 文档及其 Spec。
- **理由**：底层接口必须保持确定性可重放和语义无关；性格与难度是具体玩法选择，允许玩法包独立迭代。以随机选择器替代性格设计会丢失已认可的上层设计，反向把具体策略塞入底层则会破坏解耦。
- **对下游影响**：基类层可登记 AI 行为类及其可组合契约，但不得固化具体人格数值；玩法层负责声明具体 Profile，并通过稳定选择端口消费引擎能力。
- **状态**：已确认（项目所有者明确裁决）
- **日期**：2026-08-10

### D-071 六类枪械的战术能力定义

- **结论**：确认手枪/步枪/机枪/霰弹枪/狙击枪/冲锋枪的差异化战术能力，作为基类层能力库登记并在玩法层实例化：
  1. **手枪·快拔** `weapon.capability.quickdraw`：背包状态时获得零费动作，可与一只手上的物品交换。
  2. **步枪·架枪** `weapon.capability.mount_weapon`：1AP进入架枪状态，无需瞄准即可对当前位置所有可见敌人射击，移动后自动取消。
  3. **机枪·压制射击** `weapon.capability.suppressive_fire`：命中时对同微型场景所有角色造成1点穿刺伤害，掩体/半掩体内无效。
  4. **霰弹枪·散射** `weapon.capability.scatter_shot`：距离=1时开枪无需瞄准，命中则对目标所在微型场景全部单位造成同等伤害。
  5. **狙击枪·屏息** `weapon.capability.hold_breath`：瞄准状态下花1AP进入屏息，开枪时DC-2，持续到脱离瞄准（切换目标或重瞄不算脱离）。
  6. **冲锋枪·突击推进** `weapon.capability.assault_advance`：射击后、下次AP花费前，获得一次性零费动作【冲锋】进行常规移动。
- **涉及文档**：`src/class/weapons/index.json` 第258-316行；`src/play/profiles/weapons/wp_*.json` 全部6份实例。
- **理由**：项目所有者在早期访谈中明确提出这6种特质，但未形成正式裁决，导致基类层只登记了3个凑数用的装饰性标签（`scatter_attribute`/`sweep_attribute`/`burst_attribute`），玩法层实例未引用真实能力。本次裁决将口头设计落地为可引用的基类能力与玩法参数。
- **对下游影响**：旧的3个凑数能力ID已从玩法实例中移除，替换为上述6个真实战术能力；每个能力在玩法层配有具体参数（AP成本、触发条件、作用范围等）。武器实例的 `actions` 数组需在后续实施中扩展为调用这些能力的具体动作。
- **状态**：已确认并落地（基类层能力已登记，玩法层实例已更新引用与参数）
- **日期**：2026-08-12
