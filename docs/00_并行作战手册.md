# 并行作战手册（Parallel Operations Playbook）

> **用途**：取代"有工作就干"的盲目并行。规定**什么任务才允许并行、怎么派发、怎么追踪、怎么回流**，让并行**稳定、可见、不再制造混乱**。
> **配套**：进度看 `docs/00_主状态板.md`；裁决入口是 `docs/L_审查报告/00_并行产出裁决与整理.md`；行为原则见 `.kiro/steering/架构决策原则.md` 与 `CLAUDE.md`。
> **最后更新**：2026-08-09

---

## 一、根因诊断：上一轮为什么会乱

| 乱象 | 根因 | 本手册对策 |
|---|---|---|
| 报告囤积、互相矛盾 | 审计与并行同时进行，人人产出报告，无统一裁决入口 | **审计只陈述、不裁决**；裁决只进决策记录/裁决入口（§五） |
| Spec 之间架构冲突（如 `src/l2` vs `spec-compiler`） | 两处并行实现同一职责，用适配器连起来固化重复 | **结构问题先做所有权裁决**（架构决策原则 §二） |
| 进度不可知 | `tasks.md` 复选框与现实脱节，多处状态源 | **唯一真相源=主状态板**，以测试为准 |
| 派发即依赖漂移 | 任务在依赖未冻结时就开工 | **任务就绪门**（§二），未就绪不派发 |
| 子会话改了别人的目录 | 无边界约定 | **不跨 Spec 改交付物，只写交接项**（§四） |

---

## 二、任务就绪门（Definition of Ready）——不满足不许派发

一个任务**同时满足以下 5 条**才可进入并行队列（否则标 🔒 未就绪，留在主状态板等待）：

1. **规范已冻结**：任务引用的 Spec/设计/契约在本任务期内不会变动。
2. **依赖已闭合**：所依赖的裁决/端口/上游产物**已存在且稳定**（不是"预计会有"）。
3. **DoD 可机器校验**：完成定义能落到具体命令断言（某测试文件通过 / `tsc` 0 错 / 某契约门禁通过），不是"感觉做完了"。
4. **边界清晰**：明确**只能改哪些目录**、**不能碰哪些目录**、需要别人改的写成交接项。
5. **无隐式跨层耦合**：引擎层改动不与基类层任务并行；文档与其对应代码不拆成两个并行任务（它们需双向对齐）。

> **可并行判据**（CLAUDE.md 并行策略）：多个任务两两之间无依赖 + 各自规范清晰可自主迭代 → 才并行。

## 三、并行 vs Sub-Agent vs 顺序：怎么选

```
任务之间有依赖 / 需双向对齐？
  ├─ 是 → 顺序执行（或拆到无依赖粒度再并行）
  └─ 否 → 规范是否清晰到可自主迭代？
            ├─ 是 → 并行派发（多份完整 Prompt，见 §六模板）
            └─ 否 → 先用 Sub-Agent 收集上下文/探索（不受频率限制）
```

- **/goal 或"不要停"模式下**：禁止用"停下来给用户复制 Prompt"的方式并行；**只能用 Sub-Agent 在当前会话内并行**，不受频率限制。
- **普通模式下**：可输出多份 Prompt 让用户在独立会话并行，同时当前会话继续推进下一个独立任务。

## 四、并行子会话的行为契约（每个派发 Prompt 必须内嵌）

1. **只改声明的目录**；需要别人改的，写成**交接项**记录到主状态板/交接 Prompt，**不直接动对方目录**。
2. **依赖端口，不依赖内部形状**：上游仍在变时，不写"适配它当前实现"的适配器；发布/消费**稳定端口契约**（参考 `src/core/ugc/integration/l2-port-contract.ts`）。
3. **发现职责重复**：先判**结构问题**（都自称权威→所有权裁决）还是**接口问题**（同架构异签名→才可适配）。结构问题**登记并提请裁决，不自行适配绕过**。
4. **发现文档矛盾/未决**：**登记 + 提请裁决**，**不默认否决**已批准机制（D-060）。
5. **收尾必跑三条命令**：`npx tsc --noEmit`、`npx vitest run`（相关范围）、`npm run lint`；不得旁路验证流水线。
6. **禁止**：`// TODO`/占位/伪代码、为过测试打特殊化补丁、把"替身/默认值通过"当集成完成。

## 五、产出回流的唯一路径（防止再次囤积报告）

```
子会话发现 ──▶ 审计报告（docs/L_审查报告/*.md，只陈述事实，★不裁决）
                    │
                    ▼
        裁决入口（docs/L_审查报告/00_并行产出裁决与整理.md）── 汇总、判定
                    │
                    ▼
        决策记录（docs/访谈决策记录.md，D-0xx）── 唯一权威结论
                    │
                    ▼
        主状态板（docs/00_主状态板.md）── 刷新进度与队列
```

- 审计报告**不得**下"违反原则/必须删除"的结论——那是裁决，越权。
- 同一结论只在**决策记录**里有一份权威；其他文档**引用**它，不复述、不改写。

## 六、派发 Prompt 标准模板

每份并行 Prompt 必须包含以下 8 段（缺段即视为未就绪）：

```markdown
## 任务：<PT-xx 一句话目标>

### 1. 背景与意图
<为什么做这件事，属于哪一层，对应主状态板哪个 PT>

### 2. 权威依据（先读）
<L0 宪法相关条 / 决策记录 D-0xx / 冻结的 Spec 与设计文件路径>

### 3. 就绪确认
- 依赖：<已闭合的依赖，逐条列出其"已存在"的证据路径>
- 冻结：<本任务期内不会变的规范>

### 4. 允许改动的目录（白名单）
<只能改这些>

### 5. 禁止触碰（黑名单）
<别人的交付物；需其改动的写成交接项>

### 6. 行为契约
援引本手册 §四全部 6 条。

### 7. DoD（可机器校验）
- [ ] <命令级断言，如：`vitest run <path>` 全绿；`tsc --noEmit` 0 错>

### 8. 回流方式
- 事实 → 审计报告；裁决诉求 → 裁决入口；结论 → 决策记录；进度 → 主状态板交接项。
```

## 八、检查点（每轮并行收束时，主控会话执行）

1. 三条命令全绿？否 → 先收敛再继续。
2. 有没有子会话改了黑名单目录 / 用适配器绕过结构问题？有 → 回退并转所有权裁决。
3. 新产出的报告是否都回流到了裁决入口，没有变成孤立囤积？
4. 主状态板的健康快照、PT 队列、开放事项是否已刷新？
5. 有没有"文档矛盾被默认否决"的情况？有 → 按 D-060 纠正为"登记 + 提请裁决"。
