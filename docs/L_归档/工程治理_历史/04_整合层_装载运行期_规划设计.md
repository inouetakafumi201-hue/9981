## 一、它是什么

### 1.1 宪法给出的空洞

三层依赖链以 `已装载对局` 收束。该链只回答"怎样形成并运行一局规则"：

```text
引擎层（Kernel） → 基类层（Class） → 玩法层（Play） → 已装载对局
```

但全仓没有任何被宪法认可的 `已装载对局` 载体：没有"把三个层组装起来、跑起一局"的**生产组合根**，没有"一局"的量级容器（对局外壳），没有把玩家/UI/AI/地图/运营 接进来的**入口接线**。`loadCoreMechanics` 与测试组合根 `createFullHarness`、装载驱动 `state-machine-load-driver` 都真实存在、也都真实跑通，但它们散在 `testing/` 与 `__tests__/`，是**测试探针**而非生产入口。

整合层就是来填这个宪法空洞的：它是**"已装载对局"这一运行态的生产面**——把三层已有的积木拼成一台可被玩家、AI、地图生产、运营会话共同驱动的对局运行时。

### 1.2 严格边界（这条线绝不能碰）

- 已装载对局是**三层依赖链的终点**，不是第四运行层。整合层不新增规则语义、不引入新的"层"，它只是把三层已声明的规则能力通过既有端口**组合、装载、驱动并暴露出去**。
- 表现系统、创作系统、运营系统、叙事设定是**正交域**，各消费稳定端口（D-067～D-070），**不得被塞进已装载对局**。玩法层不 import `src/ui`、`src/devboard`、`src/play/ai-*`（AI 是玩法策略?——AI adapters 走端口，不反向被 runtime 持有状态写入权）。
- 唯一状态写入通道仍是 `OpRegistry.invoke`（宪法 1.1）。任何"宿主直接改 worldState"都是越权。
- 玩家可见数值守 1-5 铁律；对局外壳内部量级（回合号、实体数、循环圈数）属内部值例外。

### 1.3 现状盘点：已有积木 vs 待补齐

| 能力 | 现状 | 生产面缺口 |
|------|------|-----------|
| 引擎组合根（接齐全部 Op+Hook+Holder） | `createFullHarness`（`src/core/kernel/testing/full-harness.ts:80`，**测试向**） | 生产组合根 |
| 玩法层装载（五阶段调度 roll→settle→playerAction→npcAction→cleanup） | `loadCoreMechanics`（`src/play/core-mechanics/load.ts:458`，8 步含 Linter） | 已被装载驱动消费，OK |

## 二、面貌（架构组成）

整合层 = **一个组合根 + 六个接线面**。它不发明新语义，只把已有端口按严格三层与正交域纪律"焊"起来。

### 2.1 组合根（Composition Root）—— 生产侧 `createLoadedMatch`

`createFullHarness`（测试向）的**生产镜像**，职责是把引擎原语 → 玩法装载体 → 门禁 config → 对局外壳 → 六接线面一次性组装成单一不变量对象：

```text
createLoadedMatch(装载请求)
  ├─ 引擎面：OpRegistry + DefRegistry + WorldStateHolder + ExprEngine + QueryEngine
  │          （既有 createFullHarness 的能力子集，去 testing/ 化，落生产组合根）
  ├─ 门禁面：用生产 CoreMechanicsConfig（非 official-test config）调 loadCoreMechanics
  │          → 8 步：Linter → playpackLoader.load → ruleProvider → 3×prop.set → projection
  │          → { ok, diagnostics, projection, blocked }（失败不返回半可用对象）
  ├─ 外壳面：new MatchShell(holder, projection, 终局回调查询)   ← 对局外壳（2.4）
  ├─ 演员面：玩家 entry（PlayerQueue）+ AI entry（createPlayAiRuntime）已注入
  ├─ 地图面：编译后的 MapData → PrefabDef → prefab.spawn 入 world（2.5）
  ├─ UI 面：绑定 UiSystemPorts 七个端口到真实 holder/actionCatalog/facade（2.3）
  └─ 返回：单一 LoadedMatch（只读门面 + 授权提交通道 + 事件订阅 + 外壳控制）
```

约束：`createLoadedMatch` 只有装载期一次性的组装权；**装载完成后对已装载对局的唯一写入通道仍是 `CoreMechanicsFacade`（经 OpRegistry.invoke）**，宿主不得持 WorldStateHolder 直接改状态。

### 2.2 依赖与端口纪律

- 方向：`src/play` 合法 import `src/core`（引擎）、`src/l2`（基类，经端口）；整合层组合根位于 `src/play` 之下，**不得 import `src/ui`、`src/devboard`、`src/game`（无）之外的表现/创作/运营侧实现**。表现与创作通过稳定端口被注入（消费方→端口→整合层装进去），不是整合层拉起它们。
- **引用权在玩法层**（owner 定型，2026-08-15）：玩法层拥有对基类/引擎能力的引用权，是组合与装载的唯一宿主。整合层是"玩法层能力出口"（组合根 + 对局外壳 + UI 宿主），不做任何玩法语义裁决。
- **L1↔L2 注册表桥归基类层，不是整合层职责**（§五 Q-5 已裁）：L2 adapters 消费 `ActiveRegistry`/`KernelContract`，需一座 `OpRegistry/DefRegistry` ↔ `ActiveRegistry/KernelContract` 的**只读桥**，保持 L2 不用反向依赖引擎实现。它属于基类层该交付的稳定端口（前置地基），整合层只"消费它装进去"，不新增这块（§三"新增四块"据此收紧为三块）。
- 机器可校验守门：为每一接线面配一个 `*contract*` 断言文件 + PBT（学 `src/core/ugc/integration/l2-port-contract.ts`），断言"该接线确实数据通、方向对、无越权写"。
- **组合根与测试组合根的装配一致性**（§五 Q-4 已裁）：生产组合根与 `createFullHarness` 的 Op/Hook/Holder 装配不得分叉，产物断言二者装配字节级一致（学 base-layer-bombardment "8.1 归一化"门禁思路）。
- 零耦合守卫：用测试断言"整合层尚未绑定到未冻结依赖"（防提前把正交域拉进运行时）。

### 2.3 UI 面（表现系统端口绑定）

`createUiSystem` 已有完整 7 端口接口，缺宿主侧实现。整合层为它注入真实实现：

| UiSystemPort | 宿主绑定 |
|---|---|
| `projection` | 已装载对局的只读语义投影（`loadCoreMechanics` 构造，`fetchProjection/fetchDescriptor`） |
| `events` | `PresentationGateway.subscribe('*')` 桥接 `EventPort.subscribe` |
| `actionQuery` | `CoreMechanicsRuntime.queryActions`（'ui' 全展开） |
| `revision` | `currentSequence()` → 装载 revision 器 |
| `actions` | `sendIntent` → `CoreMechanicsFacade.submit`（唯一判罚路径，UI 不含裁决） |
| `pendingContracts` | 装载期契约（pending-contract-port）主机实现 |
| `diagnostics` | 装载 diagnostics 接收器（DiagnosticSink） |

纪律：UI 只读语义投影、只发意图，**不持状态写入权**（D-067 2.1）；legacy `ui-adapter.ts` 若不拆可并入此桥，否则登记移除。

> **承接链（§五 Q-5 + 05 立项轮廓 §四·补）**：`sendIntent → CoreMechanicsFacade.submit` 这一 UI→已装载对局的写回，在基类层注册表桥生产装配点落地后可改为**同样只经真实 `OpRegistry.invoke` 单通道**：`createUiSystem.actions` 端口由基类层桥产出的 KernelContract（真实 OpRegistry）包裹的 action-submitter 承接，谓其"与玩家/AI 同一判罚路径"。桥的现状核验见 `docs/工程治理/05_玩法层彻查CEME_立项轮廓.md` §四·补。

### 2.4 对局外壳（Match Shell）—— 整块新建

这是整合层唯一"新增数据结构"，负责把"被装载的规则流"养成为"**一局**"：

- 组成：`回合号`（当前 phase + round）、`终局判定`（致命倒地/零血死亡 → 死亡锚）、`胜负结算`（胜利条件查询）、`终局事件`（`outcome.reach` 原语之上承载真实对局结果）。
- 事件出口：对局外壳只经 `PresentationGateway.subscribe('*')` 与外壳自持的有限事件（round 变更、death、victory、matchEnd）对外发声；**终局事件是单次语义**，闭合后 `LoadedMatch` 对外态切到 `ended`，不再接受提交。
- 参照：`05_底层引擎架构:BattleRoyaleMode` 的 `spawn/victoryCondition/circle` 是**概念草稿**，外壳可借鉴其胜负声明式却不照搬其实现。
- 新增明确点：玩法包 `playpack.ts` 目前 `outcomes:[]` 空——`对局外壳 > outcome-reach 原语` 的关系需在玩法层规格里补一处"一局可声明结局种类"的契约（已裁归玩法层，由专项 A 彻查声明，见 §四专项切分）。

> **✅ 已落地（2026-08-16，专项 B）**：对局外壳 `src/play/loading-runtime/match-shell.ts` `createMatchShell` 已实现——消费玩法层只读终局查询 `TerminalQuery`（`match-lifecycle.ts` 的 `matchEnded/matchEndDetail/round`）做 round+phase/终局/胜负/ended 判定；`submitGuard` 在 `ended` 后拒绝提交（`E_OP_NOT_ACCEPTED`）；`matchEnd` 事件**单次语义**由 `checkTerminal` 的 `endedBroadcast` 保证；契约测试 `test/play/loading-runtime/loaded-match.ports.contract.test.ts` 已覆盖外壳终局/拒绝/单次事件。
> **剩余白盒最后一公里**：外壳的各事件出口尚存在组合根内的 `broadcastShell`/`shellEventRelay` 未接入真实 `PresentationGateway`（组合根 `createLoadedMatch` 不持有 PresentationGateway 实例，只在 `index.ts:343-363` 以注释形式的转发桩声明）；五阶段端到端（装载→首个 roll→advance 推进→终局）装配仍分散在测试侧（`state-machine.e2e`/`load-equivalence.e2e`），尚无生产侧"加载驱动"把组合根 + 外壳 + 玩家/AI/UI 串成一局跑通。此为专项 B 完成表内的剩余待办，非专项 B 已交付范围内的缺陷。

### 2.5 地图面（Map→Match 生产桥）

- 已证可行链路：`src/play/map/compile.ts:89` `compileMap` → MapData → PrefabDef → `prefab.spawn`（`map-spawn-e2e.test.ts` 证明）。
- 整合层补生产接线：编译后 MapData 在装载期 spawn 入 world，成为可参与一局规则的实体/微场景。
- **边界**：MapData `floor→layers` 契约扩展（任意 `height?:number` 可空、留空=三界之外独立层、`opacity=min(1,|Δh|×0.1)`、跨层可见性）是**独立专项**（主状态板"尚待立项"之①）；整合层这次**只消费现有 MapData 契约**订货面桥，不代写契约扩展。

### 2.6 L1↔L2 注册表桥（Registry Bridge）—— 基类层缺漏，非整合层新增

- 引擎/play 走 `OpRegistry`+`DefRegistry`；L2 的 UI/AI 适配器走 `ActiveRegistry`+`KernelContract`——两套注册表至今无桥。
- **归属已裁（§五 Q-5）**：这是 L2 adapters（UI/AI）消费引擎 Op 的**前置接线**，属于基类层该补的地基（稳定端口），不是整合层新增四块之一。整合层只"消费它装进去"，把它当作基类层缺漏去批、独立对账。
- 桥只读、不反向依赖、配契约断言 + PBT。
- **✅ 已落地（2026-08-16，专项 D）**：生产装配点 `src/l2/kernel/registry-bridge.ts`（`createRegistryBridge`）用真实 `OpRegistry`/`DefRegistry` 产出 `KernelContract` + 只读 Def 视图，`createKernelContractFromOpRegistry` 生产调用点 0→1；契约测试 `test/l2/integration/registry-bridge.contract.test.ts` 8 绿（单通道 invoke / hasOp 真实 / 继承解析真实 / 错误透传 / hook 不伪造 / hook=false 时依赖 Hook 动作被拒零 invoke / recordCause）。**承接链消费方接线（§2.3 的 `createUiSystem.actions` 端口改由桥产 KernelContract 包裹的 action-submitter 承接）留专项 B**——适配器未接桥是消费方接线，专项 D 只 export 装配点、登记衔接；桥的宿主注入点在专项 B 组合根内完成。

### 2.7 演员面（Player 入口 + AI 入口）

- **玩家**：解决 `PLAYER_QUEUE_GAP`——玩家 actor 经装载期以参与者（participant）身份进入 `ruleProvider` 的 playerQueue（学 M10 `driveMultiTurn` 对 playerQueue 的手动清法与注册，但转成装载期自动注册）。参与者资格判定归玩法层缺漏，由专项 A 彻查（已裁 §五 Q-4/Q-2）。
- **AI**：`createPlayAiRuntime` 接上 `loadCoreMechanics` + `advancePhase`（此前从未接）。AI 经 `BoundedAIDecisionFacade` gateway 决策、经 `CoreMechanicsFacade` 提交，走与玩家/UI 同一条判罚路径。

### 2.8 domain-entry（空态 → 首 roll）

`createEmptyWorldState` → 装载五角色 props/statuses → 外壳就位 → **首个 roll**。这承接 M10 状态机靶"睡下→起床回满到 5"的装载语义，是"已装载对局开始运行"的入口时序。

## 三、技术（实现落点）

- **路径约定**：模块名拟 `src/play/loading-runtime/`（整合层落玩法层之下，随"玩法层拥有引用权"定性），`test/l2/integration/` 或 `test/play/loading-runtime/` 定向测试。`tsconfig include:["src","test"]` 目录级自动纳入新子目录，无需改 root 配置。不建 `src/integration`（避免与三层依赖链位阶混淆），最终以 owner 拍板为准（§五 Q-1）。
- **复用为主、新增为辅**：~90% 来自既有端口与组合根能力子集，真正新增的只有**三块**：生产组合根、对局外壳、UI 宿主侧实现（L1↔L2 注册表桥已归基类层，§五 Q-5）。
- **门禁对齐**：`npx tsc --noEmit`（全域 0 err）+ `npx vitest run`（相关范围）+ `npm run lint` + `npm run verify:docs`；新增 `*contract*` 门禁与 PBT 断言接线面，避免"串起来"却被孤立验证放行。
- **装载期体面**：生产 config 不得用 `official-state-machine-config.ts`（测试专用）。生产 `defaultCoreMechanicsConfig` 严格属玩法层（装载 config 是玩法包的一部分），由整合层装载时注入，不归整合层持有（§五 Q-3 已裁语义）。
