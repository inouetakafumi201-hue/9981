## 二、复核过程中发现并纠正的测试自身逻辑 bug

以下 bug 存在于**测试文件**内（不是 `src/l2/**` 的缺陷），是在把 `.skip` 换成真实实现后、
测试首次真正被执行时才暴露的——这正是"整体 SKIP 掩盖测试逻辑错误"的典型风险，记录如下以避免
重蹈覆辙。

### P04：字段冲突断言错认宿主
- **现象**：注入"多继承字段冲突"用例时，断言体对 `leafId`（主继承谱系的叶子节点）调用
  `resolve`，但字段冲突实际被构造在一个独立的 `gen-conflict-child` 定义上，与 `leafId` 无关。
- **根因**：构造函数里冲突子定义的标识没有被传给断言体，断言体误以为冲突会体现在对
  `leafId` 的解析结果里。
- **修复**：把 `conflictChildId` 从构造结果里带出来，断言体分别对 `leafId`（环检测）与
  `conflictChildId`（字段冲突检测）调用 `resolve`，不再混用一次调用覆盖两种失效模式。

### P04：显式合并规则与类型兼容性的关系
- **现象**：`declareMergeRule=true, injectIncompatibleFieldType=true` 时，测试期望仍产出
  `INHERIT_INCOMPATIBLE_FIELD_TYPE`，但真实实现 `resolveDefinition` 的 `mergeLineageFields`
  在有显式合并规则时按 precedence 直接选出唯一胜出字段，不再检查类型兼容性。
- **根因**：测试 oracle 想当然地认为"类型不兼容"与"是否有合并规则"是两个独立维度，
  但被测实现的真实语义是：显式规则本身就是"有效解决方案"，规则生效时跳过兼容性检查。
- **修复**：按 `!declareMergeRule` 门控两个错误分支，与实现语义对齐。

### P08：环注入与"删除留下入边"注入的场景冲突
- **现象**：`injectReferenceCycle` 与 `injectRemovalWithInboundEdge`（以及其他注入）同时为真时，
  两阶段激活的第一阶段（建立基线）会先被环或其他错误拒绝，导致
  `REF_INBOUND_LEFT_DANGLING` 永远无法被触发观察到。
- **根因**：删除子句需要一个能成功建立的基线才能观察"删除后悬空"，与其余注入互斥。
- **修复**：用 `fc.pre` 让"删除留下入边"注入与其余全部注入互斥。

### P13：占用契约引用缺失定义 + 单阶段激活无法体现"删除遗留入边"
- **现象 1**：`occupancyContractRef` 声明为 `required: true` 但测试从未提供对应定义，
  导致"合法输入应通过"分支永远失败（`REF_MISSING_TARGET`）。
- **现象 2**：父级删除与父级/子场景的首次声明放在同一个候选包内提交，导致"入边"和
  "被删目标"同时首次出现，不构成真实的"删除遗留入边"场景（无法观察到
  `SPACE_PARENT_REMOVAL_ORPHANS_CHILD`）。
- **修复**：补充 `occupancyContractDefinition()`；将测试拆为两阶段——先用
  `buildInitialPackage`（父级 + 占用契约 + 子微型场景）建立基线，再用
  `buildRemovalPackage`（只含对父级的 `removals`）提交第二个候选事务。

### P14：oracle 期望代码与真实规则代码不一致
- **现象**：`inventSpecialTierMechanism` 违规的期望代码写成 `LAYER_L3_OWNERSHIP`，
  `skill.differsOnlyByNameOrValue` 违规的期望代码写成 `STATUS_PSEUDO_SUBTYPE`。
- **根因**：真实实现分别产出 `SOURCE_PROMOTION_REQUIRES_DECISION`（`item-vehicle-rules.ts`
  `validateWeapon`，因 Q-01 未决而不是层级越界）与 `SKILL_MISSING_CONTRACT_FIELD`
  （`effect-ai-rules.ts` `validateSkill`，`STATUS_PSEUDO_SUBTYPE` 是 status 族专用代码）。
- **修复**：按真实规则源码逐条核对并纠正 oracle。

以上四类 bug 的共同教训：**"断言体已完整写出"不等于"断言体是对的"**——在实现落地前，
一份从未真正执行过的断言体既可能藏着构造错误，也可能藏着对被测语义的误解。任务要求
"不放宽断言"，但同样重要的是"不能想当然地相信未跑过的断言"；本次复核中所有修复都是让
oracle 与真实实现的**已验证**行为对齐，而不是放宽判定标准。

## 三、当前仍 SKIP 的子句：真实实现缺口（非模块缺失）

以下 4 处 SKIP 全部是"模块已存在，但未覆盖该失效模式"，与最初"整个模块不存在"的阻塞性质
不同——这些是本次复核中新发现的 `src/l2/**` 缺口，按文件所有权限制（本次任务只能改动
`test/properties/**`）不能修复实现本体，故拆分为独立 `it.skip` 并完整记录。

### P05：移除 `typeDefining: true` 能力未被拒绝或反映为类型变化
- **测试文件**：`test/properties/P05-composition-commutativity.property.test.ts`
  （`runTypeDefiningRemovalClause`）
- **缺口位置**：`src/l2/resolution/definition-resolver.ts` 的 `resolveDefinition`
- **缺口描述**：`ResolvedDefinition.typeIdentity` 直接取自 `definition.typeIdentity`，
  与 `composition` 数组内容完全无关。移除一个 `typeDefining: true` 的可选能力时，
  既不会产生 `COMPOSE_TYPE_DEFINING_CAPABILITY_REMOVED` 诊断，也不会反映为
  `Type_Identity` 变化——两条候选定义无论 composition 如何变化，只要 `typeIdentity`
  字段本身不变，解析结果的 `typeIdentity` 就恒定不变。
- **违反的需求**：Requirements 3.11 / design.md Property 5
  「移除类型决定的可选能力必须拒绝或反映为 Type_Identity 变化」。
- **修复建议**：`resolveDefinition` 在计算 `typeIdentity` 时应扫描 `composition` 中
  `typeDefining: true` 的组件是否仍全部存在；缺失时产出
  `COMPOSE_TYPE_DEFINING_CAPABILITY_REMOVED` 或据此重新计算类型身份。

### P10：覆盖使依赖者类型不兼容未被检测
- **测试文件**：`test/properties/P10-atomic-activation-rollback.property.test.ts`
  （`runOverrideInvalidatesDependentClause`）
- **缺口位置**：`src/l2/resolution/reference-graph.ts`（图收集范围）+
  `src/l2/resolution/dependent-revalidation.ts`（覆盖重验证深度）
- **缺口描述**：`DIAGNOSTIC_CODES.REF_OVERRIDE_INVALIDATES_DEPENDENT` 只在诊断代码目录里
  声明，从未被任何规则产生（已用 grep 确认零匹配）。根因：`buildReferenceGraph` 只收集
  候选包**自身定义**的引用，不会为"停留在活动集、未被本次候选重新提交"的依赖者重新收集
  引用；`revalidateDependents` 对 `overrideIntent` 只检查"覆盖目标是否存在于候选中"
  （产生 `REF_OVERRIDE_TARGET_MISSING`），不检查覆盖后依赖者的引用是否仍类型兼容。
- **违反的需求**：Requirements 12.6-12.7 / design.md Property 8、10。
- **修复建议**：`revalidateDependents` 处理 `overrideIntent` 时，应对每个被覆盖定义的
  活动入边依赖者，用覆盖后的新定义重新执行一次 `matchesExpected` 类型检查。

### P11：可见性条目内容未按授权范围裁剪
- **测试文件**：`test/properties/P11-readonly-projection.property.test.ts`
  （`runVisibilityEntryClippingClause`）
- **缺口位置**：`src/l2/registry/read-only-projection.ts` 的 `projectVisibility`
- **缺口描述**：`projectVisibility` 只按 `authorizedAgents` 过滤"哪些 agent 的可见性条目
  会出现在投影里"，但每个条目内部的 `visibleEntityIds` / `visibleNodeIds` 原样复制自
  运行时状态，完全不做二次裁剪。若运行时状态里某个已授权 agent 的可见性条目声称能看到
  `scope.visibleNodeIds` 之外的节点，投影会原样透出。
- **违反的需求**：Requirements 10.7、14.1 / design.md「投影...按授权的认知与可见范围裁剪」。
- **修复建议**：`projectVisibility` 映射每个条目时，对 `visibleEntityIds` /
  `visibleNodeIds` 分别与 `scope.visibleEntityIds` / `scope.visibleNodeIds` 求交集。

### P11：`PresentationDescriptor` 未深度冻结
- **测试文件**：`test/properties/P11-readonly-projection.property.test.ts`
  （`runDescriptorImmutabilityClause`）
- **缺口位置**：`src/l2/adapters/ui-adapter.ts` 的 `uiDescriptor`
- **缺口描述**：`uiDescriptor` 构造描述符对象后直接 `return ok(descriptor, warnings)`，
  全文件不含任何 `deepFreeze` / `Object.freeze` 调用（已用 grep 确认零匹配）。
- **违反的需求**：Requirements 14.1 / design.md「深度不可变值返回」（适用于全部只读投影
  产出，Property 11 明确覆盖 `Presentation_Descriptor`）。
- **修复建议**：`uiDescriptor` 返回前对 `descriptor` 调用
  `deepFreeze`（`src/l2/model/immutable.ts` 已提供该工具）。
