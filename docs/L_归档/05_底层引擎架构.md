# 底层引擎架构设计

## 架构哲学
【这个文档极其重要，深化重点，保证完全完备，不能有一丝一毫的mvp。整个可行性就在这了，力求未来0追加】
【这里没提到ai系统，得分计算也算在底层里】
### 核心理念
**层层叠叠的接口外包和模块化**：
- 仅仅把武器对象模块化了还不行
- 要对整个类别提取范式封装对象
- 把整个伤害判定模块化
- 连整个被动结算都要模块化

### 设计目标
> 任意玩法细节，都能被表达为有限实体上的状态、关系、动作、效果与规则组合，而不需要新增第二套结算系统。

## 三层架构

### 1. 内核层（Kernel Layer）
保证任何合法配置都能确定地执行，不崩溃、不死循环、不产生非法状态

**职责**：
- 实体生命周期管理
- 容器关系维护
- 动作验证与执行
- 状态一致性保证

### 2. 规则范式层（Rule Paradigm Layer）
提供库存、伤害、移动、乘载、状态、回合、目标选择等可复用模块

**职责**：
- 通用机制实现
- 标准管道定义
- 能力组件库

### 3. 玩法包层（Game Mode Layer）
定义大逃杀、夺旗、追逐、合作生存等具体规则

**职责**：
- 出生规则
- 胜利条件
- 特定规则集
- 数值约束

## 六个基础概念

### 1. Entity（实体）
有稳定ID的对象

```typescript
interface Entity {
  id: string;
  components: Component[];
  owner?: EntityId;
  lifecycle: 'active' | 'disabled' | 'removed';
}
```

**关键点**：
- 玩家、物品、载具、NPC都是实体
- 没有"玩家类"、"物品类"的继承关系
- 通过挂载不同组件区分功能

### 2. Component（组件）
实体上的结构化状态

```typescript
// 常见组件类型
Position        // 空间位置
Container       // 容器能力（拥有槽位）
Slot            // 槽位（可被占用）
Occupant        // 占用者信息
ActionProvider  // 提供动作
ResourcePool    // 资源池（AP、生命、燃料）
Health          // 生命值
StatusHolder    // 状态持有者
Controller      // 控制权
Portable        // 可携带
Mobility        // 移动能力
```

**组合示例**：
```
电锯 = 
  Portable (可携带)
  + OccupySlot(size: Large, slots: both_hands)
  + ActionProvider(近战攻击)
  + ResourcePool(fuel: 5)
  + Tags([heavy, armor_piercing])
```

### 3. Relation（关系）
实体之间有类型、有方向的关系

```typescript
interface Relation {
  type: 'ownership' | 'team' | 'hostility' | 'control' | 'discovered';
  from: EntityId;
  to: EntityId;
  properties?: Record<string, any>;
}
```

**示例**：
- 所有权：玩家拥有手枪
- 队伍：玩家A和玩家B是队友
- 敌意：玩家A对玩家B敌对
- 已发现：玩家A已找到玩家B

### 4. Location（位置）
可以被占据或容纳的位置

```typescript
interface Location {
  id: string;
  type: 'world_node' | 'slot' | 'portal';
  capacity: number;
  accepted_traits: string[];
  exclusive_groups?: string[];
  parent?: LocationId;
  adjacency: Edge[];
}
```

**三种位置关系**：
```
容纳关系（Containment）：手枪位于背包槽
拓扑关系（Topology）：教室与走廊通过门相连
影响关系（Influence）：二楼窗户可射击一楼操场
```

### 5. Action（动作）
参与者可以声明的状态转移

```typescript
interface Action {
  initiator: EntityId;      // 谁声明
  actor: EntityId;          // 谁执行
  source?: EntityId;        // 能力来源（武器等）
  targets: EntityId[];      // 目标集合
  requirements: Condition[]; // 前置条件
  costs: Cost[];            // 资源消耗
  effects: Effect[];        // 产生的效果
  failure: FailurePolicy;   // 失败处理
  timing: TimingInfo;       // 时序信息
  disclosure: Visibility;   // 可见性
}
```

### 6. Rule（规则）
对动作、效果、事件及查询结果施加约束或修正

```typescript
interface Rule {
  trigger: EventType;
  condition: Predicate;
  modification: Modifier;
  priority: number;
}
```

## 四个运行过程

### 1. Query（查询）
从当前视角查询对象、关系、目标和可用动作

```typescript
function queryAvailableActions(actor: EntityId): Action[] {
  // 局部作用域查询
  const scope = getLocalScope(actor);
  // 收集动作提供者
  const providers = collectActionProviders(scope);
  // 应用过滤器
  return filterByConditions(providers, actor);
}
```

**局部作用域四层级**：
1. 自身（Self）
2. 子树（Downstream/Inventory）
3. 父节点（Upstream/Location）
4. 兄弟节点（Siblings/Surrounding）

### 2. Validate（验证）
判断动作是否合法并计算成本

```typescript
function validateAction(action: Action): ValidationResult {
  // 检查前置条件
  if (!checkRequirements(action.requirements)) {
    return { valid: false, reason: 'requirements_not_met' };
  }
  
  // 检查资源
  if (!hasResources(action.actor, action.costs)) {
    return { valid: false, reason: 'insufficient_resources' };
  }
  
  // 检查目标合法性
  if (!validateTargets(action.targets)) {
    return { valid: false, reason: 'invalid_targets' };
  }
  
  return { valid: true, costs: action.costs };
}
```

### 3. Resolve（解析）
把动作展开成有限、原子的基础效果

```typescript
function resolveAction(action: Action): Effect[] {
  const effects: Effect[] = [];
  
  // 预留资源
  reserveCosts(action.costs);
  
  // 执行效果管道
  for (const effect of action.effects) {
    const resolved = resolveEffect(effect, action);
    effects.push(...resolved);
  }
  
  // 原子提交
  commitEffects(effects);
  
  // 触发事件
  emitFacts(action, effects);
  
  return effects;
}
```

### 4. Observe（观察）
记录事实，并按可见性向不同观察者公开信息

```typescript
function emitObservation(fact: Fact): void {
  // 确定可见性
  const observers = determineObservers(fact);
  
  // 向每个观察者发送适当的信息
  for (const observer of observers) {
    const filtered = filterByVisibility(fact, observer);
    notifyObserver(observer, filtered);
  }
}
```

## 核心系统管道

### 伤害结算管道

```typescript
function resolveDamage(request: DamageRequest): DamageResult {
  // 1. 命中判定
  if (!checkHit(request)) {
    return { hit: false, damage: 0 };
  }
  
  // 2. 替代效果检查（如反伤、免疫）
  const substitution = checkSubstitution(request);
  if (substitution) {
    return substitution;
  }
  
  // 3. 来源修正
  let amount = request.amount;
  amount = applySourceModifiers(amount, request.source);
  
  // 4. 目标修正
  amount = applyTargetModifiers(amount, request.target);
  
  // 5. 护甲/抗性/格挡
  amount = applyDefenses(amount, request.target, request.tags);
  
  // 6. 最小值与上限
  amount = clamp(amount, 0, MAX_DAMAGE);
  
  // 7. 应用到资源
  applyToHealth(request.target, amount);
  
  // 8. 失能/死亡判定
  checkIncapacitation(request.target);
  
  // 9. 产生事实
  emitFact('damage_dealt', { 
    source: request.source, 
    target: request.target, 
    amount 
  });
  
  return { hit: true, damage: amount };
}
```

### 物品转移管道

```typescript
function transferItem(
  item: EntityId, 
  from: LocationId, 
  to: LocationId
): TransferResult {
  // 1. 验证容量
  if (!hasCapacity(to, item)) {
    return { success: false, reason: 'no_capacity' };
  }
  
  // 2. 验证接纳约束
  if (!acceptsItem(to, item)) {
    return { success: false, reason: 'not_accepted' };
  }
  
  // 3. 原子转移
  atomic(() => {
    removeFromContainer(from, item);
    addToContainer(to, item);
    updateParent(item, to);
  });
  
  // 4. 触发事件
  emitFact('item_transferred', { item, from, to });
  
  // 5. 更新聚合属性（如负重）
  updateAggregatedProperties(getOwner(to));
  
  return { success: true };
}
```

### 状态管道

```typescript
function applyStatus(
  target: EntityId, 
  status: StatusDefinition
): StatusResult {
  // 1. 检查免疫
  if (hasImmunity(target, status.type)) {
    return { applied: false, reason: 'immune' };
  }
  
  // 2. 检查冲突
  const existing = getStatus(target, status.type);
  if (existing) {
    // 同名状态取最长持续时间
    if (existing.duration < status.duration) {
      updateStatusDuration(existing, status.duration);
    }
    return { applied: false, reason: 'already_exists' };
  }
  
  // 3. 添加状态
  addStatus(target, status);
  
  // 4. 调度移除
  if (status.duration > 0) {
    scheduleEffect({
      delay: status.duration,
      effect: () => removeStatus(target, status.id)
    });
  }
  
  // 5. 触发进入效果
  triggerOnEnter(status, target);
  
  return { applied: true, status };
}
```

## 必须守住的不变量

这些是保证UGC"不会搞崩"的核心约束：

### 1. 确定性（Determinism）
相同初始状态、命令序列和随机种子必须得到相同结果

### 2. 原子性（Atomicity）
动作要么完整提交，要么完全不发生

### 3. 权限性（Authority）
只有当前控制者能为实体选择动作

### 4. 有限性（Finiteness）
每个动作、触发链和目标集合都有明确上限

### 5. 可终止性（Termination）
禁止无界循环、递归和无限生成实体

### 6. 可解释性（Explicability）
每次状态变化都能追溯到动作、规则和来源

### 7. 无回合外选择（No Out-of-Turn Choices）
默认所有响应自动结算

### 8. 随机显式化（Explicit Randomness）
随机只通过引擎RNG原语产生，并记录种子与结果

### 9. 稳定排序（Stable Ordering）
同时触发和并列选择必须有统一顺序

### 10. 状态合法性（State Validity）
每次提交后验证位置、容量、资源、控制权和生命周期

### 11. 无隐藏写入口（No Hidden Write Access）
UGC、LLM、AI和UI都只能提交同一种命令

### 12. 版本固定（Version Locking）
一局对战绑定规则包版本和内容哈希，不能静默热改

## 零费动作的处理

### 三种处理方式

#### 1. 动作捆绑（Action Bundling）
```typescript
// 将0费动作作为1费动作的修饰符
interface CompositeAction {
  primary: Action;  // 1 AP
  attachments: ZeroAPAction[];  // 0 AP
}

// 示例：移动并顺便丢弃
{
  primary: { type: 'move', cost: 1 },
  attachments: [{ type: 'drop', item: 'rusty_key' }]
}
```

#### 2. 反射式触发（Reflexive Trigger）
```typescript
// 在AP搜索前，用简单条件判断执行0费动作
function reflexLayer(actor: EntityId): void {
  if (hasItem(actor, 'adrenaline') && getHealth(actor) <= 2) {
    useItem(actor, 'adrenaline');  // 0 AP
  }
}
```

#### 3. 贪婪后置插入（Greedy Post-Insertion）
```typescript
// 规划好路径后，沿途"蹭"0费动作
function optimizePath(path: Action[]): Action[] {
  return path.map(action => {
    const opportunities = findZeroAPOpportunities(action);
    return { ...action, attachments: opportunities };
  });
}
```

## 技术实现建议

### 语言选择
- **TypeScript/JavaScript**：快速原型，易于UGC集成
- **Rust**：高性能核心，WASM部署
- **Python**：AI训练和LLM集成

### 架构模式
- **ECS（Entity-Component-System）**：实体组件系统
- **Event Sourcing**：事件溯源，支持回放
- **CQRS**：命令查询分离

### 数据格式
- **JSON**：规则定义、地图数据、实体配置
- **MessagePack/Protobuf**：网络传输
- **SQLite**：持久化存储

### 性能优化
- **空间索引**：四叉树/网格，快速查询邻近实体
- **缓存机制**：动作枚举结果缓存，状态变化时失效
- **批处理**：多个效果批量提交
- **增量更新**：只同步变化的部分
