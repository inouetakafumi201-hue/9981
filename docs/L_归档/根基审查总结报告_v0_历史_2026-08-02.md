## 核心发现

### 1. 整合而非堆砌

**错误做法**（之前犯的错误）：
```
需要商店 → 创建 ShopSystem
需要任务 → 创建 QuestSystem
需要成就 → 创建 AchievementSystem
...无限系统
```

**正确做法**（根基整合）：
```
物品堆叠 + 条件网关 + 查询服务
    ↓
一个底层承载：
  - 商店（检定金币 → 转移物品）
  - 合成（检定材料 → 产出物品）
  - 任务（检定道具 → 获得奖励）
  - 赌博（检定金币 → 随机物品）
  - 交易（双向检定 → 双向转移）
```

---

### 2. 五大整合架构

#### 整合 A：资源流动
```
物品堆叠 + 资源池 + 条件网关
  = 统一的资源检定与转移协议
```

**承载**：商店、合成、交易、任务、技能消耗、过桥费、声望门槛

---

#### 整合 B：事件响应
```
事件系统 + 被动触发 + 查询服务
  = 统一的响应式联动框架
```

**承载**：荆棘反伤、击杀回血、任务追踪、成就、光环、联动机关、连锁反应

---

#### 整合 C：状态承载
```
实体状态 + 节点状态 + 连接状态
  = 统一的 StatusEffect 挂载容器
```

**承载**：实体中毒、地面着火、门损坏、桥断裂、载具损坏、装备磨损

---

#### 整合 D：信息查询
```
阵营系统 + 视野系统 + 查询服务
  = 统一的过滤查询接口
```

**承载**：AI 目标选择、自动攻击、警报系统、范围技能、UI 标记、共享视野

---

#### 整合 E：脚本编排
```
触发器系统 + 事件系统 + 条件网关
  = 统一的 UGC 编程接口
```

**承载**：剧情触发、陷阱、机关、动态刷怪、任务目标、成就、胜利条件、教学提示

## 示例：商店如何实现

### 错误理解（之前的做法）
```typescript
interface Shop {
  inventory: Item[];
  prices: Map<ItemId, number>;
  currency: string;
}

class ShopSystem {
  buy(shop: Shop, player: Player, item: ItemId) {
    // 专用系统，无法复用
  }
}
```

### 正确理解（根基组合）
```typescript
// 商店 = 容器实体 + 条件网关
const shop: Entity = {
  category: 'container',
  inventory: {
    items: [sword, potion, shield],
  },
  interaction: {
    type: 'gateway',
    gateway: {
      conditions: [
        { type: 'has_resource', resource: 'gold', amount: 50 }
      ],
      cost: { resources: { gold: 50 } },
      effects: [
        { type: 'transfer_item', from: 'shop', to: 'player', item: 'sword' }
      ]
    }
  }
};

// 自动贩卖机 = 同样结构，只是外观不同
const vendingMachine: Entity = {
  category: 'container',
  // ... 完全相同的 gateway 结构
};

// 赌博机 = 条件相同，效果改为随机
const slotMachine: Entity = {
  category: 'container',
  interaction: {
    type: 'gateway',
    gateway: {
      conditions: [{ type: 'has_resource', resource: 'gold', amount: 10 }],
      cost: { resources: { gold: 10 } },
      effects: [
        { type: 'random_item', pool: ['sword', 'potion', 'nothing'], weights: [0.1, 0.3, 0.6] }
      ]
    }
  }
};
```

**一个根基（条件网关），承载 N 种机制**：
- 商店
- 自动贩卖机
- 赌博机
- 合成台
- 任务 NPC
- 过桥收费
- 等级门槛

## 示例：任务如何实现

### 错误理解（之前的做法）
```typescript
interface Quest {
  objectives: QuestObjective[];
  rewards: Reward[];
}

class QuestSystem {
  updateProgress(quest: Quest, event: any) {
    // 专用系统，与其他系统解耦困难
  }
}
```

### 正确理解（根基组合）
```typescript
// 任务 = 事件订阅 + 条件检查 + 奖励网关

// 1. 事件订阅（自动追踪）
eventSystem.on('entity_killed', (data) => {
  if (data.target.type === 'zombie') {
    player.resources.set('quest_zombie_kills', 
      player.resources.get('quest_zombie_kills') + 1
    );
  }
});

// 2. 任务 NPC = 条件网关
const questNPC: Entity = {
  interaction: {
    type: 'gateway',
    gateway: {
      conditions: [
        { type: 'has_resource', resource: 'quest_zombie_kills', amount: 5 }
      ],
      cost: { resources: { quest_zombie_kills: 5 } },  // 可选：消耗进度
      effects: [
        { type: 'add_resource', resource: 'exp', amount: 100 },
        { type: 'add_item', item: 'legendary_sword' }
      ]
    }
  }
};
```

**一个根基（事件系统 + 条件网关），承载 N 种机制**：
- 任务追踪
- 成就系统
- 统计系统
- 日志记录
- 回放系统

## 关键设计决策

### 决策 1：物品 vs 资源

**问题**：金币是物品还是资源？

**决策**：**两者都是**，通过统一查询接口抽象
```typescript
getResourceAmount(entity, 'gold')
  → 如果 gold 是物品，count_items()
  → 如果 gold 是资源，entity.resources['gold']
```

**好处**：
- UGC 可以选择金币是否可掉落
- 条件网关不需要关心来源
- 同一套 API 支持 Minecraft 风格（物品金币）和 WoW 风格（账户金币）

---

### 决策 2：触发器 vs 专用系统

**问题**：任务系统、成就系统、触发器系统，三者都有"监听事件 → 检查条件 → 执行效果"，是否独立实现？

**决策**：**统一为触发器系统**
```typescript
// 任务 = 触发器
{ event: 'entity_killed', condition: {...}, effects: [...] }

// 成就 = 触发器
{ event: 'entity_killed', condition: {...}, effects: [{ type: 'unlock_achievement' }] }

// 剧情触发 = 触发器
{ event: 'entity_moved', condition: {...}, effects: [{ type: 'play_cutscene' }] }
```

**好处**：
- 一套代码，三种用途
- UGC 用同一个配置文件
- 性能优化只做一次

---

### 决策 3：状态系统的统一

**问题**：实体状态、节点状态、连接状态，是否三套系统？

**决策**：**统一为 StatusEffect**
```typescript
// 同一个数据结构
interface StatusEffect {
  type: string;
  duration: number;
  effects: Effect[];
}

// 三种挂载容器
Entity.status: StatusEffect[]
Node.environmentStatus: StatusEffect[]
Connection.status: StatusEffect[]
```

**好处**：
- 状态交互矩阵只写一次
- 状态叠加规则统一
- UGC 配置格式统一

## 风险与缓解

### 风险 1：性能（100+ 实体查询）

**缓解措施**：
- 空间分区（只查询附近节点）
- 查询结果缓存（位置不变时复用）
- 惰性计算（需要时才查询）
- 预过滤（按 category 建立索引）

---

### 风险 2：触发链死循环

**缓解措施**：
- 触发深度限制（maxDepth = 5）
- 触发链记录（检测循环）
- 事件防抖（同一事件同一帧只触发一次）

---

### 风险 3：UGC 安全性

**缓解措施**：
- 静态 Linter（检查条件表达式）
- 运行时沙盒（限制计算开销）
- 条件深度限制（嵌套 ≤ 5 层）
- 触发器数量限制（≤ 100 个）

---

### 风险 4：复杂度爆炸

**缓解措施**：
- 分阶段实施（P0 → P1 → P2）
- MVP 只做 4 个根基
- 每个根基独立测试
- 渐进式整合

## 总结

### 核心洞察

**不是为每个功能创建系统，而是为 N 个功能创建一个根基。**

- 商店 ≠ ShopSystem
- 商店 = 容器 + 条件网关

- 任务 ≠ QuestSystem
- 任务 = 事件订阅 + 条件检查

- 成就 ≠ AchievementSystem
- 成就 = 触发器的一种应用

**一个底层结构应该能承载 3+ 种表层机制，这才是"根基"。**

---

### 设计哲学的延续

✅ **极简离散系统**：根基更简洁  
✅ **如无必要，勿增实体**：减少专用系统  
✅ **结构复用优于功能堆砌**：得到完美体现  
✅ **0 追加设计**：根基完整后真正可扩展
