## 权威优先级

规范宪法 → 已确认访谈决策 → 引擎层不变量与职责边界 → 基类层有效契约 → 玩法层定稿规则 → 历史示例或旧路线图。

禁止使用“模板”“内容层”等废用术语；UGC 语境中的数据产物应使用准确的定义、实例或玩法包称谓。

## 必须完成的审查

1. UGC 输入必须是纯声明式 JSON：只描述数据、条件、引用和已知效果组合，不允许任意代码、命令式循环、变量赋值、脚本注入或外部命令执行。
2. UGC 不得新增引擎层 Ref 前缀、Op 分发机制、Expr 求值器、Hook 调度器、事务模型或持久化机制。
3. UGC Adapter 只能产生候选声明式定义并提交统一验证，不得旁路 Definition Validator、直接激活内容或直接写 WorldState。
4. 不恢复“物品体积”等废弃机制。
5. 不把“所有数值都限制为 1-5”机械扩展到内部计数、版本号、资源大小和技术配额；玩家可见玩法数值必须为 1-5，其他数值需按规范归类并明确边界。
6. 明确对 core mechanics、space-items、AI 的类型化引用。缺失、歧义、错误类型或循环引用必须拒绝并产生结构化诊断。
7. 覆盖未知字段、非法 Def kind、重复 ID、继承环、组合冲突、资源配额、恶意深度、版本迁移、确定性规范化和加载原子性。
8. 语义字段缺失或非法时必须拒绝；只有非语义表现资源才能显式降级，且不得改变规则结果。
9. 区分基类层实例定义与玩法层具体数值、胜负规则及玩法包配置，禁止越层激活。
10. 每条需求必须可测试、可追踪，并明确错误代码类别或诊断要求；删除重复和不可验证陈述。

## 写入边界

- 只修改 `.kiro/specs/wakeup-ugc/requirements.md`。
- 不创建 `design.md`、`tasks.md` 或任何其他文件。
- 不修改任何上游 requirements、规范宪法、领域文档或共享报告。
- 不写实现代码，不运行构建或测试。
- 开始时检查目标文件和 Git diff；保留人工改动。若发现其他会话正在修改目标文件，停止并报告，不得覆盖。

## 完成前反向审查

检查：代码注入面、旁路验证、越权激活、废案复活、数值边界误用、循环或炸弹型输入、非确定性输出、语义错误被静默降级、跨 Spec 重复定义、不可测试需求和来源缺失。
