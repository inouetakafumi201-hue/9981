# 底层宪法贯彻审查 Prompt 集

> 用于并行执行多个审查任务，确保代码和文档符合宪法三层架构。
> 每个 prompt 可独立交给一个 AI agent 执行。

---

## Prompt 1：引擎 API 护城河审查

```
## 任务
审查 `src/core/kernel/` 目录下的所有代码，确认是否违反了"引擎 API 护城河"原则。

## 宪法依据
- 玩法层绝对不能调用引擎层 API
- 玩法层只能通过基类层提供的语法工作
- 唯一写入通道：`OpRegistry.invoke`

## 审查要点

### 1.1 硬编码检查
在 `src/core/kernel/` 中搜索以下硬编码模式：
- 直接调用 `entity.create`、`entity.destroy` 而非通过 `OpRegistry.invoke`
- 直接修改 `state.props` 而非通过 `prop.set` / `prop.add` Op
- 在 Op 实现中直接调用其他 Op 的内部逻辑（应通过 `OpRegistry.invoke`）

### 1.2 命名空间检查
确认以下模块是否只暴露了 Op 接口，不暴露内部实现：
- `ops/registry.ts` - Op 注册表
- `ops/entity-ops.ts` - 实体操作
- `ops/prop-ops.ts` - 属性操作
- `ops/structural-ops.ts` - 结构操作

### 1.3 Hook 通道检查
- `events/dispatcher.ts` 是否已接入 Op 调用链路
- Hook 是否正确触发（在 Op 执行前后）

## 输出格式
```markdown
### 违规项
| 文件 | 行号 | 违规内容 | 修复建议 |
|------|------|----------|----------|

### 符合项
| 文件 | 说明 |
|------|------|

### 待确认
| 位置 | 疑问 |
|------|------|
```

## Prompt 2：基类层边界审查

```
## 任务
审查 `src/core/kernel/` 中的代码，确认是否有"基类层职责侵入引擎层"的情况。

## 宪法依据
- 引擎层不知道"武器"、"技能"、"AP"是什么
- 引擎层只提供 Entity、Component、Relation、Op、Expr 等底层原语
- 基类层封装引擎 API，形成独立语法

## 审查要点

### 2.1 语义泄漏检查
在 `src/core/kernel/` 中搜索以下关键词，确认是否作为硬编码逻辑出现：
- `weapon`、`gun`、`melee` - 武器语义
- `ap`、`action`、`cost` - 动作点语义
- `hp`、`health`、`damage` - 生命值语义
- `buff`、`debuff`、`status` - 状态语义

**如果这些词出现在引擎层**，检查：
- 是作为通用术语（如 `cost` 在任何场景都通用）还是硬编码逻辑
- 是否有对应的 Op 可以表达相同功能

### 2.2 Op 命名检查
确认 `ops/` 目录下的 Op 名称是否为通用名称，不含玩法语义：
- ✅ `entity.create`、`prop.add`、`relation.set` - 通用
- ❌ `weapon.attack`、`ap.spend`、`hp.damage` - 含玩法语义

### 2.3 Component 定义检查
确认 `components/` 中的 Component 是否为通用定义：
- ✅ `Position`、`Container`、`ResourcePool` - 通用
- ❌ `Health`、`WeaponSlot`、`AmmoCount` - 含玩法语义

## 输出格式
```markdown
### 语义泄漏
| 文件 | 行号 | 泄漏内容 | 判定（硬编码/可接受） | 修复建议 |
|------|------|----------|---------------------|----------|

### 符合项
| 检查点 | 结果 |
|--------|------|

### 待确认
| 位置 | 疑问 |
|------|------|
```

## Prompt 4：基类层 API 完备性审查

```
## 任务
审查 `src/core/kernel/` 是否提供了基类层需要的全部 Op 接口。

## 宪法依据
- 基类层封装引擎 API，形成独立语法
- 基类层必须能够完全生成全部玩法
- 玩法层绝对不能直接调用引擎层 API

## 审查要点

### 4.1 Op 覆盖度检查
对照以下基类类别，检查是否有对应 Op 支持：

| 基类类别 | 需要的 Op | 代码中是否存在 |
|----------|-----------|----------------|
| 武器类 | attack、reload | | 射击、装填 |
| 伤害类 | damage、heal | | 伤害治疗 |
| 移动类 | move、enter、exit | | 移动、进入、离开 |
| 状态类 | apply_status、remove_status | | 施加、移除状态 |
| 物品类 | pickup、drop、use | | 拾取、丢弃、使用 |
| 容器类 | add_to_container、remove_from_container | | 放入、取出 |

### 4.2 Op 签名一致性
检查同名 Op 的签名是否一致：
- `entity.create` 在所有调用处是否使用相同参数
- `prop.add` / `prop.set` 的参数格式是否统一

### 4.3 缺失 Op 识别
识别玩法层可能需要但引擎层未提供的 Op：
- 在 `docs/` 中搜索"需要 XXX Op"或"缺少 XXX 功能"
- 对照 12_根基完备性审查_v2.md 中的缺失项

## Prompt 5：玩法层边界审查

```
## 任务
审查 `specs/` 目录下的玩法层 Spec，确认是否遵守"不能调用引擎层 API"的铁律。

## 宪法依据
- 玩法层绝对不能调用引擎层 API
- 玩法层只能通过基类层提供的语法工作
- 玩法层变更不得回溯修改基类层定义

## 审查要点

### 5.1 直接引擎调用检查
在 `specs/` 中搜索以下模式：
- 直接引用 `src/core/kernel/` 的内部路径
- 使用 `entity.create`、`prop.set` 等引擎层 API
- 绕过基类层直接操作底层状态

### 5.2 基类层引用检查
确认玩法层是否正确引用基类层：
- 是否通过基类层定义的接口工作
- 是否设置了数值约束（1-5 范围）
- 是否组合了基类而非硬编码新类型

### 5.3 迭代边界检查
确认玩法层变更是否遵守边界：
- 是否回溯修改了基类层定义
- 是否引入了需要修改引擎层的新需求

|-----------|----------|----------|

|-----------|-----------|------|
| | | |

### 迭代边界问题

## 执行指南

### 并行执行
以上 5 个 prompt 可以同时交给不同的 AI agent 执行，每个 agent 专注于一个审查维度。

### 执行顺序建议
1. 先执行 **Prompt 1（引擎 API 护城河）** 和 **Prompt 2（基类层边界）**——这两个是底层贯彻的核心
2. 再执行 **Prompt 3（文档对齐）**——基于前两个的结果
3. 最后执行 **Prompt 4（API 完备性）** 和 **Prompt 5（玩法层边界）**——检查完整链路

### 输出汇总
所有 prompt 执行完毕后，汇总输出到 `docs/宪法贯彻审查报告.md`。
