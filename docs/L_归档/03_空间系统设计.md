# 空间系统设计

## 场景节点分类

### 空间的两套正交坐标

必须先分清两组概念，它们**不是**同一套分类的五个档位：

**坐标一：天然空间的三档 + 过渡（构成地图骨架）**

> **补充（逻辑重难点）**：微型场景**没有 owner 字段**——它是按占用者存续的普通 Node，创建/卸载完全由占用者数量的现查结果驱动，不由任何"归属者"判断。微型场景上唯一记录触发来源的字段是 `props.creator`（写入一次，仅供溯源，内核不得据此判断该微型场景是否应继续存在，见工程需求 9.2-9.3）。"过渡场景创造了跨越两个天然场景的微型场景"的准确含义是：**同一个过渡场景（同一个 Link）作为触发者，可以在两侧分别各触发创建一个微型场景 Node**——每个 Node 仍然只有唯一的 `parent`，指向它所在那一侧的天然场景，但两个 Node 的 `props.creator` 都指向同一个触发它们的过渡场景，借此可以查出"这两个微型场景同属一条连接"。下文"过渡场景阻挡机制"一节的判断，正是靠现查这两侧各自的占用者数量得出，而不是靠某种共享的"owner"逻辑。

```
大场景 / 中场景 / 小场景  ← 遵循"大中小特殊"母语，由地图作者划定
过渡场景                  ← 连接用，通常不可长期停留
```

**坐标二：微型场景（附属层）**
```
微型场景  ← 不是天然的，由实体创造，附属于某个天然场景
```

> 大/中场景构成地图的主要拓扑骨架；小场景是天然空间的最小一级；微型场景附属于它们，是近战与接触交互的空间前提。

#### 1. 大场景（Large Scene）
**特征**：
- 最大连接数：≤5个
- 可作为出生点
- 空间开阔，容纳多人

**规则**：
- 重武器/负重在此移动 +1 AP
- 两个玩家同时在此，需要花1 AP "找到"对方才能交互
- 战略缓冲带，适合重整旗鼓、搜刮资源

**示例**：大操场、教学楼整栋、食堂广场

#### 2. 中场景（Medium Scene）
**特征**：
- 最大连接数：≤4个
- 不能作为出生点
- 标准战术空间

**规则**：
- 移动消耗正常（1 AP）
- 两个玩家同时在此，需要花1 AP "找到"对方

**示例**：物理实验室、食堂一楼、教室

#### 3. 小场景（Small Scene）
**定义**：天然空间的最小一级，遵循大/中/小分类。**不是**"微型场景"。

**特征**：
- 最大连接数：≤3个
- 天然存在，由地图作者划定
- 选择密度最低，是天然的堵桥点与掩体
- 通常伴随高价值资源

**规则**：
- 移动消耗正常（1 AP）
- 小场景内**所有活体共处小场景自带的共享微型场景**（小场景节点固有属性）
- **空旷地禁入**：小场景内禁止创建个人微型场景，"来到空旷地"按钮复用 = 移动到共享微型场景
- 贴身成本降为 0 AP（因为已在同一微型场景）
- 没有缓冲，进入即意味着白刃战

**示例**：楼梯间、枪店柜台、厕所

> 注意：**车内、柜子里不是小场景**，它们是实体创造的微型场景，见下节。

#### 4. 微型场景（Micro Scene）
**定义**：**不是天然的，是由实体或过渡场景创造的**局部接触空间。它与大/中/小三档正交，附属于某个天然场景。

**特征**：
- 由某个实体（活体、载具、柜子等）或过渡场景生成
- 依附于所属的天然场景，不能脱离父场景独活
- 是近战与直接交互的**唯一空间前提**

**微型场景的三种创建者**：
1. **活体**：在大/中场景移动到"空旷地"时，创建个人微型场景
2. **过渡场景**：门/窗创建 1-2 个微型场景（平行双侧，垂直单侧）
3. **小场景节点**：自带一个共享微型场景（固有属性）

**核心规则**：
- **"找到 X"的本质 = 来到 X 这个实体的微型场景**
  - 在大/中场景中，两个活体默认不在同一微型场景，必须花 1 AP "找到"才能近战
  - **载具例外**："找到车"是进入该载具实体的影响范围，而非"进入微型场景"——载具不是微型场景，是独立实体（详见04物品与装备系统载具章节 D-011/D-030 收敛结论）
- 微型场景**由每个活体各自私有**（大/中场景）。贴身是**成对的对称关系**：A 贴身 B ⟺ B 贴身 A
- **小场景中贴身成本 0 AP**（已在共享微型场景）
- **脱离贴身** 1 AP；或移动到别的天然场景时自动解除

**空旷地（Vacant Ground）**：
- 定义：活体移动到天然场景后，以自身为中心创建的个人微型场景
- 大/中场景："来到空旷地" = 创建个人微型场景，只有你
- 小场景：**禁止创建个人空旷地**，"来到空旷地"按钮复用 = 移动到共享微型场景
- 术语复用的设计意图：UI 一致性 + 语义清晰（空旷地 = 场景中央）

**过渡场景阻挡机制**：
- 过渡场景创造的微型场景，`props.creator` 都指向同一个过渡场景（同一 Link），但每个微型场景各自的 `parent` 仍指向它所在那一侧的天然场景，且各自的占用者数量独立现查 —— "整体阻挡"由判定逻辑主动查两侧各自的占用者数量得出，不是靠某种共享字段自动生效
- 过渡场景创造的微型场景上，**任意一侧**有活体或具有 `blocking` 属性的实体 → 整个过渡场景不可通行
- 平行过渡（门、平窗）：双侧各创建一个微型场景，任一侧被占 → 双向阻挡
- 垂直过渡（跳窗）：仅上侧创建微型场景，下侧无微型场景 → 单向阻挡判定
- **战术应用**：防守方主动"来到门边"（小场景内 0 AP）→ 门被堵；攻击方可用远程/延长武器破局

**示例**：某玩家周身、车内、柜子里、载具内部、门边、窗边

**与小场景的区别**（这是全文档术语基准）：

| | 小场景 | 微型场景 |
|---|---|---|
| 来源 | 天然，地图作者划定 | 实体创造 |
| 归属 | 地图骨架的一档 | 附属于天然场景 |
| 分类 | 属于大/中/小三档 | 与三档正交 |
| 连接上限 | ≤3 | 不适用（附属关系） |

#### 5. 过渡场景（Transition/Portal）
**特征**：
- 不是停留节点，是连接通道
- 可设置为0 AP通过
- 承载检定和效果

**规则**：
- 无法停留/无资源，纯连接作用
- 可附加通过条件和效果
- 拉长关键区域之间的物理距离

**示例**：楼梯、窗户、走廊、管道

### 五并列拓扑原则

**核心约束**：严格限制每个节点的连接数，防止选项爆炸

```
小场景：最多 3 个关联出口
中场景：最多 4 个连接
大场景：最多 5 个连接
```

上限挂在**天然场景**上（微型场景是附属层，不参与这套计数）。

**注意**：连接包括一切会让活体转移到另一个可行动位置的入口：
- 普通移动通道
- 躲入柜子（进入该柜子的微型场景）
- 上车（进入载具实体，载具不是微型场景而是实体；详见04物品与装备系统载具章节）
- 翻窗、上楼、通风口等过渡节点

**同一套数字的第二个用途 —— 过渡场景阻挡容量**：
```
大场景 5 / 中场景 4 / 小场景 3
```
这套数字不直接约束天然场景内的活体数量（天然场景无容量上限），而是通过**过渡场景的微型场景阻挡机制**间接节流：
- 每个过渡场景创建的微型场景被占用时，该通道阻塞
- 尸潮必须排队通过门/窗，自然分批涌入
- 玩家有反应时间，不会被瞬间围殴

常识依据："大场景四面受敌，小场景一夫当关"，体现在出入口的数量，而非房间本身的容量。

> 旧术语"接敌面"已废弃 —— 它试图约束"同时被几个人打"，但正确的设计是约束"通道瓶颈"。详见微型场景一节的过渡场景阻挡机制。

**为什么这个约束至关重要？**

1. **脑力搜索深度控制**
   - 平均3个出口：下两轮有3×3=9种可能（人脑可控）
   - 平均8个出口：下两轮有8×8=64种可能（玩家放弃思考）

2. **图形化界面清爽性**
   - 限制保证地图在视觉上是平面图或接近平面图
   - 轨道不会交叉，视觉极其优雅清爽

3. **空间张力节奏**
   - 大场景（5连接）：交通枢纽，四通八达但易被伏击
   - 中场景（4连接）：标准战场，进退有据
   - 微场景（3连接）：死胡同与掩体，"一夫当关"

## 过渡门户（Portal）系统

### 门户统一抽象

楼梯、窗户、跳台都是"门户"，是特殊的节点/边组合

### 门户属性定义

```json
{
  "portal_id": "window_2f_to_1f",
  "kind": "window",  // stair | ladder | window | hatch | balcony | vent
  "cost_override": 0,  // AP消耗，可为0
  "checks": ["agility >= 2"],  // 技能/属性检定
  "effects": ["fall_damage: 2", "slow: 1_round"],  // 穿越时的效果
  "directionality": "one_way_down",  // 双向/单向
  "los_bridge": true,  // 是否桥接视线/射击
  "floor_delta": -1  // 连接楼层差（用于自动计算坠落伤害）
}
```

### 常见门户类型

#### 楼梯
- 成本：1 AP（或0 AP作为过渡）
- 双向通行
- 重装buff：额外+1 AP或迟缓1回合
- 视线：不透明

#### 窗户（向下）
- 成本：0 AP（跳窗）
- 单向：只能从高到低
- 效果：坠落伤害（根据floor_delta自动计算）
- 视线：透明（可射击）

#### 窗户（攀爬）
- 成本：2 AP
- 单向：从低到高
- 前置条件：持有攀爬工具
- 视线：透明

#### 梯子
- 成本：1 AP
- 双向通行
- 占用双手（不能拿重物）
- 视线：半透明

### 门户效果示例

#### 坠落伤害计算
```
floor_delta = -2（从3楼到1楼）
base_damage = abs(floor_delta)  // 基础2点
if has_tag("heavy"):
    damage += 1  // 重装额外+1
if has_tag("light") or has_skill("parkour"):
    damage -= 1  // 轻装或技能-1
final_damage = max(0, damage)
```

#### 检定机制
```
通过楼梯（重装）：
- 检测：actor.has_tag("heavy")
- 效果：add_status("slow", duration=1) 或 cost += 1
```

## 地图设计规范

### 经典校园地图示例

#### 节点列表
```
大场景：
- 大操场（5连接）：前门、后门、看台、器材室、教学楼入口
- 教学楼中庭（4连接）：1F走廊、2F楼梯、前门、侧门

中场景：
- 1F教室A（4连接）：走廊、窗户A、窗户B、后门
- 2F教室B（4连接）：走廊、窗户、楼梯、前门
- 食堂一楼（4连接）：正门、厨房、楼梯、窗户

微型场景：
- 楼梯间（2连接）：上、下
- 柜子内（1连接）：出
- 车内（2连接）：上车、下车

过渡场景：
- 各楼层楼梯（连接上下层）
- 窗户（连接室内外）
- 走廊（连接房间，可选是否算节点）
```

### 地图平衡原则

#### AP距离平衡
**从出生点到关键资源的AP消耗必须平衡**

示例：
```
路线A：操场 → (1) → 走廊 → (1) → 教室 → (1) → 拿手枪
总消耗：3 AP，获得：2伤武器

路线B：操场 → (1) → 器材室 → (2，微型危险) → 拿霰弹枪
总消耗：3 AP，获得：3伤武器，但风险更高

路线C：操场 → (1) → 教学楼 → (1) → 楼梯 → (0) → 2F → (1) → 狙击枪
总消耗：3 AP，获得：3伤远程武器，但位置暴露
```

#### 对称性与变化性
- 多个出生点到核心区域的距离应大致相等（±1 AP）
- 但每条路径应有不同的风险/收益特征
- 避免"唯一最优路线"的出现

### 特殊地点设计

#### 高价值区域
- 必须是微型场景（风险匹配收益）
- 或需要特殊条件进入（钥匙、技能）
- 周围有多条逃生路线（避免死角陷阱）

#### 战略要点
- 通常是中场景或大场景交界
- 连接数接近上限
- 视野覆盖广（可观察多个方向）

#### 伏击点
- 小场景连接到主要通道
- 单向视线优势（可看到但不易被看到）
- 有快速撤离路线

## 楼层与垂直空间

### 楼层表示方法：叠层视图（已定案）

采用**叠层视图**，理由是通用性最强（分层面板与剖面图顶多在 UGC 中理论可用）。

**图层距离参数**决定叠加行为：
```
距离 = 0  → 直接卸载掉基础图层（视为同层的场景切换）
距离 > 0  → 叠加在原图层上，保持拓扑关系
```

- 主视图显示当前楼层完整细节
- 原图层（下层）以**半透明**显示，多见于二楼、三楼
- 竖向门户（楼梯/梯子）在各层的屏幕坐标尽量对齐，保证动画连贯
- 默认不画跨层连线，悬停时才亮起

> 注意：叠层不只表示楼层，也可表示同层的不同场景叠加。

### 垂直交互规则

#### 跨层视线
- 通过窗户可以射击不同楼层
- 使用los_bridge属性标记
- 射击态时才显示视线通道

#### 跨层移动
- 只能通过门户（楼梯、窗户等）
- 不能自由跳跃或飞行（除非特殊能力）
- 每个门户都有明确的AP成本和效果

#### 跨层距离计算
- 跳窗（单向门户）：到下层天然场景的距离统一按**距离1**计算，体现居高临下优势
- 楼梯等双向门户：按"离开+1、进入+1"叠加计算（离开当前楼层记一次+1，进入下一楼层再记一次+1，两段累加），不与跳窗的计算方式混用

## 空间关系的三种类型

底层必须区分三种不同的空间关系：

### 1. 容纳关系（Containment）
- **语义**：A在B里面
- **特征**：通常要求单一父级且不能成环
- **示例**：手枪位于背包槽，玩家位于驾驶位

### 2. 拓扑关系（Topology）
- **语义**：A和B通过某种方式相连
- **特征**：可以成环、可以单向，带通过条件
- **示例**：教室与走廊通过门相连

### 3. 影响关系（Influence）
- **语义**：A可以影响B但不能移动到B
- **特征**：只允许特定类型的传播（视线、声音、攻击）
- **示例**：二楼窗户可以看见并射击一楼操场

## 特殊空间机制

### "找到"机制

**本质：找到 X = 进入 X 这个实体生成的微型场景。** 它不是一个独立的"发现"系统，而是空间移动在微型场景层的复用。

```
玩家A在教室（中场景），玩家B也在教室

A想近战B：
1. 花费 1 AP 执行"找到B"
2. A 进入 B 的微型场景
3. 此时 A 可以对 B 执行近战等接触动作

离开条件（不是"关系断开"，而是不再同处一个微型场景）：
- B 移动到其他天然场景
- B 进入另一个实体的微型场景（如躲进柜子、上车）
- A 自己离开
```

**适用范围**：
- 大场景、中场景：需要"找到"
- 小场景：**不需要** —— 所有活体天然共处一个微型场景
- "找到车"同理：花 1 AP 进入那辆车的微型场景，才能上车/爆胎

### 无人场景的散落物清理

**规则**：物品一旦被丢在场景地面，且**所有活体**都离开该天然场景后，它被**删除**。

判定主体是**活体**（玩家 AI 或 NPC），不是"所有实体"——否则一辆车或一个环境实体会意外阻止清理。

**豁免**：被正式放入容器的物品保留。容器包括：
- 玩家死亡后留下的背包（2-4 格）
- 汽车及其货舱
- 固定环境容器（箱子、储物柜）

**清理范围**：以**所属的天然场景整体**判断。微型场景附属于天然场景，因此柜子里、车内的地面物不单独计算——但载具内部作为容器，其中物品不受地面清理影响。

**这条规则同时完成四件事**：
- 清理视觉垃圾
- 降低全局物品状态负担
- 让"保存物品"必须通过容器完成
- 让"丢弃后离开"成为**销毁物资的战术手段**（阻止对手获得自己拿不走的装备）

### 隐蔽与潜行
- 某些微型场景（柜子、角落）可以提供隐蔽
- 隐蔽状态下不需要被"找到"就存在
- 但执行攻击等主动行动会暴露位置

### 缩圈：按主场景离散收缩

不使用几何圆（与离散节点地图冲突）。规则：

1. 确定一个**中心点**
2. 使用周边缩圈拟合算法决定收缩顺序
3. **每回合缩去一个大场景或中场景**
4. 其附属微型场景**随父场景一起处理**（柜子、车内不能脱离父场景独活）
5. 收缩结果**提前公开**，使玩家可以计算路线

**玩家心智**：
> 每回合失去一个主场景；附属于它的柜子、车内等微型空间不能脱离父场景独活。

**稳定性承诺**：中心与顺序一旦确定，**不因临时门户变化（如 C4 开洞）重新计算**——否则公开计划会失去可靠性。

**边界规则**（正典 7557 明确标记，已定案）：
- **缩去效果**：不是立即淘汰、不禁止停留，而是**持续伤害** —— 在缩去场景内每回合造成 1 点毒伤
- **提前公开轮数**：下一批收缩场景提前 **1 轮**公开
- **中心点选定**：暂定**纯随机**选取 1 个大/中场景作为中心
- **载具与缩圈的关系**：不适用 —— 载具不是微型场景而是**实体**，缩圈规则只处理天然场景与附属其上的微型场景；载具的位置随它自身的 Entity 状态变化，不受此处父场景切换规则约束

### 区域效果
- 某些效果作用于整个场景节点
- 例如：燃烧的房间（每回合在此受1伤害）
- 例如：辐射区（进入时获得中毒状态）
- 例如：黑暗房间（无法被远程攻击）

## 编辑器自动检查

### 拓扑Linter
地图编辑时自动检查：

1. **度数检查**（只对天然场景计数）
   - 小场景连接数 ≤ 3
   - 中场景连接数 ≤ 4
   - 大场景连接数 ≤ 5

2. **连通性检查**
   - 所有节点必须可达（没有孤岛）
   - 至少有一个大场景作为出生点

3. **门户合理性**
   - 单向门户必须有返回路径（或明确标注单向陷阱）
   - 跨层门户的floor_delta必须匹配实际层数
   - 0 AP门户不能形成无限循环

4. **平衡性预警**
   - 计算各出生点到关键资源的最短AP距离
   - 如果差距>2 AP，给出警告

## 空间设计最佳实践

### DO
- ✅ 用门户系统统一所有过渡
- ✅ 严格遵守五并列原则
- ✅ 为每个场景类型设计明确的战术意义
- ✅ 使用锚点和分层而非虚线
- ✅ 让空间本身讲述故事

### DON'T
- ❌ 创建超过上限的连接数
- ❌ 混淆容纳、拓扑、影响三种关系
- ❌ 让小场景连接到5个地方（会毁掉"一夫当关"的空间性格）
- ❌ 把小场景与微型场景当成同一个概念
- ❌ 用大量虚线连接跨层节点
- ❌ 忽略AP距离平衡
