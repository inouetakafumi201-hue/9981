### 一之补二：门禁范围守卫 `test/toolchain/gate-coverage.test.ts`（让"已修复"变成"不会再坏"）

> **为什么必须有这个文件**：配置盲区的本质是**没有任何东西在监视范围本身**。只把 `include` 改对、再在文档里写一句"已修复"，下一次有人为了跑得快把 `include` 收窄、或新建一个 `test/<新目录>`，盲区就无声回来了。守卫把"范围"本身变成断言。
> 依据 `.kiro/steering/架构决策原则.md`「契约要机器可校验」「零耦合要有守卫」。

| 编号 | 守住的不变量 | 实现要点 |
|---|---|---|
| **G1** | 磁盘上 `src/`、`test/` 下每个 `.ts`/`.tsx` **都在** typecheck 的 program 里 | 用 `ts.readConfigFile` + `ts.parseJsonConfigFileContent`（TypeScript 自己的解析器）算 `fileNames`，**不自己实现 glob 语义**——否则守卫与真实 `tsc` 会产生偏差，守卫本身就成了新的信任缺口 |
| **G2** | `vitest.config.ts` 每个 include glob 的静态根都落在被检查的树里 | 取首个含通配符的段之前的部分作为根；新增 `e2e/**` 之类会立刻失败，迫使同步扩大 typecheck |
| **G3** | `typecheck` 脚本不得用 `-p`/`--project` 换成窄配置；`typecheck:l2` 仍存在且仍指向 `tsconfig.l2.json`；且 L2 范围**严格小于**全域范围 | 后两条防止"补充门禁"再次退化成没人跑的死配置，或悄悄膨胀成假的全域 |
| **G4** | `lint` 目标含 `src` 与 `test`；磁盘上出现 `.tsx` 时 `--ext` 必须含 `.tsx` | 解析 `package.json` 的 lint 脚本参数（正确跳过 `--ext` 等带值选项） |
| **G5** | lint 对 `test/` **真的生效** | 断言行为而非配置字符串：ESLint 不忽略 `test/` 各顶层子树的代表文件，且在 `test/` 路径下 lint 一段重复键代码会真的报出 `no-dupe-keys` error；另静态排除 `.eslintignore` / `ignorePatterns` 的出现 |
| **G6** | `verify` 串联 typecheck → lint → test | 顺序也断言（typecheck 在 lint 之前） |

> **守卫本身经过反向验证**（否则它可能是一组永真断言）：把 `tsconfig.json` 的 include 改回 `["src","test/properties"]`、`lint` 改回 `eslint src --ext .ts` 后重跑，**恰好且只有 G1、G4 两条失败**；恢复后 12 条全过。
> **性能取舍（自主判断，如实标注）**：G5 最初对 `test/` 下全部 38 个文件调用 `ESLint#isPathIgnored`，实测 42 秒——会把守卫拖成没人愿意跑的慢测试。改为"每个顶层子目录取一个代表文件"后 5 秒内跑完。理由是忽略规则的粒度本来就是目录；更细粒度的漏检由"不存在 `.eslintignore` / `ignorePatterns`"这条静态断言兜住。这是我做的取舍，不是 Prompt 要求。
> **附带改动**：为让守卫被 `npm test` 跑到，`vitest.config.ts` 的 include 增加了 `'test/toolchain/**/*.test.ts'`（纯新增，未改动既有三条的语义）。
