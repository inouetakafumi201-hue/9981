## 一、这条管线为什么先落地数据契约

程序生成地图这条路已经被否掉了：不依赖网格就举步维艰，而背景一定要有审美加持，生成器给不出来。既然背景是**手工挑选的整图**，管线的形态就变了——不是"生成地图"，是**在一张选定的底图上标注拓扑**。

于是管线天然分成两半，各自的迭代节奏完全不同：

| | 美术侧 | 拓扑侧 |
|---|---|---|
| 产出 | 一张 1080P 斜测轴平面图 | 节点、连接、放置 |
| 迭代频率 | 低（选定后基本不动） | 高（每次玩法调整都改） |
| 谁做 | 图像工具 + 人工挑选 | 创作者（或 LLM） |
| 失败代价 | 重新挑图 | 改几行数据 |

两半只在一个地方相交：**归一化坐标**。美术侧交付底图，拓扑侧在 `[0,1]²` 上标点。底图换成 4K、换成另一张构图，只要节点的相对位置还成立，拓扑数据一个字都不用改。这就是这条管线唯一的关键解耦。

所以先落地的不是编辑器，是 `MapData`。它一旦能被校验和编译，管线就已经可以跑——手写 JSON、LLM 生成 JSON 都能立刻进入流程，编辑器只是后来补上的一种更舒服的输入方式。**编辑器是可选的，数据契约不是。**

## 二、六个阶段与每个交界处的产物

```
① 底图获取        →  一张 PNG（选定，不再变）
② 局部重绘修正    →  同尺寸 PNG（挡路的建筑、透视问题就地改掉）
③ 切片与分层      →  底图 + 楼层声明（室内转入更小比例尺的分层地图）
④ 拓扑标注        →  MapData.nodes / edges（归一化坐标 + 行动曲线）
⑤ 实例放置        →  MapData.placements（只放仓库里已有的完整实例体）
⑥ 校验与发布      →  PrefabDef（编译产物）
```

阶段 ①②③ 是美术侧，产物是图片和楼层数字。阶段 ④⑤ 是拓扑侧，产物是 `MapData`。阶段 ⑥ 是机械的，`compileMap()` 一个函数。

**被房子遮住的路就直接不要走。** 这不是妥协而是约束带来的好处：整张图不做任何透视和碰撞计算，可走性完全由 ④ 标出来的连接决定。图上看得见但没连边的地方，就是走不了的地方。

## 三、数据契约

`MapData` 的构造只有一句话：

> **MapData = PrefabDef + 几何**

几何（`at`、`floor`、`path`、`backdrop`）只服务渲染与编辑。编译时**全部丢弃**，剩下的正好是引擎已有的 `PrefabDef`。这让 06 那条"删掉还能不能跑"的判据从修辞变成可执行的断言：

```ts
// src/play/map/__tests__/map-pipeline.test.ts
it('编译产物里没有任何几何——这就是"删掉几何照样跑"的可执行形式', ...)
```

管线的终点因此不需要任何新的引擎能力：`prefab.spawn` 是一条已经被测过的路径。

| 字段 | 归属 | 编译后 |
|------|------|--------|
| `nodes[].id` | 拓扑 | → `PrefabDef.nodes[].key` |
| `nodes[].def` `scale` `name` | 拓扑 | → `def` / `props` |
| `nodes[].at` `floor` | **几何** | 丢弃 |
| `edges[].a` `b` `def` `directionality` | 拓扑 | → `links[]`（`directed`） |
| `edges[].path` | **几何** | 丢弃 |
| `placements[]` | 拓扑 | → `entities[]` |
| `backdrop` | **几何** | 丢弃 |

### 3.1 曲线不决定代价，作者也不逐边填代价

两件事，别混：

1. **几何不决定代价。** `compile.ts` 在代码层面根本不 import `curve.ts`，所以曲线长度物理上无法参与拓扑。这条规则由依赖结构保证，不靠自觉。对应的测试把 `gate` 的折线加到 42 个样条点，断言编译产物逐字节相同，且运行期 `dist` 仍是 2。
2. **代价也不是作者逐边填的数。** `MapEdge` 故意**没有** `weight` 字段。通行代价属于门户类型——走廊 1 AP、门开 1 AP、门锁 2 AP、楼梯 1 AP、跳窗 0 AP（单向 高→低）、攀爬 2 AP（单向 低→高），见 L2/03 门户系统一节。作者只选 `def`，数值由该门户类型在基类层声明。否则同一类楼梯会在不同地图里代价不同，平衡数值就散了。

`dist` 的代价公式是 `link.weight * nodes[b].weight`（默认 `'sum'` 度量）。第 2 条目前**尚未接通**：门户类型的 AP 值还没有任何通道进入 `link.weight`，见第五节。

### 3.2 连接数上限按场景档位

| 档位 | 上限 | 出处 |
|------|------|------|
| 大场景 | ≤ 5 | L2/03 第 36 行 |
| 中场景 | ≤ 4 | L2/03 第 52 行 |
| 小场景 | ≤ 3 | L2/03 第 69 行 |

`src/class/scenes/index.json` 里的 `connection_limit = 5` 是五并列原则的**天花板**，不是每档的限额。校验器按上表逐档执行。L0 第十二条的五并列例外只覆盖公共变量（如 Boss 血量），**拓扑连接没有例外分支**。

这条两层分工由 `__tests__/connection-limit-layering.test.ts` 机械钉死，防的是两个方向的退化：某一档被放宽到超过天花板（能过玩法层校验却违反基类层边界），或三档全等于天花板（「天花板 + 收紧」退化成重复登记同一个数，03 号文档的空间性格丢失）。

### 3.3 Expr 键名遮蔽

`Expr` 是**非判别联合**：任何含 `path` / `op` / `call` / `q` / `var` 键的字面对象都会被求值器当成表达式节点。而 `path` 在地图语境里是极其可能的属性名（"走廊"）。这是一类静默数据损坏——不报错，只是被误解。

校验器把它作为 `MAP_OVERRIDE_KEY_SHADOWS_EXPR` 拦在发布前，并建议改名（`path` → `pathValue`）。

## 四、两层校验

| | `validateMapStructure` | `validateMapAgainstClasses` |
|---|---|---|
| 需要 IO | ❌ | ✅（要基类层目录） |
| 调用频率 | 编辑器里每次改动 | 保存 / 发布时 |
| 能发现 | 坐标越界、嵌套非法、父子环、自环、端点未吸附、连接数超限、键名遮蔽 | 场景类型未登记、尺度与 def 不符、过渡类型未登记、实例不可放置 |

两条设计约定：

1. **诊断是列表，不是异常。** 一次报出全部问题并按路径稳定排序，而不是遇到第一个就中断。创作者需要看到全貌。
2. **`error` 阻止发布，但从不阻止保存。** 半成品地图必须能存盘——否则创作过程本身被校验器绑死。

每条诊断都带 `correction`，说的是**怎么改**而不只是哪里错。测试对此有断言：任何诊断缺少人类可读的 `message` 或 `correction` 都会失败。

### 4.1 引擎是第二道闸

跨目录引用校验漏掉的东西，`prefab.spawn` 自己会拒绝（未登记的 def 直接 spawn 失败）。这是有意的冗余：校验器给创作者友好的错误信息，引擎保证即使校验被绕过也不会产出损坏的世界。

### 5.1 门户类型的 AP 值没有通道进入 `link.weight`

`PrefabDef.links[]` 的字段只有 `{ a, b, def, directed? }`——**没有 weight**。`prefab.spawn` 调 `createLinkShape(id, a, b, { def, directed })`，也不传 weight。所以经由蓝图诞生的每一条连接，运行期 `weight` 都是默认值 `1`。

对比之下，逐个手搓的路径是通的：`link.create` 接受 `weight`，`node.create` 接受 `weight` 和 `parent`。**`PrefabDef` 严格弱于逐件构造**——这是引擎层的一处不对称，不是管线的疏忽。

这件事**现在还不该修**，因为具体门户类型（走廊 / 门 / 楼梯 / 窗）根本还没在 `src/class/` 登记（只有抽象的 `transition.class.scene_link`）。也就是说眼下没有任何数值需要被搬运，先修管道等于修一根没有水的管子。正确顺序是：先登记门户类型及其 AP 值，再决定怎么让"类型上的数"落到实例上。

顺带一个已核实的事实，它会影响那个决定：**引擎层目前没有任何机制把 `Def` 上的值拷到实例上。** `Def` 有 `props` / `clamp` / `schema`，但 spawn 只展开 `opts?.props`。所以"让类型的代价自动流下来"不是现成行为，是要新增的机制。

### 5.2 `nodes[].parent` 被静默丢弃

同一个根因，更大的洞。`PrefabDef.nodes[]` 是 `{ key, def, props? }`——**没有 parent**。作者在 `MapData` 里写的父子关系编译后消失，spawn 出来的节点全是平级。

三条校验码（`MAP_PARENT_NOT_FOUND`、`MAP_ILLEGAL_SCENE_NESTING`、`MAP_PARENT_CYCLE`）本身逻辑正确，但它们守着一个到不了运行期的字段。

这不是小洞，因为 parent 在运行期是活的、且有三处依赖：

- L2/03 的距离公式要靠场景层级判"跨天然场景 +1（大场景 ×2）"；
- 微型场景的挂载就是 `parent: hostNodeId`（`micro-scene.ts:39`）；
- `graph.ts:47` 用 `.filter((n) => n.parent === parentId)` 做子节点查询。

修它和 5.1 是同一个引擎层问题的两面，所以一起做，不分开打补丁。

### 5.3 与「前端动态图形化——活体运动与对峙」的衔接

本管线产出的不仅仅是被编译进 `PrefabDef` 的**拓扑**，还包含供运行期表现消费的**几何/区域图元**。`docs/表现系统/01_图形化与UI.md`「前端动态图形化」一节定义了这些图元的运行期语义：

- **物理遮挡 / 视觉遮挡 / 高低地 / 过渡窗口**：既是本管线的**数据契约**，又是**可通行判定（双段寻路段1）**的输入。段1（游戏运行时启动预运算）把这些区域 + 碰撞箱预运算为「可通行域」，段2（实时挤压寻路）在其上做活体间避让。
- **碰撞箱** = 地图注册图元（随活体放置自动生成，非引擎层字段），作为可通行域的约束边。
- **预运算发生在运行期启动时，不在编辑器**：编辑时只存图元的严格声明（人层编码），编译时/运行时翻译为可通行域，不预计算路径。

这保证了「编译器丢弃几何」的原则仍成立（拓扑侧仍只产 `PrefabDef`），几何语义作为**独立的表现/寻路数据面**走表现系统，二者不混入同一份编译产物。

## 六、明确不做

- **程序生成地图**。已否决，理由见第一节。
- **透视 / 碰撞计算**。整图是一张图，可走性由连接定义。
- **像素坐标**。只有归一化坐标，否则换底图就得重标全图。
- **由曲线长度推导代价**。见 3.1。
- **在地图里现造场景类型或实例**。地图编辑器只放置仓库里已有的完整实例体，不做修改（06 第一节）。
