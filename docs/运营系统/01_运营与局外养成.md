## 一、定位：运营系统在三层运行期依赖链之外

引擎层、基类层、玩法层描述的是**一局游戏怎样运行**。运营系统描述的是：

- 玩家当前是否处于对局；
- 下一次加载哪份场景信息与玩法包；
- 如何在主线、附加副本、联机任务与创作活动之间移动；
- 对局之间如何形成长期经营与推进。

因此运营系统**不是 L4，也不是第四个运行期架构层**。它是三层之外的会话调度与局外体验域：

```text
运营系统
  ├─ 选择并装载场景信息 + 玩法包
  ├─ 管理对局进入、退出、异步匹配和长期推进
  └─ 不定义对局内实体、动作、伤害、AP 或胜负规则
          ↓ 装载边界
引擎层 + 基类层 + 玩法层
  └─ 负责被装载对局的全部实际运行
```

### 1.1 边界铁律

1. 运营系统不得成为第二套玩法规则引擎。
2. 运营系统不得绕过 `OpRegistry.invoke` 写入正在运行的对局状态。
3. 运营系统通过稳定的会话、装载与节奏端口依赖运行期，不依赖其内部数据形状。
4. 对局切换由运营系统重载场景信息与玩法包完成，不在基类层新增“匹配网关”或“传送网关”类别。
5. 一人节奏与战斗轮的升降发生在同一对局内，不触发场景或玩法包重载。

### 1.2 为什么不新增网关基类

竞技入口、主线出口与副本入口在玩家体验上可以表现为节点，但其点击结果是**更换整份对局上下文**，不是当前对局里的通行、检定或资源转换。把它们塞进网关类会让基类层知道会话编排，并把运营系统反向耦合到对局内结构。

运营节点只向会话调度端口提交“请求进入某项活动”的意图；是否匹配、加载何种场景和玩法包，由运营系统决定。
## 二、总体验：节点就是局外菜单

传统“竞技匹配 / 其他模式 / 自建房”按钮矩阵不是本作的默认入口。玩家在一个可移动的运营拓扑中行动，节点及其局部操作承担菜单职责。

```text
长期驻地（公司 / 庇护所 / 其他阶段性形态）
  ├─ 主线出口
  ├─ 不定期配发的附加副本
  ├─ 联机任务入口
  ├─ 商店与经营节点
  ├─ 工作台与创作入口
  └─ 收藏室
```

“公司”“庇护所”是可能随单机进程变化的叙事外观，不是本框架冻结的唯一驻地名称。节点职责保持稳定，叙事承载物可以替换。

### 2.1 单机与联机不分成两个产品入口

- 本作可被完整地视为单机游戏，联机是重要特色而不是另一套主菜单。
- 单机拥有明确主线，是长期推进的主要出口。
- 叙事采用碎片化表达，但“主线存在且可推进”必须清楚，不得把碎片化误写成没有主线。
- 联机活动以特殊任务的形式嵌入同一运营拓扑。
- 附加副本是主线之外的加法，由运营系统不定期配发，不替代主线。

### 2.2 异步匹配

玩家在联机任务节点发起匹配后，可以继续在驻地移动和使用其他非冲突节点。匹配过程不得把玩家锁在等待界面或要求原地停留。

匹配完成后，运营系统给出可见、可取消的就绪提示；接受后才进入装载边界。具体取消时限、队伍规则与失败重试属于后续联机专题，不在本框架中指定。

## 三、两种必须区分的表现状态

“一人模式”和“少 UI 模式”不是同义词，也不得共用一个开关。

| 状态 | 所在范围 | 战斗可能性 | 轮次栏 | 核心目的 |
|---|---|---|---|---|
| **一人模式** | 对局内 | 可以 | 保留但静止，突出玩家状态栏作用 | 让单人操纵连续、稳定、有轻微时间压力 |
| **少 UI 模式** | 主要用于局外驻地；玩法包也可显式用于解谜或文段 | 不允许 | 隐藏 | 去除对当前活动无意义的战斗信息 |

### 3.1 一人模式的进入条件

当同一对局中只有玩家本人，且当前不存在 AI 或其他玩家时，进入一人模式。它是**同一对局内的动态操纵节奏变化**，不是新的玩法包，也不重载场景。

任一 AI 或其他玩家进入有效活动范围后，战斗轮升起并恢复当前玩法包的标准战斗节奏；条件再次满足时，战斗轮落回一人状态。升降不能清空或重建对局状态。
### 3.2 一人模式的回合节奏

一人模式不把回合制改造成连续时间制，AP 经济也不变：

1. 玩家稳定以 **1 AP 推进 1 回合**。
2. 轮次栏不移动、不做竞争排序，只作为突出的玩家状态栏存在。
3. 玩家执行操作后，空闲计时重新开始。
4. 若连续 `x` 秒没有操作，节奏控制器请求权威运行时自然流逝 1 回合，然后重新计时。
5. `x` 是表现与操纵节奏参数，由实机调试确定；目标约等于玩家一次稳定快速决策的周期，不在设计文档中预设固定秒数。

自动流逝不是本地时钟直接改写规则。计时器到期只能通过与手动操作相同的权威通道提交“空回合推进”请求；请求被拒绝、状态已变化或一人条件失效时，不得补写或强推回合。

这形成的压力不是显眼倒计时，而是“世界会在你长期不操作时继续运转”。玩家快速连续决策时，回合边界应几乎无感。

### 3.3 少 UI 模式

少 UI 模式隐藏行动轮列表、HP、SP、AP 与战斗动作面板，只保留当前节点移动、局部交互、必要文本和运营反馈。

- 驻地默认使用少 UI 模式。
- 玩法包可以显式请求少 UI 表现，用于无战斗的解谜或文段。
- 一旦活动允许战斗，就不再属于少 UI 模式。
- 少 UI 模式只减少表现，不赋予额外规则权限，也不允许 UI 本地推进状态。

## 四、局外养成 MVP：经营与推进，而非仓库堆叠

局外养成不采用塔科夫式仓库、自由配装与逐件带入带出。自由度过高会把对局间时间变成物品管理，并破坏低心智性。

它也不退化成大厅里的一排纯数值条。MVP 的核心是：**玩家通过少量可理解的置办和经营行为，让长期驻地与主线推进发生可见变化。**

### 4.1 反无限变强

局外成长不是单纯让玩家持续变强，必要时甚至要反对这种增长方向。

- 置办内容可以帮助玩家走完主线前期的上升路线。
- 置办内容不得形成无限叠加的永久战力曲线。
- 对局仍由所加载玩法包决定开局配置、资源与规则；运营系统不得把收藏自动变成对局携带物。
- 长期推进优先改变“可进入什么、驻地如何发展、主线如何展开”，而不是只增加伤害或生命。
### 4.2 收藏室

长期取得的收藏与进展对象统一进入**收藏室**。

收藏室与 UGC 的“仓库”严格区分：

| 概念 | 保存什么 | 是否作为对局自由配装 |
|---|---|---|
| **仓库** | 创作系统中拥有的实例与表达词汇产权 | 否；服务工作台与地图创作 |
| **收藏室** | 运营推进中取得、置办或纪念的长期对象 | 否；不提供塔科夫式带入带出 |

收藏室不是物品栏的放大版，不默认提供逐件整理、容量优化、套装演算或对局前装包。其最小职责是让长期取得的事物可见、可回顾，并作为经营推进的稳定承载点。

收藏对象的具体类别、陈列交互与主线影响属于后续设计；在冻结前不得把收藏室偷偷实现为仓库。

### 4.3 低心智经营

五并列和 1–5 原则在运营系统仍然提供认知约束，但不能机械套用到无需玩家演算的内部总量，例如累计货币余额、累计游玩次数或剧情进度记录。

放宽只针对**数值记录**，不针对同时决策：

- 同屏需要比较和选择的主要经营选项仍应收敛。
- 货币总量可以超过 5，但价格设计不能要求玩家频繁做复杂换算。
- 不得用多币种数量制造虚假深度。
- 当多个系统都能表达同一推进时，优先合并入口而不是增加新的条和菜单。

## 五、UGC 经济与世界观经济的关系

UGC 货币体系与世界观内经营货币应当**可以互通，但保持心智独立**：

- 玩家应能理解自己是在进行创作研发，还是在经营驻地与推进主线。
- 两套体系不能共用一堆难以区分的余额、价格与权限标记。
- 互通不等于实时一比一换算；具体交换方向、损耗、门槛和来源尚未冻结。
- UGC 如何以“研发”等世界观理由嵌入运营系统，留给后续专题。

MVP 只发布跨域端口：运营系统可以读取创作侧给出的已确认产出/权益摘要，创作侧可以读取运营系统批准的可消费额度；双方不得依赖对方内部仓库、货币账本或实例形状。

禁止用默认汇率、赠送货币或替身余额宣称经济集成已经完成。

## 六、颜色在运营系统的使用

运营系统与对局内共用 `08_图形化与UI.md` 的全局颜色语义，不建立第二套局外调色板。商店、收藏室、匹配状态和主线节点都必须按同一套“玩家看到颜色会先猜到什么”规则选择主色。
运营系统只补充以下应用边界：

- 青色优先承担社交、交流与经济入口。
- 绿色可表达免费、低价、折扣和安全取得，但不能代替青色表示整个商店。
- 金色、银色只作少量高光与区别标记，不构成严格评级阶梯。
- 红色可标危险主线或高风险任务，但“高级任务”本身不能因为高级而使用红色。
- 灰色冷却节点仍可点击时，必须用高光、凸起与材质感表达可交互；不可点击状态必须扁平、无高光。

## 七、MVP 范围

### 7.1 必须定义

1. 一个可移动的运营节点拓扑，能承载主线出口、异步联机入口、基础经营入口与收藏室。
2. 对局进入/退出时的场景信息与玩法包装载边界。
3. 一人模式与战斗轮在同一对局内的动态升降。
4. 一人模式的 1 AP/回合节奏、无操作自动流逝与操作重置计时。
5. 驻地少 UI 表现。
6. 异步匹配期间可继续在驻地活动。
7. 收藏室与 UGC 仓库的职责隔离。
8. 明确主线存在，并为碎片化叙事留下环境、物品与节点文本位置。

### 7.2 本轮明确不定

- 驻地最终是公司、庇护所还是其他形态。
- 完整主线剧情、结局和世界观解释。
- 克隆人、记忆转移、导流技术与法律制度的完整设定。
- 附加副本的配发周期与奖励表。
- 具体货币种类、汇率、产出、回收与通胀控制。
- UGC 研发的完整经营循环。
- 收藏对象清单、陈列上限与主线增益明细。
- 联机匹配算法、房间协议与队伍权限。

这些不是被否决，而是后期专题；实现不得用临时默认值把它们伪装成已定案。

## 八、验收边界

- 删除运营系统后，任何已装载对局仍能按三层规则独立运行。
- 更换玩法包或场景数据时，不需要修改运营节点的数据结构。
- 异步匹配不会冻结驻地移动与非冲突交互。
- 一人模式升降不会重载场景、重建实体或重置玩法包状态。
- 收藏室不能用于对局前逐件配装，也不能读取 UGC 仓库内部数据。
- 少 UI 模式不显示战斗 HUD，且任何允许战斗的活动都不能伪装成少 UI 模式。
- 运营系统所有对局内写入仍经权威动作通道，计时器不能直接推进规则状态。
