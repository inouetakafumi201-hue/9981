# UGC 系统

> **归属**：基类层负责 UGC 候选产物的结构契约、统一校验端口与可组合能力；编辑器、工作台、产权、审核、发布和分发归 `docs/创作系统/`。
> **状态**：核心契约定稿；创作工具与生态能力持续演进。
> **最后更新**：2026-08-16（补：官方 TS / UGC JSON 只差表达手段，不差装载权限）
> **依赖**：`docs/L0_规范宪法.md`、`docs/00_架构域与文档分类.md`、`docs/L1_引擎层/05_底层引擎架构.md`

## 一、核心理念

### “较低的创作自由，创造了大多数人绝对的创造自由”

传统 UGC 平台把任意编程能力交给少数创作者，结果是大多数玩家只能消费。WakeUp 采用相反路线：

- 限制产物形态：只能声明实体、组件、关系、基类组合、玩法规则和已登记能力。
- 降低创作门槛：玩家可以通过图形工具或自然语言 Agent 产出声明式数据。
- 保证系统稳定：产物在进入权威注册表前经过统一编译、校验、引用解析与诊断。
- 保持三层边界：候选产物必须明确归属基类层或玩法层，不允许把编辑器实现混入运行期。

UGC 的目标不是“让数据勉强加载”，而是让非程序员能理解自己做了什么、哪里不成立、应如何修正。

## 二、架构边界与候选产物

### 2.1 UGC 产出永远是数据

- 规则 DSL 是纯声明式 JSON（D-019）。
- 禁止 `eval`、动态 TS/JS、Lua 脚本或任意代码执行。
- 所有行为必须映射到已登记 Op；最终状态写入仍经 `OpRegistry.invoke`。
- 创作来源不提供特权：手写、编辑器、自然语言适配器和导入产物适用完全相同的校验规则。
- **表达手段分级、装载权限不分级（D-081 / L0 第十四条）**：官方/开发者可用 TypeScript 对象字面量表达玩法包；UGC 玩法包必须为纯声明式 JSON、零 TypeScript。两种形态都经同一装载契约进入注册表，装载后 Def 快照地位等价。

### 2.2 候选归属

每个激活单元必须恰好声明一个目标归属：

| 目标 | 允许产出 | 禁止夹带 |
|------|----------|----------|
| **基类层候选** | 新基类类别、实例契约、能力、值集、结构边界、组合约束 | 具体玩法数值、胜负条件、UI 实现 |
| **玩法层候选** | 基类层实例组合、具体 1–5 数值、流程、玩法规则与玩法 Linter 定义 | 新引擎原语、编辑器逻辑、地图原数据、地图表现资产、世界观正文 |

创作系统只生成候选，不直接写注册表。候选必须经过所属层的权威入口才能激活。

> **熟悉度 / 梦境素材库 / 蓝本**：本文件只定义被创作产物的结构契约与统一校验，不定义「谁能创作、以什么资格创作」的世界内规则。创作资格（熟悉度=创作资格、学习→元素素材、蓝本=完整梦境蓝本、自建梦→梦主）的契约见 `docs/创作系统/02_熟悉度与梦境素材库.md`。

### 2.3 创作工具分工

| 职责 | 正式位置 |
|------|----------|
| 工作台、地图编辑器、交互流程 | `docs/创作系统/01_创作工具与产权.md` |
| 地图美术、标注、编译和发布管线 | `docs/创作系统/02_地图生产管线.md` |
| UI、动画、音频与创作界面表现 | `docs/表现系统/` |
| 候选结构、校验契约、可组合能力 | 本文档与基类层目录 |

删除创作工具后，已装载玩法包仍必须能够独立运行；玩法层生产代码禁止反向依赖编辑器。

### 2.4 地图包与带地图的玩法包边界

地图不是玩法层的一个普通 Def，也不因为被放入同一目录或 zip 就自动成为玩法层内容。正式内容分类如下：

- 玩法层：可复用的 ActionDef、RuleDef、ScheduleDef、PhaseDef、OutcomeDef、PolicyDef、DecisionDef 等声明式定义。
- 玩法文件：一次模式、剧情或对局的流程、生命周期、地图绑定、演出绑定和结果组合。
- 地图原数据文件：Canonical MapData v2，描述 layers、nodes、edges、placements 和空间数据。
- 地图表现资产：底图、图层、切片、动画、音频和环境资源；不产生规则事实。
- 地图玩法文件：将玩法层定义绑定到地图节点、边、触发器和局部流程。
- 地图包：地图原数据、地图表现资产、可选地图玩法文件和内容清单的交付集合。
- 带地图的玩法包：可引用玩法文件、地图包、玩法层和局部表现覆盖的 UGC/扩展集合。

“玩法包”只作为内容集合或传输泛称；目录、对象和 zip 都可以承载这些内容，zip 不是内容类型。官方地图包可以独立交付，UGC 带地图玩法包仍须经过统一清单、依赖、权限、schema 和规则校验。

地图注册、玩法层注册和地图包装配可以共享统一校验与唯一写入通道，但不因此合并内容类型或安全边界。

**开发者 vs 玩家（两个完全不同且永远泾渭分明的权限形态）：**

| | 开发者 / 官方 | 玩家 |
|---|---|---|
| **装载语义** | 装载后**覆盖** = 常驻，状态固定为**最终版**，无插拔 | 始终**插拔**（可回滚），不影响最终版 |
| **是否可「替换源码」** | ✅ 可。任何时刻都可有选择地对一个更新包保持装载状态，对官方是自由的 | ❌ 不可。只能在已定的装载列表里插拔，不能改「最终版」（即玩法包永远玩插拔，developer 才能替换源码） |
| **背后的机制** | 同一套「注册新内容，同 key 覆盖」 | 同一套系统，但通过装载列表表达、可回滚 |

**「地图特殊」只发生在技术层**：地图上面挂各种组件，装载时「一个地图 = 聚合了它上面挂的所有新实例」。在玩法包逻辑里没有差别——注册一个新地图，等于把前面注册的所有新实例整合到一起；若愿意，可把新玩法 / 新模式挂到这个地图上，并把新胜负条件 / 玩法绑定该地图 → 一个全新游戏模式就完成了。

**地图数据与玩法层分离装载**：地图原数据通过地图包或兼容的独立 MapData 输入装载，玩法层通过 PlaypackDef 装载；地图玩法文件负责二者的声明式绑定。未来统一 MapBundle 入口后，仍保持内容类型和安全边界分离，不把地图原数据复制进通用玩法层。

## 三、三档创作自由度

### 3.1 换皮与派生

选择已有实例，修改显示名、表现引用或玩法层允许覆盖的字段。派生结果必须有新稳定 ID 和来源记录，不改变原实例。

```json
{
  "id": "item:golden-pistol:7f3a",
  "derivedFrom": "item:standard-pistol",
  "displayName": "黄金手枪",
  "appearanceRef": "appearance:golden-pistol"
}
```

### 3.2 组合

从基类层能力与实例中组合出新实例。例如霰弹枪可以由枪类、散射属性与枪械伤害能力组合；具体伤害、范围等数值由玩法层声明。

```json
{
  "id": "weapon:scatter-example",
  "classRefs": [
    "weapon-class:gun",
    "weapon-attribute:scatter",
    "damage-class:gun"
  ],
  "playValues": {
    "range": 2,
    "damage": 3
  }
}
```

> 已废止“攻击形状/形状轴”三选一设计。散射、扫射、连发是可组合武器属性；没有属性时默认单体，无需额外形状字段。

### 3.3 定义新能力

定义新的基类、状态、检定或玩法规则。此档仍只能组合已有引擎原语；若需求必须新增引擎原语，应转为引擎层设计提案，不得由 UGC 自行扩展内核。

## 四、声明式规则 DSL

### 4.1 标准结构

```json
{
  "id": "rule:banana-peel",
  "kind": "rule",
  "version": "1.0.0",
  "trigger": {
    "eventRef": "event:entity-enter-node",
    "filter": {
      "entityRef": "item:banana-peel"
    }
  },
  "conditions": [
    {
      "exprRef": "expr:entity-exists",
      "args": ["item:banana-peel"]
    }
  ],
  "effects": [
    {
      "op": "attachment.add",
      "target": "$event.entity",
      "attachmentRef": "status:fallen",
      "duration": 1
    },
    {
      "op": "entity.remove",
      "target": "item:banana-peel"
    }
  ]
}
```

### 4.2 约束

- 不支持命令式任意循环（无界 while）、任意变量赋值、动态函数或任意代码。
- 支持声明式绑定（`let` / `be`）与受控迭代（`forEach` / `while`+`maxIter`）——后者属于声明式 DSL 表达面，不属于「变量赋值 / 命令式循环」禁令范围（D-081 / L0 第十四条 14.3）。
- 条件由 Expr/Query 表达，效果只引用已登记 Op。
- `$event.*`、`$source.*`、`$target.*` 等引用必须由 schema 声明，不能依赖字符串猜测。
- 复用规则以稳定 Def 引用和参数契约表达，不复制实现，也不使用废用术语。
- 随机行为必须请求命名随机流，保证重放与回退一致。

## 五、静态验证系统

> **D-023 正式落地**：数值检查不按“当前 UI 是否显示”过滤。规则数据中的数值默认都按 1–5 校验；只有 schema 明确标注为版本、时间戳、随机种子、实体计数等内部量纲时才可豁免。

### 5.1 验证流水线

```text
严格 JSON 解码
  → schema 与版本检查
  → 术语与归属检查
  → 数值量纲检查
  → 稳定 ID 与引用解析
  → 权限与唯一写入通道检查
  → 循环、软锁与配额检查
  → 场景化性质验证
  → 结构化诊断
  → 全部通过后才允许注册
```

验证失败时不得写入半成品，也不得用默认语义伪装成功。表现资源缺失可以表现降级；会改变规则含义的字段缺失必须拒绝。

### 5.2 Schema 与版本

- 顶层对象、字段类型、判别字段和必填项必须与发布契约一致。
- 未知字段不能静默吞掉；应按兼容策略诊断或拒绝。
- 版本号只用于兼容判断，不参与 1–5 玩法数值检查。
- 迁移必须显式、可重放且保留来源；禁止根据数据内容猜版本。

### 5.3 数值量纲检查

```typescript
function validateNumber(
  path: string,
  value: number,
  field: FieldSchema,
): Diagnostic | undefined {
  if (field.unit && INTERNAL_UNITS.has(field.unit)) return undefined;

  if (!Number.isInteger(value) || value < 1 || value > 5) {
    return {
      code: 'UGC_VALUE_OUT_OF_RANGE',
      path,
      message: `字段 ${path} 必须是 1-5 的整数`,
      correction: '把玩法数值调整到 1-5，或在 schema 中使用已批准的内部量纲',
    };
  }

  return undefined;
}
```

内部量纲白名单必须闭合并经过审查，不能由创作者自定义一个 `unit` 字符串来绕过限制。

### 5.4 引用完整性

- 所有基类、实例、状态、事件、Op、Expr、Query、地图节点和资源引用必须可解析。
- 引用目标的归属、版本和能力必须与使用位置兼容。
- 未冻结能力必须返回结构化阻塞诊断，不能替换为相似能力。
- 稳定 ID 与显示名分离；改显示名不得破坏引用。

### 5.5 循环与软锁

- 容纳关系禁止成环；拓扑关系按其契约允许成环。
- 零费附着动作不得形成无界状态增益或无限触发链。
- Hook/事件触发图必须检查无预算终止路径。
- 玩法包不得制造无法退出、无法推进且未明确声明为结局的软锁状态。
- 循环诊断必须展示最短可解释链，例如 `A → B → C → A`。

### 5.6 权限与层级检查

校验器必须拒绝：

- 基类层候选写具体玩法数值或胜负规则。
- 玩法层候选新增引擎原语或修改基类契约。
- 绕过 Action/Intent 校验直接修改其他参与者资源。
- 使用未登记写入通道、动态代码或网络/文件系统能力。
- 创作来源试图以“官方”“自然语言”或“导入”身份获得更宽规则。

### 5.7 配额与性能边界

实体数、文件大小、诊断上限和结算预算属于内部技术量纲，可以超过 5，但必须由发布契约声明上限。超限时在装载期拒绝，不允许在运行时卡死后才回退。

### 5.8 场景化验证与性质测试

静态结构通过后，可在隔离的确定性状态中生成场景并验证：

- 规则在预算内终止。
- 不产生未登记状态或悬空引用。
- 重放得到相同结果。
- 失败事务保持前态。
- 地图可达性、门户方向和玩法包声明的不变量成立。

这里的“隔离测试”不是执行创作者代码，而是让固定解释器运行声明式数据。

### 5.9 诊断契约

每条诊断至少包含：

```typescript
interface UGCDiagnostic {
  readonly code: string;
  readonly severity: 'error' | 'warning' | 'info';
  readonly path: string;
  readonly message: string;
  readonly correction: string;
  readonly sourceSpan?: SourceSpan;
  readonly relatedPaths?: readonly string[];
}
```

- `error` 阻止发布和激活，但不阻止保存半成品。
- `warning` 提醒风险，不得被当作已修复。
- 一次返回全部有界诊断，并稳定排序；不能只抛第一个错误。
- 错误码服务机器，`message` 与 `correction` 服务创作者，两者缺一不可。

## 六、Agent 式创作流程

### 6.1 完整闭环

```text
用户表达创意
  → Agent 初始化认知
  → 澄清边界与列出少量解释候选
  → 选择目标归属（Class 或 Play）
  → 生成声明式候选
  → 运行静态验证与场景化验证
  → 用自然语言解释诊断并迭代
  → 完整复述最终机制
  → 用户确认
  → 保存候选、来源与会话记录
  → 经权威入口注册或导出
```

### 6.2 初始化认知

生成任何数据前，Agent 先完成三件事：

1. 判断需求最适合由现有基类组合、玩法包配置还是新基类候选表达。
2. 对真正有歧义的地方给出少量解释候选和自己的倾向。
3. 指出可能的设计问题、层级越界、未决契约或认知负担。

即使改一个数值，也要说明目标字段、归属、影响范围与校验结果；不能为了“简单请求”绕过确认和来源记录。

### 6.3 边界追问示例

玩家提出“香蕉皮，别人踩到会摔倒”时，Agent 应确认：

- 触发是进入节点、进入局部空间还是拾取？
- “摔倒”引用哪个已登记状态，持续多久？
- 是否一次性销毁？
- 放置和触发分别需要什么动作权限？
- 该产物是可复用基类实例，还是某玩法包的具体物品？

Agent 不得一次性猜完并直接激活。

### 6.4 创作后确认

- 完整复述触发、条件、效果、数值、引用和失败行为。
- 展示静态验证结果与仍未解决的警告。
- 保存最终数据、来源、版本和完整会话记录。
- 生成清晰简介，便于他人在装载前理解玩法包。

## 七、玩法包编译器出口头

### 7.1 统一验证入口

玩法包是 LLM 工具、玩家上传、审核系统的共同产物。为避免分散验证逻辑，所有玩法包必须经过统一编译器：

```typescript
interface PlaypackInput {
  readonly id: string;
  readonly name: string;
  readonly version: string;
  readonly manifests: ReadonlyMap<string, string>;  // 路径 → JSON 字符串
  readonly assets: ReadonlyMap<string, ArrayBuffer>; // 路径 → 二进制内容
  readonly source: 'llm-generated' | 'player-uploaded' | 'uploaded' | 'official';
  readonly creatorSteamId: string | null;
}

type PlaypackCompileResult =
  | { ok: true; artifact: CompiledPlaypack }
  | { ok: false; diagnostics: readonly PlaypackDiagnostic[] };
```

`CompileResult` 的编译产物（`CompiledPlaypack`）携带安全等级 `tier`：

```typescript
interface CompiledPlaypack {
  // …结构、引用、诊断等既有字段…
  readonly tier: 'standard' | 'advanced'; // 由编译器可达性扫描判定，见 §7.5
}
```

> **Tier 与「高级」是两套互不替代的维度**：`tier`（复杂度评分，§7.3 的 Tier 1-4）只计量结构复杂度、用于定价分档；此处的 `tier: 'standard' | 'advanced'` 是**安全等级**，由编译器对产物做可达性扫描判定，决定可用场景。前者回答「有多复杂」，后者回答「能否探索联机」。两者名称接近但语义无关，不可互相推导。

编译器组合现有能力而非新增规则：

1. **JSON 解析**：使用 `parseStrictDataJson`（拒绝注释、尾逗号、重复键）
2. **Profile 审计**：调用 `auditNumericValues`（数值归属、1-5 范围）
3. **地图编译**：调用 `validateMapStructure` + `compileMap`
4. **引用完整性**：收集所有 `.class.` 引用，供审核系统使用

### 7.2 诊断的 autoFixable 标志

每条诊断携带 `autoFixable: boolean`，告诉 LLM 哪些问题可以自动修正：

| 问题类型 | autoFixable | suggestedFix |
|----------|-------------|--------------|
| 数值越界（damage: 47） | ✅ true | 5（限幅到上限） |
| 缺少必填字段 | ✅ true | 从上下文推断的默认值 |
| 引用不存在的基类 | ❌ false | 需要人工决定用哪个 |
| JSON 语法错误 | ❌ false | LLM 无法定位 |
| 地图结构错误（坐标越界、父子环） | ❌ false | 涉及拓扑结构 |

LLM 收到 `autoFixable: true` 的诊断时：

1. 读取 `suggestedFix`
2. 修改 JSON
3. 重新提交编译
4. 最多重试 3 次，仍失败则返回用户

### 7.3 复杂度评分与定价分档

复杂度评分只计数结构，不管强度：

```typescript
complexityScore = profileCount × 10 + mapCount × 50 + customRuleCount × 100
```

推荐分档（实际定价由运营决定）：

| 分档 | 评分范围 | 典型内容 |
|------|----------|----------|
| Tier 1 | < 100 | ≤10 个实例，无地图 |
| Tier 2 | 100-499 | ≤50 个实例，或 1 张地图 |
| Tier 3 | 500-999 | >50 个实例，或多张地图 |
| Tier 4 | ≥1000 | 含自定义规则 |

**关键原则**：买了用不好没有危害。花大钱买复杂实例、不理解就乱放，结果只是做出不好玩的地图，损失全部内化。

### 7.4 来源不提供特权

`source` 字段（`llm-generated` / `player-uploaded` / `uploaded` / `official`）只进入审计与诊断，**不改变 Schema、配额、severity 或任何验证规则**。

这意味着：

- LLM 生成的玩法包和手写的玩法包走完全相同的校验管线
- 免费上传的黑箱包和官方包必须过全量校验
- "来源"只是溯源标签，不是特权标识

### 7.5 高级判定：安全等级由编译器扫描产物决定

玩法包在编译时由编译器对**玩法包整体**做**可达性静态扫描**：凡**含引擎层引用**的玩法包 → 打「**高级**」标签（`tier: 'advanced'`）。**含地图定义不构成高级**——地图只是带地图 tag。

- **判定看产物、不看来源/声明**：不依据 `source` 字段、作者声明或玩家认知判定，只看编译产物本身是否含引擎层引用。
- **命中式而非显式声明**：只要产物中可达一个引擎层原语（如 kernel Op、Def kind、引擎层 Ref 前缀），命中即触发高级，不要求作者显式声明「我是高级包」。
- **警告器提示**：命中高级时附一条明确提示——「此玩法包涉及引擎层的改动，将被定义为高级玩法包，无法进行探索联机」。
- **高级包可用范围**：仅限**自建房联机 / 单机**，**探索匹配匹配不到**（对探索匹配不可见）。

> 高级判定与 §7.3 的「Tier 复杂度评分」是两套互不替代的维度：Tier 只用于定价分档（回答"有多复杂"），高级判定决定可用场景（回答"能否探索联机"）。

### 7.6 玩法包装载语义：无名重装载模型

玩法包装载收敛为一套**无名重装载模型**（D-073 / D-075），核心是「JSON 重新定义即替换或新增，最终声明即最终版」：

配权规则四句：

1. **玩法包是无名的（不引入 namespace / 来源归属维度）**：玩法包装载后，状态固定即为新版本（新玩法层）。不存在「拔出玩法包」——只有**回滚到未装载某玩法包之前的状态**；剔除一个包，本质是把**剩余玩法包按新顺序重新装载一遍**。
2. **顺序即优先级，后装覆盖先装**：玩法包按装载顺序应用，**后装载的包覆盖先装载的**。图形化用一个拖拽先后顺序列表表达装载顺序/覆盖优先级，玩家可直接理解，不报错。
3. **剔除（回滚）= 从列表移除该包 + 触发一次整体重装载**：其余包按新顺序重载为新版本。剔除其他地图遵循**不重载原则（不报错，跳过）**。
4. **剩 ID 即退役（不设 DELETE 声明）**：对一个 def 用 `replace` 出新版、下方引用留空，则只剩其 ID；只剩 ID 的 def **不可再被引用**，即逻辑上删除。它**不伤及仍引用它的老数据**，只使「引用失效」而非「引用崩溃」。

同 `key` 的 ID 用**随机符号尾数**编码，**重名概率极低**；重名时**后注册覆盖先注册（同 key 即替换）**。

**来源 / 归属不进入装载优先级判定**：装载优先级只由装载顺序决定，不因来源（官方 / 上传 / LLM）或归属而改变相对次序。

### 7.7 内容类型与交互地位

现行内容语义以七类 ContentKind 为准；本节保留“素材”和“限免组件”的交互地位说明，不再用 zip 或目录形态作为内容分类依据。

| 内容类型 | 主要职责 | 交互/装载地位 |
|------|----------|----------|
| **玩法层** | 可复用 ActionDef、RuleDef、ScheduleDef、PhaseDef、OutcomeDef、PolicyDef、DecisionDef 等定义 | 经 PlaypackDef 装载进入规则运行链 |
| **玩法文件** | 一次模式、剧情或对局的流程、生命周期、地图绑定与结果组合 | 经清单和依赖校验后按需装载 |
| **地图原数据文件** | Canonical MapData v2 的 layers、nodes、edges、placements | 地图包或兼容独立 MapData 输入的装载入口 |
| **地图表现资产** | 底图、图层、切片、动画、音频和环境资源 | 通过资源适配器按视觉窗口载入 |
| **地图玩法文件** | 玩法层定义到地图节点、边、触发器和局部流程的绑定 | 随地图包或带地图玩法包按入口装载 |
| **地图包** | 地图原数据、表现资产、可选地图玩法文件和内容清单 | 官方或 UGC 的地图中心交付集合 |
| **带地图的玩法包** | 玩法文件、地图包引用、局部定义和表现覆盖 | UGC/扩展集合，按安全策略审核和装载 |

- **玩法包**未附具体 ContentKind 时，只表示内容集合或传输泛称；目录、对象和 zip 均可作为载体，zip 不决定语义。
- **素材**仍是素材库中的单个可选用内容对象，是否被打包不改变其内容职责。
- **限免组件**仍是地图附带的临时免费实例，其可带出规则由创作/运营契约决定。
- 地图原数据、地图表现资产和玩法层定义可以在一次对局中协同装载，但不因此合并内容类型或安全边界。

### 7.8 实现位置

```
src/play/playpack-compiler/
├── types.ts           # PlaypackInput、CompileResult、Diagnostic
├── compile.ts         # 主编译逻辑（调用现有编译器）
├── complexity.ts      # 复杂度评分与分档建议
└── __tests__/         # 端到端测试（73 个测试）
```

编译器已实现并测试，但 LLM 工具的前端（采访界面、支付界面、形象编辑器）未实现。

> **单调重定义实现映射（D-073 / D-077）**：§7.6 的无名重装载模型需落到装载器——`src/core/kernel/schedule/playpack.ts` 与 L2 `DefinitionRegistry` 当前是「声明型冲突解决」（`E_LOAD_CONFLICT` + `REF_OVERRIDE_NOT_DECLARED`）。按 D-073，把装载改为单调重定义：同 key 后装覆盖先装、同 key 即替换或新增、剩 ID 即退役、跨作用域冲突拒绝；重定义在装载事务的原子 swap 之前完成，运行期不热改写已生效注册表（唯一写入通道 + 原子验证不可绕过）。地图位按 ID（随机符号尾数）区分，同 key 撞位才判「不可替换」，异 key 不互排。该改造的工程需求/设计/性质见 `.kiro/specs/wakeup-engine-layer/`。

### 7.9 官方 TS 与 UGC JSON 的分离

- 官方可以用 TypeScript 对象字面量 authoring 玩法包，例如 `src/play/core-mechanics/defs/playpack.ts` 里的 `CoreMechanicsPlaypack`。
- UGC 只能写 JSON，例如 `src/play/action-turn/playpack.json`。
- 这只是表达手段分离，不是装载权限分离。
- 两者都必须先成为 `PlaypackDef` 候选，再进入 `PlaypackLoader.load` / `PlaypackActivator.activate` 统一管道。
- 装载后它们在注册表里的 Def 快照地位完全一样，后装同 key 覆盖先装（D-073）。
- UGC JSON 的表达力必须足够：至少能改到基类层、能引用引擎层、能写流程、状态机、条件和容器。

## 八、LLM 职责边界

### 可以做

- 理解自然语言意图并识别目标归属。
- 追问边界条件，提出少量可解释方案。
- 查询现有目录和稳定端口。
- 生成声明式 JSON 候选（直接写 JSON，理解基类层与官方玩法层）。
- 调用同一套验证流水线并解释诊断。
- 生成说明、变更摘要和测试场景。
- **新增实例**：组合基类层能力，填充玩法层数值。
- **引用地图**：玩家自己创作的地图和官方地图。
- **定义高阶玩法机制**：通过组合基类衍生，不直接作用于实例的机制。

### 不能做

- 直接执行游戏逻辑或充当权威裁判。
- 运行任意代码或生成可执行脚本。
- 绕过静态验证、权限检查或未决契约。
- 修改引擎不变量或擅自新增 Op。
- 用默认值掩盖规则字段缺失。
- 通过新造内部量纲绕过 1–5。
- 把自己的推断写成已获项目所有者确认的规则。
- **新增基类**：基类定义可上升至引擎层接壤，LLM 写不出来。
- **新增表现层实现**：只能用现有的视觉效果、UI 组件、动画编排。
- **直接操作地图编辑器**：地图编辑需要几何标注（归一化坐标、曲线）。

### 与工具链的协同

LLM 通过 Function Calling（方案 A）调用工具：

| 工具函数 | 用途 | 返回值 |
|----------|------|--------|
| `compile_playpack` | 编译并验证玩法包 | `PlaypackCompileResult` |
| `query_base_classes` | 查询可用基类 | 基类列表（category 过滤） |
| `query_player_maps` | 查询玩家地图 | 地图列表（可引用的） |
| `show_image_editor` | 弹出形象编辑器 | 素材路径（像素编辑器 / 样板库 / 上传） |

备用方案 B（纯文本指令 + 正则解析）：LLM 在回复中插入 ` ```json:路径 ` 代码块，前端解析并调用编译器。方案 A 优先，因为 DeepSeek V4 / GLM-5 都支持 Function Calling。

## 九、扩展能力与边界

### 9.1 已支持的扩展方向

- 新地图拓扑与具体地图数据。
- 新物品、武器、防具、容器和载具实例组合。

- 任意代码、网络访问、文件系统访问。

- 越过目标层修改其他层权威契约。
- 用重复实现或适配器固化两套“唯一入口”。

## 十、分享、审核与分发

### 10.1 轻量内容包

内容包由声明式 JSON、必要的图像/音频资源和 manifest 构成。资源体积是工程指标，不受玩家可见 1–5 限制；发布系统应支持缓存、内容哈希和增量下载。

```json
{
  "contentId": "ugc:zombie-school",
  "version": "1.2.0",
  "authorId": "creator:example",
  "contentHash": "sha256:…",
  "engineCompatibility": ">=1.0.0",
  "requiredCapabilities": ["capability:portals", "capability:status-effects"]
}
```

### 10.2 即时装载流程

```text
发现内容
  → 检查本地缓存与哈希
  → 下载缺失资源
  → 严格解码与全量验证
  → 显示诊断或变更摘要
  → 用户确认
  → 权威注册与装载
```

下载完成不等于可装载；任何版本、引用或权限错误都必须在注册前阻断。

**装载语义遵循 §7.6 无名重装载模型**：

- **回滚 = 移除重装载**：剔除一个玩法包，本质是把剩余玩法包按新顺序重新装载一遍，不存在「拔出玩法包」。
- **跨作用域冲突一律拒绝**：同 key 撞位遵循「后装覆盖先装」的单调重定义；**跨作用域（本包声明以外的归属 / 命名空间）冲突一律拒绝，不设「确认放行」**。

### 10.3 双轨内容生态

| 通道 | 职责 |
|------|------|
| **官方规则通道** | 经过严格平衡和兼容验证，可用于官方活动、排位或锦标赛 |
| **社区实验通道** | 承载快速迭代、特殊玩法和 AI 辅助创作；仍执行同一安全与结构校验 |

“实验”不代表可以绕过验证，只表示平衡与长期兼容承诺不同。

### 10.4 自动审核

自动审核至少覆盖：

- 结构、引用、性能与恶意行为检查。
- 不当内容和版权风险标记。
- 与已声明许可证、来源和作者身份的一致性。
- 漏洞利用、权限绕过和隐藏数据侧信道。

自动审核必须输出可申诉的结构化原因，不能只给黑箱分数。

**上传玩法包的核准入池**：

- **上传必审核入池**：玩家上传的玩法包若要联机（含自建房），必须**异步提交审核**；审核通过、打上标记后才能进入池子。
- **更新需重审**：玩法包更新后必须**重新审核**，不能沿用旧版本的核准状态。
- **上传两态**（D-077）：一态为**可插拔的普通玩法包**（带 UGC 角标，符合玩家叙事认知）；二态按地图**切成多个口子**，只能从各自入口进入，进图装载阶段装载整个包（见 §7.6、D-079）。

### 10.5 社区审核

- 新内容可标记为未验证或实验性。
- 玩家可以评分、举报并提交可复现问题。
- 社区认可不替代机器校验。
- 官方收录必须产生新版本、来源记录和明确的权利状态，不能静默“升格”。

### 10.6 发现与激励

- 标签应区分机器推导与社区投票来源。
- 推荐依据应可解释，避免只奖励高频发布。
- 创作者成就、游玩反馈和收益属于运营/创作专题；不得反向改变规则校验强度。

产权、仓库、派生、黑箱包和经济边界详见 `docs/创作系统/01_创作工具与产权.md`。

## 十一、LLM 工具的采访流程

### 11.1 完整循环

```text
玩家提出需求（或指定玩法包 + 加工需求,不包含地图编辑）
  → 判断能否形成完全无歧义的玩法逻辑
  → 标出哪些需要补充、哪些不够合理、违反哪些建议原则
  → 进行 2-4 轮采访（单选 + 可补充的图形化模式）
  → 循循善诱,诱导做出完善且合理的配置规范
  → 可调用"形象编辑"工具（左侧像素编辑器 / 样板库 / 上传图片）
  → 认为已穷尽意图且可行后,显示支付界面（游戏内货币,价格按复杂层级分档）
  → 自主设计并写好玩法包,填好简介、详细机制介绍
  → 展示给玩家确认（与其他玩家查看此玩法包的界面相同）
  → 可点击"继续加工",再开一次循环
  → 保存最后一版,可直接用于联机
```

### 11.2 采访结构

**没有固定的问题树,但有结构引导：**

| 轮次 | 目标 | 典型问题 |
|------|------|----------|
| 第 1 轮 | 确定玩法类型与核心机制 | 这是大逃杀 / 夺旗 / 团队竞技？主要依靠近战还是远程？ |
| 第 2 轮 | 补充规则细节 | 初始装备？缩圈规则？胜利条件？ |
| 第 3 轮 | 数值配置与平衡 | 伤害表？AP 成本？血量上限？ |
| 第 4 轮（可选） | 特殊机制确认 | 是否有 NPC？特殊状态？环境效果？ |

**注重高效**：如果玩家的需求已经足够明确（例如"标准大逃杀,近战流派,空手开局"）,可以只问 1-2 轮确认关键数值。

**违反建议原则的处理**：

- 违反五并列原则（>5 个同时可选项）→ **警告,但不硬拦截**
- 违反 1-5 数值约束 → **编译器会拦截**（error 诊断）
- 违反已确认决策（例如试图让伤害翻倍但不走骰点机制）→ **警告并说明设计原因**
- 违反三层架构（试图修改引擎层）→ **直接拒绝**（LLM 写不出来）

### 11.3 形象编辑工具

弹出窗口,根据要编辑的形象类型,形式会不一样：

- **左侧**：像素编辑器（32×32 或 64×64,根据类型决定）
- **右侧三个入口**：
  1. 自主绘制（提供调色板、笔刷、橡皮擦、填充）
  2. 样板库选择（官方预设图标库）
  3. 上传图片（上线后可因政策原因关闭）

**约束**：
- 图标尺寸固定（武器 32×32,载具 64×64）
- 格式限制（PNG/JPG,透明通道可选）
- 文件大小限制（≤256 KB）

### 11.4 支付界面与定价分档

**价格固定分档,不以强度而以层次为判定：**

| 档次 | 价格（游戏内货币） | 典型内容 |
|------|-------------------|----------|
| Tier 1 | 100 | ≤10 个实例,无地图 |
| Tier 2 | 300 | ≤50 个实例,或 1 张地图 |
| Tier 3 | 900 | >50 个实例,或多张地图 |
| Tier 4 | 2700 | 含自定义规则（暂未开放） |

**计算公式**（后端自动计算,前端展示）：
```
复杂度评分 = 新增/重定义实例数 × 10 + 地图数 × 50 + 自定义规则数 × 100
```

**关键原则**：买了用不好没有危害。花大钱买复杂玩法包,不理解就乱用,结果只是做出不好玩的模式,损失全部内化。

### 11.5 确认界面

**与其他玩家查看玩法包的界面完全相同**,包括：

- 玩法包名称与版本
- 简介（LLM 生成的一段话描述）
- 详细机制介绍（展开后可见,包含实例列表、规则配置、数值表）
- 作者标识（创作者 Steam ID）
- 复杂度评分（Tier 1-4）
- "开始游戏" / "继续加工" 两个按钮

"继续加工"实质上是再开一次采访循环,**迭代并保存最后一版**。

### 11.6 发布渠道

| 渠道 | 审核要求 | 可用范围 |
|------|----------|----------|
| **单机** | 无审核,随便用 | 仅本地 |
| **联机（LLM 生成）** | 无审核,直接可用 | 所有联机房间 |
| **联机（自主上传）** | 需审核通过 | 审核通过后可用 |

**LLM 生成的玩法包可以直接用于联机**,原因：

1. 编译器已经验证了结构、数值、引用完整性
2. LLM 不会生成恶意代码（它写不出来）
3. 风控机制已经过滤了提示词注入与敏感内容

**自主上传的玩法包需要审核**,原因：

1. 可能包含手写的复杂逻辑（高阶开发者可以直接调用引擎层）
2. 可能包含恶意素材（政治、色情、暴力）

## 十二、LLM 工具的风控机制

### 12.1 关键词计分风控

**敏感词库**（三类）：

| 类别 | 示例 | 权重 | 阈值 |
|------|------|------|------|
| 政治敏感 | [具体词库运营配置] | 50 | 累积 100 分封号 |
| 色情暴力 | [具体词库运营配置] | 30 | 累积 100 分封号 |
| 欺诈诱导 | "免费刷币" / "必胜外挂" | 40 | 累积 100 分封号 |

**提示词注入检测**（更重要）：

- 检测模式：正则匹配 + 语义相似度
- 触发词：`ignore previous`, `system prompt`, `you are now`, `forget all`, `role: admin`
- **触发后行为**：
  1. 风控权重 +80（接近阈值）
  2. 暗中调用二次校验（见 12.2）
  3. 会话内容进入人工审核池

**累积分数查询**：

- 玩家可以在设置里查看自己的风控分数（透明化）
- 每次触发会显示：`+30 分（检测到敏感词:XXX）,当前累积 45/100`
- 达到 100 分时弹窗提示：`风控分数已满,Steam 账号将被封禁,可申诉`

### 12.2 二次校验（暗中调用）

**触发条件**：

1. 提示词注入检测命中
2. 单次对话 token 消耗异常（>单次上限 80%）
3. 生成内容与玩家输入语义相似度过低（<0.3）

**执行方式**：

1. 将玩家的原始输入（不含 LLM 回复）扔给另一个封闭上下文的便宜模型（GLM-4-Flash 或 DeepSeek-V3）
2. 快速判断：这是正常的玩法包需求,还是试图攻击系统？
3. 如果两个模型的判断不一致（主模型说"正常",校验模型说"攻击"）→ 风控权重 +50,进入人工审核池

**不告知玩家**：二次校验在后台静默执行,玩家不可见。只有触发封号时才会在申诉流程中看到"二次校验未通过"的记录。

### 12.3 会话留档与申诉

**所有与 AI 的对话都能留档**：

- 玩家输入（原始文本）
- LLM 回复（包括工具调用记录）
- 风控事件（触发时间、触发词、权重增量）
- 二次校验结果（如果有）

**封号申诉流程**：

1. 玩家在 Steam 社区提交申诉
2. 人工审核员查看完整会话记录
3. 判断是误触发（例如讨论游戏机制时用了"ignore"这个词）还是真实攻击
4. 误触发 → 解封 + 清零风控分数
5. 真实攻击 → 维持封号

### 12.4 Token 硬上限

**单次加工循环 token 硬上限**：50,000 tokens（输入 + 输出）

**超出后行为**：

1. 截断对话,显示提示：`当前加工循环已达到复杂度上限,请简化需求或分次加工`
2. 已生成的部分保存为草稿,可以"继续加工"
3. 风控权重 +10（轻微惩罚,因为可能是玩家真的需求太复杂）

**为什么设置硬上限**：

1. 防止恶意消耗算力（例如让 LLM 生成 1000 个实例）
2. 防止提示词注入通过"淹没上下文"绕过检测
3. 控制单次加工的经济成本

## 十三、长期文档体系

底层与装载闭环稳定后，持续维护三类不同读者的文档：

1. **开发者 / Agent 规范**：最完整的接口、边界、诊断和事实源；用于实现与架构审查。
2. **创作 Agent 指令集**：教会 Agent 查询目录、追问边界、生成候选、解释诊断和确认结果；不能把全库内容硬塞进单一提示词，应依赖实时查询定位。
3. **玩家创作协议**：以可读案例解释能做什么、怎样组合、为何被拒绝，服务图形工具用户与愿意深入的创作者。

三份文档共享稳定 ID 和机器契约，但不能互相复制形成三套权威。开发者规范是接口事实源，另外两份是面向不同读者的投影。

## 十四、明确不恢复的历史内容

- 使用废用术语的复用语法，已改为稳定 Def 引用与参数契约。
- Lua/JS 脚本沙盒、任意代码执行与插件逃生口。
- “缺少规则字段就填默认值并继续”的宽松装载方式。
- 两套互相冲突的局内投票改规则流程；如未来重启，必须单独立项并重新裁决。
- 把编辑器、审核或分发写成基类层运行时职责。
