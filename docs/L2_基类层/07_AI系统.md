# AI 系统设计

> **架构原则**：主干使用 **αβ 剪枝搜索 + 随机选择器**（可怕的通用性），语义意图作为**宏动作生成器**压缩搜索分支。NPC AI 与玩家 AI 彻底分离，不共享算法。

---

## 架构总览

### 两套独立的 AI 系统

| | 玩家 AI（可选辅助） | NPC AI（必需） |
|---|---|---|
| **用途** | 玩家挂机 / 提示系统 | 驱动所有 NPC 行为 |
| **算法** | αβ 剪枝 + 随机选择器 | 守卫范式（状态-目标-意图） |
| **资源** | 复用 AP 价格表 + 玩家回合 | 复用 AP 价格表，独立行动阶段 |
| **目标** | 模拟理性玩家决策 | 提供可预测的威胁与挑战 |

**严禁混用**：玩家 AI 不能用来驱动 NPC，NPC 逻辑不能用来辅助玩家。

---

## 玩家 AI（挂机 / 提示系统）

### 核心：αβ 剪枝搜索 + 随机选择器

**设计哲学**：像棋类 AI 一样，通用且可扩展。

```typescript
interface PlayerAI {
  // 主入口
  selectAction(state: GameState, player: EntityId, depth: number): Action;
  
  // αβ 搜索（maxⁿ / 老实模型，无 maximizingPlayer 参数）
  alphaBeta(
    agent: EntityId,
    beliefSlice: BeliefState,   // 搜索入口处 sliceFor(agent, worldState) 算一次，递归层直接继承
    depth: number,
    alpha: number,
    beta: number
  ): { score: number; action: Action };
  
  // 随机选择器（打破平局）
  randomSelector(actions: Action[], scores: number[]): Action;
  
  // 估值函数（调用底层服务，经 evaluateGuard 守卫校验）
  evaluate(agent: EntityId, beliefSlice: BeliefState): number;
  
  // 搜索入口切片
  sliceFor(agent: EntityId, worldState: GameState): BeliefState;
}
```

**PolicyDef search 模式 schema**（`schedule/policy.ts`）：

```typescript
interface PolicyDef extends Def {
  readonly kind: 'policy';
  readonly mode: 'rules' | 'search' | 'scripted';
  // ...
  /** mode:'search' — 搜索深度上限 */
  readonly searchDepth?: number;
  /** mode:'search' — 搜索目标表达式（Expr，求值后经 evaluateGuard 守卫）*/
  readonly searchGoal?: Expr;
}
```

- `searchDepth` 控制递归层数（depth=5 = 5个连续单步决策点）。
- `searchGoal` 是玩法包提供的 `Expr`，求值结果经 `evaluateGuard` 守卫校验为有限数后才参与剪枝判断。

#### 签名说明：beliefSlice 替代 state: GameState

- **改造原因**：原 `state: GameState` 把"完整世界事实"塞进搜索。但 AI 在不完全信息下做决策，递归层看到的应是"该 agent 当前可推断的世界切片"，否则会把对手的信息也并入递归。
- **search 入口算一次**：调用 `sliceFor(agent, worldState)` 构造 `BeliefState`，仅在搜索 root 调用一次。
- **递归层继承**：αβ/maxⁿ 递归过程中直接传递同一 `BeliefState` 引用，不再从世界重新切片； belieSlice 按 agent 视角"冻结"于该决策点，保证整条决策链视角一致。
- **切片构造过程**（`sliceFor` 函数）：
  1. 用 `Query.visibleTo`（已实现）过滤出真正看得见的对象；
  2. 对看不见但"记得"的对象，读 `Agent.knowledgeScope.facts` 里记的最后已知位置当替身（`facts['position:${targetId}']`）；
  3. 两者都没有的，直接从参与者集合剔除。
- **不等同于传统 GameState**：BeliefState 包含可见实体确定值 + 不可见实体的概率/不确定带（见 belief-slice 模块）。

#### 签名说明：去掉 maximizingPlayer，改用老实模型（maxⁿ）

- **maximizingPlayer: boolean 已移除**：二人 αβ 的"我方最大化 / 对方最小化"二元切换，本游戏不适用。
- **本游戏是多人异步 / 老实模型（maxⁿ）**：每个 agent 递归时各自计算**自己的分数**并回传，不虚构一个"联合对手"来对自己最小化。
- **为何不能偏执化（联合极小化对手）**：偏执化会系统性低估"对手互耗"类正确打法——例如 A 让 B、C 互打而自己规避，这种打法收益来自对手彼此消耗而非本方直接行动。把对手联合起来对我极小化，会假设"两个对手协同反我"，于是低估任何引诱互耗的着法（评分被压成接近放弃互耗）。maxⁿ 让每个对手只最大化自己，互耗着法的价值才能如实浮出。

### αβ 剪枝流程（maxⁿ 老实模型）

```
1. 生成当前所有合法动作（来自底层 ActionSystem，受白名单标签过滤）
2. 对每个动作：
   a. 应用动作 → 生成后继 BeliefState（同一引用，不重新切片）
   b. 递归搜索下一个 agent 回合（各自 maxⁿ，不联合对手） → 获得该 agent 自身评分
   c. αβ 剪枝（超出边界立即停止）
3. 选择评分最高的动作
4. 如果多个动作评分相同 → 随机选择器
```

**深度语义（需求 29.6 / 29.7 锁死）**：

- **`depth=5` 的定义**：5 个**连续单步决策点**。每一层对应一次"下一个 agent 完成其单步决策"的节点，**不是**"5 个完整角色回合"。
- **绝无同时博弈 / Nash 均衡问题**：需求 29.6-29.7 锁死结算顺序（每一决策点只有一个 agent 在动作），因此 5 层搜索等价于 5 步串行推进，不引入同步/博弈矩阵问题。
- **对应关系**：1 个 agent 决策 = 1 步；多人序列 = 多步；与"多回合前瞻"不同，深度只数**决策点**，不数**角色**或**结算批次**。

**剪枝优化**：
- 断崖领先终止（一个动作评分远超其他 → 不再搜索）
- 移动顺序启发（优先搜索高价值动作）
- 缓存已搜索状态（Transposition Table）

### 搜索树外：体力 / 强力骰（异步独立门槛）

- **不作为搜索分支**：体力判定 / 强力骰触发不走分支枚举，避免把"是否够体力 / 是否掷强力骰"膨胀成搜索树分支。
- **异步独立门槛判断**：在进入决策前，按各 agent 自身阈值先做一轮独立检查（参考 `evaluate-guard` / `tiering` 的阈值语义）：
  - 体力 < 阈值 → 跳过需消耗 AP 的着法类别
  - 强力骰 ≥ 阈值 → 走高置信分支（白名单着法中优先）
- **与搜索解耦的好处**：门槛判断只依赖 agent 局部状态，计算量 O(1)，且与多 agent maxⁿ 解耦，不会产生"对方门槛"污染 BeliefState 的问题。

### 语义意图：宏动作生成器

**不是决策层，是压缩搜索分支的工具。**

interface SemanticIntent {

**认真设计意图能大大提升性能和真实感**：
- 减少搜索分支（100+ 动作 → 5 个宏动作）
- 提供语义可解释性（玩家能理解 AI 在干什么）
- 易于调试（意图评分可视化）

### 精算层 vs 粗略层（两档策略）

搜索决策入口固定分类为两档，**整条决策链全程不升降级**（避免中途切换导致回溯一致性丢失）。

| 档位 | 适用规模 | 展开策略 |
|---|---|---|
| **精算层** | 0–2 个活跃 agent（含玩家） | 完整 maxⁿ 递归，与玩家搜索深度相同 |
| **粗略层** | 其余全部（≥3 个活跃 agent 或大批量 NPC） | 白名单着法展开，默认 `ai-significant` 标签；未配置标签时默认按粗略处理（**不是**默认精算） |

**关键约束**：
1. **根节点固定分类**：搜索起点根据"活跃 agent 数量"与"白名单标签配置"一次决定档位，之后整条搜索链沿用。
2. **不升降级**：递归过程中即使活跃数变化或中途发现新 agent，不切换档位——这是防止"不同分支用不同预算"导致的评分不可比问题的核心。
3. **粗略层白名单**：
   - 基于 `Def.tags`（标签名由玩法包定义，内核不掌握"对胜负有意义"的语义，只提供机制）。
   - 玩法包给需要 AI 纳入博弈的动作打上 `ai-significant` 标签，只有带此标签的动作才进入粗略层候选分支。
   - 白名单标签的正式字段命名：**`Def.tags`**（来自 `actions/types.ts` 中的 `ActionDef extends Def`），在 `tiering.ts` 中通过 `action.tags?.includes(tag)` 过滤。
4. **默认行为**：未配置 `ai-significant` 标签时 → **默认粗略**（白名单为空 = 不允许任何动作 = 静默跳过）。这不是"内核替玩法包做安全兜底"，而是"这个玩法包还没写完"——默认精算等于内核偷偷替未完成的玩法包做了一次游戏设计判断。

**典型场景举例**：
- 玩家单挑 1 个 NPC：精算层，完整 maxⁿ。
- 玩家 + 3 个丧尸 + 1 个守卫：粗略层，NPC 走白名单，玩家层仍可精算（取决于调用方是否分叉），但统一走"整条链固定一档"规则。
- 批量 NPC 互殴（无玩家）：粗略层。

### 估值函数（调用底层服务 + 守卫校验）

**不在 AI 模块实现，调用 `EvaluationService`（05 文档内核层）。**

```typescript
function evaluate(agent: EntityId, beliefSlice: BeliefState): number {
  return evaluationService.evaluateInBelief(
    beliefSlice.entities[agent],
    beliefSlice
  );
}
```

**AI 模块不包含估值逻辑**，只负责搜索。估值入口同样以 `beliefSlice` 为输入（而非全 `GameState`），保证搜索、估值、切片三处视角一致。

**`evaluate` 返回值守卫（evaluateGuard）**：
`PolicyDef.searchGoal` 是一个 `Expr`，其 `eval` 返回类型是 `Value | null`——`Value` 允许字符串/数组/对象/Ref，不一定是数字。但 alpha-beta 的每次剪枝判断（`score > beta`）要求分数是**有限实数**。

若某条 `evaluate` 因路径越界或类型不匹配返回 `null`/NaN/Infinity，JS 中 `null > beta` 直接是 `false`，搜索会静默把这个分支当成一个特定的低分处理，不产生任何诊断——这是与"静默合成畸形状态"同一类的缺陷。

**修法**：在搜索的 `evaluate` 调用边界上强制加 `evaluateGuard` 守卫：
- 非法返回值（null / NaN / Infinity）→ 捕获，产出诊断信息，使用中性默认值（0）替代
- 合法有限数 → 直接透传
- 守卫结果写入 `SearchResult.guardedDiagnoses`，供调试分析

```typescript
interface SearchResult {
  // ...
  readonly evaluatedWithGuard: boolean;   // 是否触发了守卫 fallback
  readonly guardDiagnoses: string[];       // 守卫诊断信息
}
```

## NPC AI：守卫范式

### 核心：状态-目标-意图

**已定案的 NPC 流程闭环**：

```
初始状态：醒来 → 巡逻
    ↓ 感知阈值达标
触发状态：寻声 / 追逐锁定
    ↓ 解除条件满足
返回：巡逻（尝试返回轨道）
```

**这是第一个 NPC 范式，也是守卫范式。**

### 状态机定义

```typescript
type NPCState = 
  | 'sleeping'     // 睡眠中（床上）
  | 'patrolling'   // 巡逻
  | 'listening'    // 寻声
  | 'chasing'      // 追逐锁定
  | 'attacking';   // 战斗

interface NPCStateMachine {
  current: NPCState;
  target?: EntityId;      // 当前目标（玩家/声音源/巡逻点）
  memory: {
    lastSeenPosition?: NodeId;
    patrolRoute: NodeId[];
    currentPatrolIndex: number;
  };
}
```

### 行动选择（每个 NPC 回合）

```typescript
function selectNPCAction(npc: NPCEntity, state: GameState): Action {
  switch (npc.stateMachine.current) {
    case 'patrolling':
      return patrolBehavior(npc, state);
    
    case 'listening':
      return moveTowardsSound(npc, state);
    
    case 'chasing':
      return chaseTarget(npc, state);
    
    case 'attacking':
      return combatBehavior(npc, state);
  }
}

// 巡逻行为
function patrolBehavior(npc: NPCEntity, state: GameState): Action {
  const route = npc.stateMachine.memory.patrolRoute;
  const index = npc.stateMachine.memory.currentPatrolIndex;
  const nextPoint = route[index];
  
  if (npc.location === nextPoint) {
    npc.stateMachine.memory.currentPatrolIndex = (index + 1) % route.length;
    return { type: 'wait', cost: { ap: 1 } };
  }
  
  return { type: 'move', target: nextPoint, cost: { ap: 1 } };
}

// 追逐行为
function chaseTarget(npc: NPCEntity, state: GameState): Action {
  const target = npc.stateMachine.target!;
  const targetNode = state.entities[target].location;
  
  // 简单路径查找（A* 或 Dijkstra）
  const path = findPath(npc.location, targetNode, state);
  const nextNode = path[1]; // path[0] 是当前位置
  
  return { type: 'move', target: nextNode, cost: { ap: 1 } };
}

// 战斗行为
function combatBehavior(npc: NPCEntity, state: GameState): Action {
  const target = npc.stateMachine.target!;
  const weapon = npc.inventory.hands.right; // 假设右手持武器
  
  if (!weapon) {
    return { type: 'melee', target, cost: { ap: 1 } };
  }
  
  if (weapon.properties.profile === 'melee') {
    return { type: 'melee', target, weapon, cost: { ap: 1 } };
  }
  
  // 枪械
  const distance = calculateDistance(npc.location, state.entities[target].location);
  const dc = getDistanceDC(weapon.properties.profile, distance);
  return { type: 'ranged_attack', target, weapon, dc, cost: { ap: 1 } };
}
```

### 感知系统集成

**当前唯一落地：声音传播**

```typescript
interface PerceptionSystem {
  // 计算 NPC 接收到的声音强度
  calculateSoundLevel(npc: EntityId, source: NodeId, baseVolume: number): number;
  
  // 判断是否触发状态转换
  checkThreshold(npc: NPCEntity, perception: number): boolean;
}

// 声音衰减（按场景类型）
const SOUND_DAMPING = {
  large: 0.3,   // 空旷场景，声音衰减少
  medium: 0.5,
  small: 0.7,   // 封闭场景，声音衰减多
  transition: 0.4
};

function calculateSoundLevel(
  npc: EntityId,
  source: NodeId,
  baseVolume: number,
  state: GameState
): number {
  const path = findPath(state.entities[npc].location, source, state);
  let volume = baseVolume;
  
  for (let i = 0; i < path.length - 1; i++) {
    const node = state.nodes[path[i]];
    volume *= (1 - SOUND_DAMPING[node.type]);
  }
  
  return volume;
}
```

### 追逐锁定（已定案）

**规则**：追逐阶段不会被其他声音影响。

```typescript
function updatePerception(npc: NPCEntity, state: GameState): void {
  if (npc.stateMachine.current === 'chasing') {
    // 锁定状态，忽略其他感知
    return;
  }
  
  // 检查声音
  const sounds = state.events.filter(e => e.type === 'sound');
  for (const sound of sounds) {
    const level = calculateSoundLevel(npc.id, sound.source, sound.volume, state);
    if (level >= npc.listenThreshold) {
      npc.stateMachine.current = 'listening';
      npc.stateMachine.target = sound.source;
      break;
    }
  }
  
  // 检查视线
  const players = state.entities.filter(e => e.category === 'living' && e.isPlayer);
  for (const player of players) {
    if (canSee(npc, player, state)) {
      npc.stateMachine.current = 'chasing';
      npc.stateMachine.target = player.id;
      npc.stateMachine.memory.lastSeenPosition = player.location;
      break;
    }
  }
}

// NPC 视野：2（只能看到同微型场景的目标）
function canSee(npc: NPCEntity, target: Entity, state: GameState): boolean {
  if (npc.location !== target.location) return false;
  
  // 检查是否在同一微型场景
  const npcMicroScene = findMicroScene(npc.id, state);
  const targetMicroScene = findMicroScene(target.id, state);
  
  return npcMicroScene?.id === targetMicroScene?.id;
}
```

### 解除追逐条件（已定案）

```
到达 lastSeenPosition 且仍未看到玩家 → 返回巡逻
```

```typescript
function checkChaseEnd(npc: NPCEntity, state: GameState): boolean {
  const lastSeen = npc.stateMachine.memory.lastSeenPosition;
  
  if (npc.location === lastSeen) {
    const target = state.entities[npc.stateMachine.target!];
    if (!canSee(npc, target, state)) {
      npc.stateMachine.current = 'patrolling';
      npc.stateMachine.target = undefined;
      return true;
    }
  }
  
  return false;
}
```

## NPC 与玩家 AI 的根本区别

| 维度 | 玩家 AI | NPC AI |
|---|---|---|
| **算法** | αβ 剪枝搜索（通用） | 状态机（特化） |
| **目标** | 赢得游戏 | 提供挑战 + 可预测性 |
| **资源** | 参与投点 | 固定 AP 分配（默认 1 AP，可配置 — D-052） |
| **决策深度** | 多回合前瞻 | 单回合贪心 |
| **随机性** | 只在平局时 | 巡逻线固定 + 状态确定性 |
| **复用性** | 可扩展到任何玩法 | 需为每个 NPC 类型设计范式 |

**不能用玩家 AI 驱动 NPC 的原因**：
- NPC 需要可预测（玩家能学习其模式）
- NPC 搜索深度会拖慢游戏（100 个僵尸 × 5 层搜索 = 卡死）
- 状态机更容易平衡难度（调整阈值即可）

## NPC 的资源配置接口（D-052）

NPC **没有轮次**，全部在玩家轮次结束后按稳定编号顺序行动。其资源配置字段如下（基类层只提供接口与默认值，具体实例数值由玩法层 `L3_玩法层/05_NPC行为配置.md` 给出）：

| 字段 | 默认值 | 可配置 | 说明 |
|------|--------|--------|------|
| **AP** | **1** | ✅ | 每回合可用行动点 |
| **SP 上限** | **3** | ✅ | 低于玩家的 5 |
| **开局 SP** | **0** | ✅ | — |
| **是否主动使用体力** | — | ✅ | 决定 NPC 会不会自己掷强力骰 |

### 为什么 NPC 需要体力系统

**NPC 的 SP 纯粹是为了让玩家能在 PVE 中打出弱点甚至过载。** 如果 NPC 没有体力，弱点攻击的"对方体力 +1"和过载压制在 PVE 中完全失效——玩家既学不到这套机制，也无法在打僵尸时练习。SP 上限 3 意味着 **NPC 比玩家更容易被压到过载**，这正是"去杀僵尸"的收益之一。

### 硬性限制

**NPC 的体力不可能用来抢轮次**（不可用于逆转 / 超逆转）——因为 NPC 本身就没有轮次。

> **与 `speed` 字段的关系**：下节 `ZombieType.speed` 是"影响 AP 分配"的旧占位字段。按 D-052，NPC 的 AP 是**显式配置的整数**（默认 1），因此 `speed` 的小数值（1.5 / 2）不能直接当作 AP 使用，需要在 NPC 行为配置文档中明确它到 AP 整数的映射规则，或改为直接写 AP。该映射**尚未裁决**，实现前须确认。
