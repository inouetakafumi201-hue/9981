## L-01 载器 Carrier —— 容器承载面「承载活体」的特化形态

### 触发源（症状）
`src/class/vehicles/index.json` 的能力参数在玩法层 profile 上找不到顶层 key → `audit.ts` 越权（已登记 `UNRESOLVED_PARAMETER_BINDINGS`）。其中：
- `occupantDisposition` / `cargoDisposition`（对内部活体/物品的处置规则）无处落槽；
- `speed` / `moveApCost`（移动数值承载面不清）。

### 根因（立项判断）
不是字段写错，而是**引擎层缺少「让活体进容器承载槽」的写通道，以及「载器」这一特化形态未被具名**。容器（`Container`/`Slot`）是引擎层唯一通用承载基元，`Slot.holds: Ref` 本就可指向物品（`i:`）或活体（`e:`）；但既有 `item.move` 硬要求对象在 `draft.items`，活体无法经写通道进槽，玩法层 `vehicle` 因此伪装成普通实体、用 field-name 槽硬填载器语义，撞出越权。

### 已在代码层核实的事实（立项依据，非空白起点）
- **基类层契约已留未决边界**：`src/l2/model/family-contracts.ts` 的 `VehicleContract` 带 `interiorMicroSceneBoundary?` 字段（注释：命名的 Q-04「载具内部微型场景与外部交互点的边界未决，不得在此推导机制」，见 `docs/l2/model/family-contracts.ts:418`）。`space-items-projection.ts` 把载具的托管关系按 `kind:'vehicle'` 投影。**即「载具内部是不是微型场景」在基类层至今未决，不是已冻结成微型场景**——这与载器的「内部无场景」方向一致，立项是把它接上而非推翻。
- **唯一登记点**：`UNRESOLVED_PARAMETER_BINDINGS` 只登记了一条 `VEHICLE_PARAMETER_BINDING_GAP`，其 `blockedBy` 原文写「L2 基类层线裁决参数承载面」。本立项把根因更新为「容器承载活体写通道缺位 / 载器特化未命名（需求改写该 `blockedBy`：根因是承载写通道缺位，参数承载面是其症状）」。
- **审计豁免**：载具当前不参与能力参数绑定校验，`audit.ts` 用 `PARAMETER_BINDING_FIELD[vehicles]` 空值注释 + `VEHICLE_META_FIELDS` 覆盖——这是对「承载写通道缺位」的临时豁免，非正解。
- **引擎层演示级模型**：`05_底层引擎架构.md` `EntityCategory` 仍含 `vehicle` 且挂 `MicroSceneComponent`、`category:'vehicle'`——这是文档演示层旧示意，需在全面审查（L-03）中与载器「内部无场景」对齐修正。

### 载器定义（引擎层抽象，不含玩法，2026-08-14 调和）
- **基于容器、非同级新基元**：容器是引擎层**唯一通用承载基元**；载器是容器家族中「内部承载活体（与物品）且内部无场景」的**特化形态**。它复用 `Container`/`Slot`，不改其形式，用 `category:'carrier'` 明确标记该承载面的「可承载活体」语义。
- **可进入**：内部可载活体/物品。
- **内部无场景**：内部是结构槽位，**不是微型场景**，不占微型场景生命周期、不参与「找到」判定（与场景正交）。
- **可作用于内部成员**：可给内部活体/物品提供属性（例如掩体），由规则引用/赋予。
- **内外交互有通用介入边界点**：对内部成员的任何操作与副作用都可能被规则影响；**不预设它是拦截**——所有槽位化，规则可任意插入拦截、施加状态等。引擎只保证「介入点存在且不被结构阻止」。
- **典型**：车、能藏身的草垛、掩体型载器等，凡「承载活体/物品且内部无场景」的实体都属载器，应用面极广。

### 与基类/玩法的边界
- 载器是**引擎层容器承载面的特化**，不是基类层类。
- `Vehicle`（能开的载具）是**基类层**用「容器（座位槽+货舱）+ 交互 + 移动 + 血量逻辑」堆出来的实例，不是引擎本体新结构。
- 现行 `VehicleEntity` 被建模成 `MicroSceneComponent`（车内作为微型场景）——**这是错误定位**，应与「内部无场景」正交原则对齐（车内乘员进容器座位槽，不建车载微型场景）。

### 结构增量方向（待 L-01 立项细化）
- 在 `src/core/kernel/topology/` 具名载器承载面（`category:'carrier'`），复用 `Container`/`Slot`，不新建第二套承载结构。
- 破除「容器槽位只能放物品」对载器承载面的适用——承载面内部 `holds` 可指向活体(`e:`)或物品(`i:`)。
- 补承载循环/嵌套/溢出的结构约束（若需）与校验码。
- 与 `structural-ops`、`cascade-destroy`、散落物清理/世界清理的交互对齐（载器内活体算不算「离开节点」等）需统一裁定。

### 开口问题（须在立项敲定）
1. **载器是容器家族承载面的具名特化，活体承载本就该落进容器承载面**（2026-08-14 项目所有者最终裁定，闭合；见本立项定义调和批注）。方向已定：具名载器承载面（`category: 'carrier'`）+ 容器承载活体写通道（`container.enter/exit`），不改容器 `Slot` 语义、不做容器形式伤筋动骨。
2. 载器承载面内部 `holds` 的承载对象约束表达式形态（能不能活体、能不能物品、是不是按载器能力配置）。
3. 「内外交互介入边界点」在引擎层用何种稳定钩子表达（规则插入点），不预设玩法用法。
4. 载器承载面内活体的移动/退出/销毁的生命周期与现有实体清理规则的对接。
5. 现有「实体不能嵌套容纳另一个实体作为子对象」禁令对载器承载面的例外边界（声明 `category:'carrier'` 的承载面可承载，普通实体仍禁）。

### 后续
立项敲定后，作为「引擎层全面增量审查（L-03）」的最高优先输入先行稳固；未建模前不得在运行期依赖此承载写通道 / 载器特化。

### 与既有裁决/登记的对接（避免重复登记、消除错位）
- **载具在空间 Spec 中是「实体、乘员在实体内、不建模为微型场景」的既有裁决**（D-038、D-030、D-056），本立项与之一致；`VehicleContract.interiorMicroSceneBoundary`（Q-04）作为载器「内部无场景」的对接点保留。
- **UNRESOLVED_PARAMETER_BINDINGS / VEHICLE_PARAMETER_BINDING_GAP 的 blockedBy** 需在立项敲定时改写：从「L2 裁决参数承载面」指向本立项（根因=容器承载活体写通道缺位 / 载器特化未命名）。立项落地后，若可把相应字段判为「挂到容器承载面介入点」而非 profile 顶层字段，则该差距登记随消解。
- **本立项不重复登记**：`D-038`（载具是实体、半掩体授予）、`D-040`（掩体二维正交）、`D-030`（站车旁即可交互、不区分门）已在决策记录，本立项只作其引擎结构承载要求，不重述玩法规则。

## L-02 实体内部槽 Entity Internal Slots —— 载器承载面的承载槽

### 触发源
载器承载面需要「承载活体/物品且内部无场景」的结构槽；既有 `item.move` 只按物品处理，无法让活体进槽。

### 立项判断
实体内部承载槽是载器承载面的结构本体，是引擎层结构声明（复用 `Container.Slot` 的具名形态，不是第二套承载基元）。它是「实体内部可承载对象的槽位」这一结构约束，比基类定义更基础。

### 方向
- 复用 `Container.Slot`（`holds: Ref` 本就可指向活体(`e:`)或物品(`i:`)），配容器承载活体写通道（`container.enter/exit`）；不另立平行槽结构。
- 内部成员不占微型场景生命周期、不参与「找到」（正交原则硬规定）。
- 与「内外交互介入边界点」配套（L-01 开口问题 3）。

### 后续
随 L-01 一并立项，先行建模；覆盖结构、校验码、Op、属性测试。

## L-04 玩法包装载语义改造：单调重定义

### 触发源 / 裁决
D-073：玩法包无名、顺序即优先级（后装覆盖先装）、剔除=回滚重装载、剩 ID 即退役、同 key 即替换。否定 namespace / 归属判定线。

### 现状与缺口
- L1 `PlaypackLoader` 同 key 冲突默认 remap；L2 `DefinitionRegistry` 同 key 须 `REF_OVERRIDE_NOT_DECLARED`——两者都是「修改须显式声明」模型，与单调重定义相反。
- 需改为「同 key 覆盖/新增、跨作用域冲突一律拒绝」的单调重定义。

### 引擎层约束（铁律，不可绕过）
- 唯一写入通道 + 原子验证不可绕过。「重新定义即替换」只发生在装载事务的原子 swap 之前；运行期不得直接改写已生效注册表。

## L-05 地图唯一锚点 / 不可替换

### 触发源 / 裁决
D-076/D-077：地图 = 唯一装载锚点，不可替换，拒绝地图位重载；带图包只能来自上传或官方。

## L-06 高级玩法包判定（编译器静态扫描）

### 触发源 / 裁决
D-077：编译器对玩法包产物做可达性静态扫描，凡含**引擎层引用** → tag「高级」+ 警告器；高级包限自建房/单机、探索匹配不可见。含**地图定义**只带地图 tag，**不构成高级判据**（2026-08-14 调和）。

### 要点
判定**看产物、不看来源/声明、命中式而非显式声明**（一个可达的引擎层原语即触发）；高级判定与「Tier（复杂度评分）」严格区分。
