## 审查总纲

本批次审查按照**哲学宪法原则**对引擎层前四层进行原则性彻查，验证：
1. 宪法合规性（术语铁律、三层架构边界、完备性判据）
2. 设计决策的不可绕过性、三处复用、不含玩法语义
3. 边界情况、反对模式、扩展性边界

### 思维实验结论

**边界情况**：
1. Entity同时在node和slot → 被不变量禁止（E_INV_DUAL_LOCATION fatal）
2. 无Ref前缀 → 世界状态无法寻址，系统崩溃 → 证明不可绕过
3. 无Agent概念的中途换人 → 需改造引擎代码 → 证明不可绕过

**反模式检测**：
1. 外挂风险：props自由区可能被滥用存储作弊数据 → **高风险**：需表现层校验+服务端权威
2. 存储可执行代码：ExprDef纯函数设计有效防护 ✅
3. props自由区滥用导致不可恢复状态 → 需操作日志+回滚机制兜底

**扩展性边界**：
1. 第15种Ref前缀 → 需改Id类型定义+Linter+所有解析器，高侵入
2. Tag带参数（如"武器.枪.霰弹.双管"） → **高风险**：当前Tag是字符串，层级需靠约定，建议规范中明确
3. Def钻石继承 → ⚠️ 规范未明确，建议禁止或规定消解策略

### 建议

1. **[高]** 明确Ref前缀新增的审批流程与 механиза 检测
2. **[中]** 规范Tag命名约定（是否支持层级语法）
3. **[中]** Def继承的语义冲突检测纳入Linter强制项
4. **[低]** 规范abstract标记的使用场景

### Query能力边界

**可表达的查询类型**：
- 按类型过滤（entities/items/nodes/links/attachments/defs/agents）
- 空间限定（in: radius/spread/具体节点）
- 认知过滤（visibleTo）
- 条件组合（where）
- 排序+分页（orderBy/desc/limit）

**不可表达的查询类型**：
1. 跨时间窗口聚合（如"最近3回合的平均伤害"）→ 需用法ATs + 外部计数器
2. 递归查询（如"所有后代实体"）→ 需预定义关系或多次查询
3. 模糊匹配 → 不支持正则

### 安全边界验证

| 检查项 | 状态 | 说明 |
|--------|------|------|
| 无eval | ✅ | 固定算子集合 |
| 无字符串拼接执行 | ✅ | 内置算子不可扩展 |
| 除零返回null | ✅ | 满足全函数要求 |
| 调用图无环 | ✅ | Linter加载期检测 |

### 思维实验结论

**边界情况**：
1. spread在高连通图上 → budget截断足够，需实测确认缺省值
2. dist在无路径节点间 → 返回null，玩法���负责处理
3. 除零返回null → 可能静默传播，但全函数设计可接受

**反模式检测**：
1. 用Expr模拟图灵完备计算 → ✅ 被禁止：固定算子集合+加载期无环检测
2. 具名表达式递归 → ✅ 被禁止：Linter无环检测
3. Query访问不变量外状态 → ✅ 不可能：Query只读

**扩展性边界**：
1. 第50个算子 → 需改Expr类型+Linter+求值器，高侵入
2. 玩家自定义函数 → 不支持，符合安全设计
3. ExprDef的MOD override → ✅ 支持，overrides一个DefId即可

### 风险项

1. **[中风险]** spread的budget缺省值未给定，需实测确定
2. **[低风险]** Query不支持跨时间窗口聚合，复杂统计需额外计数器

### 思维实验结论

**边界情况**：
1. before的veto和modify的payload修改同时发生 → veto优先，操作取消，modify不执行
2. instead候选重入 → 重入锁break，进入default
3. after rollback后ctx.emit事件保留 → ✅ 用于重建状态变化
4. 32层深度对复杂MOD链 → ⚠️ **中风险**：MOD叠加可能触顶，建议可配置

**反模式检测**：
1. Hook实现"无限生命" → ✅ 被防止：hp是props，Hook只能读写它，需before:damage+veto
2. modify无限改写payload → ⚠️ **中风险**：无单次修改次数限制，复杂MOD链可能失控
3. instead劫持其他Hook效果 → ✅ 被防止：instead按四元组排序只执行第一个

**扩展性边界**：
1. 第6个阶段 → 需改Hook调度器+排序逻辑，高侵入
2. Hook访问前置Hook返回值 → ❌ 不支持，符合单向数据流
3. 嵌套事件（before.after.entity.create）→ ❌ 不支持，事件类型是字符串

### 风险项

1. **[中风险]** modify阶段无单次payload修改次数限制，可能导致复杂MOD链失控
2. **[中风险]** 32层depth上限对复杂MOD链可能不足，建议PlaypackDef提供maxDepth配置
3. **[低风险]** instead阶段的四元组排序对container/slot索引有依赖，需保证索引稳定性

## 审查结论

### 整体评价

**L1-L4层设计质量：优秀**

- 十一轮迭代打磨，架构成熟度高
- 宪法合规性全面达标
- 完备性判据贯穿每项设计决策
- 思维实验覆盖充分

### 主要发现

1. **第十一轮是关键转折**：w:0补全、容器索引无条件化、stack.split原子性定稿，使得L1层真正收敛
2. **L4的modify阶段存在潜在风险**：无payload修改次数限制，可能被复杂MOD链滥用
3. **Journal的权限边界需要明确**：作为通用回放机制，需防止被滥用于"时间倒流"作弊

### 建议优先级

| 优先级 | 建议 | 层级 |
|--------|------|------|
| P0 | 明确Journal读权限边界 | L3 |
| P1 | 建立Ref前缀新增审批机制 | L1 |
| P2 | add modify阶段payload修改预算 | L4 |
| P3 | PlaypackDef增加maxDepth配置 | L4 |
