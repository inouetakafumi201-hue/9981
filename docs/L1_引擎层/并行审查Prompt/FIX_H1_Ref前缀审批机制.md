# FIX_H1_Ref前缀新增审批机制修复方案

> **文档性质**：P0高风险项修复方案  
> **问题来源**：并行审查Phase发现的架构扩展性漏洞  
> **最后更新**：2026-08-05

---

## 1. 问题描述

当前Ref前缀体系（§1.2）定义了10个前缀，是**封闭集合**，可机械校验。但Spec中**未明确新增前缀的审批机制**。

**风险**：前缀体系膨胀、架构一致性破坏、实现负担失控

---

## 2. Spec修改草案（核心内容）

### 在§1.2后增加§1.2.1

```markdown
#### 1.2.1 前缀新增的审批机制（宪法级约束）

Ref前缀体系是**封闭集合**，新增前缀是**宪法级变更**，必须通过以下审批：

**审批四阶段**：
1. 提案（含动机、完备性判据验证、影响评估）
2. 宪法审查（不可绕过、三处复用、不含语义）
3. 影响评估（Spec修改≤5章节、新Op≤10个）
4. 批准归档（更新§1.2、§18.1、宪法术语表）

**拒绝案例**（澄清边界）：
- `r:Resource` - 可用props表达
- `p:Player` - 含玩法语义
- `m:Message` - 未满足三处复用

**已批准前缀决策记录**：
| 前缀 | 不可绕过理由 | 批准轮次 |
|------|-------------|---------|
| e/i/n/l/c/s/d | 基础拓扑与容纳 | 初版 |
| a | 临时状态附加 | 第四轮 |
| g | 决策者归位 | 第六轮 |
| w | 全局单例 | 第十一轮 |
```

### §4.6不变量增加2条

```markdown
| 前缀集合封闭 | Ref前缀集合在运行期不可扩展 |
| Id命名空间隔离 | 不同前缀的Id空间独立 |
```

### §13.4新增错误码2个

```
E_REF_UNKNOWN_PREFIX - 非法前缀检测
E_REF_FORBIDDEN_EXTEND - 试图定义新前缀
```
