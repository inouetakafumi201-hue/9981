# 底层引擎架构设计

> **架构目标**：保证未来 **0 追加** —— 任意玩法细节都能被表达为有限数据结构上的状态、关系、动作、效果与规则组合，而不需要新增第二套结算系统。

---

## 架构哲学

### 核心理念

**层层叠叠的接口外包和模块化**：
- 不只是把武器对象模块化
- 要对整个类别提取范式封装对象
- 把整个伤害判定模块化
- 连整个被动结算都要模块化
- **把估值函数（得分计算）纳入底层服务**，AI 模块只消费评分接口

### 设计目标

> 任意玩法细节，都能被表达为有限基底上的状态、关系、动作、效果与规则组合，而不需要新增第二套结算系统。

**引擎层基底是层化命令引擎。** 单一原语：**Entity = ID + 状态容器**，状态以字段挂载（`props`、`containers`、`attachments`、`relations` 等），语义由基类层/玩法层注入。本引擎**不采用标准 ECS 的 archetype 表 + system 遍历形态**，也不采用 DDD 的多聚合根形态——而是以**统一事务边界（WorldState） + 集中不变量守卫**确保一致性。详见「数据形状」节。

**Node 与 Item 是置于 ECS 之上的两种数据壳，不是与实体平级的第三/第四原语：**
- **节点（Node、`n:`）**是场景空间的图骨架——拓扑顶点，通过 `connections` 邻接表构成地图拓扑，`containedEntities/containedItems` 是它挂载在拓扑上的内容索引。它是图论场景结构，并非 ECS 原语。
- **物品（Item、`i:`）**是实体容器槽内承载的数据对象（`Slot.holds: Ref` 可指向 `e:<实体>` 或 `i:<物品>`），不具自主行为，进入容器前不直接与节点/实体交互。

下文保留「节点 / 物品 / 实体」的分节展开，是为了清晰描述三类角色各自的数据形状与规则；**这不是三个平级的原语**——实体的组件系统是唯一原语机制，节点与物品在实现上以对应结构/组件表达。实体（`e:`）、节点（`n:`）、物品（`i:`）的 Id 前缀同为封闭集合，见 `元机制内核Spec_v1.md` §1.1。

---

## 三层架构

### 1. 引擎层（Kernel）
**职责**：保证任何合法配置都能确定地执行，不崩溃、不死循环、不产生非法状态

- 节点（场景骨架）、物品（容器承载体）与实体的生命周期管理；原语机制是「实体+组件」一套
- 容器关系维护
- 动作验证与执行
- 状态一致性保证
- **估值函数服务**（为 AI 和规则提供评分）

### 2. 基类层（Class）
**职责**：提供库存、伤害、移动、乘载、状态、回合、目标选择等可复用模块

- 通用机制实现（背包、战斗、移动、睡眠/起床）
- 标准流程定义（射击流程、精密交互流程、处决流程）
- 能力组件库（武器谱型、防具、状态效果）

### 3. 玩法层（Play）
**职责**：定义大逃杀、夺旗、追逐、合作生存等具体规则

- 出生规则
- 胜利条件
- 特定规则集
- 数值约束

## 三大底层结构：节点 / 物品 / 实体

**角色定位**：本节描述的三种数据结构，是引擎在层化命令引擎之上的场景与内容数据形状，而非三个平级的原语机制。状态容器（Entity/Component）是核心机制，节点与物品分别以图骨架与容器承载体出现，作为实体与场景的数据视图存在。三者 Id 前缀（`e:`/`n:`/`i:`）为封闭集合、可机械校验。

> 旧表述「三大底层结构平级且不可混用」易被误读为存在三种平行原语，与宪法 L1 原语清单（Entity/Component/Relation/Op/Expr/Hook，无 Node/Item）冲突。现按主体意图收束：**核心机制是「状态容器 + 具名字段」一套**，Node/Item 是实体场景中的两类结构化数据。

按此定位，分述三者形状与规则如下。

### 1. 节点（Node）

**定义**：场景空间的离散单位，构成地图拓扑骨架。

```typescript
interface Node {
  id: string;
  type: 'large' | 'medium' | 'small' | 'transition';
  connections: Connection[];  // 最多 5/4/3 条（按类型）
  containedItems: ItemId[];   // 散落物品
  containedEntities: EntityId[]; // 停留的实体
  properties: {
    coverLevel?: number;      // 掩体等级
    hazard?: HazardType;      // 环境危害（火/毒/水/电）
    noiseDamping?: number;    // 声音衰减系数
  };
}

interface Connection {
  target: NodeId;
  portal?: EntityId;  // 门、窗等实体（如果有）
  cost: number;       // 通行 AP 消耗
  condition?: Condition; // 通行条件（如需要钥匙）
}
```

**关键规则**：
- 节点不能移动
- 节点只能通过 `connections` 与其他节点相连
- 散落物品清理：所有活体离开该节点后，`containedItems` 清空

### 2. 物品（Item）

**定义**：可以被放入容器槽位的对象，没有自主行为。

```typescript
interface Item {
  id: string;
  type: ItemType;  // 'weapon' | 'consumable' | 'accessory' | 'material'
  slots: number;   // 占用槽位数（1 或 2）
  properties: Record<string, any>; // 类型特定属性
}

// 武器物品
interface WeaponItem extends Item {
  type: 'weapon';
  properties: {
    profile: BalisticProfile;  // 谱型（手枪/霰弹枪/步枪等）
    damage: number;
    attackShape: 'single' | 'spread' | 'area';
    twoHanded: boolean;  // 使用时需空一只手
    attachments?: {
      scope?: ItemId;
      grip?: ItemId;
      magazine?: ItemId;
      silencer?: ItemId;
    };
  };
}

// 防具物品
interface ArmorItem extends Item {
  type: 'consumable';
  subtype: 'armor';
  properties: {
    tier: 'light' | 'medium' | 'heavy';
    durability: 'intact' | 'worn' | 'broken';
  };
}
```

**关键规则**：
- 物品**不是**实体的子类型
- 物品与实体必须通过**转换**才能实现状态互换（如折叠自行车 ↔ 展开的自行车）
- 物品不能直接与节点/实体交互，必须先进入某个容器

### 3. 实体（Entity）

**定义**：与节点、物品并列的底层结构，能占据空间、创建微型场景、执行动作。

```typescript
interface Entity {
  id: string;
  category: EntityCategory;  // 见下文分类
  location: NodeId;          // 所在节点
  microScene?: MicroScene;   // 创建的微型场景（如果有）
  components: Component[];   // 组件化能力
  lifecycle: 'active' | 'disabled' | 'removed';
}

type EntityCategory = 
  | 'living'      // 活体（玩家、NPC）
  | 'container'   // 容器：唯一通用承载基元（背包/装备位/双手槽/柜子/死亡背包/载具座位货舱）；「载器」是其承载活体的具名特化——见「载器」节
  | 'portal'      // 门户（门、窗）
  | 'bed'         // 床
  | 'environmental'; // 环境实体（爆炸物、陷阱）

// 活体实体
interface LivingEntity extends Entity {
  category: 'living';
  components: [
    HealthComponent,
    StaminaComponent,
    InventoryComponent,
    APComponent,
    StateComponent
  ];
}

// 载具实体 —— 内部座位/货舱均为容器槽承载（车内不建模为微型场景，D-038/D-056）
// 座位/货舱承载面可用 category:'carrier' 具名为「载器」语义，声明其可承载活体（见「载器」节）
interface VehicleEntity extends Entity {
  category: 'container';  // 载具用容器承载：座位槽（可载活体）+ 货舱（载物品）
  components: [
    MovementComponent,
    ContainerComponent  // 座位 + 货舱，Container.Slot.holds 可指向 i: 或 e:
  ];
}

// 死亡背包实体
interface DeathBackpackEntity extends Entity {
  category: 'container';
  components: [
    ContainerComponent
  ];
  properties: {
    readOnly: true;  // 只出不进
    capacity: 2 | 4 | 6; // 取决于玩家背包拓展状态
  };
}

// 床实体
interface BedEntity extends Entity {
  category: 'bed';
  components: [
    MicroSceneComponent,  // 床上空间
    SpawnPointComponent   // 重生点（如果是固定床）
  ];
  properties: {
    portable?: boolean;  // 是否可折叠/移动
  };
}
```

**关键规则**：
- 只有**活体**（`category: 'living'`）参与：
  - 散落物清理判定（所有活体离开节点 → 物品清空）
  - 世界清理（移除 `lifecycle: 'removed'` 的实体）
  - 自主行动判断
- 实体可以创建**微型场景**（下节）
- 实体不能嵌套容纳另一个实体作为子对象（容器槽位只能放物品），**除声明 `category:'carrier'` 承载面的容器例外**（见下节）

## 载器（Carrier）—— 容器家族中「承载活体」的特化形态

> **权威落点（2026-08-14 项目所有者调和）**：**容器（Container）是引擎层唯一通用的承载基元**——所有「带物品槽/承载槽」的东西（角色背包、装备位、双手槽、柜子、死亡背包、载具座位/货舱）都通过容器实现。`Slot.holds: Ref` 本就可指向 Item **或** Entity。**载器不是与容器同级的独立结构，也不新增第二套承载基元**；载器是对「容器内部槽承载活体（并兼具物品）」这一家族形态的明确命名与约束特化。实用性与完备性至上：**不改容器形式**，只调和定义。牵头立项见 `docs/L1_引擎层/引擎层紧急多维立项.md` L-01/L-02；设计正稿见 `.kiro/specs/wakeup-engine-layer/`。

### 定义（引擎层抽象，不含玩法）

**容器是唯一承载基元。** 容器的 `Slot.holds` 天然支持：
- **物品（`i:`）**——角色背包、装备位、柜子、死亡背包、限用货舱；
- **活体（`e:`）**——载具座位、被抓住的敌人、宠物携带笼。

**载器是容器家族中「承载活体且内部无场景」的特化形态**：它复用同一个 `Container`/`Slot`，用 `category:'carrier'` 明确标记「内部槽可承载活体、且内部不建模为微型场景」的属性，并限定该承载面的语义约束：

- **不新增基元**：载器不是与容器平级的独立一等结构，不是 `Container.Slot` 的泛化或再造，也不需要单独的六并列条目。一切容器规则、不变量、写通道对载器承载面一并适用。
- **内部无场景**：载器内部是结构槽位，**不是微型场景**，不占微型场景生命周期、不参与「找到」判定（与场景正交）。
- **可作用于内部成员**：可给内部活体/物品提供属性（例如掩体），由规则引用/赋予。
- **内外交互有通用介入边界点**：对内部成员的任何操作与副作用都可能被规则影响；**不预设它是拦截**——所有槽位化，规则可任意插入拦截、施加状态。引擎只保证「介入点存在且不被结构阻止」。
- **典型**：车、能藏身的草垛、掩体型载器等，凡「承载活体/物品且内部无场景」的实体都属载器。

### 容器承载活体的写通道

`Slot.holds: Ref` 类型层已可指向 Item 或 Entity，机制底座已就位；本立项补齐的是「让活体进槽」的写通道（既有 `item.move` 硬要求对象在 `draft.items`），在 `OpRegistry` 注册（`structural:true`，可被 before/after veto 拦截）：

```
container.enter    // 把活体放进容器承载槽（accept/capacity/location-exclusive 校验）
container.exit     // 把容器内活体移出，放到 node 或另一槽
```

**不变量（容器已有，载器承载面一并适用）**：单一容纳、单一位置、位置互斥（`node`/`slot` 不并存）、无环容纳（容器不得直接或间接容纳自身宿主）。销毁时按 `destroyOwnedContainers`/`clearHoldingSlot` 两向模式释放内部成员（清 `slot`/`holds`，成员完整保留）。**不改 `Container`/`Slot` 既有形式**——载器承载面只在容器既有结构上做约束声明。

### 与基类层/音效玩法的边界

- 容器是引擎层**通用承载基元**；载器是其「承载活体且内部无场景」的特化形态，不是基类层类。
- `Vehicle`（能开的载具）是**基类层**用「容器（座位槽+货舱）+ 交互 + 移动 + 血量逻辑」堆出来的实例，内部座位/货舱就是容器槽，不是新结构。
- **载具内部不建模为微型场景**（D-038/D-056）：车内乘员进容器座位槽，不建车载微型场景（Q-04 后续访谈裁决，`VehicleContract.interiorMicroSceneBoundary` 保留为对接点）。
- 「实体不能嵌套容纳另一个实体」禁令对普通实体仍有效；**只有声明 `category:'carrier'` 的容器承载面例外**，可机器校验。

## 微型场景（Micro Scene）

**定义**：由实体创造的局部接触空间，附属于所在节点。

```typescript
interface MicroScene {
  id: string;
  owner: EntityId;  // 创建者（活体、载具、柜子等）
  parentNode: NodeId; // 所属天然场景
  occupants: EntityId[]; // 当前进入者（活体）
  properties: {
    fire?: boolean;
    water?: boolean;
    oil?: boolean;
    electricity?: boolean;
  };
}
```

**核心机制**：
- **"找到 X" = 进入 X 的微型场景**（花费 1 AP）
- 同一微型场景内的活体**共用一个接敌面**
- 小场景中所有活体天然共处一个微型场景（无需"找到"）
- 大/中场景中，活体默认不在同一微型场景
- 微型场景随父节点销毁（缩圈时）

## 数据形状（不变量与命令边界）

> **2026-08-26 修订**：本节原标题为「组件系统（ECS 架构）」，因实际形态并非标准 ECS（无 archetype 表、无 system 风格组件遍历、`Entity` 存在具名字段而非平铺 components），故改名并据实描述当前结构。下方 `HealthComponent`/`StaminaComponent` 等类型是**设计草图**，运行时实际形态为 `Entity.props: Record<string, Value>` 的无类型 JSON 袋；这两者的统一是 `wakeup-base-layer-ecs` / `wakeup-cas-gap-closure` spec 在做的收敛工作（尚未完成）。

### 当前数据形态（非 ECS）

| 要素 | 当前落点 | 与标准 ECS 的差异 |
|---|---|---|
| **Entity（实体）** | `Entity = { id, def, tags, props, node?, slot?, containers, attachments, relations }`——稳定 ID + **具名字段**，无独立 `components` 字段 | 标准 ECS：`{ id, components: Record<CId, T> }` |
| **Component（组件）** | 当前以两类形式存在——(1) 顶层 `Entity` 的具名字段（`props`/`containers`/`attachments`/`relations` 等）；(2) `Entity.props: Record<string, Value>` 的无类型 JSON 袋 | 标准 ECS：每种组件是独立类型，存入 archetype 表 |
| **System（系统）** | **无**——`src/core/kernel/ops/` 目录下零个 system 风格组件遍历。Op 是**单目标命令 + 事务脚本**（`makeEntityCreate` 处理一个实体、`item.move` 处理一个 item） | 标准 ECS：system 迭代所有具备某组件的实体 |
| **不变量守卫** | `InvariantChecker.checkAll(finalDraft)` 在每次 `OpRegistry.invoke` 提交前扫所有实体（共 16 条不变量） | 标准 ECS：每 archetype 表独立维护组件级约束 |

### 形态偏离 ECS 的设计取舍

- **具名字段 + 事务脚本** 的好处：单目标命令语义清晰、调试简单、规则直接、操作可单元测试
- **代价**：`cascadeRelationsAndAttachments` / `destroyOwnedContainers` 等需要 O(N) 扫图维持一致；`item.move` 找源 slot 要扫所有容器；`Entity.props` 失去类型守护
- **去向**：见 `.kiro/specs/wakeup-base-layer-ecs/`（基类层 ECS 收敛）和 `.zcode/plans/whitespace-closure-A-B-batches.md`（两套契约单源化）——这两份工作是把当前形态向更接近 ECS 的方向**收敛**，不是宣称已经达成

### 核心组件（设计草图，运行时落 `Entity.props`）

> **状态**：以下类型是设计层的占位表达；运行时实际数据位于 `Entity.props: Record<string, Value>`。spec 完成前不要把 `HealthComponent.current` 当作权威字段。

#### HealthComponent（生命值）
```typescript
interface HealthComponent {
  current: number;
  max: number;  // 标准 5 点
  onZero: 'downed' | 'death';  // 零血时触发状态
}
```

#### StaminaComponent（体力）
```typescript
interface StaminaComponent {
  current: number;
  max: number;
  recoveryConditions: ('sleep' | 'failedRoll' | 'execute')[];
}
```

#### APComponent（行动点）
```typescript
interface APComponent {
  current: number;
  source: 'roll' | 'fixed' | 'none';  // 玩家投点 | NPC固定 | 不消耗AP
}
```

#### InventoryComponent（背包）
```typescript
interface InventoryComponent {
  hands: {
    left?: ItemId;
    right?: ItemId;
  };
  backpack: ItemId[];  // 初始 2 格，拓展后 4 格
  equipped: {
    armor?: ItemId;
    shield?: ItemId;
  };
}
```

#### StateComponent（状态效果）
```typescript
interface StateComponent {
  active: State[];
}

interface State {
  type: string;  // 'sleeping' | 'downed' | 'blocking' | 'heavy_load' | ...
  duration?: number;  // 持续回合数
  source?: EntityId;  // 施加来源
  params?: Record<string, any>;
}
```

#### ContainerComponent（容器能力）
```typescript
interface ContainerComponent {
  slots: ItemId[];
  capacity: number;
  readOnly?: boolean;  // 死亡背包专用
}
```

#### MicroSceneComponent（创建微型场景能力）
```typescript
interface MicroSceneComponent {
  scene: MicroScene;
}
```

## 动作系统（Action System）

### 动作定义

**铁律**：一个动作永远消耗 **1 AP**。所谓"2 AP 动作"实际是两个 1 AP 动作 + 中间状态。

```typescript
interface Action {
  id: string;
  name: string;
  initiator: EntityId;      // 声明者
  actor: EntityId;          // 执行者（通常相同）
  source?: EntityId;        // 能力来源（武器/技能）
  targets: EntityId[];      // 目标
  
  // 前置条件
  requirements: Condition[];
  
  // 资源消耗
  costs: {
    ap: 0 | 1;  // 只有这两个值
    stamina?: number;
    items?: ItemId[];
  };
  
  // 效果
  effects: Effect[];
  
  // 失败处理
  onFailure?: Effect[];
  
  // 时序
  timing: 'immediate' | 'deferred';  // 立即 | 延迟（需等待结算）
  
  // 可见性
  disclosure: 'public' | 'hidden' | 'revealed_on_execute';
}
```

### 标准流程（复用单位）

#### 射击流程
```
1. [1 AP] 瞄准 + 射击
   - 前置：持有远程武器，目标在射程内
   - 计算距离 DC（根据谱型 + 距离范式）
   - 投 d6 ≥ DC → 命中
   - 超出 DC 2+ → 伤害提升
   - 效果：造成伤害

无"瞄准"作为独立动作，射击是原子操作。
```

#### 精密交互流程（撬锁示例）
```
1. [1 AP] 开始撬锁
   - 效果：自身获得 [撬锁中] 状态，绑定目标门

2. [1 AP] 完成撬锁（下回合或本回合剩余 AP）
   - 前置：自身有 [撬锁中] 状态
   - 效果：门解锁，移除 [撬锁中] 状态

中断条件：移动、受击、主动取消 → [撬锁中] 状态消失，进度作废
```

#### 令其长眠流程
```
1. [1 AP] 令其长眠
   - 前置：目标零血倒地，自身与目标同微型场景
   - 效果：
     - 目标死亡
     - 自身体力回满
     - 生成死亡背包实体于目标所在节点
```

## 估值函数服务（Evaluation Service）

**归属**：引擎层服务，不属于 AI 模块。

**职责**：为 AI 搜索（αβ 剪枝）和规则判定提供统一的评分接口。

```typescript
interface EvaluationService {
  // 活体当前局势评分
  evaluateEntity(entity: LivingEntity, context: GameState): number;
  
  // 动作预期收益评分
  evaluateAction(action: Action, context: GameState): number;
  
  // 位置价值评分
  evaluatePosition(node: NodeId, context: GameState): number;
  
  // 物品价值评分
  evaluateItem(item: Item, holder: EntityId, context: GameState): number;
}

// 评分权重配置（可被玩法包覆盖）
interface EvaluationWeights {
  health: number;
  stamina: number;
  ap: number;
  weaponQuality: number;
  positionSafety: number;
  distanceToTarget: number;
  distanceToCircle: number;
}
```

**设计要点**：
- 评分函数**不包含搜索逻辑**，只返回数值
- AI 模块（αβ 剪枝）调用此服务，不自己实现估值
- 规则模块可调用此服务做决策（如 NPC 优先拾取高价值物品）

## 回合与时序系统

### 回合流程

```typescript
interface TurnSystem {
  phases: [
    'roll',      // 投点阶段：所有玩家同时投骰
    'resolve',   // 结算阶段：分配 AP，判定体力退还
    'action',    // 行动阶段：按 AP 从高到低依次行动
    'npc',       // NPC 阶段：按编号顺序行动
    'cleanup'    // 清理阶段：状态倒计时，触发持续效果
  ];
}
```

### 时序纯洁性原则

**禁止**：
- 回合外选择（不在自己回合的玩家不能做主动抉择）
- 异步等待（所有玩家 AP 耗尽或弃权才进入下一阶段）

**允许**：
- 被动触发（受击时盾牌自动格挡）
- 零费动作（不产生搜索分支）

    reduction: (dmg: number) => Math.max(dmg - 1, 0),

  medium: {
    reduction: (dmg: number) => Math.max(dmg - 1, 1),
    breakOn: 1

## 扩展性保证

### 新增武器
只需新增**谱型定义** + **距离 DC 行**，无需改动战斗模块代码。

### 新增状态
只需新增**状态定义** + **交互规则**，状态系统自动处理。

### 新增玩法模式
只需实现**玩法层接口**，复用所有基类层模块。

### 新增 NPC 类型
只需配置**状态-目标-意图**参数，复用守卫范式 + αβ 搜索。
