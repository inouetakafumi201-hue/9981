## 第一条：三层架构

WakeUp 项目分为三层架构：

| 层级 | 名称 | 定义 | 例子 |
|------|------|------|------|
| **L1** | 引擎层 | 底层原语集，语义无关；核心是**实体组件系统（ECS）**——Entity = ID + 组件列表，一切能力由 Component 提供，由 System（Op/Hook）分发 | Entity、Component、System、Op、Expr、Hook |
| **L2** | 基类层 | 实例库，语义最小单元 | 枪类、武器属性（散射/扫射/连发）、移动模式 |
| **L3** | 玩法层 | 组合 + 实例化 + 数值约束 | 霰弹枪实例、大逃杀规则 |

> **ECS 定性（2026-08-14 补）**：L1 引擎层是标准 ECS，三要素齐备——实体只是 ID + 组件列表的容器，组件挂载结构化状态，Op/Hook 作为 System 读写组件。Node（场景图顶点）与 Item（容器承载对象）是置于实体组件系统之上的两类结构化数据，不是与实体平级的原语。详见 `docs/L1_引擎层/05_底层引擎架构.md` 文首与「组件系统（ECS 架构）」节。

## 第三条：层级约束

### 引擎层约束

```
✅ 引擎层可以：
- 定义 Entity、Component、Relation、Op、Expr
- 定义 Hook 调度机制
- 定义查询引擎
- 定义持久化机制

❌ 引擎层禁止：
- 定义"武器"、"技能"、"载具"等语义概念
- 预设任何具体玩法规则
- 为任何实例指定具体数值
```

### 基类层约束

```
✅ 基类层可以：
- 定义实例类型（枪类、载具类、技能类）
- 定义实例的基类组合方式
- 定义实例的可配置参数

❌ 基类层禁止：
- 设置具体数值（如伤害=3）
- 定义具体玩法规则（如大逃杀胜负条件）
- 预设具体游戏模式
```

### 玩法层约束

```
✅ 玩法层可以：
- 组合基类创建实例
- 设置具体数值
- 定义具体玩法规则
- 验证市场玩法

❌ 玩法层禁止：
- 违反引擎层的约束
- 违反基类层的定义规则
```

## 第四条：数值约束

**所有玩家可见数值严格限制在 1-5 范围内，无例外。**

包括：
- 生命值：1-5
- 伤害：1-5
- AP 成本：1-5
- 持续回合：1-5
- 物品槽位：1-5
- 连接节点数：1-5

**内部数值例外**（玩家不可见）：
- 回合编号
- 实体数量
- 距离计算
- 结算预算
- 性能统计

**投点骰（D-054 已并入）**：投点固定使用 1 颗 d6。原始骰点属于内部瞬时数值（Internal_Metric）——只作为行动轮差距结算的输入，不作为长期演算或持久展示的玩家可见数值；故 d6 产出 6、强力骰修正使结果最高到 8，均不触及本条 1-5 约束。玩家可见的产出（AP 1-3、行动顺序）仍严格落在 1-5。此处无 d5。

### 单动作原则（AP 铁律 — 2026-08-13 项目所有者重申并晋升入宪）

**项目里没有"加 AP"设计。** 一个动作**永远**恰好消耗 1 AP；任何需要多个时间单位的交互，都必须拆成**多个 1 AP 动作 + 显式中间状态**来表达，不得通过单次消耗 2 AP 的原子动作或 `apModifier:+N` 式的"加 AP"修饰实现。

- 文档/实现中凡出现"花费 2 AP"的字面，其真实结构必是"花 1 AP 进入过渡状态 + 花 1 AP 完成"，中间态必须可观察。
- 状态（如迟缓、冰冻、重装）**不得**携带"该动作额外 +1 AP"的加价语义；它应表达为"使相关移动/交互进入过渡状态、需要额外一次 1 AP 动作来完成"。
- 迟缓设定（据此特定化）：**离开任何天然场景都需要一次中间状态**（1 AP 进入过渡态，1 AP 完成移动）。若同时手持重物，离开大场景**不叠加状态**，仅按过渡链逐段计费——单段仍是 1 AP，总成本由段数累加（示例：迟缓+重装离开大场景 = 3 AP，即三个 1 AP 段，不是"一次 3 AP 动作"）。
- 快速路径异常（如提升机动）仅释放/缩短过渡态，不引入"负 AP"；AP 成本恒为 1 或 0。

> 注：此原则原记录于 `docs/L2_基类层/02_游戏机制.md`（§行动点铁律）与 `.kiro/specs/wakeup-core-mechanics`（Requirement 6），2026-08-13 由项目所有者确认为宪法级条款，故在 L0 立本条以统一权威落点，防止被 `apModifier` 类加价字段回退。

## 第五条：五并列原则

任何时刻玩家面对的选项不超过 5 个。

**例外**：公共使用的少量变量除外（如 Boss 血量），但必须满足以下条件：
1. 所有玩家共用同一份数据
2. 不允许部分玩家独占（如队伍私有变量、公用变量等）
3. 公共变量的修改必须对所有玩家同时生效

---

## 第六条：设计原则优先级

设计原则的优先级（从高到低）：

1. **低心智性**：玩家需要同时维护的独立信息越少越好
2. **可玩性**
3. **复用性**
4. **常识性**

**层级含义**：即使一个机制非常符合常识、复用程度很高，只要它持续增加玩家必须维护的状态或污染行为菜单，就应优先删除。

## 第十二条：五并列原则例外

### 例外条件

以下情况可以超过五并列限制：

| 条件 | 说明 |
|------|------|
| 公共变量 | 所有玩家共用的数据（如Boss血量） |
| 机制类型 | 不同的机制类型（如10种弱点类型、10种伤害类型） |
| 同时生效 | 修改必须对所有玩家同时生效 |

### 禁止情况

以下情况必须遵守五并列原则：

| 禁止类型 | 说明 |
|----------|------|
| 私有变量 | 部分玩家独占的变量 |
| 队伍变量 | 队伍内部私有数据 |
| 非同步修改 | 修改不实时同步给所有玩家 |

## 第十三条：正交架构域（D-067~D-070）

### 13.1 三层之外的正交域

三层规则链（Kernel → Class → Play）只回答"怎样形成并运行一局规则"。以下五个架构域与三层协作，但**不是规则链的第四层**：

| 域 | 职责 | 与三层的关系 |
|---|---|---|
| **表现系统** | UI、动画、音效、无障碍 | 读取语义投影，提交待校验意图 |
| **创作系统** | 编辑器、地图生产、发布 | 生成候选，经三层统一校验 |
| **运营系统** | 会话装载、匹配、长期推进 | 并列装载玩法包+表现+叙事 |
| **工程治理** | 路线图、技术栈、测试 | 约束开发过程，不进运行时 |
| **叙事设定** | 世界观、角色、地点 | 通过稳定ID被玩法包引用 |

### 13.2 玩法层纯度

玩法层**只允许**：
- 玩法包 Def 与装载清单
- 基类实例组合及具体 1-5 数值
- 胜负条件、回合流程、策略
- 直接参与一局运行的地图数据
- 稳定叙事 ID 引用
- 与技术无关的可观察性规则

玩法层**禁止**：
- HUD 布局、控件、动画曲线、音效路径
- 编辑器、产权、审核、发布流程
- 匹配、局外养成、活动编排
- 技术选型、路线图、测试策略
- 世界观正文

### 13.3 稳定端口原则

- 表现系统读取三层发布的只读语义投影，提交待校验意图
- 创作系统生成候选产物，经统一编译校验后注册
- 运营系统并列装载玩法包、表现 Profile、叙事包
- 跨域依赖必须指向稳定端口，不依赖活跃内部形状
- 发现职责重复时先做所有权裁决，不用适配器掩盖

详见 [`00_架构域与文档分类.md`](./00_架构域与文档分类.md)
