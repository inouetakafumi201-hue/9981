## 一、玩法层职责

玩法层是**L3层**，位于基类层之上，是三层规则运行链的最后一环。

```
玩法层 = 基类实例组合 + 1-5 数值约束 + 规则配置；地图原数据、地图表现资产和地图局部编排属于独立内容类型
```

### 1.1 玩法层拥有的职责

- 玩法层 Def 与装载清单
- 基类层实例组合及启用关系
- 具体玩家可见数值，且严格位于 1–5
- 胜负条件、回合流程、调度、策略和玩法 Linter 规则
- 玩法文件可引用的稳定规则、动作、阶段和结果定义
- 对稳定叙事 ID 的引用及其规则映射
- 与技术无关的可观察性要求（如"隐藏动作结算前不可见"）
- 角色演员选择意图：玩法包可以使用人类可读的角色名选择演员，但只记录角色名/选择语义，不记录图片路径、素材管线目录或生成脚本细节；实际素材挂载由表现/创作侧完成。

### 1.2 玩法层禁止拥有的职责

- HUD 布局、控件结构、屏幕位置、动画曲线、音效和资源路径
- 设备适配、教程界面、观战界面和无障碍实现
- 编辑器步骤、创作工作台、产权、审核、发布和分发流程
- 匹配、局外养成、活动编排和会话生命周期
- 技术选型、开发路线、测试策略和工程门禁
- 世界观、角色传记、地点正文和时间线正文

**详见**：[`../00_架构域与文档分类.md`](../00_架构域与文档分类.md) 第四节

## 四、七类内容边界与玩法包规范

本节冻结玩法层相关的七类内容。玩法包不是唯一语义类型，而是内容集合或传输泛称；官方目录、内存对象和 zip 都可以承载同一集合。

- **玩法层**：可复用的 ActionDef、RuleDef、ScheduleDef、PhaseDef、OutcomeDef、PolicyDef、DecisionDef、AttachmentDef 和 Expression 定义集合。
- **带地图的玩法包**：可包含玩法文件、地图包引用、局部定义和表现覆盖的 UGC 或扩展集合；它不是玩法层本身。
- **地图原数据文件**：Canonical MapData v2，描述 layers、nodes、edges、placements 和空间数据；legacy v1 只在导入边界规范化。
- **地图文件或图片**：统一称为地图表现资产，包括底图、图层、切片、动画、音频和环境资源；表现资产不决定规则事实。
- **地图玩法文件**：把玩法层定义绑定到地图节点、边、触发器、流程和局部演出；不复制通用规则。
- **玩法文件**：描述一次模式、剧情或对局的流程调度、生命周期、地图绑定、演出绑定和结果组合；通过端口引用玩法层和表现层。
- **地图包**：以地图为中心的交付集合，包含地图原数据文件、地图表现资产、可选地图玩法文件和内容清单；不要求使用 zip。

### 4.1 玩法层与其他内容的引用关系

```text
玩法层定义 ← 玩法文件 / 地图玩法文件引用
地图原数据文件 + 地图表现资产 + 可选地图玩法文件 → 地图包
玩法文件 + 地图包引用 + 局部扩展 → 带地图的玩法包
```

玩法包一词如未附加具体 ContentKind，只表示“可传输或可装载的内容集合”，不得据此推断是否带地图、是否官方或是否为 zip。

玩法层定义可以作为内容集合中的逻辑部分被装载；玩法包一词只表示内容集合或传输泛称。具体玩法包、地图包和带地图玩法包的边界遵循本节 4.1 的七类内容定义。

1. **数值约束**：所有玩家可见数值严格限制在1-5范围内
2. **基类组合**：通过组合基类层实例生成玩法包
3. **规则配置**：定义玩法包特有的规则和胜利条件
4. **不可违反L1/L2**：玩法层不得违反引擎层和基类层的定义
5. **纯净性**：不包含表现、创作、运营、工程或叙事正文

### 4.2 玩法层定义与内容集合

玩法层定义只包含可复用规则语义和其装载元数据：

```typescript
interface PlayLayerDefinition {
  id: string;
  name: string;
  baseClassInstances: string[];
  numericalConfig: Record<string, 1|2|3|4|5>;
  rules: RuleDefinition[];
  narrativeRefs: string[];
  observabilityRules: ObservabilityRule[];
}

interface PlayFileReference {
  playFileId: string;
  requires: string[];
  mapBundleId?: string;
}

interface MapBundleReference {
  mapBundleId: string;
  mapDataEntryId: string;
  visualAssetEntryIds: string[];
  mapPlayFileId?: string;
}
```

玩法文件负责一次模式、剧情或对局的流程调度、生命周期、地图节点绑定、演出绑定和结果组合。地图包负责地图原数据、地图表现资产、可选地图玩法文件和内容清单。带地图的玩法包可以把玩法文件与地图包引用组合成一个可传输集合，但这不改变各内容类型的安全边界。

“玩法包”未带 `ContentKind` 时只表示内容集合或传输泛称；官方目录、内存对象和 zip 都可以作为载体。

### 4.3 与其他架构域的关系

```
表现系统 ──读取语义投影──> 玩法包运行时状态
表现系统 ──提交待校验意图──> 玩法包 Action 端口

创作系统 ──生成候选玩法包──> 玩法层统一校验 ──> 权威玩法包注册表

运营系统 ──并列装载──> 玩法包 + 表现 Profile + 叙事包
```

### 4.4 角色演员选择与素材挂载边界

玩法层允许在玩法包或角色配置中写入人类可读的角色名，例如“紫衣黑帽侦探”“医护人员”。这只是**选择哪位演员的语义意图**，不是美术资源路径，也不是对素材目录的所有权声明。

- AI / 迭代者需要选演员时，直接扫描素材生成根目录的一级子目录，并按目录名识别候选角色；不要求额外的全局索引、aliases 或不可读 ID。
- 素材目录名允许中文，也允许在素材整理阶段直接改名。玩法文档和玩法数据不应保存 `run/` 下的具体路径，以免素材整理改名破坏玩法包。
- 表现/创作侧在挂载时读取所选角色名，找到当时的素材目录并形成可消费的成品副本或快照，再将实际资源交给表现层。
- 玩法层不负责扫描素材目录、读取 PNG、决定帧号或拼接 URL；这些属于创作/表现侧的挂载职责。
- 角色名找不到或素材缺失时，挂载流程必须报告缺失，不得让玩法规则自行猜测另一个角色替代。

因此角色选择链是：

```text
玩法层记录角色名（选择意图）
  → 创作/表现侧扫描素材根目录
  → 选中当时的角色目录并挂载快照
  → 表现层根据玩法状态播放对应帧
```

这条边界保留了“改文件夹名即可整理素材”的开发流畅度，同时避免玩法层依赖具体素材路径。

**禁止**：
- 玩法包反向依赖具体 UI 实现
- 玩法包绕过统一校验直接注入
- 运营编排被伪装成玩法包内规则
