## 一、架构总览（三层，已冻结的形状）

```
L1 引擎层 Kernel（src/core/kernel）——0 游戏知识，只认实体/状态/关系/动作/规则/事务/Hook
   └─ 铁律：0 追加。已接线 Hook 分发（wire-hooks）。是稳定基座。
        ↓ 上层只经公开 Op/Query/queryActions/Policy/Decision/Intent 消费
L2 基类层 Class（src/l2 规范模型+装载管线 · src/class 实例目录 · src/core/ugc UGC接入 · src/core/kernel/ai AI消费者）
   └─ 铁律：实例不含玩法数值、不含玩法规则；可组合/继承/扩展。
        ↓ 玩法层组合基类层实例 + 数值约束(1-5) + 玩法规则
L3 玩法层 Play（src/play）——具体数值、玩法包、玩法规则
   └─ 铁律：纯数据、高频迭代、不回溯改基类层。
```

**唯一写入通道**：所有状态改变经 `OpRegistry.invoke`。玩法层仅 `core-mechanics/load.ts` 可引用 `OpRegistry`。

## 三、每条线的可信断点（从哪往下写）

### L1 引擎层 — ✅ 完成，作为冻结基座
- 断点：无新增开发。仅在上层需要时**补公开契约**，且遵守 0 追加铁律。
- 风险：上层若绕过公开 Op 直接依赖内核内部形状 → 违规，须挡回。

### L2 基类·管线 (l2-base-layer-spec) — ✅ 高信任，待收敛执行
- 真实完成：`src/l2` 编译/校验/解析/注册/运行时提交 + `model/**` 规范常量；37 测试全绿。
- 断点：**执行 D-061**（把 `spec-compiler` 独有缺口迁入 `src/l2`、更名引擎级 JSON 原语、退役 `SpecificationCompiler`）。→ **PT-01**（🔒 等 D-061 批准 + PT-02 先行）。

### UGC (wakeup-ugc) — ✅ 高信任，被 l2 端口阻塞
- 真实完成：61/64；主链路 + 机器可校验端口契约 `l2-port-contract.ts`（含零耦合守卫）。
- 断点：**l2 侧交付消费端口**（validation/resolution/registries[layer]）→ **PT-02**（🟢 就绪，见交接 Prompt）。它解除 `wakeup-ugc` task 11.1。

### AI (wakeup-ai) — ✅ 高信任
- 真实完成：`src/core/kernel/ai` 全套组件 + 9 测试文件；design 明确 AI 落于此（受限引擎消费者）。
- 断点：功能层面已达 spec 声称范围。**建议**：一次覆盖率审计（可选，PT-04），并把 AI 的层级归属（引擎目录内的 L2 消费者）在文档上讲清（低优先）。

### L3 核心机制 (wakeup-core-mechanics) — ⚠️ 低信任，**冻结待裁决**
- 真实状态：机制内容有**两套并行实现**——`action-turn/playpack.json`（纯数据，30 测试，可信）与 `core-mechanics/*.ts`（TS，**零测试**，含装载期治理 Linter）。二者对 U-002 结论**相反**。
- 断点：**先批准 D-062（收敛方向）+ 由所有者定 U-002**，再执行 **PT-07**（收敛为单一权威数据源 + 补齐 tasks 9–10 必交付属性测试）。**在此之前不得向下写核心机制实现**。

### L2 空间物品 (wakeup-space-items) — 🟡 tasks 过时，真实工作在既有规则
- 真实状态：`src/class/space-items/` 不存在（D-058 否决）；空间/物品/载具/微场景/门/死亡容器校验**已大量落在** `src/l2/validation/{spatial,item-vehicle,action-gateway}-rules.ts`，目录数据在 `src/class/<族>/index.json`。
- 断点：**先按 D-058 重写 tasks.md**（校验既有 + 补缺口，而非新建目录）→ **PT-08a**；再补 requirements 1–14 中尚未被现有规则覆盖的校验面 → **PT-08b**。

### UI/演出 (wakeup-ui-animation) — 🔴 绿地
- 真实状态：`src/ui` 不存在；依赖的 `src/l2/model`/`adapters` 已冻结（`attackShape` 已按 2026-08-08 删除）。
- 断点：从 **task 0（建 `src/ui` + 纳入 lint 边界）** 起按序推进 → **PT-09**（🟢 就绪，依赖已冻结）。

## 七、信任缺口与本报告未覆盖的诚实边界

- **`test/l2/**` 不在 `tsconfig` 默认 typecheck**（无 npm 脚本跑 `tsconfig.l2.json`）→ "引用已删字段"类错误 `tsc` 抓不到（本轮 `attackShape` 陈旧断言即由此漏过）。根治=**PT-06**。
- **`core-mechanics/*.ts` 零测试**：其正确性目前**无任何机器证据**，不可信任为"完成"。
- **`wakeup-ai` 覆盖率未逐条审计**：代码组件齐全、9 测试文件通过，但未核对每条 requirement 的断言完备性（可选 PT-04）。
- **`wakeup-space-items` requirements 1–14 的逐条覆盖映射**本报告只给了结论级判断，精确到"每条 requirement ↔ 哪个规则函数"的映射需 PT-08a 落实。
- 本报告**未**重跑 12 个 `kernel-l*-test` 独立子项目（约 733MB node_modules），其状态沿用 `KERNEL_VERIFICATION_STATUS.md`。

## 八、结论：可信设计的一句话总结

**L1 引擎、L2 管线、UGC、AI 四条线已被测试证明可信，可作为稳定基座**；**L3 核心机制存在未裁决的双实现结构冲突（D-062）且 TS 侧零测试，是当前最大的信任缺口，必须先裁决再往下写**；**空间物品线的 tasks 已被 D-058 作废需重写**；**UI 线是干净绿地可即刻开工**。并行只从 §五「🟢 现在就能并行」的线派发，🔒 线等决策。
