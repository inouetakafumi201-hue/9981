# 架构域与文档分类

> **性质**：三层运行规则依赖链与正交架构域的分类规范。
> **依据**：`docs/L0_规范宪法.md`、访谈裁决 D-063、D-067～D-070。
> **目标**：保持引擎层（Kernel）→基类层（Class）→玩法层（Play）严格纯净，同时让表现、创作、运营、工程与叙事拥有正式且可独立演进的位置。
> **禁止误读**：本文定义的正交架构域不是 L4，也不改变三层规则链的位阶。

---

## 一、唯一的对局规则运行依赖链

```text
引擎层（Kernel）
  ↓ 提供无游戏语义的原语、Op、Query、Expr、Hook、随机流与持久化能力
基类层（Class）
  ↓ 使用引擎端口定义可枚举、可组合且不含具体玩法语义的基类与实例
玩法层（Play）
  ↓ 组合基类层实例，声明具体数值、流程、胜负条件、地图数据与策略
已装载对局
```

该链只回答“怎样形成并运行一局规则”。三层之外的系统不得被插入链中，也不得被命名为下一层。

### 1.1 引擎层（Kernel）

- 只认识实体、组件、关系、动作、表达式、查询、事件、随机流和持久化等通用概念。
- 唯一状态写入通道是 `OpRegistry.invoke`。
- 不认识武器、AI 性格、HUD、地图编辑器或具体玩法包。

### 1.2 基类层（Class）

- 承载可枚举、可组合且不含具体玩法语义的基类与实例契约。
- 可声明能力、组合约束、结构边界与可配置字段。
- 不写具体玩法数值，不决定某实例在哪个玩法包出现，也不拥有表现描述符。

### 1.3 玩法层（Play）

- 只承载可独立装载、校验和运行的玩法包。
- 组合基类层实例并赋予具体 1–5 数值，声明流程、胜负条件、调度、策略与具体地图数据。
- 不承载具体 UI、动效、音频、工具操作、发布流程、运营编排、工程方法或世界观正文。

---

## 二、正交架构域

正交域可以消费三层发布的稳定端口或向三层提交候选数据，但不是规则运行链中的后继层。

| 架构域 | 拥有的职责 | 明确不拥有 |
|--------|------------|------------|
| **表现系统** | UI、动画、音频、粒子、震动、无障碍、多设备适配、表现 Profile | 规则状态权威、胜负判定、玩法数值、基类定义 |
| **创作系统** | 编辑器、工作台、地图生产、静态校验交互、产权、审核、发布与分发 | 已装载对局的规则执行、基类/玩法权威注册表 |
| **运营系统** | 会话装载、对局进出、异步匹配、长期推进、活动编排 | 对局内部规则结算、表现实现、基类语义 |
| **工程治理** | 路线图、技术栈、开发流程、测试与质量策略 | 运行时语义和内容规范 |
| **叙事设定** | 世界观、角色、地点、组织、时间线、叙事一致性 | 具体玩法规则、运行时状态写入、UI 实现 |

### 2.1 表现系统

表现系统读取权威规则状态的只读语义投影，生成玩家可感知的界面和反馈。它可以收集玩家输入，但只能形成待校验意图，不得本地决定规则结果或直接改写状态。

### 2.2 创作系统

创作系统生成声明式候选产物。候选产物必须经过所属层的统一编译、校验、引用解析和注册流程，才能成为基类层实例或玩法包。编辑器预览、默认值或替身通过不等于集成完成。

### 2.3 运营系统

运营系统选择并装载玩法包、可选表现 Profile 与叙事包，管理对局外的会话和长期推进。已装载对局仍只由三层规则链运行。运营系统不是第四运行层。

### 2.4 工程治理

工程治理约束项目如何开发和验证，不向运行时产物提供游戏语义。路线图、技术选型、测试矩阵和发布门禁统一归此域。

### 2.5 叙事设定

叙事设定保存长期扩展的世界观权威正文。规则文档通过稳定叙事 ID 建立映射，避免复制正文和形成分叉权威。

## 三、稳定端口与依赖方向

### 3.1 总体方向

```text
创作系统 ──候选产物──> Class / Play 统一编译与校验端口
运营系统 ──装载请求──> 会话与玩法包装载端口

Kernel / Class / Play ──只读语义投影──> 表现系统
表现系统 ──待校验意图──> 权威 Action / Intent 端口 ──> OpRegistry.invoke

叙事设定 ──稳定叙事 ID / 叙事包──> Play 或运营组合
工程治理 ──门禁与流程约束──> 仓库产物（不进入运行时依赖图）
```

### 3.2 表现读取端口

- 三层发布与界面技术无关的只读语义投影。
- 投影表达规则事实、可观察性、可用动作和不可用原因，不表达控件树、屏幕坐标、动画资源或音效路径。
- 表现系统拥有 `PresentationDescriptor`、表现 Profile、动效映射和设备适配。
- 基类层不得为了某一 UI 的当前内部形状发布专用适配结构。

### 3.3 意图提交端口

- 表现系统只提交规范化意图和必要的参与者/目标引用。
- 权威端口负责校验可见性、权限、成本、时序与规则前置条件。
- 所有最终状态写入仍映射到 Op，并经 `OpRegistry.invoke`。
- 禁止 UI 本地扣除 AP、推进回合、决定命中或直接修改实体状态。

### 3.4 创作产物端口

- 创作系统输出基类候选或玩法包候选，不直接写权威注册表。
- 候选必须带来源、版本、稳定 ID 与诊断定位信息。
- 基类候选走基类层统一契约；玩法包候选走玩法层装载与 Linter 契约。
- 地图编辑、编译和发布流程归创作系统；编译后的具体地图数据可归玩法包。

### 3.5 运营装载端口

- 运营系统以并列输入组合玩法包、表现 Profile 和叙事包，不让玩法包引用具体表现 Profile。
- 装载失败必须返回结构化诊断，不得用默认值掩盖缺失契约。
- 会话切换不得伪装成对局内网关基类。

### 3.6 契约守卫

跨域契约必须机器可校验，至少覆盖：

1. Play 生产代码不得 import 表现系统或创作系统。
2. 表现系统不得拥有权威规则状态写入通道。
3. 创作工具不得绕过统一校验和注册入口。
4. 表现描述符不得在基类层与表现系统形成双重权威。
5. 未冻结依赖应有“零耦合”守卫；不得先写针对其当前内部结构的适配器。

## 四、玩法层纯度判据

### 4.1 允许进入玩法层

- 玩法包 Def 与装载清单。
- 基类层实例组合及启用关系。
- 具体玩家可见数值，且严格位于 1–5。
- 胜负条件、回合流程、调度、策略和玩法 Linter 规则。
- 直接参与一局运行的具体地图数据。
- 对稳定叙事 ID 的引用及其规则映射。
- 与技术无关的可观察性要求，例如“隐藏动作结算前不可见”。

### 4.2 禁止进入玩法层

- HUD 布局、控件结构、屏幕位置、动画曲线、音效和资源路径。
- 设备适配、教程界面、观战界面和无障碍实现。
- 编辑器步骤、创作工作台、产权、审核、发布和分发流程。
- 匹配、局外养成、活动编排和会话生命周期。
- 技术选型、开发路线、测试策略和工程门禁。
- 世界观、角色传记、地点正文和时间线正文。

### 4.3 混合文档拆分规则

1. 先识别直接参与规则运行的数据与约束，将其保留在三层对应位置。
2. 将具体感知方式迁至表现系统，将生产方式迁至创作系统。
3. 将会话外编排迁至运营系统，将工程方法迁至工程治理，将世界观正文迁至叙事设定。
4. 原文档用稳定交叉引用连接，不复制完整段落。
5. 无法裁决的内容登记为未决项，不因文档混乱而默认删除。

## 五、文档分类判据

对任意章节依次提问：

1. **它是否定义无游戏语义的运行原语？** 是 → 引擎层。
2. **它是否满足可枚举、可组合、不含具体玩法语义？** 是 → 基类层。
3. **它是否直接构成一局可装载玩法的规则或具体数据？** 是 → 玩法层。
4. **它是否决定玩家如何感知或输入？** 是 → 表现系统。
5. **它是否决定内容如何被制作、校验、审核、发布或分发？** 是 → 创作系统。
6. **它是否决定会话外装载、匹配、长期推进或活动编排？** 是 → 运营系统。
7. **它是否约束开发、测试或技术选型？** 是 → 工程治理。
8. **它是否是世界观或叙事权威正文？** 是 → 叙事设定。

同一文档命中多个答案时必须拆分，不得用“主要属于某处”为由保留跨域职责。

## 七、现有代码的过渡债务与交接边界

### 7.1 已知过渡债务

- `src/l2/model/projection.ts` 与 `src/l2/adapters/ui-adapter.ts` 当前包含面向 UI 的形状。
- `wakeup-ui-animation` Spec 已采用 `src/ui/` 与端口注入方向，但部分文档仍把表现描述符归基类层、把具体表现 Profile 归玩法层。
- `l2-base-layer-spec` 仍把原 `08_图形化与UI.md` 及工程文档列为来源，并包含表现描述符所有权。

### 7.2 收敛原则

- 最终由基类侧发布通用、只读、与界面技术无关的语义投影；表现描述符由表现系统单独拥有。
- 不在 `src/l2` 与 `src/ui` 并行实现同一职责，再用适配器把重复连接起来。
- 现有 UI 适配代码冻结扩张；代码迁移由其所属 Spec 接受交接并执行。
- 本轮文档整理只修正文档所有权与端口契约，不跨 Spec 强改他人交付代码。

### 7.3 必须登记的交接项

1. `wakeup-ui-animation`：更新来源路径、表现描述符所有权与 Profile 归属；建立跨域机器守卫。
2. `l2-base-layer-spec`：移除表现与工程文档来源；把 UI 专用描述符迁出基类层，仅保留通用语义投影。
3. 运营相关实现：以会话/装载端口消费玩法包、表现 Profile、叙事包，禁止建立“运营层 → Play → UI”的纵向链。

## 八、维护规则

- 新文档先按第五节判据确定唯一归属，再创建路径。
- 任何正交域不得使用 `L4` 或“第四层”命名。
- 归档内容迁回现行文档时必须逐项建立“保留、迁移、废弃、未决”记录，禁止静默删减。
- 跨域依赖必须指向稳定端口，不得依赖对方当前内部目录或对象形状。
- 发现两处都声称同一职责的唯一权威时，先做所有权裁决；禁止以适配器掩盖结构重复。
