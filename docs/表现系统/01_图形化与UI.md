# 图形化与 UI 设计

---

## 视觉风格定位

### 像素风 + 简笔画叠加

**核心理念**（已定案）：
- **交互组件**：像素艺术（高饱和度，32×32 或 64×64）
- **地图背景**：简笔画风格（清爽、低饱和度）
- **叠加层分离**：前景像素 + 背景草图，视觉层次清晰

**为什么这套组合？**
1. **UGC 友好**：数字绘图板 + AI 辅助即可创作大批量像素元素
2. **数据轻量**：一张地图 < 1MB
3. **对比鲜明**：高饱和像素元素在低饱和背景上一目了然
4. **工具支持**：游戏内创建工具可用简单像素填充 + 缩放
5. **风格统一**：像素网格天然约束 UGC 内容视觉一致

**不使用 Sprite Canvas 技术**（按你指示）。

### 正面斜投影（Cabinet / Cavalier Projection）

**这是本游戏固定、唯一的视角与打法——不可换成其它任何"斜交"角度。**

- **视角定义 = 正面斜投影 (Cabinet / Cavalier Projection)**，类比说明：类似正面斜投影风格（D-025：此处为视角技术类比，规范名称是"正面斜投影"）。
  - 角色/实体的**正面朝向镜头**（正是它朝你），同时用斜投影把**侧面**也画出来（一个面的纵深折向画面外的一侧），造成"又朝前、又能看见侧面深度"的立体感。**不是 45° 向东/向西扭转的侧身。**
  - 既然正面朝前的人物也能画侧面，那我们一贯的"有朝向（不正对镜头）"也成立：朝向通过斜投影折出的侧面自然表现。
- **一份表述、两个英文口令**：`front-facing with Cabinet/cavalier oblique projection of the side` 或 `front-facing oblique (cavalier) projection`（D-025：AI 提示词可用类比游戏名辅助，但中文规范名称统一为"正面斜投影"）。不写模糊的 "three-quarter / isometric / 斜侧"。
- **地图同此**：地图可视化的视角与角色同一法则（见 §地图可视化）。全游戏不再使用"任意斜侧角/45°侧身"这类模糊词。
- **落点**：所有角色出图提示词统一带 `front-facing cabinet/cavalier oblique projection`（PLT-01 §固定骨架 `[VIEW]` 是唯一口令来源）；3D 造型调色板见 `PLT-01_画风对齐_三维形体_提示词调色板迭代.md`。

## 五条视觉定律

**这是全游戏视觉一致性的基准。**

### 1. 全局颜色语义映射

本表同时约束对局、局外驻地、创作界面与运营节点。**同一种主色不得因界面切换而改义**。

| 颜色 | 核心语义 | 当前机制覆盖 |
|---|---|---|
| **红色** | 生命减损、伤害、致命危险 | HP、受伤、伤害数字、毒圈、坠落伤害、高风险任务；不再泛指一切攻击 |
| **蓝色** | 清醒度、体力（清醒值 / SP），以及科技、处决机会 | 清醒条、体力消费、强力骰、导流科技、令其长眠、可处决闪烁 |
| **黄色** | 感官、注意、警戒 | 噪音、巡逻、警戒范围、需要主动看一眼的线索；不再表示 AP |
| **橙色** | 行动点 / AP、行动消耗及其进度 | AP 计数与成本、撬锁/检定进度、行动正在生效 |
| **绿色** | 安全、正面交互、免费与让利 | 拾取、已开的门、正面状态、0 AP、免费、低价、折扣 |
| **紫色** | 关系约束、局部行动菜单替换、远程 | 网关、条件/检定入口、擒抱/招架约束、远程攻击、射程与瞄准关系 |
| **珊瑚色** | 近战、格斗、攻击性行为、暴力 | 近战攻击目标、拳脚、主动施暴；必须与生命/伤害的血红色明确区分 |
| **青色** | 社交、交流，以及所有 UGC / 创意工坊相关的来源与创作物语义 | 对话、组队沟通、创作者入口、创意工坊、上传/订阅的玩家创作物 |
| **灰色** | 冷却、延迟、不会立刻生效 | 冷却中的动作、等待生效；可由橙色过渡为灰色 |
| **灰白** | **可交互但受制于当前状态**：带高光与材质感，标示"对象可用/可使用"，仅在悬停或高亮时显现在灰阶对象上；灰白高光 ≠ 灰色静置 | 门户（默认）、可点击冷却节点的高光、中性交互容器；平时灰白，进入可交互才亮起 |
| **纯白 / 奶白** | **梦境边界与过载的概念色**：泛化表达入睡、入梦、梦境本源与"过载/溢出"；纯白更具视觉冲击（闪光、过载、梦境阈值），过载时纯白即如闪光弹闪现 | 入梦/睡眠门户氛围、床显形演出、淡白→泛白→纯白三阶段、纯白=进入即迷失；纯白与奶白在本游戏中可互换，纯白用于高冲击 |
| **金色 / 银色** | 区别性品级高光 | 高级动作、宝物或少量重要对象；只分金银概念，不构成严格评级阶梯 |

#### 语义色与材质通道

- **语义色**回答“它是什么 / 正在做什么”；金银只作边缘、高光或局部材质，不覆盖主语义色。
- 灰色对象仍可点击：可点击态使用高光、凸起和高级材质感；不可点击态必须扁平、无高光。**不可点击不能再只靠灰色表达。**
- 冷却使用橙 → 灰的过程表现；已经冷却完成时回到其功能主色。
- 一个对象涉及多个分类时，主色取玩家只看颜色时最可能猜中的**下一项主要功能**；次要语义用局部徽章、边缘或文字承载，不混成第三种主色。

#### 双重分类裁决例

| 对象 | 主色 | 次要通道 | 理由 |
|---|---|---|---|
| 商店入口 | 青 | 紫色约束框；绿色折扣标记 | 玩家先猜交易入口 / 社交面，而不是先猜网关 |
| 上锁门 | 紫 | 橙色成本/进度；红色伤害后果 | 玩家先猜条件约束 |
| 远程瞄准线 | 紫 | 命中后的伤害用红色 | 玩家先猜远程关系 |
| 近战攻击目标 | 珊瑚 | 实际伤害结算用红色 | 玩家先猜近战暴力 |
| 免费经济项 | 青 | 绿色 Free / 折扣徽章 | 交易入口 / 创作者面是功能，免费是价格状态 |

> **修订说明（2026-08-10）**：旧“七色语义”已被本表取代。AP 从黄色迁至橙色；黄色收窄为感官/警戒；近战从紫色迁至珊瑚色；紫色收敛为关系约束、局部菜单替换与远程；新增青色经济/交流域及金银高光轴。

> **修订说明（2026-08-13）**：蓝色语义前移为与清醒度、体力直接挂钩（科技/处决次之）；青色与经济脱钩，转向全面承接社交、交流及 UGC/创意工坊的来源与创作物；经济不再占独立主色，交易/经营入口改走青色社交/交流面承载。**灰白不再与奶白混同**：灰白回归"可交互但受制于当前状态"的高光描边语义；"奶白"独立为新色「纯白/奶白」，承接梦境边界与过载（淡白→泛白→纯白、过载闪光、床显形），纯白即梦境阈值概念色。

### 2. 边缘发光交互语法

**悬停高亮 + 边缘发光，不用传统按钮**：

> **命名规范（D-025）**：本方案的规范名称是**边缘发光交互提示**。不得用第三方游戏名作为技术方案的规范名称（此处曾写作"Among Us 风格"，已按 D-025 与 `wakeup-ui-animation` Spec Requirement 6.3 改为技术描述性命名）。

| 发光颜色 | 语义 | 示例 |
|---|---|---|
| **白光** | 一般可通行 / 可移动 | 相邻节点、无额外条件的路径 |
| **黄光** | 感官线索 / 警戒 | 噪音源、巡逻与需要主动注意的线索 |
| **橙光** | AP 消耗 / 进行中 | 成本徽章、撬锁或检定进度 |
| **红光** | 生命伤害 / 致命危险 | 毒圈、坠落后果、伤害结算 |
| **蓝光** | 清醒科技 / 可处决 | 零血倒地目标、导流相关交互 |
| **紫光** | 网关约束 / 远程关系 | 上锁门、检定入口、远程目标与射程 |
| **珊瑚光** | 近战 / 暴力 | 近战攻击目标、格斗行为 |
| **绿光** | 安全 / 正面 / 免费 | 可拾取物、已开的门、免费项 |
| **青光** | 社交 / UGC / 创作 | 对话、组队、创作者入口与创意工坊内容 |

金银只作为上述发光的少量高光或描边，不独立改变交互功能。灰色冷却对象若仍可点击，必须保留凸起与高光；扁平无高光才表示不可点击。

**交互流程**：
1. 鼠标悬停 → 目标对象边缘发光
2. 点击 → 执行动作或弹出上下文菜单
3. 不可交互的对象不发光

## 轮次栏（核心组件，D-036）

**轮次栏是图形化实现中最重要的 UI 组件。** 它把行动排名、生命值、清醒值三项信息合并到一个常驻组件里，并同时充当投掷/比较动效的舞台。

### 形态与职责

| 项目 | 规范 |
|---|---|
| **位置** | **屏幕左侧常驻**，与持久状态栏一样始终可见，不随回合阶段切换而隐藏 |
| **形态** | 由若干玩家**头像 + 名字**构成的**纵向「轮次框」列表**；**每一个轮次 = 一个独立的框**，框可以有形状，因为切换时框会做形态变化的动画 |
| **内容** | 每一条同时显示该玩家的**生命值与清醒值** → **兼任简易状态栏** |
| **动效舞台** | 投点动画、条形比较等动态效果**就在这几个框的旁边完成**，不另开独立面板 |
| **排序** | 按行动轮排名，立即生效（每次变化后重新排序） |

### 轮到谁与玩家自己的突出（高光语义）

- **轮到的人 = 高亮**：当前行动方的框被高亮，高亮是**反光感**（材质/光泽感的高亮），不是普通描边亮起。
- **玩家自己的轮次框 = 比他人更大且更突出**：突出程度约为**一个骰子图标的宽度**（即玩家框比他人框宽出约一骰宽），且玩家的条状也**更粗**一些；但**颜色变化规则与他人一致**（不换肤色/语义色）。
- **体力（清醒值/SP）高光**：轮到玩家时，其清醒值/体力条带反光高光。

### 视觉布局

```
轮次栏示意（左侧常驻）：
┌──────────────────────┐
│ ① 👤 玩家A            │  ← 排名 + 头像 + 名字
│    ❤️❤️❤️❤️⬜  💧💧⬜⬜⬜ │  ← 血量（红 5 格）+ 清醒值（蓝 5 格）
├──────────────────────┤
│ ② 👤 玩家B            │     当前行动者→该框高亮（反光感）
│    ❤️❤️❤️⬜⬜  💧💧💧💧⬜ │
├──────────────────────┤
│ ③ 👤 玩家C  （已行动） │  ← 变灰/降饱和（D-035）
│    ❤️❤️⬜⬜⬜  💧⬜⬜⬜⬜ │
└──────────────────────┘
        ↑
 动效在此区域右侧可就地播放（投点、条形比较）
 但骰子图标不是固定在轮次栏一起——它悬空（见下）
```

**轮次框核心规则**（2026-08-15 定案）：
- **每个轮次 = 一个独立的轮次框**：框可有形状，因为切换时有形态动画。
- **轮到的人 = 高亮（反光感）**：不是普通描边亮起，而是像光反射的**反光高光**（glossy reflective shine）。
- **玩家自己的框比他人大且粗约一个骰子宽度**：视觉突出度非常强，其清醒/体力带反光高光，但颜色规则与他人一致。
- **轮次栏设计按 8 人容量规划**：必须能容纳 8 个轮次框的纵向空间。

### 骰子图标与投掷条状对比（悬空图标，非轮次栏附属）

**骰子只在当前行动者右侧悬空出现**（2026-08-15 定案）：
- **骰子图标 = 悬空的图标，不固定绑在轮次栏上**：它**只有在统一投点或某个行动投点时，才在轮到谁的轮次框右侧悬空出现**。平时不可见。
- **骰子左侧 = 玩家序号（1/2/3/4/5）**：骰子左侧的方块标注玩家序号，作为横条的锚点标识（不是武器图标）。
- **投完之后的投影条**：投完之后，骰子的右侧**射出一根条**，多个参与者的投射条并排，形成**一排横向条状对比**。
- **投点对比条颜色规则**（2026-08-15 定案）：横条颜色对应投点结果获得的 AP（从低到高）
  - **0 AP = 灰色**
  - **1 AP = 绿色**
  - **2 AP = 橙色**
  - **3 AP = 红色**
  - 横条**长度**代表投点数值大小（直观对比谁投得高）
  - 横条是**明亮的彩色条**，不是深色上显框
- **玩家条状的延伸来源**：玩家的条状**从轮次栏右侧延伸出来**；玩家由于框更突出（约一骰宽 + 更粗），其延伸条也相应更突出；**骰子在上图层**（盖在条状之上）。
- **骰子横条面板适配 = 面板上移**：当下方轮次框伸出横条时，骰子横条面板整体上移，避免与右下动作面板重叠。

### 已行动者的标记（D-035）

- AP 用完的玩家**不从轮次栏移除**，只做**变灰或饱和度下降**处理
- 该效果的唯一语义是"他这回合已经行动过了"
- **不应做得过于显著**——不加大叉、不加"已结束"横幅

### 为什么合并成一个组件

轮次、血量、清醒值这三项是玩家**每一步决策都要参考**的信息，合并到同一个常驻组件里可以显著降低视线切换成本（低心智性）。

把投点动效放在状态条旁边，则让"**投出的点数 → 得到的 AP → 排名变化**"这条因果链在同一视觉区域内闭环，玩家不需要在弹窗和排名之间来回对照。

### 轮次栏的三种呈现状态

| 呈现状态 | 轮次栏行为 | 其他战斗 UI |
|---|---|---|
| 标准战斗节奏 | 按权威行动轮排序并播放变化 | 正常显示 |
| 一人模式 | 不移动、不竞争，只突出玩家状态栏；每次实际回合推进仍由权威投影确认 | 保留必要 HP / SP / AP 与动作反馈 |
| 少 UI 模式 | 隐藏 | 隐藏；只保留节点移动、局部交互和必要文本 |

一人模式与标准战斗节奏在**同一对局内动态升降**：没有 AI 与其他玩家时落回静止状态，任一 AI 或其他玩家出现时升起。升降不能重载场景、重建轮次栏数据或重置玩法包状态。

少 UI 模式不是一人模式的进一步折叠，而是非战斗活动的独立表现配置。任何允许战斗的活动都不得使用少 UI 模式。

**弱点信息对所有人完全公开**，不需要消耗 AP 侦察。

| 项目 | 规范 |
|---|---|
| **呈现** | 弱点图标**常驻飘在角色头顶** |

## 核心数值显示

### 投点阶段 UI：**强力骰** 与 **逆转** 两个推挡滑块（关键）

> **就地播放（D-036）**：以下结算面板**不是独立弹窗**。投点动画与条形比较**在轮次栏的状态条旁边就地播放**，让"投出的点数 → 得到的 AP → 排名变化"在同一视觉区域内闭环。下方框图仅表示信息内容，不代表独立面板布局。
>
> **两个滑块不可漏：强力骰 + 逆转。** 它们都是**可往上推、切换到 1–2 档**的推挡滑块，不是普通单选：

- **强力骰滑块**（橙色/AP/主动加注侧）：往上推到 1–2 档，消耗清醒值/体力，给投出结果加收益。
- **逆转滑块**（紫色/反制侧）：往上推到 1–2 档，用于逆转/反制别人的投点结果。

**不同档位的特效不同**：推到不同档，投点演出/滑块的视觉特效（充能感、光效、颜色浓度、粒子）都不同，让玩家一眼看出"这一档多激进"。档位越高，特效越重。

**推挡滑块 = 4 档（0 / 1 / 2 / 3），下标 0 / 1 / 2 / 2**（2026-08-15 定案）：第 4 档与第 3 档距离较近，是一种"极限档"视觉暗示。**审美强过逻辑**，虽然说不清哪里好，但**为了拓展性 + 审美比三齿轮强**，保留 4 档设计。

#### 骰子悬空 + 横条生长动画（2026-08-15 定案）

**骰子只在当前行动者右侧悬空出现**：
- 骰子不是固定绑在轮次栏一起的悬浮图标，只在**统一投点 / 某行动投点时**，才于**轮到谁的轮次框右侧**悬空出现。
- 大部分时候玩家只关心自己投多少；看别人的结果，看右侧伸出的横条对比就够了。

**骰子左侧 = 玩家序号（1/2/3/4/5）**：
- 骰子左侧的方块标注**玩家序号 1-5**（不是武器图标），作为横条的锚点标识。

**横条生长动画三段式**：
1. **灰白伸出**：横条从序号右侧伸出时是灰白色；
2. **强力骰特效 + 快速伸长**：使用了强力骰的玩家，右侧显示 **+1 或 +2 图标/特效**，且**伸长速度比其他人快**；
3. **统一刷色 + 泛红加成**：所有条都伸完后，再统一**从左侧像高光一样刷地填充颜色**（按结果区分 AP：2AP/0AP 等用不同颜色）；**强力骰多出的部分泛红**（让人一眼看出"这段是强力骰加的"）。

**横条有格状刻度、无上限框**：
- 横条带格状刻度（让人直观看出投了几点），但无固定上限黑框、长度由实际点数决定。

**骰子横条面板适配 = 面板上移**：
- 当下方轮次框伸出横条时，**骰子横条面板整体上移**，避免与右下动作面板重叠。

```
│                             │
│ 🎲 投 d6 ≥ 4 → 命中（2 伤） │
│ 🎲 投 d6 ≥ 6 → 翻倍（4 伤） │  ← 超出 DC 2 点 → 伤害翻倍
│                             │
│ 消耗：1 AP                   │
│ [确认] [取消]               │
└─────────────────────────────┘
```

**距离 DC 表**（悬停武器时显示整行）：

```
手枪距离 DC 表：
距离  1   2   3   4   5   6+
DC   2   3   4   5   6   6

当前距离 3 → DC 4
```

> **距离基准（D-051）**：距离编号**从 1 开始**，距离 1 = 贴身（同一微型场景），距离 2 = 不同微型场景但同一天然场景，距离 3/4+ 按距离公式计算。本表已完成 +1 平移。

### 瞄准状态的紫色点线（D-033，颜色语义修订）

`[瞄准中]` 状态**可见，但低显著性**。

| 项目 | 规范 |
|---|---|
| **触发方式** | 鼠标**悬停**在某个角色上 |
| **表现** | 若该角色正在瞄准，显示一条**紫色点线**指向其瞄准目标 |
| **绘制** | 起点 = 瞄准者，终点 = 目标，紫色点线/虚线，**仅悬停时出现** |
| **禁止** | **不使用头顶感叹号**等强提示 |

```
悬停玩家 B 时：
   👤B · · · · · · · ▶ 👤C
        ↑ 紫色点线（B 正在远程瞄准 C）
```

> **设计理由**：两步流程的远程武器必须让对手有机会反应，否则"反应窗口"名存实亡。但用强提示（感叹号）会让规避变成无脑操作，改为"需要主动看一眼"保留了观察成本，同时不构成信息壁垒。

> **对照**：招架是**真隐藏**（无任何标识，见 D-032），瞄准是**低显著性公开**。两者不可混用同一套表现。

## 技术实现建议

### 渲染层级

```
Z-Index 分层：
  0: 背景图（简笔画）
  1: 节点区域填充
  2: 门户图标
  3: 地面物品
  4: 实体（玩家、NPC、载具）
  5: 悬停高亮 / 边缘发光
  6: UI 面板（半透明遮罩）
  7: 弹出菜单
```

### 动画规范

- **移动**：棋子沿路径滑动（0.3 秒）
- **攻击**：远程使用紫色关系线、近战使用珊瑚色动作线；命中后目标以红色闪烁（0.2 秒）
- **拾取**：物品飞向背包（0.2 秒）
- **受伤**：血条减少 + 红色闪烁（0.3 秒）
- **倒地**：人物旋转躺下（0.4 秒）
- **令其长眠**：蓝色光效 + 清醒条瞬间填满（0.5 秒）
- **上车 / 下车**：车辆图标高亮 + 角色淡入淡出（0.2 秒）
- **撬锁完成**（精密交互完成）：锁图标变绿 + 短促闪烁（0.2 秒）
- **蹲下 / 起立**：角色高度变化（0.2 秒）

### 全屏动画清单（D-026 + D-032）

全屏骨骼动画（0.5-1 秒）**仅限四项**低频、仪式感强的动作：

| 动作 | 触发条件 |
|---|---|
| **翻窗** | — |
| **跳窗** | — |
| **令其长眠** | 对零血倒地目标处决 |
| **招架触发** | **仅当被近战攻击时**（D-032 新增） |

**招架的三种结算表现**：

| 情况 | 表现 |
|---|---|
| 被近战攻击 | **全屏动画**（擒拿/招架演出：珊瑚色近战主语义，紫色约束边缘） |
| 被远距离伤害命中 | **静默失效**，无动画、无提示 |
| 受到无法招架的伤害 | **静默失效**，无动画、无提示 |

> **为什么静默**：静默打断保证招架不会因为一次远程流弹，就给对手提供免费的信息反馈（招架是真隐藏信息）。

## 多设备与响应式表现（归档恢复）

> **来源追踪**：`docs/L_归档/08_图形化与UI设计.md`。视觉风格三选一草案不恢复；本节只恢复多设备、输入等价与布局适配设计。

### 桌面端（主要目标）

- **渲染目标分辨率：1080p（1920×1080，16:9）**；HUD、全屏动画、界面布局均按此设计。精灵是唯一的位图小件，其余（全屏动画、界面、面板）一律按 1080p 设计。
- 横向宽屏优先，地图主视图保持最大可用区域。
- 鼠标点击、拖拽、悬停和键盘导航都必须可用。
- 轮次栏常驻左侧；动作与物品面板不得遮挡当前目标和路径预览。

### 平板端

- 横向与竖向均可适配，次要面板折叠为抽屉。
- 所有悬停信息必须有点击或长按等价入口。
- 拖拽必须提供取消区和落点预览；不合法落点回到原位并说明原因。
- 触控目标应保留足够间距，不能把桌面端小图标直接缩放过去。

### 手机端（可选支持）

- 竖向优先，地图、轮次栏和局部动作面板按当前任务分区切换。
- 面板合并不等于删除信息；折叠内容必须可在一次明确操作内恢复。
- 单手操作优先把确认、取消和常用模式切换放在可达区域。
- 复杂创作工具不要求在手机端完整等价；查看、试玩和轻量修改可以作为独立能力发布。

### 响应式不变量

1. 规则事实不能因屏幕尺寸不同而隐藏到不可访问。
2. 付费动作与附着动作继续使用两个独立菜单。
3. 颜色、图标、文字和材质语义在设备间保持一致。
4. 响应式重排只改变位置和密度，不改变动作权限、成本或结算顺序。
5. 表现系统只提交意图；任何设备都不能本地预先扣除 AP 或推进状态。

## 观战表现（D-034，归档恢复）

MVP 的观战状态复用在局只读投影，不建立第二套规则事实或信息过滤通道。

- 观战者可以自由移动镜头并切换关注对象。
- 在全信息默认规则下，可以查看所有参与者的公开状态、装备和动作结果。
- 观战 UI 复用轮次栏、状态详情和地图表现，但隐藏或禁用所有会提交对局动作的控件。
- 未来有限视野玩法包若显式存在，观战默认是解除视野范围限制的全知视角；玩法包必须另行说明例外。
- 禁用控件必须标明“观战只读”，不能仅变灰而没有原因。

## 教程与新手引导（归档恢复）

### 首次体验

1. 用短演出建立“起床”概念，但允许跳过且不影响规则装载。
2. 只高亮当前一步需要理解的可交互对象。
3. 按真实规则逐步开放移动、动作、物品、清醒值和轮次栏解释。
4. 每一步都让玩家执行真实意图并等待权威结果，不使用假的本地状态。
5. 教程结束后，所有机制仍可从上下文帮助重新查看。

### 提示契约

```text
提示标题：移动
目标：选择一个白光相邻节点
规则事实：提交移动意图，标准成本由权威动作投影给出
反馈：显示成功、不可用原因或路径变化
```

- 提示使用图标、文字和目标高亮，不只靠颜色。
- 不提前展示尚未出现的复杂系统，避免一次塞入过多概念。
- 玩家已证明掌握的提示可以降级为非阻塞提醒。
- 教程不得写死玩法数值；从当前玩法包的只读动作投影读取成本和说明。

### 上下文帮助

- 任意主要界面都提供明确帮助入口。
- 帮助内容解释“规则事实、当前状态、可做什么、为什么不可做”，不只解释按钮位置。
- 帮助链接到稳定语义 ID，而不是依赖显示文本匹配。
- 在创作界面中，帮助还应展示诊断修正建议和对应字段路径。

## 文字、语义标签与屏幕阅读（归档恢复）

### 文字大小

- 正文默认不得低于等效 12pt；像素字体仍必须保持字形可辨识。
- 提供可调文字大小，并允许主要面板随文字重排，而不是裁切或覆盖。
- 放大后仍必须能访问全部动作、诊断和确认按钮。
- 关键资源不使用极小上标作为唯一信息载体。

### 语义标签

所有可交互元素至少暴露：

- 稳定语义角色（按钮、列表项、状态、地图节点、门户、物品等）。
- 可读名称与当前状态。
- 可用/不可用及具体原因。
- 动作成本、目标和可能后果的结构化描述。
- 焦点顺序与分组关系。

图标、粒子、边缘发光和动画不能成为唯一信息源；必须有文字或语义标签等价通道。

### 屏幕阅读与 TTS

- 轮次变化、当前参与者、资源变化和结构化拒绝可按优先级播报。
- 高频视觉粒子不逐个播报，只播报其语义结果。
- 隐藏动作不得通过辅助技术提前泄露；屏幕阅读输出必须消费同一可见性过滤后的投影。
- 地图节点使用“名称、类型、可达目标数、当前选择状态”描述；详细对象列表按需展开。
- 用户可调整播报详细度，并暂停非关键播报。

### 可访问性边界

D-066 已把完整色盲调色与逐色纹理矩阵移至 Post-MVP；本节不改变该裁决。MVP 仍必须提供图标、文字、材质、语义标签、键盘操作和屏幕阅读基础支持，因为它们同时服务低心智性与输入等价。

## 创作工具的表现接入

### 驻地活动

驻地活动需要**叙事载体**（登记处、酒馆、工坊等场景），但这是独立课题，等世界观定稿后再填。现阶段只需确保端口预留：

- 驻地活动的 `ActionDescriptor` 从哪来？复用战斗内的 `uiDescriptor` 端口，但使用 `PresentationProfile.pacingPresentations = 'minimal-ui'`（少 UI 模式）
- 如何与战斗内投影共用 `UiView` 结构？驻地是 `UiView` 的一个配置实例，不是第二套实现

> **熟悉度条 / 梦境素材库 / 自建梦主界面的图形化**：这些界面的画法（线框、交互、排布）由表现系统后续专题承担，本条标为**待细化**。其规则与内容侧契约定义在 `docs/创作系统/02_熟悉度与梦境素材库.md` 与 `docs/运营系统/01_运营与局外养成.md` §十，表现侧在此只预留端口，不画线框。

### 驻地演出：纯白显形与往返传送

现实侧驻地的入梦/返回，统一用**纯白显形**做门（语义看视觉定律「纯白/奶白=梦境边界与过载」，见 §1 颜色表）。两次往返各有子流程，演出走**多帧曲线、不僵硬单帧跳变**；床是**固定实体，往返全程不消失**。完整状态机在 `docs/运营系统/03_出租屋驻地与入梦流程设计.md` §六，这里只定表现契约：

- **梦 → 实**：床必在 → 人形纯白显形（约 1 秒）→ 纯白被推向床（颜色滚动/曲线）→ 人物在床上复原色彩 → 起床演出。纯白即"从梦境另一边穿过阈值回现实"的门。
- **实 → 梦**：床从平地被翻起/浮现 → 人 + 床整体纯白 → 复原色彩 → 人物从床跳下进入梦境。纯白即"跨入梦境阈值"的门。
- **纯白 > 其他白**：显形白是高冲击过载感（如闪光弹），是短暂的、带光辉的，不做成常态底色；常态底仍是灰白。
- **可跳过**：往返演出允许跳过且不影响规则装载（沿用"首次体验/教程"的可跳过原则）。

> **睡眠姿态补充**（§4 姿态表）：`睡眠`姿态配合床匹配机使用——床=装载入口（躺下即就绪），故睡眠姿态只在床侧呈现，且只有在匹配机已就绪、床变可交互后才触发的就绪演出，不提前播放。

### 创作工具的 UI 切换

创作工具（仓库、地图编辑器、LLM 工具、工作台）**完全独立切换屏幕**，不与战斗内 UI 共享布局。但它们共用底层端口：

- **LLM 工具**：采访流程 → 生成玩法包 → 调用编译器 → 展示诊断

> **驻地的承载物命名**（承接 `docs/运营系统/03_出租屋驻地与入梦流程设计.md` 与 `创作系统/01`）：**床=装载入口**（床A蓝=主线/竞技、床B珊瑚=联机副本、床C青=进入自己建好的沙箱）；**研究台=工作台（`src/editor/bench/`）的呈现名**（编辑节点）；**电脑=地图编辑器入口**；**书架=梦境素材库**（创作资源，青）；**保险箱=收藏室**（长期高价值/纪念）。床与研究台、书架与保险箱**均职责不同、两两不可混同**（床装载、研究台编辑；书架存创作素材、保险箱存纪念收藏）。表现侧仅在 UI 切换时按此映射命名，不画线框（待细化）。

它们都消费 `UiDiagnostic`（统一诊断格式），只是布局不同。

#### 玩法包装载的拖拽顺序列表（D-073）

玩法包按**装载顺序**应用，**后装覆盖先装**（玩家添加玩法包默认在列表下方新增，即后装）。表现侧用一个**可直观拖拽、不报错**的**先后顺序列表**表达装载顺序/覆盖优先级：

- **顺序即优先级**：列表从上到下即装载先后；拖拽某包上下移动 = 改变覆盖优先级。全程**不报错**——任何拖拽结果都合法，最终状态 = 剩余包按新顺序整体重装载（剔除也如此：从列表移除该包即触发一次整体重装载，见 D-073）。
- **玩家认知**：拖拽只在列表内调序，不引入插拔过程；"拔出玩法包"不成立，玩家看到的就是顺序化之后的最终玩法层。
- 图形化只用既有语义——**青色系承载 UGC/创造来源语义**（见视觉定律 1），包项与角标沿用青色做来源与创作物标识，**不发明新色**。

#### UGC 角标与高级角标（D-072 ∕ D-076 ∕ D-077）

把"来源 + 可交互地位"用**角标**叠加在玩法包/地图项上，全部沿用既有视觉语义（角标 / 凸起 / 颜色，见视觉定律 1/2），不新增主色：

- **UGC 角标**（青色）：承载所有 UGC / 创意工坊来源与创作物（上传的玩法包、玩家自建地图等）。上传玩法包**一态为可插拔普通玩法包**时带 UGC 角标（呼应 D-079「打 UGC 侧角标」与 D-073 的插拔心智）。
- **高级角标**：标识"含地图 或 引用引擎层"的高级玩法包。带此角标的包**只能在自建房联机、单机中使用，探索匹配不可见、匹配不到**（D-076 ∕ D-077）。交互上该角标仅在**自建房 / 单机上下文**出现，探索匹配入口不展示高级包。
- 角标只作来源/地位标识，不参与数值或编译判定（判定看产物、不看来源，见 D-077；表现侧只消费已打好的标签）。

#### 上传玩法包的两态图形化（D-076 ∕ D-077 ∕ D-079）

上传玩法包在 UI 上呈现**两种形态**，走不同入口（这是最强装载，进图装载阶段装载整个包）：

- **一态 · 可插拔普通玩法包**：带 UGC 角标，进可插拔插拔列表（上文的顺序列表），可自建房、可参加探索匹配。视觉区分用 UGC 角标（青色）。
- **二态 · 带图上传包**：按地图**切成多个口子**（有多个地图就有多个口子），只能从各自入口进；**任何口子进去装载的都是整个上传包**，禁止从其他口子进入去装它（D-079）。按地图建的隔离入口在选地图界面呈现，创建出的地图**相互隔离、打 UGC 角标**，允许在图上再加玩法包。
- 玩家认知边界：玩家认知中的玩法包**不带地图**（不会把带图包拖到一张地图上），因此带图玩法包只由上传或官方而来；游戏内只支持创建地图，不支持创建"地图玩法包"（但地图 + 身上素材整体算玩法包）。

以上图形化入口（顺序列表、角标、两态口子）的具体排布属**待细化**，表现侧此处只定交互语义与视觉约定，**不画线框**（预留端口）。

### 地图编辑器的诊断呈现

地图编辑器的 21 条诊断（`MAP_*` 系列）需要特殊交互：

- **诊断列表**：左侧面板，按 `severity` 分组（error / warning / info）
- **点击诊断**：摄像机飞到出问题的元素（根据 `subject` 字段定位节点 / 连接 / 放置）
- **高亮出问题的元素**：红色边缘闪烁（error）或黄色边缘闪烁（warning）
- **显示 `correction`**：右侧悬浮提示，面向创作者的改法

**不是战斗内 UI**，所以不使用轮次栏、动作菜单。但诊断的数据结构（`MapDiagnostic`）与战斗内的 `PlaypackDiagnostic` 同构，共用验证管线。

### 地图编辑器作为人机协作桥梁（D-072 ∕ D-074）

地图编辑器不只是标注工具，而是**开发者最重要的人机协作界面**（D-072）——它把人（创作者）的视觉操作（拖框、划线、放窗口、定锚点）翻译成**逻辑层严格声明**，AI 据此读编码而非看图猜。编辑器把"拖框 / 划线 → 逻辑语义"翻译得足够紧凑（D-074：**尽量少的框/线/点覆盖全部逻辑**）。视觉操作图元尽量少，通过严密的场景测试与穷举收敛，任何新增图元必须先过"是否必要、能否被既有图元表达"的核减审查。

编辑器在本轮补强三处交互（均为逻辑层语义的可视化翻译，**不画线框、只定交互语义**）：

- **遮挡框**：一个遮挡框可**覆盖经过它的若干条样条线**；拖框划定后，储存时同时译成**视觉遮挡 / 物理遮挡**两类严格语义（D-074）。AI 能明确读到"这两者之间是视觉遮挡 / 物理遮挡"。
- **过渡窗口组件**：**挂在某条样条线的过渡点**上即在该处形成过渡场景；过渡场景是**切分**出来的（为符合玩家心智，不自我创造，D-074）。样条线见 `docs/创作系统/01_创作工具与产权.md` §九「拉线后的塑形」。
- **语义锚点框**：**高地 / 洼地**的**阶梯式缩放**区域——拖框框出高地/洼地范围并给阶梯式缩放语义，同时**保留逻辑锚点**（供 AI 读的严格坐标与语义）。

**人机分工铁律**（D-072）：碰撞、**物理遮挡 / 视野遮挡**由**人裁定**（AI 无法稳定推断玩家看到地图时的物理直觉），人用上述有限图元表达、**编码入库**；**AI 读编码而不看图**，依据编译产物做判定与补齐。视觉层只是**人性化镀层**，储存只存**逻辑层语义**；人分层编码的视觉遮挡在储存时翻译为拓扑层的严格声明。

### 前端动态图形化——活体运动与对峙

> 本子系统专注「游戏进行时活体（玩家 / NPC / AI）怎么动」的表现层，以**极简、高质量**为准绳。代表性极简设计是**全屏动画**：它直接省去大量帧动画，特殊行动用全屏演出，把复杂状态机解耦成"一段演出 + 恢复"。本子系统在正式铺开前端时会**大量引用本节内容**，因此按「完整信息、零遗漏」记录，力求所有运行期行为有据可依。

#### 双段寻路：可通行判定 + 实时挤压

活体的寻路被**两段解耦**，段位不同、动机不同，不混成一套：

| 段 | 时机 | 内容 | 粒度 |
|---|---|---|---|
| **段1 · 可通行判定** | 游戏运行时启动**预运算** | 把场景框组 + 物理遮挡 + 地形 + 静止碰撞箱，预运算为「可通行域」；判定「这个移动命令可不可通」 | 静态（障碍不动的部分） |
| **段2 · 实时挤压寻路** | 实时 | 在可通行域内，活体间实时挤压避让 / 移动；处理运行期才变化的活体相对位置 | 动态（活体-活体） |

**预运算不在编辑器**：碰撞箱、物理遮挡、场景框等必要判定，由运行期启动时预算（可通行域 / 可达性），**不做成编辑器预计算路径**。**实时碰撞箱永远不可能靠编辑器预运算**——活体会动，位置只在运行期已知。这是两条独立路径：一段预先运算判「可不可通」，一段实时算「怎么走」。

**移动命令的闸门**：段1 判「可不可通」，不可通则行动**变灰**并提示「因阻塞无法执行」；实时寻路成功才有动画。失败是**判定**（段1/段2有界判定失败），不是搜索未成浪费性能。

**路径质量**：实时寻路需相对平滑、不穿模、**不怪异**（例如永远贴着其他碰撞箱最左侧滑过去的路线是失败的）；算法的性能与质量取舍由实现阶段定（见下文 ORCA）。

#### 碰撞箱（地图注册图元，非引擎层字段）

**任何实体都有碰撞箱。碰撞箱是一个半径圆。**

- 圆心 = 贴图最下方几何中心位置。
- 半径 = 组件宽度的一半的 **80%**（待调试，可调）。
- 默认半径适用于大部分活体；在**素材属性**中可设置（设置**属于地图内设置**，本质是**注册在地图上的图元**，不是引擎层本来就有的字段）。
- 在地图编辑器中以**淡淡的圆形阴影**表示。

碰撞箱极其重要，是图形化顺畅的重要保障。它**随活体放置自动生成**，不需要手动拖一个碰撞箱图元。

**防「挤成一坨」的兜底**：收敛时若发现挤得太紧，就**增大碰撞箱**，或在恢复对峙时**认定同微型场景的碰撞箱更大一点**（同场景碰撞箱在恢复对峙时临时放大），不发明额外约束、改用碰撞箱本身调制。

#### 三动画攻击模型

执行一次近战攻击**只需 3 个动画**，各自是独立的一次性位移，没有持续纠缠。

| # | 动画 | 内容 | 决定者 |
|---|---|---|---|
| ① | **快步跳移动** | 从原位冲到目标面前 | 固定动作、路径预给定（直冲） |
| ② | **攻击 + 受击** | 近战固定动作（身子前倾 / 剑倒下前戳）；目标无招架→正常受击停顿 + 向后位移（可能撞上物理遮挡） | 动作数据 + 受击反馈 |
| ③ | **恢复对峙** | 攻击后大家按站位、以中心点为基准（防过度偏移）各走一小步，重新回到对质状态 | 以中心为锚的收敛（见下） |

**关键解耦**：让开和归位是**两个分离的机制**——攻击时中间人让开是**一次性的瞬态**（让开一条缝，**不需要重新挤回来**）；动作完成后才执行恢复对峙调整队形。两者不混成一套连续寻路。

#### 恢复对峙：通用进场收敛原语

**触发语义**：该微型场景受到**任何行为扰动**都会触发一次恢复对峙。即使玩家在这个场景完全不动、只是吃了一次面包，也会尝试一次集体恢复对峙——只是若所有条件都没变，大概率**每个人一步都不走**。新人进入本场景、离开本场景，都执行一次。

**为什么是"原语"而非"攻击尾巴"**：恢复对峙被设计成任何单位进入一个对峙群都会触发的统一动作——从其他场景走到该对峙群也执行一次就被接纳进队形。它**不需要维持视觉回合制**：你进入对峙群、众人应付你，本身合理。这让它可复用于任何"加入一个群体"的场合，与攻击完全解耦。

**算法：向心移位的迭代松弛（暂定，非最终）**

目标：给定该微型场景内所有活体的当前位 + 全体碰撞箱 → 求一个「每个人都能站、彼此不穿、收敛于中心」的目标位分配。扰动后执行，需要位移的人到位、不需要的原地不动。

1. **可站性判定**（每个单位）：判定当前位置能否站——若**原位就**「不与任何碰撞箱重叠、且在可通行域内」→ 目标位 = 原位，**一步不走**（这就是"吃面包没人动"的机械来源，是 interesting 的 no-op 出口）。
2. **向心移位**（对被扰动 / 原位不可站者）：以该微型场景中心为锚，沿「当前位置 → 中心」方向试探前行，每步检查落点是否可站（不与任何碰撞箱重叠）；**可站则前进到最近的合法可站位停**，不可站则**退到上一个合法可站位**。
3. **被卡的兜底（模糊退让）**：入位起点可能本身不可站（新玩家降落在人群里、被攻击撞向物理遮挡被夹）。此时**不是「撞上即停」**（那会停在重叠里），而是**尝试向多个方向微位移找最近的合法可站位**（很像"挤过去 / 让开"，实际只是碰撞箱正常挤压、展现成移动，不用斥力模拟）；真无解（死胡同）才判定失败回滚。

**两种"停止"的分界（关键）**：
- **可站位** = 不与任何碰撞箱**重叠**。
- **撞上停下** = 向心方向前方被别的碰撞箱**挡住**（不导致重叠）。
- 二者不是一回事，恢复对峙要的是「停在一个不再重叠且被挡住的可站位」，而不是「撞上即停的当前位置」。

**迭代松弛不是全局求解**：没有集体求解。每个单位只回答「我往中心能挪到哪、哪个可站位最近」，逐个做、撞到就停，天然收敛、天然不穿模、天然不散乱。收敛锚 = 该微型场景的**单一中心**，不设多中心、不设间距下界（防紧靠走兜底）。

**跨微型场景的碰撞箱**：可站性判定与向心试探每一步都对着**该点周边全体碰撞箱的并集**判定——不管碰撞箱来自哪个微型场景，只要在可通行域内「原地不可站 / 撞上」即为真。这就是它能"考虑其他微型场景碰撞箱"的原因：每次都对全体碰撞箱并集做判定与试探，不是为一个孤立微型场景算。

#### 朝向：单一左右朝向，纯画面因素

- **恢复对峙不改朝向**：后退 / 前进都合理，不会因为站位改变朝向。
- **事件才触发转向**：只有特定事件让人转向；且**只有左右一个朝向维度**（没有八向 / 朝向回旋动画）。
- 例子：我攻击了你，攻击完我在你左侧 → 毫无疑问你会**改向朝向我**。
- **新玩家进入微型场景** → 可能让**随机几人**转向，**绝不能全部转过去**（要"几人看向来者"而非全员整齐转头，否则人工感极强）。
- **纯画面因素，无任何朝向玩法设计**：朝向不参与任何判定（不判背后偷袭、不判视线、不判射界），只是"谁对着谁"的表现层张力。

#### ORCA：统一避让原语（传染式连锁；无纯斥力）

本项目**不使用任何纯斥力算法**——"斥力"只是需求描述用语，实现一律以 **ORCA** 为准，从根上按 ORCA 想。"泛光圈（微型场景点）绝不可重叠"是硬约束，用 ORCA 的"每帧解可行速度"守它（斥力是施力可能振荡，ORCA 更稳、保证收敛不重叠）。

**为什么直接选 ORCA 而非先斥力**：守住"不可重叠"这个硬约束，ORCA 比纯斥力更稳（斥力可能多个点互相顶、打转，ORCA 每帧求可行速度天然无冲突、无抖动）。**因此本项目拒绝纯斥力，实现层一律 ORCA。**

**传染式连锁 ORCA（统一所有场景，把"硬/软碰撞箱固定"换掉）**

不再预先给碰撞箱贴"硬碰/软碰"。**扰动即纳入 ORCA**，用"单向传染"统一处理：

```
传染式连锁 ORCA（单向传染）
  ├─ 起点：当前微型场景的全部可动碰撞箱 = 初始纳入 ORCA 的集合
  │       恢复对峙 → 此集合做对准；ORCA 寻路 → 按排斥平滑走线
  ├─ 传染：只要我的行走 / ORCA 挤碰到了某个可动碰撞箱：
  │       ├─ 纳入 ORCA，触发它一次恢复对峙
  │       └─ 其中有些活体按朝向算法改朝向（对准我）直到恢复对峙结束
  └─ 该场景恢复对峙又可能触碰到其他场景 → 继续传染，连环引发
```

- **单向传染防止调整没完没了**：只在一个方向传播（我挤它→它恢复→它可能再挤下一个），不允许"被传染者回头扰动我"形成回路——否则无限调整。每次连锁必然在有限步内收敛。
- 传染同时作用在**实体层**（活体避让、恢复对峙、朝向）与**微场景点层**（泛光圈同样遵循传染，不能只活体避让而圈不跟着）。
- 方向（2026-08-14 定案）：传染可反向扰动发起者亦接受——"下次再解决"，因为回合制能接受"戛然而止"，接受不了的是"我离这么近却打不到"。

**碰撞箱分类（决定纳入 ORCA / 是否被扰动）**

| 分类 | 参与 ORCA / 被扰动? | 朝向逻辑? | 说明 |
|---|---|---|---|
| **可动活体** | ✅ 参与 / ✅ 受扰动 | ✅ 有 | 有朝向逻辑与算法 |
| **可动实体** | ✅ 参与 / ✅ 受扰动 | ❌ 无 | 例：**有人驾驶的车** |
| **不可动活体** | 不参与 / 不被扰动 | 一般无 | 不被连锁扰动触发恢复对峙；不意味不可推动 / 不可被 AP 行动 |
| **不可动实体** | 不参与 / 不被扰动 | — | 例：**无人驾驶的车**；仅作硬边界 |

- **"不可动"≠"物理静止"**：只表示该类碰撞箱**不因连锁扰动而触发恢复对峙**，不代表它不能被推动或不能被 AP 行动。

**车辆可动性的动态判定**：**有人驾驶的车 = 可动实体；无人驾驶的车 = 不可动实体**。故车辆的可动性随驾驶状态动态变化（有人开=参与 ORCA、无人开=不参与）。这同时是"不可动实体归属静默归位"（见回合制并发一节）的直接驱动——一辆无人车停着，其可动微场景点若飘走，车会被归位到最近同天然场景点。

**泛光圈（微场景点）与实体数成比例**：泛光圈半径随该微场景点的**实体数量**变化（实体多→圈大）。圈变大若与邻圈重叠 → 触发扰动 → 传染式 ORCA 相互排斥；恢复对峙的传染会在微场景点层或实体层把重叠消掉。故"泛光圈不可重叠"在圈动态变化时也由同一套传染机制守住，零新增逻辑。（"泛光圈 = 可落脚/可交互目的地"的呈现语义见地图编辑器一节。）

**ORCA 寻路的失败机制（反哺玩法，动态平衡）——保留、支持**

同场景 ORCA 寻路是即时演算，可能不失败、或无法预先判定失败；**但"寻路失败"这一机制是正确的，保留**：

- 它是**独立于玩法层、反哺玩法**的行为，不退回玩法规则。
- 守护动态图形化使命：**过于堵塞的场景无法无限进入**——大大降低"场景因人群拥挤而拥挤、从而削弱微型场景强调"概念的活跃性。
- 且是**动态平衡**的（拥挤→寻路失败→不再进入→不更挤），是"妙手偶得"。
- 失败通道：堵塞即失败、不进更多、动态平衡。

**结论**：ORCA 解决核心避让（传染 + 单向连锁 + 不穿模 + 对称让路 + 高效），「向心收敛回对峙 / 原子可站判定 / 泛光圈动态」由外层状态机或传染机制包。ORCA 覆盖的部分引用工业实现，不自己写避让微分方程；真正新且自有价值的核心资产是"三动画 + 回合制 + 朝向 + 恢复对峙 + 传染式连锁"这套**表现编排**，在正式铺开前端时实现，不归属本次引擎层立项。

> **实现约束**：恢复对峙、双段寻路、碰撞箱的一切最终表现都只是"规则结果（静止站位 / 位移结果）的视觉重演"，不改变规则结算、不提交 AP / 状态；动画与规则结算的解耦沿用本文「动画与规则结算的解耦」一节的铁律（`after:*` 事件投递时规则已完成）。

#### 回合制与动态图形化的并发权责

表现层（动态图形化）与玩法层（规则结算）之间，存在**三个不同的权责层**，它们各自决定"要不要等动画"：

| 层级 | 行为 | 是否需要等动态图形化动画结束 |
|---|---|---|
| **行动结算（玩法层）** | 一个行动在数值 / 逻辑上结算完成，下方的选项已生成、可交互组件已在地图上高亮 | **不等**。玩家可选下一个行动，动态图形化（如恢复对峙的实体）可能尚未完全停住 |
| **行动演出（表现层）** | 恢复对峙、移动、避让等动画仍在播放 | 不阻塞下一步选择——动画可滞后于结算 |
| **轮权交接（交权）** | 要**结束这个行动轮**、交给下一个玩家 / NPC | **必须等**。即便点了跳过，仍要等所有动画结算完，表现层才放行给下一个活动方 |

**核心权衡（节奏连贯 vs 逻辑正确）**：

- **结算与演出解耦**，允许"动画还没停"就进入下一个行动：动作结算完，选项 / 高亮立刻可用；不必等恢复对峙的实体完全停止。表现层不会出**逻辑问题**（规则已结算完），只可能出**常识问题**（画面接得不太自然），而常识问题在这种取舍下可接受。
- **轮权交接是硬同步点**：只有"交权给下一个玩家 / NPC"这一刻必须等所有动画结束。这给了"戛然而止也能接受（回合制）"与"我离这么近却打不到不能忍"之间一个精确边界——动画未停但可交互 → 节奏连贯（接受）；交权必须等演出停 → 逻辑正确（安全）。
- **单人模式无此限制**：没有"同步给下一个玩家/NPC"的需求，可直接推进，无需等动画。

#### 不可动实体归属的静默归位（行动轮结束契机）

**问题**：不可动实体（如无人驾驶的车）客观上存在，但"可动的 ORCA 寻路不欢迎它"。它理论上属于"它停着所在的那个微型场景"，但若该微型场景点是"可动"、随 ORCA 飘走，过一会儿这辆车就离它的点很远——然而逻辑层仍可在"同一微型场景"一回合上车，造成**视觉（车离点远）与逻辑（同一微型场景可上车）的断裂**。

**解耦约束**：这个归位**不做成表现层逻辑**，而是：

| 层 | 角色 |
|---|---|
| **玩法规格 / 数据层** | 归属改写逻辑：把一个归属已脱节的不可动实体，改归到"距离它最近的另一个同天然场景微型场景点" |
| **表现层** | 只作**搭桥信号源**：识别"该不可动实体的点已飘得足够远"，把它作为一个"可归位"的信号递上去；**表现层自身不做任何逻辑改动** |

**归位契机：单个行动轮结束**（约定取舍）：

> 该契机是**单玩家行动轮结束**那一刻。因为回合制下**单玩家行动轮结束时世界一定静止**——结束时做一次**所在天然场景的扫描**，把归属脱节的不可动实体归位到最近同天然场景微场景点。**NPC 也遵循该逻辑**：每次一个 NPC 行动完，也暗中结算一次归位。

**它是"合理的粗略"**：技术上承认存在"同一个行动轮内多次行动、中途世界未必完全静止"的破绽，但仍选这个契机，因为"行动轮结束的静止快照"在技术上更安全（此刻世界静止，归位不打断进行中的动画、不产生逻辑矛盾）。

**这一改动动的是数据层（归属），表现层不动**；它属于"不可动实体归属"的一个有限桥点，不是常态表现逻辑。


### 对局动态图形化的标准模型

一套标准的对局动态图形化，本质是**「机制动作 → 一段可解耦的动画演出」的映射**。以"我在机制层花 1 AP 攻击一个与我同微型场景的人"为例，这个标准动作在画面上一段段展开：

```text
我（机制层花费 1 AP 攻击同微型场景目标）
  ├─ 先朝向对象
  ├─ 以「跳跃动画」移动到对象面前
  │     动画幅度比原版走路来得大
  │     （迟缓 / 重物的行动跳跃曲线也各是单独一条）
  │     ↑ 它们不用任何帧，只是动画曲线
  ├─ 身体前倾
  ├─ 手上的近战武器倒下
  ├─ 向前戳一个距离
  ├─ 对方受击（帧动画）同时往后退
  └─ 在我向前移动的过程中，经过的玩家可能被我挤开
```

**关键点**：

- **每个动作都属于动态图形化范畴**——朝向、跳跃移动、前倾、武器倒下前戳、受击后退、挤压让开，全部是「机制结算结果的外观重演」。
- **动画曲线替代帧动画**：跳跃的幅度（比走路大）、迟缓/重物的行动跳跃曲线——这些用**动画曲线**表达，不消耗帧动画资源。帧动画只保留在「确需角色身体/姿态细节的地方」（如受击帧）。
- **与规则解耦**：整段演出在 `after:attack$` 结算完成之后播放，只重演"攻击命中 + 双方位移 + 沿途挤压"的结果，不反馈改规则、不重算 AP。

> **推广**：机制越多，图形化越多——每个机制动作都对应这样一段「朝向 → 移动 → 姿态 → 效果 → 后退 → 周边挤压」的可编排演出。图形化就是把**机制结算后的每个后果**翻译成一段**符合常识、极简、无帧僵硬**的动画序列。这条标准模型是可复用的模板：新机制接入时，按此模型把"机制后果"拆成可演出的子动作，套进既有的舞蹈编排（declarative timeline / 命令式控制 + ORCA 避让 + 恢复对峙归位）。

## 动画编排的声明式时间轴

### 全屏仪式动画的契约

四项全屏仪式动画（翻窗、跳窗、令其长眠、招架触发）使用**声明式时间轴**：

```typescript
interface CeremonialTimeline {
  /** 动画轨道标识（ceremonial 轨道独占全屏） */
  readonly track: 'ceremonial' | 'overlay';
  
  /** 总时长（毫秒） */
  readonly duration: number;
  
  /** 关键帧列表 */
  readonly frames: readonly CeremonialFrame[];
  
  /** 阻塞行为（complete = 播放完才继续，skipKeyPressed = 可跳过） */
  readonly blockingUntil: 'complete' | 'skipKeyPressed';
}

interface CeremonialFrame {
  /** 触发时间（相对动画开始，毫秒） */
  readonly at: number;
  
  /** 视觉效果标识（对应 src/ui/presentation/effects/ 的预设效果） */
  readonly effect: string;
  
  /** 效果目标（actor / target / both） */
  readonly target?: 'actor' | 'target' | 'both';
  
  /** 效果参数（传给视觉效果的配置） */
  readonly params?: Readonly<Record<string, unknown>>;
}
```

**示例：令其长眠**

```typescript
const ETERNAL_SLEEP_TIMELINE: CeremonialTimeline = {
  track: 'ceremonial',
  duration: 500,
  frames: [
    { at: 0, effect: 'target_collapse', target: 'target' },
    { at: 200, effect: 'blue_glow', target: 'both' },
    { at: 400, effect: 'stamina_refill', target: 'actor', params: { amount: 5 } },
  ],
  blockingUntil: 'skipKeyPressed',
};
```

### 普通动画的命令式控制

普通动画（移动、受伤、拾取）由前端逻辑层直接控制，不走时间轴：

```typescript
// 前端代码（src/ui/presentation/choreography/）
function playMoveAnimation(from: Vec2, to: Vec2, duration: number): Promise<void> {
  // 直接操作 DOM / Canvas / WebGL
  return animate(sprite, from, to, duration);
}
```

### 动画与规则结算的解耦

**关键原则**：`after:entity.destroy` 事件投递时，规则已经完成。动画只是规则结果的视觉重演。

| 时间点 | 规则层 | 表现层 |
|--------|--------|--------|
| T0 | 玩家提交"令其长眠"意图 | UI 显示"执行中..." |
| T1 | 规则结算：目标销毁、清醒恢复到 5 | 开始播放全屏动画 |
| T2 | 事件投递：`after:entity.destroy` | 动画播放第 200ms 关键帧 |
| T3 | 无（规则已完成） | 动画播放完成或被跳过 |

**播放失败的降级**：

- 资源缺失（找不到动画素材）→ 静默跳过，直接显示规则结果
- GPU 故障 → 同上
- 用户强制跳过（按 ESC）→ 跳到动画结束帧，立刻显示规则结果

### 招架静默失败的演出

招架被远程攻击触发时**静默失败**（D-032）：

- `parry_triggered` 事件的 `safePayload` 白名单包含 `{ triggerType: 'melee' | 'ranged' }`
- UI 收到 `triggerType: 'ranged'` 时：
  - 不播放任何动画
  - 不产生任何视觉反馈
  - 不显示"失败"提示
  - **当从未开始过**

## 玩家可见数值的归属分类

### 归属分类的闭合枚举

`makeGameplayValue(raw, ownership)` 要求传入归属分类。合法的归属从 `src/l2/model/constitution.ts` 读取：

```typescript
export const GAMEPLAY_VALUE_OWNERSHIPS = [
  'damage',           // 伤害
  'cost',             // 成本（AP / SP）
  'health',           // 血量
  'stamina',          // 清醒值（玩法机制字段名保留 stamina / SP）
  'capacity',         // 容量（背包、弹匣）
  'connection_limit', // 连接数上限（地图拓扑）
  'distance',         // 距离（场景拓扑连接数）
  'dc_threshold',     // 检定阈值
] as const;

export type GameplayValueOwnership = typeof GAMEPLAY_VALUE_OWNERSHIPS[number];
```

### 类型层不区分归属

`GameplayValue` 在类型层只保证 1-5 范围，归属分类是**运行时标签**，用于诊断和审计，不用于防止"把伤害当成本"这种编译期错误：

```typescript
interface GameplayValue {
  readonly raw: number;           // 1-5 范围
  readonly ownership: GameplayValueOwnership;
}
```

**为什么不用 brand 类型区分**：

- `DamageValue` 和 `CostValue` 在数值上确实可以相等（都是 3）
- 类型系统变得非常细碎
- 运行时标签已经足够（审计器会检查"伤害字段是否标记为 damage"）

### 内部度量的 unit 字段

`InternalMetric<T>{ value, unit }` 的 `unit` 是**自由字符串**，纯文档用途：

```typescript
interface InternalMetric<T> {
  readonly value: T;
  readonly unit: string; // 'milliseconds' / 'pixels' / 'bytes' / ...
}
```

**不参与任何逻辑判断**：

```typescript
const numRuns: InternalMetric<number> = { value: 100, unit: 'runs' };
const timeout: InternalMetric<number> = { value: 5000, unit: 'milliseconds' };
```

`unit` 的作用是让代码自解释，阅读时不需要猜"这个 100 是什么单位"。
