## 二、迭代闭环实证（层 2 核心交付）

### 关键发现：稀缺系数（scarcity）是能真正改变相对排序的调参杠杆

我实测（`test/play/loading-runtime/iteration-injection.test.ts`）确认：

- **unit 杠杆无效**：把 `e:enemy.vitality` 的 unit 从 5 调到 1（允许下限）或 10（上限），遍历 16 个世界 × 10 个 correlationId，**没有任何一组改变真实选中动作**。因为所有候选共享 rootSlice，unit 等量移动全部候选终端分数，相对排序不变。
- **scarcity 杠杆有效**：把 `e:enemy.vitality` 的 scarcity 从 0.5 调到 0（`ParameterTuner` 允许，`tuner.ts:277-279` 范围 [0,5]），在 5,2 世界（自身满血、敌人残血 2）下，真实选中动作从 `a:attack` 变成 `a:heal`/`a:move`（实测 g5/g7 变 heal）。因为 scarcity 是「越残血越值钱」的倍率加成，调到 0 后 attack 的估值被压低，相对排序改变。

### 红断言 → 真实 ParameterTuner 调 JSON → 生产 AI 行为变化 → 断言变绿

`test/play/loading-runtime/iteration-injection.test.ts` 的「迭代闭环：真实红断言经 runTuningCycle 真调绿」用例：

1. **红断言**：5,2 世界（hero5 enemy2），期望 `a:heal`（保命优先），默认费目下真实决策选 `a:attack`（补刀）→ 红。
2. **真实调参**：`new ParameterTuner({ config: defaultDesignCurrencyConfig() })` 调 `e:enemy.vitality.scarcity.coefficient` 从 0.5 → 0（`direction:'decrease', magnitude:0.5`），产出 `ParameterTuningRecord`。
3. **生产 AI 行为变化**：注入调后 config 到 `makeRuntimeFor`（与 `createPlayAiRuntime` 同构的生产组合根），真实 `facade.act` 的选中动作从 `a:attack` 变成 `a:heal`。
4. **断言变绿**：遍历 8 个 correlationId，存在「默认红 + 调后绿」的 corr，断言 `found === true`。

### 生产组合根注入（层 2 的接线层）

- **改了什么**：`src/play/loading-runtime/types.ts` 给 `LoadedMatchOptions` 加 `designCurrencyConfig?: DesignCurrencyConfig`；`src/play/loading-runtime/index.ts:201` 透传给 `createPlayAiRuntime`。
- **做了哪一层**：**生产组合根**（非新测试组合根）。理由：这是达成「生产真吃调参」的正道，改动极小（2 处），且 `createPlayAiRuntime` 本就支持注入。已在 `iteration-injection.test.ts` 验证「磁盘读出的调参 JSON 可注入 createLoadedMatch 且装载成功」。
- **诚实边界**：`createLoadedMatch` 的 AI runtime 用独立 holder/registry（`index.ts:174-180` 注释），注入的 config 只影响 AI 决策估值，不改任何玩法规则。

### golden 全绿

- 相关范围 `npx vitest run src/core/kernel/ai test/ai-tuning src/play/loading-runtime` → **34 files / 218 tests 全绿**（含新增 `iteration-injection.test.ts` 5 用例）。
- 既有 `iteration-e2e.test.ts`（Task 3 的 cycle-detected 诚实收束）保持绿——证明我没有绕过防转圈边界，而是用 scarcity 杠杆在边界内达成闭环。
