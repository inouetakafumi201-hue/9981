## 0. 开局约束与不可违背裁决

本规划的每一步都必须守住以下裁决。任何一条被违反即为**规划错误**，执行会话不得自行放宽：

- **D-073：不引入 namespace / 归属判定线**。玩法包无名，状态固定即新版本，不做来源归属维度。
- **D-073：顺序即优先级，后装覆盖先装**；同 key 覆盖/新增（后注册覆盖先注册），跨作用域冲突一律**拒绝**而非靠确认放行。
- **D-073：剔除 = 从列表移除 + 一次整体重装载**；剔除其他地图遵循**不重载原则（不报错，跳过）**；剩 ID 即退役（退 ID ≠ 删引用，只让引用失效而非崩溃）。
- **D-077 拧阀点（已闭合）**：「地图位按 ID 区分、同 key 才判重」作为既定前提执行，无需另行裁决。地图不可替换 ≠ 官方图与上传图冲突——两者各有唯一 ID，装进各自 map 位，不会同名撞位。
- **D-076：LLM 玩法包不能携带地图、不能独立生效**；带图包只可能来自上传或官方。
- **D-077：高级判定看产物不看来源/声明**，只做可达性静态扫描，不做额外判定。
- **D-079：上传包两态 + 口子内整包装载 + 禁止跨口子装载 + 地图隔离角标**。

**未决项登记（不自行裁决，D-060）**：
- U-INC-1：D-073「静态编译已把 def 归一化为最终版本替换源码」与「玩家插拔 + 回滚」两条语义在**同一装载引擎**内的并存细则——「开发者以装载状态为最终版本替换源码」是否要求装载引擎暴露"全量重装载为最终快照"的入口，还是仅由上层拉取快照即可，本规划未决，待仲裁。
- U-INC-2：D-073「剔除其他地图遵循不重载原则」与 D-079「带图包建多个口子」的交互——从口子内剔除其中一张地图是否触发**其余口子**的整包重装，还是仅该地图所在口子重装，本规划未决，待仲裁。

## 主梁一：装载语义改造（D-073 / D-077 主梁1）

### 目标

把现有「声明型冲突解决」装载模型改成「**单调重定义**」模型：同 key 覆盖/新增（后注册覆盖先注册）、跨作用域冲突一律拒绝、剔除 = 整体重装载、剩 ID 即退役、ID 随机符号尾数同 key 才判重。

### 依赖现状

- **L1 `src/core/kernel/schedule/playpack.ts`（`PlaypackLoader`）**：当前 5 步装载算法。`load()` 中 `findConflicts` 遇到已存在的 def id：若 incoming 的 `overrides` 表里没有该 id，即报 `E_LOAD_CONFLICT`——这正是「修改须显式声明」模型的冲突源头。另有 `overrides` 重写（`applyOverrides`）把 def id 按表 remap。
- **L2 `src/l2/registry/definition-registry.ts`（`activate`）** + `src/l2/ugc/ports/package-mapping.ts`：候选包在**工作副本**应用 add/override/remove，`overrideIntent` 未声明目标时报 `REF_OVERRIDE_NOT_DECLARED`（`src/l2/model/diagnostic-codes.ts:91`），`removals` 走显式 remove 声明。全程「修改须显式声明」。

### 算法 / 数据形状建议

1. **单调重定义核心**：同 key def 视为「重新定义」，直接覆盖工作副本中的旧值（后注册覆盖先注册），**不报错**、不需要 `override`/`remap` 声明。新增 def 直接进注册表。装载顺序由列表顺序决定（D-073「顺序即优先级」）。
2. **跨作用域冲突一律拒绝**：凡一个 def key 同时在多个包之间有不同的 `depends`/作用域归属、或与顶层历史 key 撞位且无法判为"后装覆盖"的情形，一律拒绝而非放行。具体判定以"后装覆盖先装"为唯一放行理由，其余冲突硬性拒绝。（细化边界见 U-INC-1。）
3. **剔除 = 整体重装载**：`PlaypackLoader.restoreLoaded` 已有"恢复装载历史 + 注册表 fork/replaceFrom 同步恢复"的骨架，可作为整体重装载的基础——移除包后按剩余包新顺序全量重载为新版本。
4. **剩 ID 即退役**：对一个 def 用 `replace` 出新版、下方引用留空，则只剩其 ID。退役 ID **不可再被引用**（引用校验拒绝），但不伤及仍引用它的老数据——只是引用失效而非崩溃。对应地，`definition-registry.ts` 的 `removals` 显式 remove 通道降级为「剩 ID 退役」的可选表达，不再要求显式 DELETE。
5. **ID 随机符号尾数同 key 才判重**：def id 含**随机符号尾数**（D-075），判重只看 key 部分——符号尾数相同才视为同 def 覆盖；尾数不同视为不同 ID、互不覆盖、各占各位（尤其见主梁二地图位的拧阀点）。

### 需改的代码位置

| 位置 | 现状态 | 增量改法 | 风险 |
|------|--------|---------|------|
| `src/core/kernel/schedule/playpack.ts` `findConflicts` | 同 key 无 override 声明即报 `E_LOAD_CONFLICT` | 去掉「须显式 override 声明」前提，改为同 key 即单调覆盖 | 中——需保证覆盖后引用重验证不静默失效 |
| 同 `load()` `applyOverrides` | 声明型 remap | 退化为「后装覆盖先装」的直接替换，overrides 表不再承载命名语义 | 中——与既有调用方兼容面需核对 |
| `src/l2/registry/definition-registry.ts` `activate` | add/override/remove 三通道 | 增加"同 key 覆盖"作为一等语义，remove 降格为除 ID；跨作用域冲突拒绝 | 高——是原子激活的语义核心 |
| `src/l2/ugc/ports/package-mapping.ts` | `REF_OVERRIDE_NOT_DECLARED` 拒绝 | 改为单调重定义下不再需要 override 声明即告通过；报错代码降级或移除 | 高——端口契约变更需 QA 锚点同步 |
| `src/l2/model/diagnostic-codes.ts` | `REF_OVERRIDE_NOT_DECLARED` / `REF_REMOVAL_TARGET_MISSING` | 语义重定义或退役 | 中——错误码被端口/文档引用需全量跟进 |

### 可测试的验收点

- 同 key 后装覆盖先装：注册同一 def key 两次，最终值是最后一次，**无 error**。
- 新增 def 直接生效，无需 override 声明。
- 剔除某包后整体重装载，其余包按新顺序重载为新版本。
- 剩 ID 的 def 不可再被引用（引用校验报错），但老引用者的数据不崩溃。
- 随机符号尾数不同 → 不同 ID → 不判重、不覆盖。

## 主梁二：地图锚点扩展（D-072 / D-074）

### 目标

`MapNode` / `MapEdge` 增「视觉遮挡 / 物理遮挡 / 过渡窗口 / 语义锚点」字段，配合相应 `MAP_*` 校验码；`directionality` 枚举扩 `one-way-down/up`；`compile` 不再把方向压成布尔 `directed`。

### 依赖现状（对照 `src/play/map/types.ts` 逐字段）

- `MapNode`：`id / def / scale / at(Vec2) / floor / parent? / name?`。
- `MapEdge`：`id / def / a / b / directionality(bidirectional|unidirectional) / path(Vec2[])`。
- `compile.ts` `linkSpecOf` 把 `directionality === 'unidirectional'` 压成布尔 `directed`。
- `validate.ts` 结构校验集中节点/连接/放置/连接数上限/曲线，无遮挡/锚点判据。

### 增量字段（types.ts）

| 对象 | 新增字段 | 类型 / 取值 | 语义（D-072 / D-074） |
|------|---------|------------|------------------------|
| `MapEdge` | `visualOcclusion` | `boolean`（或 `enum`） | 人分层编码的**视觉遮挡**严格声明 |
| `MapEdge` | `physicalOcclusion` | `boolean`（或 `enum`） | **物理遮挡**——通行阻断语义 |
| `MapEdge` | `transitionWindow?` | `string` / 引用 | 挂在边过渡点上的过渡窗口组件 id，形成过渡场景（D-074，挂样条过渡点） |
| `MapNode` | `semanticAnchor?` | `'highground' \| 'lowground'` | 语义锚点（D-072 / D-075） |
| `Directionality` | 扩枚举 | `add 'one-way-down' \| 'one-way-up'` | 单向且带高程方向 |
| `MapEdge` | `directionality` 保留 | 扩后的联合 | 不再只是二值 |

### 校验码（validate.ts）

| 新增校验码 | 触发条件 | 严重度 |
|-----------|---------|--------|
| `MAP_ANCHOR_CONFLICT` | 同一节点既 highground 又 lowground，或锚点与遮挡声明冲突 | error |
| `MAP_OCCLUSION_ALSO_BLOCKED` | `physicalOcclusion=true` 但该边仍被编译进可通行拓扑 | error |
| `MAP_TRANSITION_WINDOW_ORPHAN` | `transitionWindow` 引用的窗口组件在放置集/素材中不存在 | error |
| `MAP_ANCHOR_UNRESOLVED` | 节点声明了锚点但未与遮挡/过渡形成闭合语义 | warning |

（以上为建议集，实际以 D-074「有限图元 + 严测穷举」的核减审查为准——任何图元的增减必须先过「能否被既有图元表达」审查。）

### compile 增量

`compile.ts` 的 `linkSpecOf` 必须**停止把方向压成布尔 `directed`**：保留 `directionality` 枚举（含 new one-way-down/up），以便高程/单向语义在编译产物端仍可读。`MapEdge` 的遮挡/锚点字段是否进 `PrefabDef`，取决于 `PrefabDef` 是否具备相应通道——若没有，则编译期丢弃（遵循"删掉几何，一局游戏照样跑"判据），遮挡/锚点由渲染层单独读 `MapData`。此判断需执行会话对 `src/core/kernel/topology/prefab.ts` 核对后定；本规划不越权决定。

### 验收点

- 新字段能进结构校验并被识别。
- 遮挡/锚点冲突能一次性报出全部问题（复用现有诊断列表形态）。
- `compileMap` 对含锚点/双向+单向边的地图可确定性重放、不报假错。
- `adjacencyOf` 对 new `one-way-down/up` 与既有双向/单向一致处理。

## 主梁三：高级判定 + 警告器（D-077 主梁2）

### 目标

编译器对玩法包产物做可达性静态扫描 → 判定「高级」标签；附带警告器提示「此玩法包涉及引擎层改动，将被定义为高级玩法包，无法进行探索联机」。高级包 = 自建房联机 / 单机。

### 依赖现状 / 判定依据

- 判定**看产物不看来源/声明**（D-077 铁律）：凡产物含**引擎层引用** 或含**地图定义** → 打「高级」标签。
- 不可违背 D-076：LLM 包不能携带地图 → LLM 包在编译期即被阻止携带地图，故 LLM 包不可能自判高级（除非引用引擎层，而引擎层 LLM 不可改，见 D-078）——但判定层不关心来源，只对产物扫描。

### 算法建议

对已解析、已通过装载校验的玩法包定义集合做**可达性图扫**：
1. 从包的根 def 出发，沿引用图（`src/l2/registry` 的 `inbound`/节点图已存在）遍历。
2. 若可达集合中出现**引擎层 def id**（引擎层引用）或 **map 位定义** → 打 `advanced` 标签。
3. 附带一条 warning 诊断（警告器），形如 `ADVANCED_PACKAGE_ENGINE_TOUCH`。

### 数据形状建议

- `PlaypackDef`（或包元数据）增 `readonly advanced?: boolean`（或判定派生字段）。
- 高级标记参与匹配隔离：探索匹配默认排除高级包，自建房/单机放行。

### 验收点

- 含引擎层引用的包 → 判定 advanced = true，且仅影响标签/匹配不阻止装载。
- 含地图定义的包 → advanced = true。
- 纯数值改动的包 → advanced = false。
- 判定不依赖来源字段（同一产物换来源标签，结果不变）。
- LLM 生成的包无法通过编译携带地图（编译期拦截，呼应 D-076）。

## 主梁四：上传两态 + 口子 + 审核（D-077 主梁3/4 + D-079）

### 目标

上传玩法包分流两态：一态变**可插拔普通玩法包**（带 UGC 角标）；二态按地图**切成多个口子**，口内装整包、禁跨口装载、地图隔离角标。上传异步入池、更新重审。

### 两态分流

| 状态 | 形态 | 入口 | 局限 |
|------|------|------|------|
| 态一 | 可插拔普通玩法包（带 UGC 角标） | 常规装载/作为玩法包 | 无地图、可插拔 |
| 态二 | 按地图切成多个口子 | 各自入口进入 | 进图装载整个包；仅入口地图；禁止跨口装载；地图隔离 + UGC 角标 |

### 口子建模（D-079）

- **按地图单位建口子**：带图上传包有几个地图就建几个口子，不是分包。
- **口子内整包装载**：从任一入口进入，装载的都是整个上传包。
- **禁止跨口子装载**：不允许从其他口子（如官方地图）进入去装这个上传包。
- **地图隔离**：创建出的地图相互隔离，打 UGC 侧角标，可在选地图界面选择。
- **允许在该地图上再往上加玩法包**（普通包可叠加）。
- **剔除其他地图**遵循不重载原则（不报错、跳过）。（口子间剔除联动见 U-INC-2。）

### 上传审核（D-077 主梁4）

- 上传玩法包若要联机（含自建房）→ 必须先**异步提交审核**，过了打标记才能进池子。
- **更新要重审**。

### 需改的位置（建议落点）

| 落点 | 内容 |
|------|------|
| `src/l2/ugc/ports` / 分享审核分发 | 异步审核状态机、入池标记、重审触发 |
| 地图装载层（`src/play/map`）+ `src/core/kernel/schedule/playpack.ts` | 口子建图、整包装载、跨口拒绝 |
| 地图隔离角标 | 元数据标记（呼应 D-077「带 UGC 角标」「地图隔离 + UGC 角标」） |

### 验收点

- 态一包可插拔、可自建房、可探索匹配（无图）。
- 态二带图上传包：从官方地图入口进入失败（禁止跨口）；从本图口子进入装载整个包。
- 若上传包未过审/更新未重审 → 不可进池、不可联机（含自建房）。
- 玩家认知边界（D-079）：游戏内只支持创建地图，不支持创建"地图玩法包"；地图+身上素材整体算玩法包。

## 主梁五：LLM 约束（D-076 / D-078）

### 目标

- LLM 生成的普通玩法文件内容集合不能独立替换地图原数据；带地图的玩法包只来自具备相应权限的上传或官方内容入口（D-076）。
- LLM 工具**双通道**：从 0 生成玩法文件或带地图玩法包候选（统一清单/编译/装载） vs 辅助修改素材（单 JSON 替换，快路径）（D-078）。

### 通道细分

| 通道 | 入口 | 产出 | 交互 |
|------|------|------|------|
| 从 0 生成玩法内容集合（默认流程） | 玩法文件或带地图玩法包创作入口 | 可插拔内容集合（通常以 zip 传输，但不以 zip 判定语义） | 完整迭代 + 反复采访/询问（D-078 6.1 完整闭环） |
| 辅助修改素材（快路径分支） | 素材库中选中某素材 → 问答框 | 改后的**单个 JSON 素材**，不建玩法包 | 单查询 → 直接行动 → 单素材替换；边界已明确则**不询问直接开始**（D-078） |

### 编译期拦截

- LLM 生成的普通玩法文件内容集合在**编译期不得替换或独立激活地图原数据**（D-076 root-cause：不是靠玩家认知，而是靠结构约束）。具备地图的玩法包候选必须走带地图内容的权限、清单和隔离入口；即使输入中包含地图 JSON，也必须经过对应 MapBundle 入口和安全校验。
- LLM 根本不识别引擎层（D-078：引擎层 LLM 不知道存在、也改不了）。

### 验收点

- LLM 包不可能过编译携带地图。
- LLM 包单独装载不生效（须挂到地图下才生效）。
- 辅助修改素材通道：产出单 JSON、不改装包、不触发打包装载流程；"不询问直接开始"分支正确触发。

## 执行顺序建议（一句话）

按「**主梁二地图锚点 → 主梁一装载单调化 → 主梁三高级判定 → 主梁四上传两态/口子/审核 → 主梁五 LLM 约束**」推进：先扩地图数据让新语义可表达、再改装载语义让覆盖/退役/判重成立、随后挂高级静态判定、再铺上传两态与审核、最后收紧 LLM 双通道。
