# 技术栈与开发流程设计

> 目标：让 Agent（AI协作者）明确知道"我们要做出什么效果"和"迭代循环怎么跑"，不需要摸石头过河。
> **归属**：工程治理，不参与三层规则运行依赖链。
> 本文档是对 `docs/表现系统/01_图形化与UI.md` 的技术落地说明，两者配合阅读。

## 一、技术栈总览

| 层级 | 选型 | 不选 | 理由 |
|---|---|---|---|
| 语言 | TypeScript（strict） | JS | 强类型是 AI 协作的"编译期守门员"，Spec 里的数值约束能被类型系统兜底 |
| UI 框架 | React 18（函数组件 + hooks） | Vue | JSX 是纯 TS 表达式，逻辑/模板/样式不分文件，AI 重构时上下文不碎片化 |
| 样式 | Tailwind CSS + design-tokens + tailwindcss-animate | 原生 CSS3 / CSS Modules | 原子类内联在标签上，AI 改样式不需要跨文件对齐；但审美方向必须靠 tokens 锁死（见第四章） |
| 动效引擎 | **Framer Motion（唯一）** + **@tsparticles（粒子，JSON 配置）** | 手写 CSS keyframes / 骨骼动画 / GSAP（后置） | 声明式 spring 动效，AI 写起来和写 Tailwind 类名一样自然，天然契合"去素材化"路线；粒子参数即 JSON，与声明式数据哲学同构 |
| UI 原语 | **Radix UI**（无样式，行为/ARIA 正确） | 自研弹窗/菜单行为 | 视觉全由 Tailwind + tokens 覆盖，Radix 只管可访问行为 |
| 图标 | **lucide-react**（纯 SVG） | 手绘 SVG path | 图标名直白，AI 猜名几乎不错；零素材图标来源 |
| 状态管理 | **Zustand** | Redux / Jotai | 少样板、无 Provider，AI 写起来最接近普通函数 |
| 路由 | **React Router** | 自研 | 表现层对局外页面跳转标准选型 |
| 音频 | **Howler.js** | 裸 `<audio>` | 游戏音频标准：BGM 交叉淡入/音效分层/音量控制 |
| 主画面渲染 | **SVG + React 声明式绑定** | PixiJS / WebGL | 见下方专项说明 |
| 核心逻辑 | 纯 TypeScript 状态机（`src/core`） | 引擎脚本 / ECS 框架依赖 | 前后端同构，核心逻辑层零前端依赖（可在 Node.js 无头运行），Vitest 100% 覆盖 |
| 网络 | Colyseus（评估中）或手写 WebSocket | 自研同步协议 | Colyseus 的 schema 状态同步天然契合"状态机广播"架构，能省掉房间管理和 diff 广播的重复劳动 |
| 测试 | Vitest + Testing Library + jsdom | Jest | 与 Vite 生态同源，配置零摩擦；组件行为测试与核心逻辑测试同一条流水线 |
| 打包/桌面端 | Vite（Web）+ Electron（需离线客户端） | Tauri | Electron 内置固定版本 Chromium，"Chrome 调成什么样，打包出来就是什么样"这个承诺只对 Electron 成立；Tauri 用系统 WebView，渲染会有差异 |

> **定稿清单**：以上带 `**` 的库已确定必须使用，完整清单（必装/可选/后置三档 + 使用纪律）见 `docs/表现系统/08_技术栈与代码生成画面.md` §2.3。

### 为什么渲染层是 SVG，不是 PixiJS/WebGL

08 文档里的五条视觉定律（三原色映射、霓虹边缘发光、攻击形状符号、姿态拓扑、地垫卡槽）本质上都是**离散状态到离散视觉符号的映射**，不是连续地理数据渲染。具体检验：

- 霓虹边缘发光 → CSS `filter: drop-shadow()` 或 SVG `<filter>` 就能做，不需要 WebGL shader。
- 攻击形状符号（●∠⬡）→ SVG path，三个固定形状，AI 写死即可。
- 节点/连线/token → SVG 元素本身就是 DOM 节点，Chrome DevTools 能直接选中查看、改属性看效果，比 WebGL canvas 里的一片黑盒透明得多。
- 地图背景是"全息投影光层"（代码生成：CSS/SVG 渐变 + filter 发光 + 透明度，非贴图）、交互组件是"像素风"贴图——背景走代码层、像素贴图用 `<image>` 标签叠加即可，不需要引入渲染引擎（D-083，2026-08-19）。

WebGL/PixiJS 只有在真正需要大量粒子、全屏 shader、或 SVG 性能到瓶颈（同屏大量 DOM 节点做逐帧动画）时才引入，作为叠加层，不侵入核心渲染逻辑。这一步押后，不在 MVP 阶段投入。

## 二、项目目录结构

```
wakeup/
├── src/
│   ├── core/                    # 纯逻辑层，禁止 import React/DOM/SVG 相关任何东西
│   │   ├── entities/            # Node / Item / Entity 三大结构定义（对应 05 文档）
│   │   ├── rules/                # 基类层：伤害/移动/背包/战斗模块
│   │   ├── modes/                # 玩法层：大逃杀等具体规则
│   │   ├── ugc/                  # UGC 规则 schema 校验器 + 沙箱执行器
│   │   └── __tests__/            # Vitest：核心逻辑的自动化测试，AI 主战场
│   │
│   ├── components/               # React + Tailwind 表现层
│   │   ├── panels/                # 物品栏、动作面板、状态栏等 UI
│   │   └── primitives/            # 按钮、进度条等基础组件（对齐 design-tokens）
│   │
│   ├── scene/                    # SVG 渲染层（对应 08 文档的三层渲染系统）
│   │   ├── NodeMap.tsx            # 节点拓扑图渲染
│   │   ├── EntitySprite.tsx       # 实体/棋子渲染
│   │   ├── EffectOverlay.tsx      # 霓虹边缘、攻击形状等交互覆盖层
│   │   └── shapes/                # 三种攻击形状的 SVG path 定义
│   │
│   ├── design/
│   │   └── tokens.ts              # 唯一美学真相源，见第四章
│   │
│   ├── network/                  # 客户端网络层（Colyseus client 或 WebSocket 封装）
│   └── main.tsx
│
├── server/
│   └── index.ts                  # 权威服务器，直接复用 src/core 的逻辑
│
└── vitest.config.ts
```

**铁律**：`src/core` 下任何文件都不能 `import` React、DOM API、SVG 相关内容。这条边界由 ESLint 规则强制（`no-restricted-imports`），不是口头约定。破坏这条边界，逻辑层就不再能在服务端无头运行，测试驱动的整套优势会塌方。

## 三、开发迭代循环（四阶段）

任何新功能（新武器、新状态、新场景交互）都走这四步，不允许跳步。这是"舒适循环"的具体形态，不是比喻。

### 阶段 1：Spec → 断言（纯文本，零渲染）

- 在对应文档（如 04_物品与装备系统）里已经写好的规则描述，直接转成 `src/core/__tests__/*.spec.ts` 里的断言。
- 先写测试断言，再让 Agent 实现——测试红灯是正常状态，不是错误。
- 此阶段完全在 Terminal 里跑（`vitest --watch`），不打开浏览器。数值≤5、连接数≤5 等约束在这一层用类型系统 + 运行时断言双重卡死。
- **验收标准**：`vitest` 全绿。此时功能在数学上已经正确，但"没有画面"。

### 阶段 2：白盒拼装（矩形/圆形/纯色块）

- 把阶段1跑通的状态机，用最基础的 SVG 图元（矩形、圆、直线）在 `src/scene` 下渲染出来，不接入任何美术资源。
- 目的是验证：拓扑关系对不对、AP消耗计算对不对、回合流程走得通不通、前后端联动（点击→发包→服务器校验→广播→重渲染）是否闭环。
- 这一步**不追求好看**，追求"数据流一眼就能看穿"。发现逻辑漏洞在这一步成本最低。
- **验收标准**：能在浏览器里完整跑一局（哪怕全是灰色方块），网络同步无误。

### 阶段 3：素材/美学接入（换皮，不改逻辑）

- 白盒验证通过后，才开始接入设计规范（design-tokens）和素材。
- 主组件：按第四章的分级规则，把参考图转成 tokens，再用 tokens 实现。
- 非主组件：调用 AI 图标/纹理生成 skill，产出直接替换白盒占位。
- 这一步严禁改动 `src/core` 逻辑，只替换 `src/scene` 和 `src/components` 的渲染层实现。如果发现"美术效果需要逻辑配合"，退回阶段1重新过 Spec，不允许在这一步直接改状态机。
- **验收标准**：Chrome 里肉眼审查动效、色彩、边缘发光是否符合五条视觉定律。

### 阶段 4：联动回归

- 素材接入后，跑一次完整的前后端集成测试（Colyseus/WebSocket 的双端联动测试），确认视觉替换没有引入时序问题（比如动效播放时长和状态机的下一步判定抢跑）。
- **验收标准**：集成测试绿 + Chrome 里手动跑一局无违和感。

```
Spec断言(Terminal) → 白盒拼装(浏览器,矩形) → 素材接入(浏览器,真实视觉) → 联动回归(双窗口)
     ↑ 零渲染                ↑ 逻辑验证优先          ↑ 换皮不改逻辑            ↑ 收口
```

这套循环的核心纪律：**逻辑对不对，永远在浏览器打开之前决定**。浏览器只用来看"对不对"里的"好不好看"这一个维度。

## 四、美学分级与去素材化流程

延续"尽可能去素材化，非主要组件用 skill 生成，主要组件才提供参考图"的原则，落地为三级流程：

### 4.1 design-tokens：唯一美学真相源

在白盒阶段（阶段2）结束、素材接入（阶段3）开始之前，必须先有 `src/design/tokens.ts`。这份文件把 08 文档的五条视觉定律转成代码常量：

```ts
// 三原色资源映射（视觉定律1，不可混用）
export const statColors = {
  hp: '#e53e3e',      // 红 - 生命值
  stamina: '#3182ce', // 蓝 - 体力
  ap: '#d69e2e',      // 黄 - 行动点
} as const;

// 霓虹边缘发光语法（视觉定律2）
export const glowByIntent = {
  movable: 'drop-shadow(0 0 4px #ffffff)',   // 白光-可通行
  precise: 'drop-shadow(0 0 4px #d69e2e)',   // 黄光-精密交互
  hostile: 'drop-shadow(0 0 4px #e53e3e)',   // 红光-攻击/危险
  executable: 'drop-shadow(0 0 4px #3182ce)',// 蓝光-可处决
} as const;

// 动效时长（对应"动画规范"章节）
export const motionDuration = {
  move: 0.3, attack: 0.2, pickup: 0.2, hurt: 0.3, fall: 0.4, execute: 0.5,
} as const;
```

**规则**：代码里禁止出现 tokens 之外的裸色值/裸时长（`p-[13px]`、`#ff0000` 这类直接在 review 里打回）。任何新颜色/新动效时长的诉求，先进 tokens.ts，再被组件消费。这是防止"AI 默认审美滑向管理后台风格"的具体机制，不是靠事后肉眼把关。

### 4.2 三级素材分工

| 级别 | 定义 | 生产方式 | 谁经手 |
|---|---|---|---|
| **主组件** | 核心棋盘、HUD、UGC创作流程等定义游戏第一印象的界面 | 你提供 AI生成+PS处理的参考图 → Agent 提取 tokens → 用 tokens 实现 | 你给参考图，不打字描述细节，Agent 提取 |
| **非主组件** | 图标、次要按钮、装饰纹理 | 现成的 AI 像素/SVG 生成 skill，直接产出，锚定同一份 tokens | 全自动，不经过你 |
| **必须的真实素材** | 角色贴图等无法用代码/生成式方案替代的资源 | 后期权衡引入，不阻塞 MVP | 按需 |

### 4.3 动效：锦上添花，库优先，原生代码兜底

- 默认路径：Framer Motion 声明式动效（spring/tween），对应"动画规范"章节列出的六种动效（移动/攻击/拾取/受伤/倒地/令其长眠）全部用代码参数化实现（时长、缓动曲线都是 tokens），不需要帧序列素材。
- 粒子/光效类：默认 **@tsparticles**（JSON 配置、Canvas 2D 渲染），参数即数据、AI 可直接调；简单辉光用 CSS `filter: drop-shadow()` / SVG filter 原生实现。**不提前引入 WebGL 渲染引擎**（那是后置档，见 08 §2.3）。
- 骨骼动画、序列帧动画：不在 MVP 范围内，属于"必须的真实素材"里最后才考虑的选项。

## 五、UGC 执行边界（安全红线）

06 文档已定义 LLM 生成 JSON 规则、静态验证、沙箱执行的流程。技术落地上补一条不可退让的边界：

> **UGC 产出永远是数据，不是代码。**

- `src/core/ugc` 下的规则解释器是被 Vitest 覆盖的普通 TS 函数，UGC JSON 规则的校验（数值≤5、连接数≤5、循环检测）复用与核心引擎相同的测试设施，不是额外挂一层沙箱模块。
- 任何时候都不允许把 UGC 内容 `eval` 成可执行的 TS/JS。规则解释器只做"读取 JSON → 匹配已知效果原语 → 调用对应处理函数"，不做动态代码生成/执行。
- 这条边界在 code review 里是硬性否决项，不因为"这样能更快实现某个 UGC 创意"而妥协。

## 六、日常窗口矩阵

开发时常驻的窗口，对应第三章的四阶段循环：

```
┌─────────────────────────────┬─────────────────────────────┐
│ 窗口1：Terminal (vitest)      │ 窗口2：浏览器 (Vite dev server) │
│ 阶段1的主战场，实时全绿是底气   │ 阶段2/3/4 的验收现场            │
├─────────────────────────────┼─────────────────────────────┤
│ 窗口3：Terminal (server 日志) │ 窗口4：Chrome DevTools         │
│ 权威服务器状态，联机同步排查    │ SVG 元素直接选中检查，比WebGL透明 │
└─────────────────────────────┴─────────────────────────────┘
```

浏览器窗口的使用频率很高，但角色被限定：它验收"好不好看"和"联动对不对"，不负责"逻辑对不对"——逻辑对错的判定权始终在窗口1的测试结果上。
