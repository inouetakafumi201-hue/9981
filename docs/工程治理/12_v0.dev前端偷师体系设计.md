## 一、核心洞察：v0.dev 的能力本质

### 1.1 v0.dev 是什么？

**技术架构**（官方描述）：
- **复合模型架构**：专业 RAG 领域知识 + SOTA 大模型推理 + 定制流式后处理纠错模型
- **Agentic 模式**：从"Prompt & Fix"进化为"Describe and Deliver"——自主搜索、读取文件、审查网页、处理图片、管理任务目标
- **沙箱实时迭代**：代码直接在 Vercel Sandbox 运行并提供预览 URL，基于实时渲染反馈闭环自主迭代修复 Bug
- **一键生产部署**：打通底层托管与发布管道，完成后可一键同步仓库或直接部署上线

**能力边界总结**：
- ✅ **视觉 → 交互组件 → 实时迭代闭环**（核心强项）
- ✅ **多模态前端迭代**（看效果图 → 生成组件 → 沙箱验证）
- ✅ **独立交付可运行模块**（完整的前端应用，非代码片段）
- ❌ **大上下文管理**（不适合单体巨石项目）
- ❌ **复杂业务逻辑**（ORCA 寻路、回合制状态机、AI 决策等）
- ❌ **JSON 契约生成**（把它当 JSON 生成器是盲目自信）

### 1.2 传统 Agent vs v0.dev

| 维度 | 传统 Agent（如 Claude） | v0.dev |
|------|------------------------|--------|
| 知识广度 | 通用知识 | 前端针对性强化 |
| 视觉理解 | 基础多模态 | 专精 UI/交互视觉 |
| 迭代方式 | 对话式反复修改 | 沙箱自主闭环迭代 |
| 交付物 | 代码片段 + 解释 | 可运行的完整应用 |
| 最佳场景 | 逻辑密集型任务 | 视觉密集型任务 |

**结论**：不要让 v0.dev 做传统 Agent 的事，也不要让传统 Agent 做 v0.dev 的事。

## 二、偷师体系：唯一主线 + 三个内容域

> 纠偏：这里不是三条并行生产线，而是一条主线（偷师前端）下拆出的三个内容域；执行上只选一条主线，不分头推进。

### 2.1 内容域 A：偷师板（动态图形化效果库）

#### 定位
一个**独立的云端演示项目**，包含所有动态图形化效果的可交互演示，供本地 Agent "偷师"提取。

#### 结构
```
WakeUp Visual Effects Showcase (v0.dev 项目)
│
├── 示例素材
│   ├── 角色精灵图（侦探/佣兵/医护，64×64）
│   ├── 场景地图（办公室/仓库，俯视图）
│   └── UI 元素（卡片/按钮/状态栏）
│
├── 效果演示区（按 docs/表现系统/10 分类）
│   ├── J - 终局与结算
│   │   ├── OutcomeReveal - 全屏梦醒 + 结果板
│   │   ├── EliminationFade - 淘汰转观战
│   │   └── CurrencyPop - 货币入账动画
│   │
│   ├── C - 状态反馈
│   │   ├── StatusExpire - 状态自然到期淡出
│   │   ├── StatusDispel - 克制解除闪现
│   │   └── WeaknessGlow - 弱点高亮
│   │
│   ├── K - 经济交互
│   │   ├── ShopPurchase - 商店购买
│   │   ├── CraftingMerge - 合成台
│   │   ├── VendingDrop - 自动贩卖机
│   │   └── DecisionPrompt - 征求输入卡
│   │
│   └── ... (所有 P0/P1 效果)
│
└── 交互控制台
    ├── 效果分类导航
    ├── 播放控制（播放/暂停/重播）
    └── 参数调整滑块（duration / intensity / color）
```

#### 工作流
1. **准备阶段**：从 `docs/表现系统/10_动态图形化补全设计报告.md` 提取所有 P0/P1 效果（~20 个）
2. **投喂阶段**：一次性投喂给 v0.dev（效果清单 + 参考图 + 示例素材 + 技术约束）
3. **生成阶段**：v0.dev 在沙箱里生成所有效果 + 自主迭代到"好看"
4. **验收阶段**：打开演示网站，逐个播放效果，不满意的在 v0.dev 聊天框里说"改成..."
5. **提取阶段**：本地 Agent 下载代码 → 识别命名规范 → 转换为 `src/ui/effects/` 调用库 → 自动生成测试

#### 命名规范铁律
- **加粗标记 = 后端组件名**：Prompt 中每个效果的加粗名称，必须与生成的组件文件名一致
- 例如：`**OutcomeReveal**` → `src/effects/OutcomeReveal.tsx`
- 本地 Agent 通过这个规范自动识别并提取

#### 技术栈锁定
- Framer Motion（曲线主力）
- tsparticles（粒子克制使用）
- Radix UI（控制面板）
- Tailwind CSS + warm palette
- lucide-react（图标）

### 2.2 主线承载：偷师前端（完整前端展示厅）

#### 定位
一个**"可交互的视觉规范"**，纯展示用途，零游戏逻辑。

**不是**：一个能玩的游戏  
**而是**：一个可以走完所有 UI 流程、播放所有动画、但不实现任何业务逻辑的前端骨架

#### 核心设计理念

**完全阉割逻辑 = 零维护成本**

- ❌ 不实现回合制状态机
- ❌ 不实现战斗结算
- ❌ 不实现 AI 决策
- ❌ 不实现 ORCA 寻路
- ❌ 不实现对峙恢复

**但保留完整的交互结构**

- ✅ 所有 UI 页面都存在且可切换
- ✅ 所有按钮都有 hover/点击效果
- ✅ 所有动画都能通过命令播放
- ✅ 地图可拖拽（纯视觉，简单的 CSS transform）
- ✅ 点击移动（纯动画，Framer Motion 的 tween）

#### 应用结构

```
开始菜单
  ↓ 点击"开始游戏"
入游戏动画（纯白显形，1 秒）
  ↓
局外大厅（空旷场景 + 命令面板）
  ├── 场景内物体（纯展示）
  │   ├── 2 个角色模型（可播放动画）
  │   ├── 1 个箱子
  │   └── 1 扇门
  │
  ├── 命令面板（调试用，右侧浮动，后期删除）
  │   ├── 动画分类（移动/攻击/受击/状态...）
  │   ├── 特效分类（纯白显形/货币入账/抽卡...）
  │   └── UI 场景切换（驻地/素材库/研究台/造梦舱/电脑...）
  │
  └── UI 场景（可通过命令面板切换）
      ├── 驻地（床/书架/保险箱/锚定导流仪/研究台/造梦舱/电脑/电视）
      ├── 保险箱（5×4 格子，可拖拽，纯视觉）
      ├── 素材库（卡片网格，可筛选，假数据；含地图/蓝本只读 tab）
      ├── 研究台（词条库 + 锻造工作台 + 合成仪式 + 塑形栏，假进度条）
      ├── 造梦舱（地图编辑器）
      ├── 电脑（梦核多应用台：套餐/活动/证据提交/玩法包 LLM）
      ├── 锚定导流仪（地图选择，难度滑块）
      └── 对局界面（完整 HUD + 地图占位 + 角色）
```

#### 命令面板：指令集中转站

**这不是装饰，是提取接口的关键**

命令面板的每个按钮 = 一条前端 API 调用：

```typescript
// v0.dev 生成的命令面板
<button onClick={() => playAnimation('move', targetPos)}>
  移动到目标点
</button>
<button onClick={() => playEffect('hit-flash')}>
  受击闪红
</button>
<button onClick={() => switchScene('material-library')}>
  切换到素材库
</button>
```

**拆掉外壳后，提取出指令集**：

```typescript
// src/commands/animations.ts
export const AnimationCommands = {
  playAnimation: (type: AnimationType, target?: Position) => { ... },
  playEffect: (effectId: string, params?: any) => { ... },
  switchScene: (sceneId: string) => { ... },
}
```

这就是后端 Agent 接线时的**真实调用接口**。

#### 对局界面的特殊处理

**完整 HUD 布局（参考 ui_v2_refined2.png）**：
- 左侧：轮次栏（7 个玩家条目，假数据）
- 底部中央：动作菜单（5 张卡片，点击播放动画）
- 底部右侧：投点滑块（可滑动，假的投点）
- 顶部：AP/SP 显示（假数值）

**地图区域**：
- 中央：一张静态背景图（办公室/仓库，AI 生成或占位图）
- 可拖拽（纯 CSS transform，无 ORCA）
- 场景内：2 个角色模型（位置固定）

**伪交互**：
- 点击地图某处 → 角色播放移动动画（简单的 `animate({ x, y })`）
- 点击动作菜单"攻击" → 角色播放攻击动画（不计算伤害）
- 点击轮次栏条目 → 镜头聚焦到该角色（简单的 scale/translate）

**关键**：这些交互**只是为了展示动画效果**，不连接任何真实游戏逻辑。

### 2.3 内容域 B：UI 整版画面（独立页面生成）

#### 适用场景
零散的、不在主流程中的独立 UI 页面：
- 设置菜单
- 暂停菜单
- 叙事对话框（P5 风格）
- 证据提交 VR 界面

#### 工作流

2. 数据结构（TypeScript interface）
3. 参考图（手绘/截图/类似游戏）
4. 技术约束（Framer Motion / Radix / Tailwind）

#### 与偷师前端的关系
生成后，这些页面可以：
- 作为独立路由集成到偷师前端
- 或直接提取到生产项目

### 3.5 本地 Agent 转换脚本

#### 功能需求
1. **下载 v0.dev 生成的代码**（Git clone 或 API 拉取）
2. **识别命名规范**（扫描 `src/effects/` 目录，匹配加粗标记）
3. **转换为 WakeUp 调用接口**：
   ```typescript
   // v0.dev 生成的原始组件
   export function OutcomeReveal({ outcome }: OutcomeRevealProps) { ... }
   
   // 转换为 WakeUp 调用接口
   export const OutcomeAnimations = {
     reveal: (outcome: 'win' | 'lose' | 'draw') => 
       EffectPlayer.play('OutcomeReveal', { outcome })
   }
   ```
4. **自动生成测试**：
   ```typescript
   describe('OutcomeAnimations', () => {
     it('reveals win outcome', () => { ... })
   })
   ```
5. **验证集成**：确保提取的代码能在 WakeUp 项目中运行

#### 技术栈
- Node.js 脚本（TypeScript）
- 文件扫描：`glob` / `fast-glob`
- AST 解析：`@babel/parser` + `@babel/traverse`（识别组件导出）
- 代码生成：`@babel/generator` 或模板字符串

## 六、风险与应对

### 风险 1：v0.dev 生成的代码不符合预期

**表现**：
- 命名不一致
- 效果不好看
- 技术栈用错

**应对**：
- 提高 Prompt 的明确度（加粗标记 + 硬纪律）
- 在沙箱里验收时，直接在聊天框里说"改成..."
- 如果多次迭代仍不满意，标记为"手工补"

### 风险 2：示例素材不足

**表现**：
- v0.dev 自己生成的素材风格不统一
- 动画效果与素材不匹配

**应对**：
- **硬性要求**：所有关键素材必须提前准备好（见 §3.3）
- 不依赖 v0.dev 的素材生成能力

### 风险 3：转换脚本识别失败

**表现**：
- 命名规范被 v0.dev 打破
- AST 解析失败

**应对**：
- 在阶段 0 验证命名规范的可靠性
- 转换脚本提供"手工映射"模式（配置文件指定组件名）

### 风险 4：生成的代码无法在 WakeUp 项目中运行

**表现**：
- 依赖冲突
- TypeScript 类型不匹配

**应对**：
- 在 Prompt 中明确指定技术栈版本（React 18 / Framer Motion 11.x）
- 转换脚本自动处理依赖对齐

## 七、边界与不适用场景

### v0.dev 不应该做的事情

1. **复杂游戏逻辑**（ORCA 寻路/回合制状态机/AI 决策）
2. **地图数据生成**（MapData JSON 契约）
3. **后端 API 实现**
4. **引擎核心**（ECS / 物理 / 碰撞检测）

### 偷师体系不适用的场景

1. **高度定制化的交互**（需要深度理解业务逻辑）
2. **实时性能敏感**（Canvas 60fps 渲染循环）
3. **跨平台原生**（Unity / Unreal / 原生移动端）

## 九、关键决策记录

### D-082：偷师前端必须完全阉割逻辑
**日期**：2026-08-18  
**背景**：讨论偷师前端是否保留简化的游戏逻辑（点击移动/简单战斗）  
**决策**：完全阉割，零游戏逻辑，纯展示性交互  
**理由**：
1. ORCA 寻路等硬骨头 v0.dev 做不了，"简化逻辑"仍需人工指导
2. 完全阉割 = 零维护成本，不会因玩法改动而失效
3. 命令式中转站才是核心，逻辑不重要

### D-083：示例素材必须提前准备
**日期**：2026-08-18  
**背景**：讨论是否让 v0.dev 自己生成素材  
**决策**：所有关键素材必须提前准备好，不依赖 v0.dev 生成  
**理由**：
1. v0.dev 生成的素材风格不可控
2. 素材质量直接决定接口效果
3. 用 WakeUp 真实素材，才能保证视觉一致性

### D-084：偷师板优先于偷师前端
**日期**：2026-08-18  
**背景**：讨论执行顺序  
**决策**：先做偷师板（动态图形化效果库），再做偷师前端  
**理由**：
1. 偷师板风险更小（20 个独立效果，失败影响范围小）
2. 偷师板的产出可以直接用于偷师前端
3. 阶段 0 验证在偷师板上做更合适
