### 2.1 为什么把判定从测试里搬出来

原 `profile-field-ownership.test.ts` 用两个私有 `Set`（`PLAYER_SCALE_KEYS` / `INTERNAL_KEYS`）表达
归属。这种形态有三个问题，都在本次审计中实际发生过：

1. **归属只存在于测试代码里**，profile 自身没有可追踪的声明，也没有理由与来源；
2. **豁免无法被审查**——`delta` 被整体判为内部度量，读代码的人看不出这等于放开了伤害上限；
3. **新字段静默通过**：只要键名不在两个集合里就落到"未分类"分支，而未分类分支只在
   `unowned` 数组里报告，一旦有人给它补一条规则就再无人复核理由是否成立。

现在登记表要求每条规则同时给出 `classification` / `rationale` / `source` / `check`，并且有一条
测试断言"登记表覆盖 profile 树里出现的每个数字键"、另一条断言"登记表里没有已不再使用的键"，
两侧都不允许漂移。

## 三、数值归属校验结果

### 3.1 四类归属的划分

| 归属 | 键名 | 取值规则 |
|------|------|----------|
| **Gameplay_Value**（玩家可见玩法数值） | `delta`、`damage`、`damageOnCollision`、`damageModifier`、`value`、`reduction`、`blockedDamage`、`ignoredDamage`、`armorRating`、`shieldHp`、`hitPoints`、`hp`、`maxHp`、`healRate`、`amount`、`apCost`、`accessibleApCost`、`cost`、`ammoCost`、`capacity`、`volume`、`range`、`speed`、`vision`、`hearing`、`alertThreshold`、`threshold`、`duration`、`durationTurns`、`turns`、`max`(耐久)、`min`(前置门槛)、`actionPoints`、`staminaMax` | 整数，**绝对值** 1-5 |
| **Structural_Bound**（结构边界） | `index`(座位序号)、`min`(clamp 下限)、`minimum`、`minDamage`、`initialStamina` | 序号 1-5；下限 0-5 |
| **Constitutional_Constant**（宪法常量） | `max`(clamp 上限、回合恢复封顶) | 整数 1-5 |
| **Internal_Metric**（内部度量） | `priority`、`hpRange`、`currentPatrolIndex`、`step`、`sides` | 有限整数，不受 1-5 约束 |

未登记的数字键一律判为 `Unclassified` 并报错（对齐 L2 需求 5.7：无分类的数值字段必须被拒绝）。

### 3.2 关键判定与理由

- **`delta` 改判为玩法数值**：属性增减幅度就是玩家看到的伤害/恢复量。负号只表示扣减方向，
  刻度按绝对值受约束，因此 `delta: -3` 合法、`delta: -99` 被拒。
- **`duration` / `durationTurns` / `turns` 统一归属**：同一概念此前因字段拼写不同落在不同分类
  （`durationTurns` 曾是内部度量、`duration` 曾是玩家刻度）。拼写差异不构成语义差异。
- **`expiresAfterTurns` 的规则被删除**：该拼写已统一为 `durationTurns`，保留旧规则等于允许两种
  拼写共存。现在再写 `expiresAfterTurns` 会被判为未分类而拒绝。
- **`sides`（骰面数）判为内部度量**：依据玩法包 `props.resolutionPolicy.initiativeDie` 记录的
  **D-054**——原始骰点是内部瞬时比较值，不作为玩家可见数值持久展示；受 1-5 约束的是可见产出
  （`delta`、AP、行动顺序）。审计早期曾要求骰面必须为 5，属过度收紧，已按裁决放开。
- **资源下限只允许 0**：`clamp.min`、`minimum`、`minDamage`、`initialStamina` 表示"资源可被耗尽"，
  写非 0 下限等于用下限抬高实际刻度，会被拒。
- **`index` 判为结构边界并受五并列约束**：座位序号是玩家同时面对的选项编号，上限 5。

### 3.3 校验结果

52 份 profile、41 个数字键名，**0 条越界、0 条未分类**。所有玩家可见数值均为 1-5 整数，
未出现小数概率或百分比。

## 四、已修复的缺陷

### 4.1 Op 声明与 effects 不一致（69 处）

| 形态 | 数量 | 说明 |
|------|------|------|
| 动作用单数 `kernelOp` 只声明一个 Op | 24 | 带多个 effect 的动作漏声明其余 Op。例：能量饮料动作实际用 `prop.add` + `attach.add`，只声明了 `prop.add`；撬锁「完成撬锁」实际用 `prop.set` + `attach.del`，只声明了 `prop.set` |
| profile 级 `kernelOps` 多声明未落地的 Op | 7 | 5 份消耗品声明了 `list.remove`、2 件防弹衣声明了 `tag.add`，但没有任何 effect 使用它们 |
| 载具 `kernelTopologyOps` 漏声明已使用的 Op | 4 | sedan/jeep/armored_car/ambulance 的 `vehicle_ram_aim` 使用 `attach.add`，但只有 ebike 声明了它 |
| 载具 `kernelTopologyOps` 多声明未使用的 Op | 5 | 5 份载具都声明了 `prefab.spawn` 与 `entity.place`，无 effect 使用 |
| 状态 profile 用了 Op 却无 profile 级声明 | 3 | `status_burning` / `status_poisoned` / `status_radiation` 使用 `prop.add` |

修复方式：
- 全部动作改用 `kernelOps` 数组，取值由该动作 `effects` 实际使用的 Op 集合机械推导（迁移脚本
  同时校验"除该字段外没有其他改动"）；
- 新增 `pendingKernelOps` + `pendingKernelOpsNote` 字段承载"已知需要、但尚未建模"的 Op。
  直接删掉 `list.remove` / `tag.add` / `prefab.spawn` 会抹掉"消耗品扣除、装备打标签、损毁生成
  仍待建模"这一意图；混在 `kernelOps` 里又让"声明必须与 effects 完全一致"无法成立。拆成独立
  字段后两者都能保留，且不变量可被机械校验。

### 4.2 effect 形态分裂

同一个 `attach.add` 在 profile 树里有四种写法。已统一为 `def` + `target` + `durationTurns`
（与引擎 `attach.add` 的实参形状最接近）：

| 位置 | 原写法 | 现写法 |
|------|--------|--------|
| `wp_sniper_m24` 瞄准 | `ref` / `status` / `duration` | `def` / `target` / `durationTurns` |
| `wp_bat_baseball` 击晕 | `def` / `target` / `expiresAfterTurns` | `def` / `target` / `durationTurns` |
| `item_energy_drink` 加速 | `def` / `target` / `expiresAt: "{turn + 2}"` | `def` / `target` / `durationTurns: 2` |

### 4.3 op 与语义不符

`ambulance.ambulance_heal` 声明 `prop.set` 却带 `modifier: "+1"`。引擎的 `prop.set` 接受目标值、
不接受增量表达式，该效果实际是"加 1 点生命"。已改为 `prop.add` + `delta: 1`，
`kernelOps` 随之改为 `["prop.add"]`。`VehicleActionEffect` 的 `modifier?: string` 已换成
`delta?: PlayerScaleValue`。

### 4.4 多 AP 原子动作（L2 需求 6.4 违规，2 处）

| 位置 | 原状 | 修复 |
|------|------|------|
| `ebike.vehicle_tire_pop_melee` | `apCost: 2`，描述写「近战武器爆胎需 2 AP（蹲下+攻击）」 | 拆成 `vehicle_tire_pop_melee_approach`（1 AP，进入 `status_aiming`）+ `vehicle_tire_pop_melee`（1 AP，`prerequisite: status_aiming`） |
| `armored_car.vehicle_pull_out` | `apCost: 2`，描述写「装甲车乘员需从特定出口下车，拽下需 2 AP」 | 拆成 `vehicle_pull_out_breach`（1 AP，进入 `status_lockpicking`）+ `vehicle_pull_out`（1 AP，`prerequisite: status_lockpicking`） |

两处总成本仍是文档的 2 AP，玩法强度未变；形态改为 L2 需求 6.2 要求的"有序多步 Paid_Action +
显式中间状态"。序列形态沿用仓库既有先例 `item_lockpick`（开始撬锁 → 完成撬锁，带 `prerequisite`）。

### 4.6 缺失的追踪记录与文档一致性

- `item_medkit.json` 补上 `unresolvedIssues`：`src/play/action-turn/决策与风险记录.md` §5.3 声称
  医疗包 0 AP / 1 AP 冲突「记录于该 profile 的 unresolvedIssues」，但该字段此前并不存在。
  取值仍保持 1 AP 未裁决。
- `wp_pistol_quickdraw` 顶层 `kernelEvents` 补上 `OnDamage`（动作级已声明，顶层漏了）。
- `status_aiming` / `status_lockpicking` 的 `source` 补上新增的载具动作来源。

### 4.7 D-052 NPC 资源配置（整条未实现 → 已补齐）

6 份 NPC profile 此前**完全没有** AP 与体力字段，而 `docs/L3_玩法层/01` §9b.2 明确要求
「AP 默认 1、SP 上限 3、开局 SP 0、是否主动使用体力」四项可配置，§9b.1 要求 NPC 不参与行动轮，
§9b.4 规定 NPC 体力不可用于抢轮次。没有体力池就意味着弱点的「对方体力 +1」与过载压制在 PVE 中
完全失效——这正是该文档给出 NPC 体力的唯一理由。

现已为 6 份 profile 补上 `resources` 块（`actionPoints: 1`、`staminaMax: 3`、`initialStamina: 0`、
`usesStaminaActively: false`、`participatesInActionTurn: false`、`canSpendStaminaOnInitiative: false`）。
取值全部来自文档明文，不含推断。`.kiro/specs/wakeup-core-mechanics/requirements.md` 第 412 行
独立记载 U-005/D-052 已裁决关闭于同一组取值，与此一致。

### 4.8 跨层字段名漂移

基类层 NPC 目录的 `compositionContract.classReferenceField` 已改为
`classComposition.behaviorClassId`，而 6 份 NPC profile 仍用 `classComposition.classIds`。
已按契约迁移为 `behaviorClassId`（单值）。**方向是玩法层跟随基类层**——宪法五·5.2 规定玩法层变更
不得回溯修改基类层定义。

### 10.3 参数绑定校验的四条保证

新增 `auditCapabilityParameterBindings`（`capability-binding.test.ts`，22 条测试）保证：

1. **必填参数齐全**——能力声明为 required 的参数必须出现在绑定分组里；
2. **无越界键**——不得出现该能力未声明的参数键，也不得按未组合的能力 id 分组；
3. **引用可解析**——`reference<spectrum-class>` 等形态的值必须落在对应登记表；
4. **字段名指向真实字段**——`field-name` 形态的值必须指向 profile 上真实存在的字段，否则取值无处可寻；
5. **`operation` 双向约束**——必须同时落在「基类层为该能力声明的 Op 白名单」与「该 profile 自己声明的
   `kernelOps` ∪ `pendingKernelOps`」之内。这条把能力绑定和 Op 声明两套契约缝到了一起。

绑定**按能力 id 分组**是必需的而非风格：`operation`、`targetSelector`、`depletionBehavior` 等键在多个
能力里同名，撬锁工具同时组合三个能力，扁平对象会让它们互相覆盖。
