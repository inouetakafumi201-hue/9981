## 一、审计方法

1. 完整阅读 requirements.md 全 16 条需求与 design.md 全部组件、数据模型与 14 条正确性性质。
2. 完整阅读 `src/class/` 全部 34 个文件与既有两个测试。
3. 逐条核对 requirements 中与基类层直接相关的契约族，判定"是否有语义定义"与"是否有可证伪测试"。
4. 补齐缺失定义与 schema，并为每条补正例 + 反例测试。
5. 交叉核对：基类层声明的引擎层 Op 必须在 `createFullHarness` 注册表中存在；基类层声明的
   诊断代码必须来自 `src/l2/model/diagnostic-codes.ts`；基类层声明的语义值集合必须与
   `src/l2/model/family-contracts.ts` 的常量逐项相等。

**判定原则**：只要一条契约"只存在于散文说明里、没有可机械读取的字段"，即计为缺失。
散文无法被引用、无法被解析、也无法在被破坏时报错。

## 三、特别检查的四项结论

### 3.1 只靠改名或数值差异产生的伪子类型

发现并修复三处，另建立一条通用护栏。

| 编号 | 问题 | 判定 | 处理 |
|---|---|---|---|
| PS-01 | `weapons.weightTiers`（轻/中/重）与 `rangeTiers`（近/中/远/超远）只有 `id` 与 `name`，无任何语义定义，且无人引用 | 它们是**档位轴上的有序语义标识**，不是武器子类型；但当时既无轴声明也无描述，等同于"用名字表示数值差异" | 新增 `bandAxes` 显式声明两条档位轴、基数、玩法层取值字段名与"档位边界归玩法层"；每个档位补 `description`、`token`、`axis`、`ordinalPosition`。测试断言档位 id **不得**出现在 `weaponClasses` 中 |
| PS-02 | `spectrum-class.burst`（连发）与 `single`/`scatter`/`area` 同列一个"谱型"轴，但它描述的是**判定节奏**而不是**效果形状**；`src/l2` 的 `ATTACK_SHAPES` 只有 3 项，与 4 个谱型无法一一对应 | 轴混用。形状轴与时序轴正交 | 谱型条目新增必填 `axis`；形状轴 3 项与 `ATTACK_SHAPES` 双射（测试断言集合相等且数量相等），时序轴条目**禁止**声明 `uiAttackShape`。**id 全部保留**，玩法层引用不受影响 |
| PS-03 | 若把过渡连接的单向/双向做成两个类，就会产生只有参数差异的伪子类型 | 预防性判定 | 只登记一个 `transition.class.scene_link`，方向性是参数；测试断言 transition 族**恰好只有一个类** |
| PS-04 | `status_frozen` 与 `status_stunned` 在（形态、类别、可配置参数）三项上完全一致，差异只藏在 `tags` 的自由文本里 | 当时确实无法机械区分 | 依据两者既有 `tags`（frozen: movement-impairment；stunned: action-restriction）赋予不同能力组合，使差异变为可读取字段。**未改动任何类别或参数**，不是重新设计语义 |

通用护栏：`findPseudoSubtypes` + `parseClassCatalog` 内置检查。
- 统一形状目录：任意两个类在（defKind、语义族、必需能力、可选能力、参数键集合）上完全一致即拒绝；
  类型身份陈述重复也拒绝。
- 状态族：任意两个状态在（形态、类别、能力集合、可配置参数集合）上完全一致即拒绝。
- 反例测试：构造 `status_sluggish` 与 `status_slowed` 同形，断言必须报 `STATUS_PSEUDO_SUBTYPE`。

### 3.2 把引擎层运行时状态伪装成基类层状态

未发现既有违规（19 个状态全部是可复用玩法语义），但当时**没有任何护栏**。已补两条：

- **键名护栏** `findL1MechanismDeclarations`：`transaction` / `journal` / `hookScheduler` /
  `exprEvaluator` / `randomStream` / `refPrefix` / `snapshotStore` / `replayCursor` 等 16 个键名
  一旦作为基类层 JSON 的键出现即拒绝（`LAYER_L1_OWNERSHIP`）。反例测试逐个验证全部 16 个键名。
- **状态语义护栏** `findRuntimeStateDisguises` + `statuses.runtimeStateBoundary`：19 个禁用概念词
  （中英各半）只作用于**状态标识与状态名称**，不作用于说明——基类层需要能在说明里写清"本能力
  消费哪个引擎层接口"，把说明一起禁掉会逼出更糟的隐晦写法。反例测试构造
  `status_in_transaction`、`status_hook_dispatching` 并断言报 `LAYER_L1_RUNTIME_STATE`。

### 3.3 组合引用悬空（槽位、容器、弹药、配件）

发现并修复四处悬空：

| 编号 | 悬空内容 | 处理 |
|---|---|---|
| DR-01 | `item.class.attachment`（配件类）没有任何"挂到哪里、接受哪些宿主、挂装后追加什么能力"的声明，是一个无出边的孤立类 | 新增 `item.capability.accessory_mount`（必需），参数含 `acceptedHostClassIds`、`grantedCapabilityIds`、`typeDefining`；武器侧新增 `weapon.capability.accessory_compatibility` |
| DR-02 | 弹药：武器只有 `ammunitionType` 一个参数名，**没有弹药物品类**，`ammunitionClassId` 无处可指 | 新增 `item.class.ammunition` + `item.capability.ammunition_supply`；武器 `weapon.capability.ammunition_binding.ammunitionClassId` 现在可解析 |
| DR-03 | 容器：宪法 §3.2 已列"容器类"，但基类层完全没有容器族；`vehicle.capability.cargo` 的货舱因此无类可指 | 新增 `containers/index.json`；`vehicle.capability.cargo.containerClassRefs` 指向 `container.class.stationary` |
| DR-04 | `vehicle.class.land` 完全没有声明它组合哪些能力，20 个载具能力全部游离；`npc.class.*` 的 `capabilityIds` 语义含混（实际是"允许"而不是"必需"，导致平民类的逃离/隐蔽互斥关系无法表达） | 载具与 NPC 均拆为 `requiredCapabilityIds` / `optionalCapabilityIds`；平民类补 `requiredCapabilityAlternatives`（逃离或隐蔽至少其一）与 `forbiddenCapabilityIds`（不得攻击） |

跨层校验（只读 `src/play`，不修改）：
- 每个玩法层载具 profile 必须声明载具类的全部必需能力，且不得使用未登记能力；
- 每个玩法层物品 profile 的能力必须落在其所声明类的许可集合内；
- 每个玩法层 NPC profile 必须满足必需能力、替代项、禁用能力三项约束。

三条测试当前全部通过，意味着必需能力集合的取法与既有 11 个物品、5 个载具、6 个 NPC profile 一致。

### 3.4 `schemas/` 是否阻碍"数值归玩法层"

结论：**不阻碍数值下沉，但阻碍语义扩展**，方向与预期相反。发现两处并修复。

| 编号 | 问题 | 影响 | 处理 |
|---|---|---|---|
| SC-01 | `damage-type.schema.json` 的 id 正则 `^DMG_(0[1-9]\|10)$`、`vulnerability-type.schema.json` 的 `^WKN_(0[1-9]\|10)$` | 把"当前恰好有 10 条"写成了硬上限。requirements 5.12 明确：来源不支持的数量常量不得晋升为规范常量 | 放宽为 `^DMG_[0-9]{2,}$` / `^WKN_[0-9]{2,}$`，并在目录里补 `categoryAxis.extensible` 与 `extensionRule`。测试断言 `DMG_11` 被接受、`DMG_1` 被拒绝 |
| SC-02 | 三个既有 schema 全部是**单记录** schema，只覆盖 statuses / damage / vulnerability；weapons、items、vehicles、npcs 四个目录**没有任何 schema**，items 只有 TypeScript 侧校验 | 四个目录的文档级结构完全无契约 | 新增 `class-catalog.schema.json`（统一形状目录全量校验，覆盖 8 个目录）与 `catalog-metadata.schema.json`（共同元数据，覆盖全部 14 个目录） |

**数值归属方向的强化**（这是本次审计中比"禁止数字"更精确的一条）：

`src/class/决策与风险记录.md` 记录的机械护栏是"`src/class` 非 schema JSON 不得出现 number 叶值"，
但**代码里当时并不存在这条检查**——既有测试只检查了 15 个禁用**键名**。同时，"完全禁止数字"
本身与 requirements 5.3–5.7 冲突：结构边界与宪法常量是允许携带数字的，只要带分类、权威来源与结构理由。

已实现的护栏 `findUnclassifiedNumericLeaves` 采用规范的表述：
**基类层的数字只允许出现在 `structuralBounds[i].value`，以及来源定位的 `line` / `column`**；
其余任何位置的数字（含数组内的数字）一律报 `SCHEMA_FIELD_MISSING_CLASSIFICATION`。
`structuralBounds` 条目缺 `classification`、`authoritativeSource` 或 `structuralRationale` 时直接拒绝。

当前基类层共有 5 个结构边界，全部带权威来源：

| 结构边界 | 取值 | 权威来源 |
|---|---|---|
| `structural-bound.action.paid_ap_unit` | 1 | requirements.md Glossary / Paid_Action |
| `structural-bound.action.attached_ap_unit` | 0 | requirements.md Glossary / Attached_Action |
| `structural-bound.scene.connection_limit` | 5 | L0 §4.3 拓扑铁律 / 五并列原则 |
| `structural-bound.micro_scene.parent_cardinality` | 1 | L0 §4.3 拓扑铁律 |
| `structural-bound.transition.endpoint_count` | 2 | requirements.md Req 7.7–7.8 |

## 四、我自主做出的设计判断（需人工复核）

以下判断没有直接的权威来源逐字支撑，是我依据三判据与规范条文推出的，**请优先复核这一节**。

| 编号 | 判断 | 理由 | 若判断错误的影响 |
|---|---|---|---|
| **J-01** | 把负重档与射程档保留在基类层，作为"档位轴"而非下沉玩法层 | Req 8.3 要求射程谱经组合表达；档位本身不含数字，档位边界明确标注归玩法层 | 若应下沉，需删除 `weightTiers`/`rangeTiers`/`bandAxes` 并让玩法层自建取值空间 |

| **J-06** | 附件族分为状态附件、属性附件、技能附件三类 | requirements Glossary 逐字列出这三种 | 无 |
| **J-07** | 新增 `attachment.capability.aura_projection` | 引擎层确实存在 `AuraEngine`（`src/core/kernel/attachment/aura-engine.ts`），基类层需要有引用它的入口 | 若光环应完全由玩法层组合，则该能力应删除 |
| **J-08** | 载具类的必需能力取为 座位绑定/上下车/驾驶/碰撞/损毁序列 五项 | 这是 Req 8.7 所列项与 5 个既有玩法层 profile 的交集；门寻址等设为可选，否则电动车会被强制要求有门 | 若必需集合应更严，需同步修改玩法层 profile（本会话不拥有该目录） |

### 12.2 一处数据加固（消除"类型身份只在散文里"）

`weapons/index.json` 的两个伤害结算语义类（`damage-class.firearm`、`damage-class.physical`）第一轮的
类型身份差异**只写在 `typeIdentity.statement` 散文里**——"结算输入来自发射机构" vs "来自直接接触"，
没有任何可机械读取的字段承载这一差异。这正是本项目反复强调要避免的"伪子类型的反面"：真差异
若不落到可比较字段，护栏既无法确认它是真差异，将来也无法阻止有人把它退化成改名。

处理：为两个结算语义类各加一个 `settlementInputKind`（`firing-mechanism` / `direct-contact`），
并新增值集 `weapon.valueset.settlement_input_kinds` 登记这两个语义标识。新增测试断言两个结算语义类
的 `settlementInputKind` 互不相同且都登记在值集中。这样"枪械伤害与物理伤害是两个类"这一判断
就有了可证伪的机械依据，而不再只是散文。此改动**不引入任何数字**，`settlementInputKind` 是语义标识。

> 自主设计判断（补入第四节）：**J-13** —— 用 `settlementInputKind` 承载结算语义类的类型身份。
> 理由：Req 8.3 要求伤害引用经组合表达，而两个结算语义类必须有可机械区分的类型身份差异（第三节 3.1 的通用原则）。
> 若判断错误的影响：若结算输入来源不应作为类型身份依据，则应改用别的可枚举字段，或将两个结算语义类合并为一个由参数区分。
