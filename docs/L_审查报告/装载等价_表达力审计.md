# 装载等价 · 表达力审计（D-081 / L0 第十四条 · 专项 A4）

> **审计日期**：2026-08-16
> **审计对象**：官方 TS 玩法包 `src/play/core-mechanics/defs/*.ts`（Expr/Effect 构造器 + 全部 Def 形态）
> **对账基准**：`src/core/kernel/schedule/playpack-codec.ts` 的 JSON 接受面（`decodePlaypack`）
> **上位约束**：`docs/L0_规范宪法.md` 第十四条「装载等价与 UGC 表达力」（D-081）
> **机器断言**：`src/play/__tests__/expressiveness-equivalence.test.ts`（89 用例）
> **只读声明**：本审计不修改任何生产源文件；发现缺口只登记为差距项与交接项。

## 一、结论摘要

对官方 TS 玩法包使用的全部构造逐项对账后：**官方 TS 包能表达的构造，JSON 玩法包都能表达**。
机器断言 89 用例全部通过（`StrictJsonCodec` → `decodePlaypack`，结构与 TS 构造器产出逐项等价）。

- 已支持（JSON 等价形态通过 decode 断言）：**87 项**。
- 有差距（已登记，不静默）：**2 项**——`payloadMap` 多字段形态、`linter`。两者都判定为
  **TS/JSON 共享的宿主边界**，不是 JSON 劣势（见第四节差距清单）。
- 依赖并行任务 A1（codec 放行 `play` 治理元数据）：**1 组**（PlayDefExtension 全字段断言）。
  A1 已在本机工作区落地（`playpack-codec.ts` 已实现 `playExtension` 结构校验，A1 测试 19 绿），
  本审计的 A1 依赖用例随之真实执行并通过；若 A1 未落地，相关断言会按 `it.runIf` 跳过并在报告中
  标注「依赖 A1，待其落地后复跑」。

关键结论：官方 defs 里的每一处构造，在 JSON 侧都有一个**逐字等价的直接写法**——不需要翻译器、
不需要 JSON 表达面扩权。JSON 包与官方 TS 包经同一 `decodePlaypack` 契约，装载后 Def 快照地位等价。

## 二、审计范围与方法

### 2.1 覆盖对象

- `src/play/core-mechanics/defs/expr.ts`：全部 Expr 构造器与 Effect 构造器（含域谓词复合与
  请求记录/暂存区模式）。
- `src/play/core-mechanics/defs/*.ts` 实际使用的全部 Def 形态字段：
  ActionDef、RuleDef、AttachmentDef、ScheduleDef/PhaseDef、OutcomeDef、PoolDef、`kind:'expr'`
  具名表达式、`Def` 公共字段（extends/abstract/tags/props/containers/slots/clamp/schema/actions/rules）。
- `src/play/core-mechanics/ownership.ts` 的 `PlayDefExtension` 全字段
  （numericOwnership/sourceTrace/costClass/parentActions/triggerPoint/requireRef/onFailure/
  presentation/unresolvedGuards）。
- 成本四形态：pool / items / attach / custom。

### 2.2 方法

1. 逐项收集官方 defs 使用的构造（构造器名、展开形态、字段面）。
2. 对每项写出**最小 JSON Def 样本**，经 `StrictJsonCodec().parse` → `decodePlaypack` 断言
   `ok:true` 且解码结构与 TS 构造等价（`toEqual` 递归深度比较）。
3. 「有差距」项必须出现在测试文件顶部的 `GAPS` 登记常量中（`expressible:false` + 缺口说明），
   测试逐条断言登记存在——**差距不静默**。
4. A1 依赖项用运行期探测（真实 decode 一个携带 `play` 的样本）判断 A1 是否落地：
   落地则用例真实执行，未落地则 `runIf` 跳过并登记依赖。

## 四、差距清单

| 编号 | 构造 | JSON 可表达 | 判定 | 说明 |
|---|---|---|---|---|
| G-1 | `payloadMap` 多字段映射 | 否（两侧都不行） | **TS/JSON 共享约束，不是 JSON 劣势** | `defs/expr.ts` 对多字段映射**刻意抛错**（`payloadMap: 多字段 emit 必须先写入请求记录再用 pathOf 读取`）。根因是引擎层 `ExprEngine` 不递归求值映射字面量成员（`ids.ts` DEVIATION-02/04）。官方 TS 与 UGC JSON 走同一请求记录模式（`prop.set` 逐字段 → `emit` data 用 `pathOf(请求记录根)`）；官方包未获得任何 JSON 不可达的通道。JSON 侧已断言请求记录模式（3.2 的 request 记录序列）通过。 |
| G-2 | `PlaypackDef.linter` | 否（codec 显式拒绝 `E_LOAD_PROHIBITED_CONSTRUCT`） | **宿主边界（对双方统一）** | 治理层 Linter 是 TS 宿主能力（可执行检查函数），L0 14.3「JSON 玩法包不得声明可执行检查（D-019 安全模型不变）」；官方 TS 包也不应把可执行检查装进玩法包内容（官方 `CoreMechanicsPlaypack.linter` 为 undefined，已断言）。两形态统一边界，不是 JSON 劣势。 |

另有 1 组**依赖项**（不是差距）：PlayDefExtension 全字段断言依赖并行任务 A1（codec 放行 `play`
治理元数据）。A1 落地前相关用例经 `it.runIf` 跳过并登记「依赖 A1，待其落地后复跑」；A1 落地后
用例真实执行（当前工作区已落地，用例已执行并通过，见第五节门禁）。

## 六、建议与交接项

1. **不新增 JSON 表达面**：矩阵显示官方构造全部可逐字直写为 JSON，不需要 codec 扩权。唯一带"函数"
   性质的 `linter` 是宿主能力，两形态都不装进玩法包内容（G-2）。
2. **`payloadMap` 语义已在注释层封死**（G-1）：`defs/expr.ts` 多字段形态直接 throw。若未来引擎层
   新增"递归求值映射"能力，`payloadMap` 的契约可以从"必须走请求记录"放宽为"可内联"，届时需同步
   复审本矩阵的 G-1 行与测试中的 `payloadMap 多字段` 断言（当前断言的是"TS 侧同样抛错/登记差距"）。
3. **`parentActions` / `unresolvedGuards` 的数组形态是硬约束**：codec（A1）已拒绝裸字符串，玩法层
   Linter 按数组读。UGC JSON 文档与后续装配桥（A3/B2）应把"写数组"作为契约要求，避免"能解码、
   不能装载"。
4. **交接给 Batch B**：B1（双形态端到端等价证明）可把本矩阵的 JSON 样本扩展为完整可运行玩法包；
   B2（UGC 全链路）以本审计的 `play` 元数据放行清单为契约基线。
