> **建立日期**：2026-08-08
> **性质**：★活动。本目录（`docs/L_审查报告/`）与各并行会话产出的审计报告、冲突登记表的
> **唯一裁决入口**。审计报告只陈述发现，**不裁决**；裁决在本文件与 `docs/访谈决策记录.md`。
> **适用范围**：所有并行会话对"某机制是否违反原则 / 是否未冻结 / 归属哪一层"的判断。

## 零、本次裁决要解决的根本误判

多个并行会话独立得出了同一类错误结论，形态是：

> 某文档没写它 / 某来源清单没列它 / 两处文档对它的描述不一致
> → **判定该机制"违反原则"或"未冻结、不得进入默认"**

**这条推理不成立。** 以行动轮（轮次争夺）与 `[失衡]` 为首的一批玩法机制，是玩法层的**最新增加**，
已由项目所有者在 2026-08-07 那一轮访谈中**正式裁决批准**（D-053、D-055 等）。
并行会话把它们判为违规，是因为读的是裁决之前的 Spec 文本，或把"文档内部有矛盾"误当成"机制无效"。

### 0.1 三条判定原则（今后一律适用）

| 原则 | 内容 |
|---|---|
| **P-1 授权方向** | 玩法层数值与规则**不需要宪法逐项授权**。只要不越层、且玩家可见数值落在 1-5 内，就是合法的。宪法列出「连接节点数：1-5」是给出**区间**，不是要求每个取值都另找来源 |
| **P-2 文档矛盾 ≠ 机制无效** | 来源文档自相矛盾时，正确处置是**提请裁决**并登记，不是**默认否决**。默认否决等于让"写得乱"变成"禁止实现"，会把已批准的设计反向删掉 |
| **P-3 来源清单不完备 ≠ 无权威** | Spec 的 `S-0x` 来源表是**引用便利**，不是权威白名单。`docs/L0_规范宪法.md`、`docs/访谈决策记录.md` 中已确认的决策、以及各层定稿文档，**无论是否被某个 Spec 列入 S 表，都具备其固有位阶** |

> 这三条与 `wakeup-space-items/requirements.md` 自己声明的适用顺序一致：
> 规范宪法 → **已确认访谈决策** → 引擎层不变量 → 基类层契约 → 玩法层定稿 → 历史示例。
> 已确认访谈决策位阶**高于**任何 Spec 自身的契约条款。

## 一、行动轮与失衡类玩法：现行状态（不得再判为违规）

以下机制**全部是标准默认玩法层规则**，实现于 `src/play/action-turn/playpack.json`。
任何审计、Spec 或目录若把它们描述为"未冻结""不得进入默认""违反固定行动顺序"，均属**过期文本**。

| 机制 | 成本 / 效果 | 裁决 |
|---|---|---|
| 逆转 | 1 AP，行动轮排名 +1，窗口期动作，与强力骰互斥 | D-053 |
| 超逆转 | 2 SP，行动轮排名 +2，窗口期动作，与强力骰互斥 | D-053 |
| 处决后行动轮提升 | 令其长眠成功后，执行者排名 +1 | D-053 |
| 弱点命中 | 对方 SP+1 / 排名 -1 / 弱点装备脱落 / 施加 `[失衡]`；**不影响伤害数值** | D-053 + D-049 |
| 招架 | 1 AP，真隐藏；被近战命中时免伤 + 攻击者 SP+1 / 排名 -1 / 施加 `[失衡]`；被远程或过期时静默失效 | D-053 + D-032 |
| `[失衡]` 状态 | 破除举盾 / 防御 / 招架等一切"准备动作"状态，持续到当前回合结束 | D-053 |
| 体力过载 | 任一效果尝试使 SP 超过上限 5 时触发；SP 封顶 5 永不为 6；未行动者失去本回合行动权；跳过一次投点后下下回合归队；过载期间仍参与他人回合并可观察 | **D-055（本次补记）** |

### 1.1 与「固定行动顺序」的关系（这是最常被误判的一点）

`wakeup-core-mechanics/requirements.md` Requirement 7.6 要求"行动顺序在结算阶段确定后保持固定"。
并行会话据此把逆转/超逆转/处决提升/弱点/招架**整体判为违规**。这个推理被明确否决：

> 固定行动顺序的本意是禁止**未经授权的隐式重排**，**不是**禁止已设计好、有明确成本的行动轮争夺。
> 正确处置是在 7.6 增加**显式例外条款**，而不是删除机制。

因此：**六项中除 `[失衡]` 外的五项均可合法改写 `turnOrder`**。装载期校验的正确形态是——
写入 `turnOrder` 的 Def 必须挂在结算阶段挂载点，**或**属于 D-053 列出的六项之一。

## 二、裁决：连接数是 5 还是 5/4/3（并行者的"冲突一 / R-14 / R-02"）

**结论：只有 5 是结构边界；4 与 3 是玩法层默认平衡值。采纳并行者的选项 B。**

### 2.1 判定依据（不是偏好，是各来源自身的定义）

| 依据 | 内容 |
|---|---|
| `docs/L0_规范宪法.md` 第四条 | 「连接节点数：1-5」被列在**玩家可见数值**清单里 —— 给的是区间，不是逐档定值 |
| L0 五并列原则 / 拓扑铁律 | 上限 5 的理由是**玩家同时认知上限** → 这才是结构边界 |
| `wakeup-space-items/requirements.md` 自身的术语定义 | 「**结构边界**：为类型结构、认知上限或引擎不变量服务的约束，**不是玩法平衡数值**」 |
| `docs/L2_基类层/03_空间系统.md` 给 4 / 3 的理由 | 小场景「选择密度最低，是天然的堵桥点与掩体」、DON'T 列表「让小场景连接到 5 个地方会毁掉'一夫当关'的空间性格」 → **空间性格 / 战术平衡** |

把 4 与 3 套进 requirements 自己的定义，它们服务的是"空间性格"，不是类型结构、认知上限或引擎不变量。
按该定义，它们**是玩法平衡数值**。

### 2.2 并行者指出的"自指问题"确实成立，但结论方向相反

他指出：`requirements.md` 要求 4.2 声称 5/4/3 的来源是 S-01 + S-02，而 S-01 只给 5、S-02 一个数字
都没给，真正写 5/4/3 的 `03_空间系统.md` 不在 S-01~S-06 里 —— 这条**核实成立**。

但由此得出的**不是**"4/3 缺来源所以要补来源"（选项 A），而是"4/3 从一开始就不该被登记为
基类层结构边界"。按 **P-1**，玩法层取 4 或 3 落在 1-5 区间内，本身就不需要额外来源授权。

### 2.3 归属判错的实际后果（这是必须改的理由）

若 4 与 3 作为基类层 `Structural_Bound` 生效，则任何想让小场景连 4 条路的玩法包都会被
基类层验证器拒绝 —— 而它并未违反任何宪法条款。这直接破坏「同一批基类被多个玩法复用」，
与宪法五·5.2「玩法层变更不得回溯修改基类层定义」的意图相反：基类层反过来锁死了玩法层的合法取值。

### 2.4 代码现状：已经正确，不要改

| 位置 | 现状 | 判定 |
|---|---|---|
| `src/class/scenes/index.json` | 单条 `structural-bound.scene.connection_limit`，`value: 5`；三档 `connectionBoundId` 全部指向它 | ✅ 正确，保持 |
| `src/l2/model/constitution.ts` | `NODE_CONNECTION_BOUND = 5`（单值），来源记录指向 L0 拓扑铁律 | ✅ 正确，保持 |
| `src/l2/validation/spatial-rules.ts` | 只检查 `connectionBound.value > 5` | ✅ 正确，保持 |

### 2.5 需要改的是文档

| 位置 | 改法 |
|---|---|
| `wakeup-space-items/requirements.md` 要求 4.2 | 结构边界统一为 **5**（来源 S-01 五并列）；删除"分别记录为 5、4、3"与随之的 S-01+S-02 来源声明 |
| 同文件 要求 4.3 | 「超过其类型上限」改为「超过五并列上限 5，或超过该玩法包声明的按档上限」 |
| 同文件 验收清单「连接数结构边界分别保持为 5、4、3」 | 改为「结构边界为单一 5；按档 5/4/3 由玩法层地图 Linter 承担」 |

## 三、裁决：空间模型是图+过渡，不是三级容纳树（"冲突二 / R-15 / R-16"）

**结论：采纳 `03_空间系统.md` 的图模型（并行者的选项 A）。微型场景可附属于大 / 中 / 小三档。**

### 3.1 决定性证据：目录自身内部矛盾（不需要靠偏好裁决）

`src/class/scenes/index.json` 同时包含这两条，它们**不能同真**：

| 行 | 内容 |
|---|---|
| `scene.class.large` / `medium` | `admitsMicroScene: false`；`scene.valueset.scene_scales` 把 small 描述为「**唯一**可承载微型场景的天然场景」 |
| `prohibition.scene.personal_vacant_ground` | 禁止**小场景**创建个人空旷地，诊断码 `SPACE_SMALL_SCENE_PERSONAL_VACANT_GROUND` |

第二条只有在"个人空旷地在**大 / 中场景**合法"的前提下才有意义。若微型场景只能挂小场景，
则个人空旷地在任何档都不合法，这条禁令沦为**永不触发的死条文**——正是本项目已记录过的
"声明了门禁却不生效"失效形态（Bug 记录 B-04、玩法层审计 §8.1 的同类）。

另一处独立佐证：`src/l2/model/family-contracts.ts` 的 `SceneFamilyContract` 带有
`personalVacantGroundMicroSceneRefs` 字段。模型层预期存在"个人空旷地微型场景"，
而目录数据把它在所有档位上都设为不可能。

### 3.2 正面依据：基类层定稿文档与已确认决策

`docs/L2_基类层/03_空间系统.md`（状态：**核心机制定稿**）明确规定微型场景的三种创建者：

| 创建者 | 创建时机 | 归属 |
|---|---|---|
| 活体 | 在**大 / 中场景**移动到"空旷地"时 | 个人私有 |
| 过渡场景 | 门 / 窗创建 1-2 个（平行双侧，垂直单侧） | 共享（两侧各一） |
| 小场景节点 | 自带一个 | 共享（所有活体） |

同文档：小场景**禁止**个人微型场景（"空旷地禁入"，按钮复用为移动到共享微型场景）。
即 —— 三档都能附属微型场景，**差别在"个人私有 vs 共享"，不在"能不能"**。

### 3.3 采纳容纳树会打断已冻结的 AP 经济学

`03_空间系统.md` 与 **D-046（已确认）**：

| 场景类型 | 找到 | 处决 | 总计 |
|---|---|---|---|
| 大 / 中场景 | 1 AP | 1 AP | **2 AP** |
| 小 / 微型场景 | 0 AP（已共享） | 1 AP | **1 AP** |

而「找到 X」的定义就是「来到 X 这个实体的微型场景」。若大 / 中场景不能附属微型场景，
大 / 中场景的「找到」就**无处落地**，那 1 AP 没有承载物，2 AP 总成本随之塌掉 ——
而文档明确称这个 2 AP 是「3 AP 奖励档的重要价值锚点」（3 AP 恰好"找人 + 处决"并剩 1 AP）。

同时距离范式也会失配：`03` 的距离是**沿过渡边累加的图距离**（「教室 → 紧邻走廊 = 距离 3」），
改成三级树后距离要按树遍历重算，所有既有 DC 表的距离语义全部失效。

### 3.4 `admittedChildSceneScales` 的处置

容纳树本身在目录内部是自洽的，它不是笔误，而是一套完整但**不同**的建模；
但它的 `sourceRecords` 只引了 L0 拓扑铁律与 l2 requirements 7，**两者都没有说容纳树**。

**裁决**：大 / 中 / 小三档之间的 `admittedChildSceneScales` 降级为**可选的叙事分组**，
且明确声明它**不参与距离计算、不参与微型场景生命周期、不参与"找到"判定**。
若无消费方，直接移除更干净。**不得**用它约束微型场景的父级档位。

### 3.5 需要改的代码（由持有 `src/class/**` 的会话执行）

| 位置 | 现状 | 目标 |
|---|---|---|
| `scenes/index.json` `scene.class.large` | `admitsMicroScene: false` | `true`；`typeIdentity.statement` 删除"也不能直接附属微型场景" |
| `scenes/index.json` `scene.class.medium` | `admitsMicroScene: false` | `true`；同上 |
| `scenes/index.json` `micro-scene.class.contact` | `admittedParentSceneScales: ["small"]` | `["large","medium","small"]` |
| `scenes/index.json` `scene.valueset.scene_scales` | small 描述为「唯一可承载微型场景的天然场景」 | 改为「自带共享微型场景、且禁止个人空旷地的天然场景」；large / medium 描述补「可承载个人空旷地微型场景」 |
| `scenes/index.json` 大 / 中场景能力 | — | 需组合"个人空旷地微型场景"能力面（对应 `personalVacantGroundMicroSceneRefs`） |
| `prohibition.scene.personal_vacant_ground` | 已正确 | ✅ 保持（改完后它才真正可触发） |
| `admittedChildSceneScales` | 容纳树语义 | 降级为叙事分组并显式声明不参与距离 / 生命周期 / 找到判定；或移除 |

> 改动后 `src/class/__tests__/class-semantic-families.test.ts` 断言 small 为唯一承载者的用例需同步更新。

## 五、裁决：死亡容器「只出不进」（"冲突四 / R-04"）

**结论：声明层与运行期机制**两者都保留，但机制**不得硬编码**。

### 5.1 两者不矛盾，各管一层

| 层 | 表达 | 位置 |
|---|---|---|
| 声明层契约 | 该容器**组合** `container.capability.deposit_disabled`（与存入能力互斥）+ `derived_content_source`（内容来自死亡事务） | `src/class/containers/index.json`（已存在，正确） |
| 运行期机制 | 如何让"只出不进"在**灌注完成之后**才生效 | 领域设计 |

### 5.2 并行者指出的"灌注悖论"成立

若容器创建时就写 `accepts: false`，则灌注自身的 `item.move` 也会被拒；而 `Slot.accepts` 是结构区
字段，已登记 Op 集合中**没有任何 Op 能在容器创建后修改它**。因此纯声明方案无法独立成立，
必须有一个运行期切换机制。这一点并行者的分析正确。

### 5.3 裁决内容

1. **灌注时序义务写进契约**：「标记在灌注事务提交后才生效」是死亡容器契约的**必需组成部分**，
   不是实现细节。任何机制实现都必须满足它。
2. **`depositDisabledMechanism` 从硬编码字面量改为开放引用**：`'before-item-move-veto'` 是当前
   唯一已知可行实现，但应表达为**可替换的机制引用**，而非固定值。理由：若将来出现能修改
   `accepts` 的结构 Op，或引擎提供容器级只读标记，实现应可切换而不必改契约。
3. **上游阻塞已解除**：并行者担心该机制依赖 Hook 接线（D-002 / H-001）而 `hookIntegrationAvailable()`
   是注入项。**核实：`src/core/kernel/wire-hooks.ts` 已存在**，`wireHooksIntoRegistry` 已把
   `OpRegistry.InvokeHooks.dispatchBefore/After` 接到真实 `HookDispatcher`，并有
   `__tests__/wire-hooks.test.ts` 的 6 个端到端用例。**R-07 的这一项不再是缺口。**
   注意配套事实：`entity.create` / `item.create` 等 8 个 Op 此前漏标 `structural: true`，已补；
   `before:item.move` 属结构类 Op，veto 分发可用。

## 六、裁决：不新建 `src/class/space-items/`（"冲突五 / R-06 / R-17"）

**结论：采纳并行者的选项 B 的意图，但落点比他提的更明确 —— 规则不进 `src/class/`，进已存在的 `src/l2/`。**

### 6.1 核实的现状

| 事实 | 核实结果 |
|---|---|
| `src/class/space-items/` | **不存在** |
| `src/class/` 现有目录 | 15 个：`actions` `attachments` `containers` `damage-types` `gateways` `items` `movement` `npcs` `scenes` `schemas` `skills` `statuses` `vehicles` `vulnerability-types` `weapons` + `catalog-loader.ts` / `class-contract.ts` / `json-contract.ts` |
| 其中落在本 Spec 域内的 | `scenes` `containers` `movement` `actions` `gateways` `attachments` `skills` `items` `weapons` `vehicles` `damage-types` —— **本 Spec 的目录层交付物大部分已被并行会话做掉** |
| 领域验证规则的落点 | **`src/l2/validation/` 已存在**，且 `spatial-rules.ts` 已实现连接上限、个人空旷地禁令等空间校验；同层另有 `item-vehicle-rules.ts`、`action-gateway-rules.ts`、`classification-rules.ts` 等 12 个规则模块 |
| 模型与契约 | `src/l2/model/family-contracts.ts`（含 `SceneFamilyContract`）、`constitution.ts`、`diagnostic-codes.ts` 均已落地 |

### 6.2 裁决的三层落点

| 内容 | 落点 | 理由 |
|---|---|---|
| **目录数据**（类、能力、值集、结构边界、禁令、未决项） | `src/class/<族>/index.json` —— 扩展既有目录，**不新建平行分类** | 避免两套场景 / 容器分类，这正是并行者自己写的禁令 |
| **领域验证规则** | `src/l2/validation/*.ts` —— 补齐既有模块的检查面 | 该目录已是事实落点，`spatial-rules.ts` 已在做这件事 |
| **跨层适配与只读投影** | `src/l2/adapters/`、`src/l2/registry/read-only-projection.ts` | 同样已存在 |

**因此 `wakeup-space-items` 的 design 任务 9「新建目录」应改写为「校验并补齐既有目录一致性」**，
任务 3 / 5 改为「补齐 `scenes` / `containers` / `vehicles` 缺失的检查面」。

### 6.3 顺带解除的一条自相矛盾

并行者的设计里同时写了"不得并列出第二套场景分类"这条禁令，又计划新建含目录的完整领域 ——
两者不能同真。本裁决取禁令，删计划。
